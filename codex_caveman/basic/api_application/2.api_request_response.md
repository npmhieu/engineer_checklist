# 2. API / Request-Response

[Index](../../README.md) · Previous: [HTTP Fundamentals](1.http_fundamentals.md) · Next: [REST API](3.rest_api.md)

## 1. What is it?

**API defines how software uses another component; request-response carries one question and its answer, like calling a function across a boundary.**

Local function: arguments, return value, exceptions. Network API: serialized input, response contract, transport failures, and uncertain outcomes.
Library APIs need no network. This lesson uses backend HTTP API.

## 2. Why do we need it?

Without API boundary, frontend needs backend internals: table names, storage credentials, and business rules.
Schema change breaks clients. Different clients enforce different rules. Database access becomes harder to control.

Contract hides implementation and states allowed operations, inputs, outputs, and failures.
Frontend can build against examples while backend changes storage behind stable contract.

Request-response gives immediate feedback for bounded work: create task, fetch profile, save preference.
It also couples caller latency and availability to server and downstream services.

Concrete bug without clear errors: backend returns HTML failure page; frontend blindly parses JSON and reports unrelated parsing error.
Contract must describe both success and failure bodies.

## 3. Under hood / mechanism / system flow

### 3a. Engine layer: data and execution

Request bytes become parsed objects. Router selects handler. Handler validates input and invokes application logic.
Application logic reads or writes storage. Handler converts result into public representation and response bytes.

Demo uses dictionary keyed by integer ID. Lookup and insertion average O(1); listing and serializing N tasks cost O(N), plus content bytes.
JSON decoding costs O(B) for B input bytes. Decoded strings and objects add memory beyond raw body.
Demo stores data only in RAM. Real durable writes require database commit and storage I/O.

Production often separates handler, service, and repository. Tiny demo keeps them together to expose full path.
Adding folders alone does not create sound boundaries.

### 3b. Rulebook layer: ownership and state changes

1. Edge accepts connection and enforces transport limits.
2. Authentication identifies caller. Authorization checks operation and resource access, when required.
3. Router and handler check method, media type, framing, JSON, and schema.
4. Business logic checks domain invariants. Database constraints enforce invariants despite concurrent requests.
5. Transaction commits accepted mutation. Response exposes public fields, status, and useful headers.
6. Client distinguishes received API failure from transport failure.

Authentication may precede routing or follow it; middleware order depends on architecture.
Demo omits identity checks and database transactions. It demonstrates parsing, validation, mutation, and response boundaries.

Failure before mutation leaves state unchanged here. Failure after commit can leave client uncertain.
Client disconnect does not automatically cancel handler or undo committed work.

One API operation can trigger several downstream calls. Deadline must cover whole operation, not reset independently at each hop.
Request ID helps trace execution. Idempotency key identifies repeated mutation intent; these keys serve different purposes.

## 4. How to apply / implement / use it?

Small contract for shared [runnable server](examples/task_server.py):

| Contract part | Demo choice |
| --- | --- |
| Operation | `POST /tasks` |
| Request format | UTF-8 JSON; `Content-Type: application/json`; explicit `Content-Length` |
| Body limit | 4096 bytes |
| Input | Object containing only `title`; string, trimmed length 1–120 Python Unicode code points |
| Success | `201`; `Location: /tasks/{id}`; generated ID, title, completion flag, links |
| Invalid syntax | `400` with `INVALID_JSON` |
| Invalid fields | `422` with `INVALID_TITLE` |
| Wrong media type | `415` with `UNSUPPORTED_MEDIA_TYPE` |
| Oversized body | `413` with `BODY_TOO_LARGE` |

Validation status choice is contract policy; some APIs use `400` for field errors.
This demo rejects unknown fields. Document that choice: silently ignoring typo `titel` hides client bugs.

Start server from repository root:

```sh
python3 codex_caveman/basic/api_application/examples/task_server.py
```

Second terminal, fresh server:

```sh
# Happy path: create, then read generated resource.
curl -i http://127.0.0.1:8000/tasks \
  -H 'Content-Type: application/json' \
  --data '{"title":"Review backend"}'
# Expect: 201, Location: /tasks/1, completed: false.
curl -i http://127.0.0.1:8000/tasks/1
# Expect: 200, stored task.

# Unhappy path: malformed JSON, before mutation.
curl -i http://127.0.0.1:8000/tasks \
  -H 'Content-Type: application/json' --data '{'
# Expect: 400, INVALID_JSON.

# Unhappy path: valid JSON, invalid title.
curl -i http://127.0.0.1:8000/tasks \
  -H 'Content-Type: application/json' --data '{"title":"   "}'
# Expect: 422, INVALID_TITLE.

# Unhappy path: wrong media type.
curl -i http://127.0.0.1:8000/tasks --data '{"title":"Review backend"}'
# Expect: 415, UNSUPPORTED_MEDIA_TYPE.

# Confirm rejected requests created no additional tasks.
curl -i http://127.0.0.1:8000/tasks
# Expect: one item, assuming fresh server and commands above.
```

Implementation core, shown without transport plumbing:

```python
data = json.loads(raw.decode("utf-8"))
title = data["title"].strip()
task = {"id": next_id, "title": title, "completed": False}
tasks[next_id] = task
```

Full file checks body limits, JSON shape, and title type before executing this mutation.
Use full file for working example; snippet alone lacks required validation.

Client rule: inspect status before treating body as successful result. Preserve machine-readable error code.
Unexpected failures should return safe error and log internal details with request ID.
Demo does not include production exception middleware or a simulated database failure.

## 5. When should I NOT use this?

Avoid holding synchronous request open for long exports or workflows requiring human approval.
Accept job, return identifier, expose status later. `202 Accepted` means processing accepted, not finished.
[HTTP defines 202 semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3).

Avoid turning every local function into network call. More boundaries mean more latency, contracts, deployment dependencies, and partial failures.

Avoid retrying every error. Validation failures need input correction; timeouts after writes need outcome reconciliation or designed idempotency.
Repeated identical POSTs create separate tasks in demo. No deduplication exists.

Other hidden costs: version compatibility, payload validation, observability, auth, client upgrades, and downstream capacity.
Demo collection is unpaginated; growing task count increases response memory and latency.

The demo is for loopback learning only. It has no authentication, durable storage, or production server hardening.
