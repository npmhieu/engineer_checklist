# 1. HTTP Fundamentals

[Index](../../README.md) · Next: [API / Request-Response](2.api_request_response.md)

## 1. What is it?

**HTTP defines request and response meanings so clients and servers can exchange resources, like shared rules for ordering food.**

Client orders; server answers. Menu analogy helps, but software also needs exact framing, formats, failures, and deadlines.

HTTP = protocol. API = exposed software contract. REST = architectural style. JSON = data format. Separate concepts.

Recognize URL parts: `https://api.example.com/tasks/42?include=owner`.

| Part | Meaning |
| --- | --- |
| `https` | HTTP protected by TLS |
| `api.example.com` | Host; default HTTPS port is 443 |
| `/tasks/42` | Path identifying target |
| `include=owner` | Query parameters; application decides meaning |

URL fragment, such as `#details`, stays client-side; HTTP request target excludes it.

## 2. Why do we need it?

Without shared protocol, every client needs custom message parsing and failure rules for every server.

Concrete pain: server sends JSON bytes; client cannot tell where response ends without framing rules.
HTTP gives message boundaries, content metadata, and outcome semantics. Existing clients, proxies, and servers can cooperate.

Another pain: changing data through `GET /deleteTask?id=42` lets crawlers or prefetchers trigger deletion.
Method semantics prevent that design mistake when application follows them.

## 3. Under hood / mechanism / system flow

### 3a. Engine layer: bytes and costs

Typical new HTTPS connection using HTTP/1.1 or HTTP/2:

1. Resolve host through DNS, unless cached or connection already exists.
2. Establish TCP connection. Establish TLS; authenticate server certificate and negotiate protocol.
3. Client serializes request. Kernel sends bytes through socket buffers.
4. Server parses framing and headers. Application reads body and runs handler.
5. Server serializes response. Client reads framed response and interprets status and body.

HTTP/1.1 uses readable message syntax. HTTP/2 uses binary frames and multiplexed streams over TCP.
HTTP/3 uses QUIC over UDP, with TLS integrated. Same application semantics; different transport and framing.

Cost model: parse body of B bytes in O(B) time. Fully buffering body needs O(B) memory.
Streaming can bound buffers, but parsed objects and application state still consume memory.
Network latency, connection setup, and database I/O often dominate tiny handler costs.

Connection reuse avoids repeated setup. HTTP/2 streams share TCP delivery; packet loss can delay multiple streams.
HTTP/3 avoids that specific cross-stream TCP blocking. Bandwidth and congestion limits remain shared.

### 3b. Rulebook layer: boundaries and reactions

| Message part | Example | Receiver behavior |
| --- | --- | --- |
| Method | `GET` | Read semantics; application must avoid requested mutation |
| Target | `/tasks/42` | Router selects resource |
| `Content-Type` | `application/json` | Describes sent body |
| `Accept` | `application/json` | States acceptable response formats |
| Status | `404` | Target not found, or server declines to disclose existence |
| `Content-Length` | `17` | Body framing in this demo; byte count, not character count |
| `Cache-Control` | `no-store` | Caches must not store this response |

Status families: `1xx` informational, `2xx` success, `3xx` redirection, `4xx` request-related failure, `5xx` server failure.
Some redirects require client follow-up; status alone does not finish business workflow.

Stateless protocol does not mean empty database. Requests carry relevant identity and context through headers, cookies, URLs, or bodies.
Servers can retain users, resources, and application sessions.

Safe methods request no state change. Idempotent methods preserve intended effect when repeated.
Logging can still occur. Repeated idempotent requests can return different statuses.

Core method and status meanings: [HTTP semantics, RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9).

## 4. How to apply / implement / use it?

Use shared [local demo](examples/task_server.py). Python 3 and curl required. From repository root, start:

```sh
python3 codex_caveman/basic/api_application/examples/task_server.py
```

Keep server running. In second terminal:

```sh
# Happy path: existing collection, initially empty.
curl --http1.1 -i http://127.0.0.1:8000/tasks
# Expect: 200, Content-Type: application/json, {"items": []}.

# Unhappy path: missing resource.
curl --http1.1 -i http://127.0.0.1:8000/tasks/999
# Expect: 404, {"error": {"code": "NOT_FOUND"}}.

# Unhappy path: method rejected for known collection.
curl --http1.1 -i -X DELETE http://127.0.0.1:8000/tasks
# Expect: 405, Allow: GET, POST.
```

Readable request shape:

```http
GET /tasks HTTP/1.1
Host: 127.0.0.1:8000
Accept: application/json

```

Blank line ends headers. Raw HTTP/1.1 uses CRLF line endings; curl supplies correct wire syntax.
Demo calculates body byte length, writes headers, ends headers, then writes body.
Demo deliberately closes connections. HTTP/1.1 itself supports persistent connections.

Observe transport failure separately:

1. Stop server with Ctrl-C.
2. Repeat `curl --max-time 2 -i http://127.0.0.1:8000/tasks`.
3. Expect connection failure, not HTTP `500`. No server response exists.

## 5. When should I NOT use this?

HTTP fits many backend boundaries. One short request-response exchange fits poorly when work takes minutes or needs continuous bidirectional traffic.
Consider accepted jobs with polling, server-sent events, or WebSocket, depending on interaction.

Avoid remote HTTP inside tight local loops. Serialization, network hops, and partial failure add costs absent from function calls.

Never assume HTTP guarantees business success, durable storage, or exactly-once writes.
A server can commit a write before response disappears. Timeout then means unknown outcome.

Do not send credentials over plaintext HTTP. Local demo binds loopback and carries no secrets.
Production needs HTTPS, authentication, authorization, and operational controls.

Demo uses Python's teaching server, volatile dictionary, and one request handler at a time.
Slow clients block progress until timeout. No production deployment claim.
[Python documents server limitations](https://docs.python.org/3/library/http.server.html).

Predict before checking answers:

| Changed constraint | Expected consequence |
| --- | --- |
| JSON contains multibyte characters | Character count can differ from encoded byte count; framing must use bytes |
| Response lost after write commits | Client cannot infer rollback; blind retry can duplicate write |
| Body grows from 1 KB to 1 GB | Full buffering creates large memory demand; enforce limits or stream |
| Proxy caches private response | Data can leak without correct cache policy and access boundaries |
| Move app to HTTP/2 | Method meanings stay; raw wire syntax changes |
