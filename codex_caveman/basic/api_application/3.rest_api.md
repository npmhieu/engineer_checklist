# 3. REST API

[Index](../../README.md) · Previous: [API / Request-Response](2.api_request_response.md)

## 1. What is it?

**REST organizes distributed interaction around resources and shared interface rules, like named documents connected through links in a browser.**

Resource = concept with identity, such as task 42. URI identifies it. Representation carries current public view, often JSON.
Same resource can have several representations. JSON object is not database row itself.

REST means Representational State Transfer. Sending JSON over HTTP alone does not establish REST.

## 2. Why do we need it?

Without shared interface, clients learn custom verbs and rules for every service: `fetchTask`, `removeTask`, `saveTaskAgain`.
Generic clients and intermediaries cannot infer safe retrieval, retry properties, or caching behavior from those names.

Resource identity separates stable public address from storage implementation.
Uniform semantics let infrastructure and clients reason about requests consistently.
Client-server separation lets UI and storage evolve separately.

Concrete bug: deletion hidden inside GET can run when browser prefetches link.
Another: every read marked uncacheable forces origin traffic even when public data could safely be reused.

REST imposes constraints to gain these properties. It does not automatically make API fast, secure, or easy to use.

## 3. Under hood / mechanism / system flow

### 3a. Engine layer: no special REST engine

Router, serializers, caches, and storage execute requests. REST supplies architectural constraints, not indexing algorithm or runtime.
Actual costs depend on payload size, query plan, round trips, cache hit rate, and concurrency.

For demo: item lookup averages O(1) in dictionary. Collection serialization grows with stored items and text bytes.
Links add payload bytes. No durable disk write happens. Production database behavior can dominate API cost.

### 3b. Rulebook layer: six constraints

| Constraint | Placement and effect |
| --- | --- |
| Client-server | UI and storage responsibilities remain separate |
| Stateless interaction | Request supplies context needed for understanding; no hidden conversation sequence required |
| Cache | Responses declare caching policy; cache can reuse eligible results |
| Uniform interface | Stable resource identity, representations, self-describing messages, hypermedia-driven transitions |
| Layered system | Client can interact through proxies or gateways without depending on internal topology |
| Code on demand, optional | Server can send executable client code; ordinary JSON API need not use it |

These constraints come from [Fielding's REST chapter](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm).

Uniform interface includes four pieces:

1. Identify resources through URIs.
2. Manipulate resources through representations.
3. Make messages describe how receivers should interpret them.
4. Drive application transitions through hypermedia controls.

Hypermedia means responses supply navigable links or action controls under understood media-type conventions.
Client knows entry point and link meanings; server supplies current targets.
Hardcoded endpoint maps with arbitrary JSON links demonstrate resource-oriented HTTP, not complete hypermedia contract.

Stateless interaction still permits persistent resources in database.
REST's constraint is stricter than HTTP permitting application sessions: hidden server-side conversation state should not determine request meaning.
Cookie transport alone does not decide compliance; what context server must remember matters.

Resource lifecycle in demo:

1. `POST /tasks` creates task. Server returns `201` and new URI in `Location`.
2. `GET` new URI returns representation. Resource state stays unchanged.
3. `DELETE` same URI removes task. Response has no body and status `204`.
4. Repeated DELETE returns `404` here. Intended final state remains absent.

Other common choices, outside demo: PUT creates or replaces target resource state; PATCH applies document-defined partial changes.
PUT is idempotent by semantics. PATCH is not inherently idempotent; patch format and operation matter.
POST is not inherently idempotent; application can add explicit deduplication contract.
[HTTP method semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-9) define these distinctions.

## 4. How to apply / implement / use it?

Use shared [task server](examples/task_server.py). It demonstrates resource identity, method semantics, links, and explicit cache policy.
It is intentionally incomplete REST: no defined hypermedia media type or action-control contract.

Minimal route contract:

| Request | Result | State effect |
| --- | --- | --- |
| `GET /tasks` | `200`, collection | None |
| `POST /tasks` | `201`, representation, `Location` | Create |
| `GET /tasks/{id}` | `200` or `404` | None |
| `DELETE /tasks/{id}` | `204` or `404` | Remove if present |
| `DELETE /tasks` | `405`, `Allow: GET, POST` | None |

Start fresh server from repository root:

```sh
python3 codex_caveman/basic/api_application/examples/task_server.py
```

Second terminal:

```sh
# Happy path: server assigns identity.
curl -i http://127.0.0.1:8000/tasks \
  -H 'Content-Type: application/json' --data '{"title":"Learn REST"}'
# Expect: 201, Location: /tasks/1, links.self: /tasks/1.

# Read URI returned by server. Fresh-server example uses ID 1.
curl -i http://127.0.0.1:8000/tasks/1
# Expect: 200, representation including self and collection links.

# Delete resource.
curl -i -X DELETE http://127.0.0.1:8000/tasks/1
# Expect: 204, zero response-body bytes.

# Unhappy path: same URI now absent.
curl -i http://127.0.0.1:8000/tasks/1
# Expect: 404, NOT_FOUND.

# Repeat DELETE: different status, same intended final state.
curl -i -X DELETE http://127.0.0.1:8000/tasks/1
# Expect: 404; task remains absent.

# Unsupported action on collection.
curl -i -X DELETE http://127.0.0.1:8000/tasks
# Expect: 405, Allow: GET, POST.
```

Every demo response uses `Cache-Control: no-store`. Explicitly disabling storage is valid cache policy, but gives no cache speedup.
For suitable public reads, define freshness and validators. With ETag, client can send `If-None-Match`; matching validator can yield `304`.
For concurrent writes, `If-Match` with validator can prevent overwriting newer state; failed precondition yields `412`.
Demo implements neither validator flow. Adding headers without comparison logic would not provide concurrency protection.

Keep resource identifiers opaque to clients. Numeric IDs here are teaching convenience; knowing ID never grants permission.

## 5. When should I NOT use this?

Avoid forcing every domain action into CRUD-shaped field edits.
Payment capture or order cancellation needs explicit invariant and transition contract. Resource design can still model operations when useful.

RPC can express command-heavy interactions directly. GraphQL can suit client-specific graph reads.
WebSocket can suit continuous bidirectional sessions. Choose from interaction needs and operational costs.

Hidden costs: many resource fetches create many round trips; stateless requests repeat context; links require stable client conventions.
Uniform interfaces can be less compact than operation-specific protocols.

Avoid exposing database schema as public resource contract. Internal normalization and access rules rarely match client view exactly.
Avoid assuming REST prevents lost updates, duplicate POSTs, or unauthorized reads. Each needs explicit controls.

Demo uses loopback, volatile storage, and no authentication. Do not deploy it as production API.
