# User Acceptance Testing (UAT)

[Lesson index](../../README.md) · [Previous](1.acceptance_criteria.md) · [Next](3.factory_acceptance_testing.md)

## 1. What is it?

UAT evaluates whether intended users or their authorized representatives can accept the solution for real business use, like having the people who will run a workflow try their actual job rather than only watching a developer demo.

## 2. Why do we need it?

Technically correct software can still produce the wrong report, omit an approval step, confuse operators, or fail a real exception workflow.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Prepare representative roles, protected realistic data, business scenarios, expected results, environment/build/config identity, and issue/decision records. Automation can prepare data and reproduce evidence, but it cannot invent user judgment or authorized sign-off. Keep not-run, blocked, failed, passed, and explicitly accepted deviations distinct.

Reference: [Primary documentation](https://istqb.org/wp-content/uploads/2024/11/ISTQB-CT-AcT_Syllabus_v1.0_2019.pdf).

### 3b. Boundaries and lifecycle

Agree scope/entry conditions → business representatives execute and explore workflows → record evidence and defects → fix/retest affected scope → authorized stakeholder records acceptance, rejection, or conditional decision under agreed policy.

## 4. How to apply / implement / use it?

Save as `user_acceptance_testing_demo.py`; run `python3 user_acceptance_testing_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from copy import deepcopy
required_cases = {"UAT-1", "UAT-2", "UAT-3"}
def decide(report, expected_build):
    if report["build"] != expected_build:
        raise ValueError("evidence belongs to another build")
    if set(report["cases"]) != required_cases:
        raise ValueError("incomplete scenario evidence")
    if any(result != "pass" for result in report["cases"].values()) or report["blocking_defects"]:
        return "not-accepted"
    if not report["reviewer"] or report["decision"] != "approved":
        return "awaiting-business-decision"
    return "accepted-under-demo-policy"
report = {"build": "candidate-7", "cases": {case: "pass" for case in required_cases},
          "blocking_defects": [], "reviewer": "business-representative-fixture",
          "decision": "pending"}
assert decide(report, "candidate-7") == "awaiting-business-decision"
report["decision"] = "approved"
assert decide(report, "candidate-7") == "accepted-under-demo-policy"
failed = deepcopy(report)
failed["cases"]["UAT-3"] = "fail"
assert decide(failed, "candidate-7") == "not-accepted"
try:
    decide(report, "candidate-8")
except ValueError:
    pass
else:
    raise AssertionError("stale acceptance evidence reused")
```

Expected: passing scenarios still await a business decision, an approved complete fixture passes its stated policy, a failed scenario blocks it, and wrong-build evidence is rejected. This is a report-consistency model with fictional reviewer data, not executed UAT or authenticated approval. The strict all-pass policy is illustrative; real conditional acceptance needs explicit authorized deviation/risk records.

### Minimal human UAT session

Use an isolated candidate and synthetic shop-1/shop-2 records. A business representative executes these through the actual UI or supported API client:

| Case | Business task | Expected evidence |
| --- | --- | --- |
| UAT-1 | Request shop-1's completed-order export, wait for completion, and inspect the file | Correct fields, row count, totals, filters, and understandable completion/download flow. |
| UAT-2 | Try to view/download shop-2's export with the shop-1 role | No foreign data is disclosed; the denial is understandable. |
| UAT-3 | Use a controlled failed export fixture and follow the documented recovery flow | Failure is visible, no misleading “complete” artifact appears, and the recovery path is usable. |

Record actual results, build/configuration identity, tester role, time, evidence location, defect IDs, and the authorized decision. Review whether the workflow meets the business need, not only whether HTTP codes match. Never inject a real production outage just to run UAT-3. Automation above validates a sample report; it does not claim these human scenarios were performed.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not ask users to rediscover all basic developer defects, substitute developer sign-off for authorized business acceptance, or equate E2E automation with UAT. Avoid exposing raw production personal data merely to make the environment realistic.

## 6. How do I know I understand it?

**Blank-page check:** Explain who represents the users, what business risk they evaluate, and why a green technical suite does not settle acceptance.

| Constraint change | Predict the failure and response |
| --- | --- |
| Candidate changes after user review | Assess impact and retest the affected baseline; do not silently attach old approval to new bytes/configuration. |
| A scenario cannot run because test data is missing | Record blocked/not-run, repair the fixture, and rerun; absence of failure is not a pass. |
