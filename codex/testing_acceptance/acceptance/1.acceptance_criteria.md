# Acceptance Criteria

[Lesson index](../../README.md) · [Previous](../automated_testing/11.chaos_test.md) · [Next](2.user_acceptance_testing.md)

## 1. What is it?

Acceptance criteria are agreed observable conditions a feature must satisfy, like a delivery checklist describing what the customer must actually receive.

## 2. Why do we need it?

Vague requests such as make exports fast let developers and stakeholders disagree after delivery, even when all implementation tests pass.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Define actor, preconditions, action, observable outcome, failure behavior, and relevant measurable limits before implementation. Criteria describe desired behavior; test cases are concrete evidence for those criteria. A shared Definition of Done covers broader team quality policy, not every feature-specific rule. Trace criteria IDs to tests/evidence and unresolved questions.

Reference: [Primary documentation](https://cucumber.io/docs/bdd/example-mapping/).

### 3b. Boundaries and lifecycle

Collaborate on examples → agree criteria and assumptions → implement/test → collect evidence for the exact baseline → stakeholders decide acceptance or request change.

## 4. How to apply / implement / use it?

Save as `acceptance_criteria_demo.py`; run `python3 acceptance_criteria_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
jobs = {}
def submit_export(principal_tenant, requested_tenant, filters):
    if principal_tenant != requested_tenant:
        return {"status": 403, "code": "export.forbidden"}
    if set(filters) - {"state"} or filters.get("state") not in {"open", "done"}:
        return {"status": 400, "code": "export.invalid_filter"}
    job_id = "job-" + str(len(jobs) + 1)
    jobs[job_id] = {"tenant": principal_tenant, "state": "queued"}
    return {"status": 202, "job_id": job_id}
accepted = submit_export("shop-1", "shop-1", {"state": "open"})
assert accepted["status"] == 202
assert jobs[accepted["job_id"]] == {"tenant": "shop-1", "state": "queued"}
before = {key: dict(value) for key, value in jobs.items()}
assert submit_export("shop-1", "shop-1", {"state": "unknown"})["status"] == 400
assert submit_export("shop-1", "shop-2", {"state": "open"})["status"] == 403
assert jobs == before
```

Expected: authorized valid intent creates one queued job; invalid/forbidden requests create none. This executable API-shaped fixture proves only those functional examples, not HTTP, verified identity, durable jobs, completion, download authorization, or performance. Principal tenant is trusted test context, never a client claim to trust blindly.

### Small acceptance specification for this fixture

| ID | Given / when | Required observation |
| --- | --- | --- |
| AC-1 | A verified shop-1 caller requests its own export with state=open | Return 202 and one job ID; that job belongs to shop-1 and is queued. |
| AC-2 | The same caller submits state=unknown | Return 400 and create no job. |
| AC-3 | The same caller requests shop-2's export | Return 403 and create no job. |

These are feature-specific criteria, not a complete export specification. Before real delivery, separately agree job durability, result correctness, tenant-scoped status/download access, expiry, and failure/retry behavior. An illustrative timing criterion could be “under the agreed 20 requests/second workload and named dataset/environment, at least 95% of eligible submissions return a durable job reference within 200 ms”; that requires its own measurement and agreed error policy. The Python fixture does not claim to meet that timing/durability criterion.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not use implementation tasks such as add Redis as the only acceptance criterion, or retroactively weaken criteria to hide a failure. Avoid unverifiable adjectives and unexplained percentages. Not every criterion needs Gherkin or UI-level automation.

## 6. How do I know I understand it?

**Blank-page check:** Rewrite fast and secure export into observable positive, negative, and nonfunctional criteria. Identify each criterion's evidence and one unresolved assumption.

| Constraint change | Predict the failure and response |
| --- | --- |
| Export input grows from 100 rows to 100,000 | A timing criterion needs a named dataset/workload, environment, measurement point, percentile, and failure policy. |
| A feature test passes but a required criterion has no test/evidence | The criterion remains unproven; do not infer acceptance from a green unrelated suite. |
