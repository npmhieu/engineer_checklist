# Factory Acceptance Testing (FAT)

[Lesson index](../../README.md) · [Previous](2.user_acceptance_testing.md)

## 1. What is it?

FAT evaluates an agreed deliverable against its specification in the supplier's controlled environment before site handover, like inspecting a commissioned machine at its maker before installing it at the customer.

## 2. Why do we need it?

A supplier demo or green CI pipeline can hide missing interfaces, configuration, documentation, recovery procedures, or deviations that become expensive to discover only after delivery.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

FAT is common in engineered/industrial deliveries; whether a backend project uses the term depends on its delivery agreement. Identify the approved software/configuration baseline, agreed test protocol, representative interfaces or declared simulators, evidence, witnesses/decision authority, and deviation handling. Factory evidence does not establish real-site networking, equipment behavior, or operational acceptance.

Reference: [Primary documentation](https://webstore.iec.ch/en/publication/67572).

### 3b. Boundaries and lifecycle

Agree protocol and responsibilities → freeze/identify supplier baseline → run agreed checks and record actual results → review deviations and retest changes → authorize the handover milestone → perform separately required site/user acceptance.

## 4. How to apply / implement / use it?

Save as `factory_acceptance_testing_demo.py`; run `python3 factory_acceptance_testing_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import hashlib
from copy import deepcopy
artifact = b"supplier candidate version 7"
approved_digest = hashlib.sha256(artifact).hexdigest()
required_checks = {"interface-contract", "configuration", "restore-procedure"}
def prepare_handover(payload, report):
    if hashlib.sha256(payload).hexdigest() != approved_digest:
        raise ValueError("wrong artifact baseline")
    if report["digest"] != approved_digest or set(report["checks"]) != required_checks:
        raise ValueError("evidence does not cover this baseline")
    if any(result != "pass" for result in report["checks"].values()):
        raise RuntimeError("agreed checks incomplete")
    if report["unapproved_deviations"]:
        raise RuntimeError("deviation review required")
    return "ready-for-authorized-handover-review"
report = {"digest": approved_digest,
          "checks": {check: "pass" for check in required_checks},
          "unapproved_deviations": []}
assert prepare_handover(artifact, report) == "ready-for-authorized-handover-review"
blocked = deepcopy(report)
blocked["unapproved_deviations"] = ["restore instructions incomplete"]
try:
    prepare_handover(artifact, blocked)
except RuntimeError:
    pass
else:
    raise AssertionError("open deviation silently accepted")
try:
    prepare_handover(b"changed candidate", report)
except ValueError:
    pass
else:
    raise AssertionError("untested artifact handed over")
```

Expected: a complete matching fixture reaches review; an unapproved deviation or changed artifact is rejected. This hashes actual bytes but models test results; it does not perform FAT, verify signatures, authenticate witnesses, grant acceptance, or establish compliance. The expected digest/protocol must come from an approved trusted baseline, not solely from an untrusted supplier report.

### Example backend FAT protocol, not a universal standard

1. Agree delivery scope, requirements-to-test mapping, build/image and configuration IDs, environment, simulator limits, witnesses, exit criteria, and deviation policy before execution.
2. Demonstrate the agreed API/client contract using a representative client; record success, rejection, and error mapping with evidence.
3. Exercise the supplied deployment/configuration and backup/restore procedure in an isolated supplier environment; verify meaningful restored data, not only process startup.
4. Review packaged documentation, access/secret handover process, monitoring instructions, and outstanding issues within the agreed scope.
5. Record results and deviations, retest affected checks after fixes, and obtain the authorized handover decision. Schedule distinct site integration, UAT, or operational checks where required.

The linked IEC 62381:2024 public description concerns **process-industry automation systems**, including factory and site acceptance/integration testing. It is context for the terminology, not a claim that all backend software must follow it or that this short protocol satisfies its full requirements. Practical context: [Siemens supplier testing and customer-factory rollout case study](https://resources.sw.siemens.com/en-US/case-study-solu-tech/).

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not impose a heavyweight FAT ceremony on every routine SaaS feature without a delivery need. Do not confuse FAT with user acceptance, site acceptance, production readiness, or regulatory certification. Applicable obligations and approval authority come from the actual project agreement and relevant reviewed standards, not this example.

## 6. How do I know I understand it?

**Blank-page check:** Design a backend supplier-handover protocol and explain which checks remain impossible until deployment at the receiving site.

| Constraint change | Predict the failure and response |
| --- | --- |
| Supplier used a simulated third-party interface | Declare that limitation and plan real integration/site tests; simulator success does not validate real credentials, latency, or networking. |
| Build/configuration changes after FAT execution | Review impact, identify the new baseline, and rerun affected agreed checks before handover. |
