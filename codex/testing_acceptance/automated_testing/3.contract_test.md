# Contract Test

[Lesson index](../../README.md) · [Previous](2.integration_test.md) · [Next](4.e2e_test.md)

## 1. What is it?

A contract test checks whether independently changing participants agree on an interface, like checking both the plug shape and expected voltage before connecting devices.

## 2. Why do we need it?

Consumer mocks and provider tests may both be green while disagreeing about field names, types, nulls, status codes, or money units.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Capture observable interactions and supported provider states, not private implementation details. Consumer-driven contracts require provider verification and a version/deployment compatibility policy; schema validation alone does not verify every consumer expectation. Checking small encoded payloads is cheap, while spinning up real providers and isolated states costs process/network/database work.

Reference: [Primary documentation](https://docs.pact.io/getting_started/how_pact_works).

### 3b. Boundaries and lifecycle

Consumer expectations are recorded → provider state is arranged → actual output is verified → supported version combinations gate deployment → incompatible changes are redesigned or versioned.

## 4. How to apply / implement / use it?

Save as `contract_test_demo.py`; run `python3 contract_test_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import json
import unittest
def provider(task_id):
    if task_id != 7:
        return 404, {"code": "task.not_found"}
    return 200, {"id": 7, "title": "learn", "optional_extra": True}
def verify(status, body):
    if status == 200:
        if type(body.get("id")) is not int or not isinstance(body.get("title"), str):
            raise AssertionError("success contract changed")
    elif status == 404:
        if body != {"code": "task.not_found"}:
            raise AssertionError("error contract changed")
    else:
        raise AssertionError("unexpected status")
class ContractTests(unittest.TestCase):
    def test_success_and_missing_provider_states(self):
        for task_id in (7, 99):
            status, body = provider(task_id)
            wire_body = json.loads(json.dumps(body))
            verify(status, wire_body)
    def test_breaking_type_is_detected(self):
        with self.assertRaises(AssertionError):
            verify(200, {"id": "7", "title": "learn"})
    def test_error_code_change_is_detected(self):
        with self.assertRaises(AssertionError):
            verify(404, {"code": "missing"})
unittest.main()
```

Expected: three tests report OK. This executable provider/consumer expectation crosses real JSON encoding but remains in-process; it is not Pact, HTTP verification, a contract registry, or a complete request/schema definition. Extra success fields are intentionally allowed. Real contract tooling should exercise the actual provider adapter and supported consumer versions.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not confuse provider verification with consumer-only mocking or use contract tests as proof of business correctness, security, or full user workflows. Overspecified harmless fields create unnecessary coupling.

## 6. How do I know I understand it?

**Blank-page check:** Write success and failure interactions, identify the contract owner, and explain which version combinations must remain deployable.

| Constraint change | Predict the failure and response |
| --- | --- |
| Provider adds an optional success field | Tolerant consumers can remain compatible, as this fixture demonstrates. |
| Provider changes cents to dollars without changing the field type | A schema may still pass; add semantic expectations and evolve the contract explicitly. |
