# Unit Test

[Lesson index](../../README.md) · [Previous](../../advanced/9.devops_delivery/7.multi_environment_deployment.md) · [Next](2.integration_test.md)

## 1. What is it?

A unit test checks one small behavior in isolation, like checking a calculator's discount button without involving the checkout network.

## 2. Why do we need it?

Pure business bugs are expensive to diagnose through a full server, and a suite that requires a database for every calculation gives slow, noisy feedback.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Choose a behavioral boundary, arrange deterministic inputs, call it, and compare with an independently specified expected result. Fakes replace effects only where necessary; mocking internal calls can lock tests to implementation. Setup/assertion CPU and allocation usually dominate tiny pure-function tests, while hidden I/O defeats isolation. Code coverage records execution, not whether useful assertions would detect a bug.

Reference: [Primary documentation](https://docs.python.org/3.12/library/unittest.html).

### 3b. Boundaries and lifecycle

Business rule is specified → developer adds small positive, boundary, and rejection cases → runner isolates fixtures and reports failures → fast CI gate blocks regressions before broader tests.

## 4. How to apply / implement / use it?

Save as `unit_test_demo.py`; run `python3 unit_test_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import unittest
def total_cents(prices, discount_bps):
    if not prices or any(type(price) is not int or price < 0 for price in prices):
        raise ValueError("nonempty cart of nonnegative integer cents required")
    if type(discount_bps) is not int or not 0 <= discount_bps <= 10000:
        raise ValueError("discount must be integer basis points")
    return sum(prices) * (10000 - discount_bps) // 10000
class TotalTests(unittest.TestCase):
    def test_discounted_total(self):
        self.assertEqual(total_cents([1000, 500], 1000), 1350)
    def test_full_discount(self):
        self.assertEqual(total_cents([500], 10000), 0)
    def test_invalid_inputs(self):
        for prices, discount in (([], 0), ([True], 0), ([-1], 0), ([500], 10001)):
            with self.subTest(prices=prices, discount=discount):
                with self.assertRaises(ValueError):
                    total_cents(prices, discount)
unittest.main()
```

Expected: three tests report OK, including four invalid-input subcases. This real pure-function suite defines integer cents, basis points, and rounding down as its fixture contract; those choices are not universal financial rules. It does not test tax, persistence, authentication, or concurrent checkout.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not use unit tests as proof that SQL, routing, or provider contracts integrate correctly. Do not mock every method, assert private call order without a behavioral reason, or target an arbitrary coverage percentage instead of important risks.

## 6. How do I know I understand it?

**Blank-page check:** Explain the unit boundary and oracle, then change the arithmetic intentionally and predict which assertion catches it. Distinguish a useful fake from a mock that merely repeats the implementation.

| Constraint change | Predict the failure and response |
| --- | --- |
| Boolean is supplied as a price | Python bool is an int subclass; exact type validation protects this chosen cents contract. |
| Business rounding changes | Agree new expected examples first, then change implementation and tests together instead of preserving accidental arithmetic. |
