# Performance Test

[Lesson index](../../README.md) · [Previous](8.stress_test.md) · [Next](10.security_test.md)

## 1. What is it?

A performance test measures time and resource behavior for a defined operation or workload, like timing and weighing one shipment before comparing delivery strategies.

## 2. Why do we need it?

Correct code can still allocate too much memory, add expensive scans, or regress latency without violating functional tests.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Performance is an umbrella covering operation benchmarks, expected load, stress, soak, and other explicit profiles. Control fixture size and environment, assert equivalent results, separate setup from measured work, and collect repeated samples. Instrumentation changes cost; Python traced allocations exclude some native memory and are not whole-process RSS.

Reference: [Primary documentation](https://docs.python.org/3.12/library/tracemalloc.html).

### 3b. Boundaries and lifecycle

Define operation/workload and budget → establish comparable baseline → verify results → measure time/memory/I/O → explain variance → gate only with justified thresholds.

## 4. How to apply / implement / use it?

Save as `performance_test_demo.py`; run `python3 performance_test_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from time import perf_counter
import tracemalloc
def measure(operation):
    tracemalloc.start()
    started = perf_counter()
    try:
        result = operation()
        elapsed = perf_counter() - started
        peak = tracemalloc.get_traced_memory()[1]
        return result, elapsed, peak
    finally:
        tracemalloc.stop()
materialized = measure(lambda: sum([number * number for number in range(20000)]))
streamed = measure(lambda: sum(number * number for number in range(20000)))
assert materialized[0] == streamed[0]
assert materialized[1] >= 0 and streamed[1] >= 0
assert materialized[2] > 0 and streamed[2] > 0
try:
    measure(lambda: 1 / 0)
except ZeroDivisionError:
    pass
else:
    raise AssertionError("failed operation swallowed")
assert not tracemalloc.is_tracing()
print({"list_seconds": materialized[1], "list_peak_bytes": materialized[2],
       "generator_seconds": streamed[1], "generator_peak_bytes": streamed[2]})
```

Expected: equal computed results, measured timings/peaks, and tracer cleanup after failure. The generator normally has a lower traced peak because it avoids materializing the full list; the script does not assert a brittle ratio or speed ordering. This is a real local measurement, not an HTTP throughput test, whole-process memory profile, or statistically reliable release baseline.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not infer production performance from one tiny run, compare unequal semantics, or ignore setup cost when production repeats that setup. A fast incorrect or failed operation is not a successful optimization.

## 6. How do I know I understand it?

**Blank-page check:** Explain what time and memory measurements include/exclude, predict input-size growth, and design a repeated baseline comparison.

| Constraint change | Predict the failure and response |
| --- | --- |
| Most memory lives in a native library | Tracemalloc may miss it; use suitable process/native-memory tools as well. |
| A change is faster but uses much more memory | Evaluate capacity/cost and tail behavior rather than accepting solely on mean duration. |
