# E2E Test

[Lesson index](../../README.md) · [Previous](3.contract_test.md) · [Next](5.regression_test.md)

## 1. What is it?

An E2E test exercises a complete supported workflow through its public entry point, like creating and collecting a real order rather than testing each internal button.

## 2. Why do we need it?

Individual components can work while entry-point wiring, parsing, state persistence, and later workflow steps fail together.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Define the system under test and keep its critical internal path real. Use isolated data, observable completion, bounded polling for asynchronous work, and cleanup; fixed sleeps create races and slow suites. Process startup, database I/O, browsers, and remote dependencies make broad tests slower and harder to diagnose than focused tests.

Reference: [Primary documentation](https://docs.python.org/3.12/library/subprocess.html).

### 3b. Boundaries and lifecycle

Arrange isolated environment → invoke public workflow → verify later operations see committed outcomes → exercise rejection → check no unintended mutation → clean up.

## 4. How to apply / implement / use it?

Save as `e2e_test_demo.py`; run `python3 e2e_test_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import json
from pathlib import Path
import subprocess
import sys
import tempfile
application = '''
import json
import sqlite3
import sys
database = sqlite3.connect(sys.argv[1])
try:
    database.execute("CREATE TABLE IF NOT EXISTS tasks(id INTEGER PRIMARY KEY, title TEXT, done INTEGER)")
    action = sys.argv[2]
    if action == "add":
        title = sys.argv[3].strip()
        if not title:
            print(json.dumps({"error": "title_required"}))
            raise SystemExit(2)
        with database:
            cursor = database.execute("INSERT INTO tasks(title,done) VALUES(?,0)", (title,))
        print(json.dumps({"id": cursor.lastrowid}))
    elif action == "complete":
        with database:
            changed = database.execute("UPDATE tasks SET done=1 WHERE id=?", (int(sys.argv[3]),)).rowcount
        if changed != 1:
            print(json.dumps({"error": "not_found"}))
            raise SystemExit(2)
        print(json.dumps({"done": True}))
    elif action == "list":
        print(json.dumps(database.execute("SELECT id,title,done FROM tasks ORDER BY id").fetchall()))
    else:
        raise SystemExit(2)
finally:
    database.close()
'''
with tempfile.TemporaryDirectory() as directory:
    database_path = str(Path(directory) / "tasks.db")
    def invoke(*arguments):
        return subprocess.run([sys.executable, "-c", application, database_path, *arguments],
                              capture_output=True, text=True, timeout=5)
    created = invoke("add", "learn")
    assert created.returncode == 0 and json.loads(created.stdout) == {"id": 1}
    assert invoke("complete", "1").returncode == 0
    assert json.loads(invoke("list").stdout) == [[1, "learn", 1]]
    rejected = invoke("complete", "99")
    assert rejected.returncode == 2 and json.loads(rejected.stdout)["error"] == "not_found"
    assert invoke("add", " ").returncode == 2
    assert json.loads(invoke("list").stdout) == [[1, "learn", 1]]
```

Expected: the script exits 0 after create → complete → list and both rejected operations. This is a genuine E2E test of the supplied tiny CLI, crossing process boundaries and a real file-backed database. It does not prove HTTP, browser, login, production database, or provider integration. The CLI intentionally lacks a production-grade argument parser and authentication.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not make every edge case an E2E flow or share mutable test accounts across parallel runs. Replace slow nondeterministic coverage with narrower tests where they prove the same invariant.

| Constraint change | Predict the failure and response |
| --- | --- |
