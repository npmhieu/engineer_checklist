# Chaos Test

[Lesson index](../../README.md) · [Previous](10.security_test.md) · [Next](../acceptance/1.acceptance_criteria.md)

## 1. What is it?

A chaos test injects a controlled fault to evaluate a stated resilience hypothesis, like a supervised emergency drill with an explicit stop and recovery plan.

## 2. Why do we need it?

Successful normal execution does not show what happens when a worker dies between a database effect and acknowledgement.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

State steady-state invariants, fault point, scope, evidence, abort/cleanup, and recovery expectations. Deterministic fault injection gives a reproducible small experiment; larger network/region experiments require stronger authorization and observability. A passing result only covers the tested fault model, not every possible failure.

Reference: [Primary documentation](https://principlesofchaos.org/).

### 3b. Boundaries and lifecycle

Baseline isolated fixture → inject owned process fault → observe persisted state → recover/retry with stable identity → verify invariants and cleanup → document uncovered failures.

## 4. How to apply / implement / use it?

Save as `chaos_test_demo.py`; run `python3 chaos_test_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from pathlib import Path
import sqlite3
import subprocess
import sys
import tempfile
worker = '''
import os
import sqlite3
import sys
database = sqlite3.connect(sys.argv[1])
with database:
    inserted = database.execute("INSERT OR IGNORE INTO inbox VALUES('evt-1')").rowcount
    if inserted:
        database.execute("UPDATE balance SET cents=cents+5")
    if sys.argv[2] == "before-commit":
        os._exit(17)
if sys.argv[2] == "after-commit":
    os._exit(18)
database.close()
'''
with tempfile.TemporaryDirectory() as directory:
    path = str(Path(directory) / "fixture.db")
    database = sqlite3.connect(path)
    database.executescript("CREATE TABLE inbox(id TEXT PRIMARY KEY);"
                          "CREATE TABLE balance(cents INTEGER); INSERT INTO balance VALUES(0);")
    database.close()
    def run(fault):
        return subprocess.run([sys.executable, "-c", worker, path, fault],
                              capture_output=True, text=True, timeout=5).returncode
    def balance():
        connection = sqlite3.connect(path)
        try:
            return connection.execute("SELECT cents FROM balance").fetchone()[0]
        finally:
            connection.close()
    assert run("before-commit") == 17
    assert balance() == 0
    assert run("after-commit") == 18
    assert balance() == 5
    assert run("none") == 0
    assert balance() == 5
```

Expected: the first owned child exits before commit and leaves 0; the second exits after commit and leaves 5; recovery replays the event without a second increment. This injects real crashes only into child processes and a disposable SQLite file it creates. It does not kill user processes, change networks, contact a broker, or prove power-loss durability, remote exactly-once effects, or production failover.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not begin with unapproved production failures or omit rollback/cleanup and abort criteria. Random damage without a hypothesis is not useful evidence; never generalize a local transaction result into a region-level guarantee.

## 6. How do I know I understand it?

**Blank-page check:** Draw both crash windows and prove why recovery preserves one local increment. Specify how a future broker acknowledgement test would extend, not replace, this evidence.

| Constraint change | Predict the failure and response |
| --- | --- |
| Effect is a remote payment rather than a local row update | The SQLite transaction cannot cover it; add provider idempotency/reconciliation and targeted fault tests. |
| Host power disappears during storage writes | That is a different failure model requiring storage/durability configuration and appropriately controlled testing. |
