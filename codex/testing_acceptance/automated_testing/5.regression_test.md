# Regression Test

[Lesson index](../../README.md) · [Previous](4.e2e_test.md) · [Next](6.smoke_test.md)

## 1. What is it?

A regression test records behavior that must remain correct after change, like permanently adding a repaired defect to an inspection checklist.

## 2. Why do we need it?

A fix can disappear during refactoring or dependency changes when its exact failure condition is never captured.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Regression describes purpose, not scope: unit, integration, contract, E2E, or performance tests can prevent recurrence. Reduce a real incident to a deterministic counterexample, prove the new test fails on the buggy behavior, and assert the intended invariant. Retain issue/requirement traceability without preserving obsolete implementations in production.

Reference: [Primary documentation](https://docs.python.org/3.12/library/unittest.html).

### 3b. Boundaries and lifecycle

Reproduce defect → add a failing focused case → fix responsible layer → confirm positive and negative behavior → keep the case in the relevant CI suite.

## 4. How to apply / implement / use it?

Save as `regression_test_demo.py`; run `python3 regression_test_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from datetime import datetime, timezone
import unittest
def in_window(moment, start, end):
    if start >= end:
        raise ValueError("nonempty window required")
    return start <= moment < end
class WindowRegressionTests(unittest.TestCase):
    def setUp(self):
        self.start = datetime(2026, 10, 18, tzinfo=timezone.utc)
        self.end = datetime(2026, 10, 19, tzinfo=timezone.utc)
    def test_start_is_included(self):
        self.assertTrue(in_window(self.start, self.start, self.end))
    def test_end_is_excluded_to_prevent_double_counting(self):
        self.assertFalse(in_window(self.end, self.start, self.end))
        self.assertTrue(self.start <= self.end <= self.end)
    def test_empty_window_is_rejected(self):
        with self.assertRaises(ValueError):
            in_window(self.start, self.start, self.start)
unittest.main()
```

Expected: three tests report OK. The endpoint case is a counterexample to the old inclusive-end predicate, which would double-count a boundary record in adjacent reporting periods. This tests UTC interval logic, not SQL timestamps, time-zone conversion, or daylight-saving business rules.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not preserve known wrong output merely because it is old, or add a giant flaky workflow when a focused test proves the fix. Intentional contract changes require reviewed updates to expectations.

## 6. How do I know I understand it?

| Constraint change | Predict the failure and response |
| --- | --- |
| Reporting changes to a local business day | Derive UTC boundaries from the specified time zone; do not assume every day has exactly 24 hours. |
| Another export path still uses an inclusive endpoint | Move or reuse the responsible query/rule and cover the alternate boundary. |
