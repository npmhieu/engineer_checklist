# Integration Test

[Lesson index](../../README.md) · [Previous](1.unit_test.md) · [Next](3.contract_test.md)

## 1. What is it?

An integration test checks collaborating real components at a chosen boundary, like testing a card reader connected to its actual checkout interface.

## 2. Why do we need it?

Mocked repositories can pass while SQL, constraints, transaction rollback, serialization, or driver behavior fail in the real assembly.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Declare which dependencies are real and which are replaced. Use isolated fixtures, supported migrations/schema, and deterministic cleanup. Database setup and disk/network I/O often cost more than the assertion; parallel suites need independent namespaces or a reliable reset strategy. SQLite is a real database but not a substitute for validating PostgreSQL-specific isolation or SQL.

Reference: [Primary documentation](https://docs.python.org/3.12/library/sqlite3.html#sqlite3-howto-transaction).

### 3b. Boundaries and lifecycle

Create isolated dependency → wire actual adapter/use case → execute success and failure → inspect durable effects/invariants → clean up even after failure.

## 4. How to apply / implement / use it?

Save as `integration_test_demo.py`; run `python3 integration_test_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import sqlite3
import unittest
def transfer(database, fail_after_debit=False):
    with database:
        database.execute("UPDATE accounts SET cents=cents-20 WHERE id=1")
        if fail_after_debit:
            raise RuntimeError("credit path unavailable")
        database.execute("UPDATE accounts SET cents=cents+20 WHERE id=2")
class TransferIntegrationTests(unittest.TestCase):
    def setUp(self):
        self.database = sqlite3.connect(":memory:")
        self.addCleanup(self.database.close)
        self.database.execute("CREATE TABLE accounts(id INTEGER PRIMARY KEY, cents INTEGER)")
        with self.database:
            self.database.executemany("INSERT INTO accounts VALUES(?,?)", [(1, 100), (2, 0)])
    def balances(self):
        return self.database.execute("SELECT cents FROM accounts ORDER BY id").fetchall()
    def test_success(self):
        transfer(self.database)
        self.assertEqual(self.balances(), [(80,), (20,)])
    def test_failure_rolls_back_debit(self):
        with self.assertRaises(RuntimeError):
            transfer(self.database, fail_after_debit=True)
        self.assertEqual(self.balances(), [(100,), (0,)])
unittest.main()
```

Expected: two tests report OK. They use a real SQLite driver and transaction rollback with a fresh database per case. The tiny transfer deliberately fixes existing account IDs and amount; it omits authorization, sufficient-funds checks, concurrent writers, file durability, and production-engine behavior.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not test a mocked database and call it database integration. Avoid shared production fixtures, test-order dependencies, and assuming rollback-based cleanup covers background jobs or external side effects.

## 6. How do I know I understand it?

**Blank-page check:** List the real boundaries crossed, then explain why the rollback assertion adds confidence that a mock cannot provide.

| Constraint change | Predict the failure and response |
| --- | --- |
| Production uses PostgreSQL-specific locks | Add tests against isolated PostgreSQL using the real schema and isolation configuration. |
| A notification is sent inside the transaction | Database rollback cannot unsend it; use a transactional intent/outbox and test that boundary separately. |
