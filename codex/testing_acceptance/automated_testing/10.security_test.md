# Security Test

[Lesson index](../../README.md) · [Previous](9.performance_test.md) · [Next](11.chaos_test.md)

## 1. What is it?

A security test checks whether an explicit threat or abuse case is blocked while permitted use still works, like testing both an authorized key and an attempted break-in.

## 2. Why do we need it?

Successful login and happy-path tests do not detect cross-tenant access, excessive permissions, mass assignment, injection, or unbounded resource use.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Translate a threat model into negative and positive cases at responsible boundaries. Use separate actors/tenants, real authorization/data scoping where possible, and verify rejected input causes no mutation or disclosure. Static analysis, dependency scanning, dynamic testing, and expert assessment complement these tests; none alone proves absence of vulnerabilities.

Reference: [Primary documentation](https://wstg.owasp.org/v4.2/4-Web_Application_Security_Testing/05-Authorization_Testing/04-Testing_for_Insecure_Direct_Object_References/).

### 3b. Boundaries and lifecycle

Authorize test scope → arrange actors/assets → perform permitted and forbidden actions → assert response plus unchanged protected state → record findings and regression coverage.

## 4. How to apply / implement / use it?

Save as `security_test_demo.py`; run `python3 security_test_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import sqlite3
import unittest
def rename(database, principal, task_id, patch):
    if set(patch) != {"title"} or not isinstance(patch["title"], str) or not patch["title"].strip():
        raise ValueError("unsupported fields")
    with database:
        changed = database.execute(
            "UPDATE tasks SET title=? WHERE id=? AND tenant=? AND owner=?",
            (patch["title"], task_id, principal["tenant"], principal["user"])).rowcount
        if changed != 1:
            raise PermissionError("missing or forbidden")
class AccessTests(unittest.TestCase):
    def setUp(self):
        self.database = sqlite3.connect(":memory:")
        self.addCleanup(self.database.close)
        self.database.execute("CREATE TABLE tasks(id TEXT PRIMARY KEY, tenant TEXT, owner TEXT, title TEXT)")
        with self.database:
            self.database.executemany("INSERT INTO tasks VALUES(?,?,?,?)", [
                ("own", "shop-1", "user-1", "first"),
                ("foreign", "shop-2", "user-1", "protected")])
        self.principal = {"tenant": "shop-1", "user": "user-1"}
    def test_permitted_write(self):
        rename(self.database, self.principal, "own", {"title": "new"})
        self.assertEqual(self.database.execute("SELECT title FROM tasks WHERE id='own'").fetchone()[0], "new")
    def test_other_tenant_and_injection_are_rejected(self):
        for task_id in ("foreign", "own' OR 1=1 --"):
            with self.subTest(task_id=task_id):
                with self.assertRaises(PermissionError):
                    rename(self.database, self.principal, task_id, {"title": "stolen"})
        self.assertEqual(self.database.execute("SELECT title FROM tasks ORDER BY id").fetchall(),
                         [("protected",), ("first",)])
    def test_mass_assignment_is_rejected(self):
        with self.assertRaises(ValueError):
            rename(self.database, self.principal, "own", {"owner": "attacker"})
unittest.main()
```

Expected: three tests report OK, including cross-tenant and injection subcases. They use real parameterized SQL and scoped updates; principal identity is a trusted fixture, not client JSON to accept. This is not authentication, HTTP parsing, complete validation, a penetration test, or proof the whole application is secure.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not attack unowned systems or run destructive scanners without authorization. Avoid equating a clean scan or coverage number with security; never fill fixtures with real customer secrets.
