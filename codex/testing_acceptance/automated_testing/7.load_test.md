# Load Test

[Lesson index](../../README.md) · [Previous](6.smoke_test.md) · [Next](8.stress_test.md)

## 1. What is it?

A load test measures correct service behavior under a specified expected workload, like running checkout with a realistic number and mix of shoppers.

## 2. Why do we need it?

One successful request reveals nothing about pool exhaustion, queue delay, tail latency, throughput, and errors under concurrent demand.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Define arrival model, operation mix, data size, concurrency/rate, duration, warm-up, and objectives. A closed-loop generator slows its offered rate when responses slow; an arrival-rate generator must report dropped/unscheduled work. Measure end-to-end residence time, successful completion, errors, and generator capacity, not only averages from successful requests.

Reference: [Primary documentation](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/).

### 3b. Boundaries and lifecycle

Validate generator with tiny traffic → establish baseline → run authorized representative load → observe client/server/resource signals → compare objectives and repeat comparable runs.

## 4. How to apply / implement / use it?

Save as `load_test_demo.py`; run `python3 load_test_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from concurrent.futures import ThreadPoolExecutor
from time import perf_counter
import hashlib
import math
def request(number, submitted):
    try:
        if number % 11 == 0:
            raise RuntimeError("injected application failure")
        hashlib.pbkdf2_hmac("sha256", b"fixture", b"local-only", 500)
        ok = True
    except RuntimeError:
        ok = False
    return ok, perf_counter() - submitted
started = perf_counter()
with ThreadPoolExecutor(max_workers=4) as executor:
    futures = [executor.submit(request, number, perf_counter()) for number in range(30)]
    outcomes = [future.result(timeout=5) for future in futures]
elapsed = perf_counter() - started
durations = sorted(duration for ok, duration in outcomes)
errors = sum(not ok for ok, duration in outcomes)
assert len(outcomes) == 30 and errors == 3
assert elapsed > 0 and all(duration >= 0 for duration in durations)
print({"completed_per_second": len(outcomes) / elapsed,
       "successful_per_second": (len(outcomes) - errors) / elapsed,
       "p95_seconds": durations[math.ceil(0.95 * len(durations)) - 1],
       "errors": errors})
```

Expected: 30 outcomes with three deliberately injected errors; timings vary. This real bounded local workload includes executor queue wait in each measured duration. It is a finite-batch fixed-concurrency harness, not an HTTP service, constant-arrival-rate generator, or production capacity test. It makes no machine-specific timing assertion; the injected 10% error rate is measurement practice, not an acceptable product target.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not run load against systems without authorization and explicit traffic/abort limits. Avoid unrealistically small datasets, unlimited generator resources, and counting fast failures as throughput success.

## 6. How do I know I understand it?

**Blank-page check:** Specify a workload and objective, then explain offered rate versus completed/successful rate and how queue wait enters latency.

| Constraint change | Predict the failure and response |
| --- | --- |
| Service slows in a closed-loop test | Offered demand falls while clients wait; a stable error rate can hide unmet target demand. |
| Generator CPU or network saturates | The test may be generator-limited; observe it independently before claiming server capacity. |
