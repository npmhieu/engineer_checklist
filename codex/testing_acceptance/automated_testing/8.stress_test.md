# Stress Test

[Lesson index](../../README.md) · [Previous](7.load_test.md) · [Next](9.performance_test.md)

## 1. What is it?

A stress test examines degradation and recovery under unusually high demand or beyond a defined operating envelope, like overloading a supervised test rig to find safe limits.

## 2. Why do we need it?

Expected-load success does not show whether overload causes controlled rejection, unbounded backlog, corruption, or a service that never recovers.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Begin from a known baseline, increase a controlled workload, observe the capacity knee and failure mode, then reduce demand and verify recovery. Stress, spike, and soak tests answer different questions: high load, abrupt change, and duration-related failure. Bound blast radius, total work, retention, and abort conditions; naming conventions vary, so state the actual profile.

Reference: [Primary documentation](https://grafana.com/docs/k6/latest/testing-guides/test-types/stress-testing/).

### 3b. Boundaries and lifecycle

Authorize scope and abort policy → baseline → ramp above normal load → observe bounded degradation → ramp down → verify drained backlog and preserved invariants.

## 4. How to apply / implement / use it?

Save as `stress_test_demo.py`; run `python3 stress_test_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from collections import deque
queue = deque()
accepted = processed = rejected = next_id = 0
def phase(arrivals, ticks):
    global accepted, processed, rejected, next_id
    initial_rejected = rejected
    for tick in range(ticks):
        for arrival in range(arrivals):
            next_id += 1
            if len(queue) == 4:
                rejected += 1
            else:
                queue.append(next_id)
                accepted += 1
        for slot in range(min(2, len(queue))):
            queue.popleft()
            processed += 1
        assert len(queue) <= 4
    return rejected - initial_rejected
assert phase(2, 3) == 0
assert phase(8, 3) > 0
phase(0, 3)
assert not queue and processed == accepted
assert phase(2, 3) == 0
assert processed == accepted and next_id == accepted + rejected
```

Expected: normal demand has no rejection, overload is rejected within a bounded queue, and recovery drains all admitted work. This deterministic synthetic-capacity model sends no real stress traffic and measures no real server limit or latency. Production evidence requires an authorized generator, representative workload, bounded ramp/abort policy, and actual resource/invariant observations.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not run an uncontrolled production breaking-point experiment or call simple request volume a correctness guarantee. Stop on agreed safety limits; a larger outage is not better evidence.

## 6. How do I know I understand it?

**Blank-page check:** Draw baseline, overload, and recovery phases and distinguish safe rejection from loss of already accepted work.

| Constraint change | Predict the failure and response |
| --- | --- |
| Intake remains above service rate forever | No finite queue solves sustained overload; admit less or increase effective capacity. |
| Traffic falls but queue age never recovers | Investigate leaked resources, stuck work, retries, and data corruption instead of declaring the ramp complete. |
