# Read Replicas

[Lesson index](../../README.md) · [Previous](1.replication.md) · [Next](3.database_failover.md)

## 1. What is it?

Read replicas serve eligible queries from replicated copies, like reading a branch ledger when a slightly delayed view is acceptable.

## 2. Why do we need it?

Heavy reporting competes with writes on the primary, but indiscriminate read routing makes users lose sight of their own recent changes.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Choose reads by consistency need, not only SQL verb. Replica replay consumes resources and may lag or conflict with long queries. Session pinning or supported replication-position barriers can provide read-your-writes; a random follower and fixed sleep cannot guarantee it.

Reference: [Primary documentation](https://www.postgresql.org/docs/current/hot-standby.html).

### 3b. Boundaries and lifecycle

Write to authority → obtain required visibility marker/session policy → route read to a sufficiently fresh eligible replica or primary → bound waits and fallback explicitly.

## 4. How to apply / implement / use it?

Save as `read_replicas_demo.py`; run `python3 read_replicas_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
primary = {"position": 8, "value": "new"}
replica = {"position": 6, "value": "old"}
def read(required_position=None):
    if required_position is not None and replica["position"] < required_position:
        if primary["position"] < required_position:
            raise TimeoutError("required visibility unavailable")
        return primary["value"]
    return replica["value"]
assert read() == "old"
assert read(required_position=8) == "new"
replica.update(position=8, value="new")
assert read(required_position=8) == "new"
try:
    read(required_position=9)
except TimeoutError:
    pass
else:
    raise AssertionError("freshness requirement silently weakened")
```

This routing model assumes all positions belong to one valid history and rejects a requirement neither copy satisfies. It does not implement PostgreSQL LSN barriers or authenticate markers; production must verify tokens, authority, timeline, and freshness rather than trust an arbitrary integer.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not route authorization changes, immediate inventory decisions, or strict read-after-write workflows to stale copies without a stronger policy. Replicas do not scale primary write throughput.

## 6. How do I know I understand it?

**Blank-page check:** Classify three reads by freshness requirement and explain the fallback when a replica cannot catch up within budget.

| Constraint change | Predict the failure and response |
| --- | --- |
| User writes then refreshes immediately | Pin or enforce a visibility barrier instead of accepting a stale follower answer. |
| Failover changes replication history | Old markers may not be comparable; use database-supported epoch/timeline semantics. |
