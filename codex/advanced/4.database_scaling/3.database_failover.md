# Database Failover

[Lesson index](../../README.md) · [Previous](2.read_replicas.md) · [Next](4.partitioning.md)

## 1. What is it?

Database failover promotes or routes to an eligible replacement authority after failure, like transferring one official ledger desk to a prepared successor.

## 2. Why do we need it?

A dead primary stops writes, but a careless promotion can lose committed data or create two writable primaries.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Detection, election/approval, fencing, replay eligibility, endpoint change, and client reconnection are distinct steps. Async replicas may lack acknowledged writes. Never select a candidate merely because its clock or local row count looks newest; promotion safety depends on the replication protocol and acknowledged-history policy.

Reference: [Primary documentation](https://www.postgresql.org/docs/current/warm-standby-failover.html).

### 3b. Boundaries and lifecycle

Detect → fence former writer → select eligible caught-up candidate → promote → update routing → reconnect/reconcile uncertain transactions → rejoin old node safely.

## 4. How to apply / implement / use it?

Save as `database_failover_demo.py`; run `python3 database_failover_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
cluster = {"writer": "node-a", "epoch": 1, "old_fenced": False}
def promote(candidate, caught_up):
    if not cluster["old_fenced"] or not caught_up:
        raise RuntimeError("unsafe promotion")
    cluster.update(writer=candidate, epoch=cluster["epoch"] + 1)
try:
    promote("node-b", True)
except RuntimeError:
    pass
assert cluster["writer"] == "node-a"
cluster["old_fenced"] = True
promote("node-b", True)
assert cluster["writer"] == "node-b" and cluster["epoch"] == 2
```

This approval-state model is not a failure detector, election algorithm, or PostgreSQL promotion script. It assumes fencing and eligibility were independently verified; a Boolean variable cannot establish them in a real network.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not automate promotion from a single failed ping or let a recovered old primary resume writes unchecked. Test client reconnects, loss policy, and split-brain prevention.
