# Partitioning

[Lesson index](../../README.md) · [Previous](3.database_failover.md) · [Next](5.sharding.md)

## 1. What is it?

Partitioning splits one logical dataset into bounded pieces, like storing ledger pages by month while keeping one logical catalog.

## 2. Why do we need it?

Large tables make retention deletion, scans, index working sets, and maintenance expensive when queries touch only a subset.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Range/list/hash partition keys drive routing and pruning. Boundaries, local indexes, uniqueness rules, partition counts, and planning overhead matter. Partitioning within one database is not automatically distribution across machines; pruning helps only when predicates expose the relevant key.

Reference: [Primary documentation](https://www.postgresql.org/docs/current/ddl-partitioning.html).

### 3b. Boundaries and lifecycle

Choose access/retention key → create bounds ahead of writes → route rows → prune eligible queries → maintain or detach old pieces under engine-specific locking rules.

## 4. How to apply / implement / use it?

Save as `partitioning_demo.py`; run `python3 partitioning_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from datetime import date
bounds = [
    (date(2026, 10, 1), date(2026, 11, 1), "october"),
    (date(2026, 11, 1), date(2026, 12, 1), "november"),
]
def route(day):
    for lower, upper, name in bounds:
        if lower <= day < upper:
            return name
    raise ValueError("no partition for date")
assert route(date(2026, 10, 31)) == "october"
assert route(date(2026, 11, 1)) == "november"
try:
    route(date(2027, 1, 1))
except ValueError:
    pass
else:
    raise AssertionError("missing partition hidden")
```

This real range-routing function demonstrates inclusive lower/exclusive upper bounds only. It is not native database partitioning or query pruning. Use your engine's DDL and EXPLAIN on representative data to verify actual behavior.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not partition a small table without a measured reason or create millions of tiny pieces. Global uniqueness and cross-partition queries may become harder.

## 6. How do I know I understand it?

**Blank-page check:** Choose a partition key from real predicates and retention needs; explain what happens at the next boundary.

| Constraint change | Predict the failure and response |
| --- | --- |
| Next month's partition is missing | Writes can fail; automate creation and alert before the boundary. |
| Query omits the partition key | Many partitions may still be scanned; partitioning is not a substitute for query/index design. |
