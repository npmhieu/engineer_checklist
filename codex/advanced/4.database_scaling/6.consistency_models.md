# Consistency Models

[Lesson index](../../README.md) · [Previous](5.sharding.md) · [Next](7.large_scale_data_architecture.md)

## 1. What is it?

Consistency models define which observations concurrent clients may see, like precise rules for when updated ledger entries must become visible.

## 2. Why do we need it?

The word consistent is too vague to predict stale reads, session regressions, or anomalies across multiple keys.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Linearizability respects real-time order for operations; serializability orders transactions but need not respect real time; strict serializability combines both. Causal/session guarantees constrain selected histories; eventual convergence alone is weaker. Transaction isolation and replication consistency are related but different axes.

Reference: [Primary documentation](https://jepsen.io/consistency).

### 3b. Boundaries and lifecycle

Specify required histories → choose database/client modes → preserve routing/session metadata → test observed histories under failures rather than infer semantics from replica count.

## 4. How to apply / implement / use it?

Save as `consistency_models_demo.py`; run `python3 consistency_models_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def session_read(value, minimum_seen, own_write):
    required = max(minimum_seen, own_write)
    if value < required:
        raise ValueError("session freshness requirement violated")
    return value
assert session_read(5, minimum_seen=4, own_write=5) == 5
try:
    session_read(3, minimum_seen=4, own_write=2)
except ValueError:
    pass
else:
    raise AssertionError("monotonic read violated")
try:
    session_read(4, minimum_seen=2, own_write=5)
except ValueError:
    pass
else:
    raise AssertionError("read-your-writes violated")
```

This model uses one monotonically versioned register to distinguish session guarantees. Numeric comparison does not establish linearizability, causal tracking across keys, or correctness across divergent histories.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not request the strongest model everywhere without understanding latency/availability cost, or assume read-your-writes means all clients see all latest writes.

## 6. How do I know I understand it?

**Blank-page check:** Construct a history allowed by eventual consistency but forbidden by monotonic reads, then distinguish serializable from strictly serializable transactions.

| Constraint change | Predict the failure and response |
| --- | --- |
| Client switches devices without session metadata | Session guarantees need supported state propagation or stronger server behavior. |
| Multiple keys encode one invariant | Single-key freshness is insufficient; choose an appropriate transactional model. |
