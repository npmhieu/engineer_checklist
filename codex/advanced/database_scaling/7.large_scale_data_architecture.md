# Large-scale Data Architecture

[Lesson index](../../README.md) · [Previous](6.consistency_models.md) · [Next](../reliability/1.circuit_breaker.md)

## 1. What is it?

Large-scale data architecture assigns authoritative, operational, analytical, and archival roles to coordinated data systems, like separate ledgers, scoreboards, and archives linked by controlled transfers.

## 2. Why do we need it?

One database serving every workload suffers contention, while ungoverned copies drift and produce incompatible business totals.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Define fact ownership, grain, contracts, lineage, freshness, privacy deletion, and recovery per store. CDC/outbox ingestion, idempotent projections, watermarks, and reconciliation connect roles. Additional systems multiply storage, network, schema, access, and operational costs.

Reference: [Primary documentation](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view).

### 3b. Boundaries and lifecycle

Commit authoritative facts → publish/ingest recoverably → derive read/analytics views → expose freshness → reconcile → rebuild or repair from retained authoritative evidence.

## 4. How to apply / implement / use it?

Save as `large_scale_data_architecture_demo.py`; run `python3 large_scale_data_architecture_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
source = {"sale-1": 500, "sale-2": 300}
projection = {"sale-1": 500}
def reconcile():
    missing = set(source) - set(projection)
    conflicting = {key for key in source.keys() & projection.keys()
                   if source[key] != projection[key]}
    return missing, conflicting
assert reconcile() == ({"sale-2"}, set())
for key in reconcile()[0]:
    projection[key] = source[key]
assert reconcile() == (set(), set())
projection["sale-1"] = 999
assert reconcile()[1] == {"sale-1"}
```

This tiny real reconciliation function demonstrates missing/conflicting derived facts. It omits extra records, deletion handling, privacy policy, incremental scans, durable ingestion, and large-data cost; production reconciliation needs those explicitly.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not add streaming, warehouse, lake, and search systems merely because they are fashionable. Each copy needs a clear owner, value, retention, and repair path.

## 6. How do I know I understand it?

**Blank-page check:** Draw one source of truth and three derived stores with freshness and recovery responsibilities.

| Constraint change | Predict the failure and response |
| --- | --- |
| A user invokes a valid deletion policy | Propagate governed deletion/tombstones to eligible copies and archives; replay must not silently resurrect erased data. |
| Analytics totals diverge | Use lineage and stable fact identity to locate the mismatch before overwriting authoritative records. |
