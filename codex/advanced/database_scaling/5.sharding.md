# Sharding

[Lesson index](../../README.md) · [Previous](4.partitioning.md) · [Next](6.consistency_models.md)

## 1. What is it?

Sharding distributes data ownership across database nodes, like assigning customer ledgers to separate branch vaults.

## 2. Why do we need it?

One node can exceed write, storage, or working-set capacity, but splitting ownership introduces routing and cross-shard coordination.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Choose a shard key with locality, distribution, and growth in mind. Routing maps, shard epochs, unique-ID strategy, rebalancing, backup, and scatter/gather queries add cost. A hot tenant remains hot; changing a modulo shard count remaps many keys and requires data migration.

Reference: [Primary documentation](https://learn.microsoft.com/en-us/azure/architecture/patterns/sharding).

### 3b. Boundaries and lifecycle

Resolve key/epoch → route to owner → execute local work → coordinate cross-shard operations explicitly → move ranges with verified ownership and cutover.

## 4. How to apply / implement / use it?

Save as `sharding_demo.py`; run `python3 sharding_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import hashlib
def shard(key, count):
    if count < 1:
        raise ValueError("positive shard count required")
    number = int.from_bytes(hashlib.sha256(key.encode()).digest()[:8], "big")
    return number % count
keys = ["tenant-" + str(number) for number in range(100)]
moved = [key for key in keys if shard(key, 2) != shard(key, 3)]
assert moved
assert shard("tenant-7", 2) == shard("tenant-7", 2)
try:
    shard("tenant-7", 0)
except ValueError:
    pass
else:
    raise AssertionError("invalid shard configuration")
```

This stable modulo router demonstrates remapping, not a safe sharding implementation or consistent hashing. Production must migrate records and protect read/write ownership during routing changes; changing this integer alone loses access to data.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not shard before simpler query, indexing, retention, vertical-scale, or replica options are evaluated. Cross-shard joins and transactions can dominate savings.

## 6. How do I know I understand it?

**Blank-page check:** Design shard key, routing ownership, tenant growth policy, and a move/rollback protocol.

| Constraint change | Predict the failure and response |
| --- | --- |
| One tenant owns half the traffic | Hashing tenant IDs cannot split that tenant's internal workload without changing ownership design. |
| Shard count changes from two to three | Many keys move; use a migration protocol rather than flipping configuration. |
