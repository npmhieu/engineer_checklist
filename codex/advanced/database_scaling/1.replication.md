# Replication

[Lesson index](../../README.md) · [Previous](../distributed_consistency/8.distributed_idempotency.md) · [Next](2.read_replicas.md)

## 1. What is it?

Replication maintains additional copies of database state, like branch ledgers updated from an authoritative change journal.

## 2. Why do we need it?

One database machine is a failure and read-capacity bottleneck, but extra copies introduce lag and recovery rules rather than automatic perfect availability.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Physical replication ships/replays storage changes such as WAL; logical replication transfers selected logical changes. Async acknowledgement can precede replica replay; synchronous modes wait for configured milestones, which differ from query-visible freshness. Replication consumes network, storage, replay CPU, and retained logs.

Reference: [Primary documentation](https://www.postgresql.org/docs/current/warm-standby.html).

### 3b. Boundaries and lifecycle

Primary commits/logs → transmit → replica receives/durably stores/applies → monitor positions and lag → recover or promote under an explicit protocol.

## 4. How to apply / implement / use it?

Save as `replication_demo.py`; run `python3 replication_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
journal = []
primary, replica = {}, {}
applied = 0
def write(key, value):
    primary[key] = value
    journal.append((key, value))
def catch_up():
    global applied
    for key, value in journal[applied:]:
        replica[key] = value
        applied += 1
write("order-1", "placed")
assert replica.get("order-1") is None
catch_up()
assert replica == primary and applied == len(journal)
write("order-1", "cancelled")
assert replica["order-1"] == "placed"
catch_up()
assert replica["order-1"] == "cancelled"
```

This ordered journal model is not PostgreSQL WAL, crash recovery, or a replication configuration. It omits persistence, deletes, transactions, schema changes, log gaps, and timeline handling.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not mistake replicas for independent backups: accidental deletes and corruption can propagate. Replication does not eliminate operational recovery work.

## 6. How do I know I understand it?

**Blank-page check:** Distinguish received, durable, replayed, and query-visible state; explain which point a configured synchronous mode waits for.

| Constraint change | Predict the failure and response |
| --- | --- |
| Replica replay stalls | Primary may keep accepting writes while lag and retained-log storage grow. |
| Primary acknowledges before any replica persists | A failover can lose acknowledged writes under that policy. |
