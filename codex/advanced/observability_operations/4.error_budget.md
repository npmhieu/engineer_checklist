# Error Budget

[Lesson index](../../README.md) · [Previous](3.service_level_agreements.md) · [Next](5.capacity_monitoring.md)

## 1. What is it?

An error budget is the tolerated bad-event allowance implied by an SLO, like a bounded reliability spending account over a defined period.

## 2. Why do we need it?

Without a shared policy, teams argue indefinitely about shipping features versus reducing failures.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

For event-based SLOs, allowance equals eligible events times one minus target; consumed allowance is bad events. Burn rate compares observed bad fraction with allowed bad fraction. Rolling windows replenish by aging data out, not by declaring an incident resolved. Time-based and event-based budgets have different denominators.

Reference: [Primary documentation](https://sre.google/workbook/alerting-on-slos/).

### 3b. Boundaries and lifecycle

Measure SLI → calculate consumed/remaining allowance and burn → apply preagreed release/reliability policy → recover sustained health.

## 4. How to apply / implement / use it?

Save as `error_budget_demo.py`; run `python3 error_budget_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def budget(total, bad, target):
    if total <= 0 or not 0 <= bad <= total or not 0 < target < 1:
        raise ValueError("invalid budget inputs")
    allowance = total * (1 - target)
    return {"allowance": allowance, "remaining": allowance - bad,
            "burn": (bad / total) / (1 - target)}
healthy = budget(10000, 5, 0.999)
assert round(healthy["remaining"]) == 5
exhausted = budget(10000, 20, 0.999)
assert exhausted["remaining"] < 0
assert round(exhausted["burn"]) == 2
try:
    budget(0, 0, 0.999)
except ValueError:
    pass
else:
    raise AssertionError("empty window treated as evidence")
```

This arithmetic uses synthetic event counts and floating-point approximations. Real policies need complete windows, trustworthy eligibility, denominator choices, and explicit handling of small samples.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not treat a budget as permission to harm users or reset it manually after a bad release. Avoid multiplying request-based allowance into downtime minutes without a valid time-based model.

## 6. How do I know I understand it?

**Blank-page check:** Derive allowance and burn from an SLO and explain what happens as a rolling window advances.

| Constraint change | Predict the failure and response |
| --- | --- |
| A fix stops new failures | Past bad events remain until they age out; remaining budget does not instantly reset. |
| Traffic falls sharply | Event-based and time-based interpretations diverge; use the declared indicator. |
