# Capacity Monitoring

[Lesson index](../../README.md) · [Previous](4.error_budget.md) · [Next](6.advanced_alerting.md)

## 1. What is it?

Capacity monitoring tracks usable headroom and saturation against expected demand, like watching remaining checkout lanes and queue growth before customers abandon.

## 2. Why do we need it?

CPU dashboards can look normal while pools, disk, quotas, partitions, or queue age approach exhaustion.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Measure workload-normalized capacity, utilization, queue/wait time, growth, and scale lead time per critical resource. Forecasts need uncertainty and failure margin; aggregate averages can hide one saturated shard. Avoid per-user metric labels while preserving meaningful bounded dimensions.

Reference: [Primary documentation](https://sre.google/sre-book/monitoring-distributed-systems/).

### 3b. Boundaries and lifecycle

Collect demand/resource signals → identify headroom and limiting scope → project exhaustion against response lead time → scale/reduce demand → verify.

## 4. How to apply / implement / use it?

Save as `capacity_monitoring_demo.py`; run `python3 capacity_monitoring_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def exhaustion_hours(used, limit, growth_per_hour):
    if limit <= 0 or used < 0 or used > limit or growth_per_hour < 0:
        raise ValueError("invalid capacity sample")
    if growth_per_hour == 0:
        return float("inf")
    return (limit - used) / growth_per_hour
assert exhaustion_hours(80, 100, 5) == 4
lead_time_hours = 6
assert exhaustion_hours(80, 100, 5) < lead_time_hours
assert exhaustion_hours(80, 100, 0) == float("inf")
try:
    exhaustion_hours(110, 100, 5)
except ValueError:
    pass
else:
    raise AssertionError("invalid sample accepted")
```

This linear forecast model does not measure real demand or predict nonlinear saturation. Zero observed growth is not evidence of unlimited future capacity; include peaks and uncertainty.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not alert on every high utilization value without impact/lead time, or average away hot shards and depleted failure headroom.

## 6. How do I know I understand it?

**Blank-page check:** Design headroom signals for database connections, disk, queue age, provider quota, and one hot partition.

| Constraint change | Predict the failure and response |
| --- | --- |
| One shard is full while fleet average is low | Monitor per-shard saturation and skew, not only fleet totals. |
| Provisioning takes longer than forecast headroom | Act early through scaling, retention, quotas, or admission control. |
