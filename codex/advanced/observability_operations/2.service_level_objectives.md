# Service Level Objectives (SLO)

[Lesson index](../../README.md) · [Previous](1.advanced_distributed_tracing.md) · [Next](3.service_level_agreements.md)

## 1. What is it?

An SLO is a quantified reliability target for a defined service-level indicator and window, like promising a specified share of customers a successful checkout experience.

## 2. Why do we need it?

Teams cannot prioritize reliability work or judge a release using vague goals such as fast and highly available.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Define eligible events, good events, measurement point, threshold, and rolling/calendar window. Availability and latency need separate or deliberately combined criteria. Missing telemetry and zero traffic require explicit handling; exclusions must reflect user experience rather than hide failures.

Reference: [Primary documentation](https://sre.google/workbook/implementing-slos/).

### 3b. Boundaries and lifecycle

Define user journey → specify SLI and target/window → measure → compare compliance → spend/error-budget policy guides engineering action.

## 4. How to apply / implement / use it?

Save as `service_level_objectives_demo.py`; run `python3 service_level_objectives_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def sli(events):
    eligible = [event for event in events if event["eligible"]]
    if not eligible:
        return None
    good = sum(event["success"] and event["ms"] <= 300 for event in eligible)
    return good / len(eligible)
events = [{"eligible": True, "success": True, "ms": 100}] * 99
events += [{"eligible": True, "success": False, "ms": 20}]
assert sli(events) == 0.99
assert sli(events) < 0.999
assert sli([]) is None
assert sli([{"eligible": False, "success": False, "ms": 0}]) is None
```

This executable synthetic combined-success/latency SLI adopts a 300 ms threshold and 99.9% target only for illustration. It does not define which real requests are eligible or prove any operational target is met.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not choose 100% reflexively, copy another service's target, or count only successful requests in the denominator. A target without a window and measurement definition is incomplete.

## 6. How do I know I understand it?

**Blank-page check:** Write one complete SLO and explain numerator, denominator, window, measurement location, and missing-data policy.

| Constraint change | Predict the failure and response |
| --- | --- |
| Errors return quickly | They remain bad events; low latency alone cannot make them good. |
| Telemetry disappears | Treat measurement confidence separately; missing data is not automatic perfect reliability. |
