# Capacity Planning

[Lesson index](../../README.md) · [Previous](2.profiling.md) · [Next](4.bottleneck_analysis.md)

## 1. What is it?

Capacity planning estimates resources needed for a workload and failure margin, like staffing enough checkout lanes for peak arrivals and one lane outage.

## 2. Why do we need it?

Average traffic sizing runs out of headroom during peaks, retries, maintenance, or a zone failure; scaling may arrive too late.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Measure per-instance sustainable capacity at the objective, workload mix, growth, bursts, and scale-up delay. Little's law L = lambda times W relates average in-system work, throughput, and residence time in a stable system with consistent boundaries/units. It does not predict tail latency or cure sustained overload.

Reference: [Primary documentation](https://sre.google/sre-book/handling-overload/).

### 3b. Boundaries and lifecycle

Forecast demand → benchmark usable capacity → reserve failure/headroom margin → verify dependencies and scaling delay → rehearse peaks and failures → revise.

## 4. How to apply / implement / use it?

Save as `capacity_planning_demo.py`; run `python3 capacity_planning_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import math
def instances(peak_rps, capacity_rps, target_fraction, lost_instances):
    if peak_rps < 0 or capacity_rps <= 0 or not 0 < target_fraction <= 1:
        raise ValueError("invalid capacity assumptions")
    return math.ceil(peak_rps / (capacity_rps * target_fraction)) + lost_instances
assert instances(240, 100, 0.6, 1) == 5
average_inflight = 200 * 0.25
assert average_inflight == 50
try:
    instances(240, 0, 0.6, 1)
except ValueError:
    pass
else:
    raise AssertionError("zero capacity accepted")
```

This arithmetic model assumes identical instances and a measured sustainable rate for the same workload. The extra-instance rule covers the named instance loss only, not an arbitrary zone loss or nonlinear database bottleneck.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not extrapolate a tiny benchmark linearly to production or count theoretical CPU capacity as objective-compliant throughput. Reserve headroom for retries and failure, not just growth.

## 6. How do I know I understand it?

**Blank-page check:** State units, workload mix, sustainable rate, scale delay, and the exact failure margin in a capacity estimate.

| Constraint change | Predict the failure and response |
| --- | --- |
| Database remains capped at 300 RPS | More app instances cannot exceed that critical downstream capacity. |
| Traffic doubles before autoscaling finishes | Admission, preprovisioned headroom, or buffering within deadlines must cover the gap. |
