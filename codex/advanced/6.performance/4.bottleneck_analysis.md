# Bottleneck Analysis

[Lesson index](../../README.md) · [Previous](3.capacity_planning.md) · [Next](5.throughput_optimization.md)

## 1. What is it?

Bottleneck analysis finds the limiting resource or serial path for a workload, like locating the narrowest station before widening the rest of a factory.

## 2. Why do we need it?

Adding application CPUs does not help when database locks, a connection pool, or a remote quota limits throughput.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Measure utilization, saturation/queueing, errors, and demand per completed operation. The limiting resource can move after a fix. Amdahl's law bounds speedup from optimizing only a fraction of runtime; real systems also change with contention and workload.

Reference: [Primary documentation](https://sre.google/sre-book/handling-overload/).

### 3b. Boundaries and lifecycle

Observe end-to-end symptom → decompose demand/waits → identify saturated critical resource → test a causal change → remeasure the new limit.

## 4. How to apply / implement / use it?

Save as `bottleneck_analysis_demo.py`; run `python3 bottleneck_analysis_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import math
capacities = {"application": 500, "database": 120, "provider": 200}
assert min(capacities, key=capacities.get) == "database"
capacities["application"] = 1000
assert min(capacities.values()) == 120
capacities["database"] = 300
assert min(capacities, key=capacities.get) == "provider"
def speedup(fraction, improvement):
    if not 0 <= fraction <= 1 or improvement <= 0:
        raise ValueError("invalid optimization")
    return 1 / ((1 - fraction) + fraction / improvement)
assert math.isclose(speedup(0.8, 4), 2.5)
assert math.isclose(speedup(0.2, 1000000), 1.25, rel_tol=0.00001)
```

This model assumes normalized equivalent end-to-end operation rates and a fixed runtime fraction. Real measurements must account for calls per request, mixed workloads, concurrency, and feedback effects before comparing capacities.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not diagnose from CPU alone or apply Amdahl's law to unrelated workload measurements. A queue is evidence of waiting, not automatically proof the waiting component is the root cause.

## 6. How do I know I understand it?

**Blank-page check:** Explain why increasing a nonlimiting capacity has no immediate throughput benefit and predict the next bottleneck.

| Constraint change | Predict the failure and response |
| --- | --- |
| Each request now makes three provider calls | Normalize provider quota to end-to-end demand; its effective capacity drops. |
| Database contention grows nonlinearly | The fixed-capacity model breaks; measure under representative concurrency. |
