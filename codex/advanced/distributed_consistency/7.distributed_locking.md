# Distributed Locking

[Lesson index](../../README.md) · [Previous](6.compensation.md) · [Next](8.distributed_idempotency.md)

## 1. What is it?

Distributed locking coordinates temporary ownership across processes, like a shared key checkout with an expiry and a numbered authority token.

## 2. Why do we need it?

Local mutexes do not coordinate different machines, and an expired lease can leave an old worker still running while a new worker starts.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Acquisition/release must be atomic under the coordinator's guarantees; release must verify ownership. A lease expiry is not execution cancellation. Monotonic fencing tokens can let the protected resource reject stale writers, but only if the resource validates/enforces them; a random owner token is not a fencing order.

Reference: [Primary documentation](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/).

### 3b. Boundaries and lifecycle

Acquire lease/token → perform protected work through a fencing-aware resource → renew under policy → release only own lease; reject stale completions after ownership changes.

## 4. How to apply / implement / use it?

Save as `distributed_locking_demo.py`; run `python3 distributed_locking_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
resource = {"highest_token": 0, "value": ""}
def write(token, value):
    if token < resource["highest_token"]:
        raise PermissionError("stale fencing token")
    resource.update(highest_token=token, value=value)
old_token, new_token = 1, 2
write(old_token, "first owner")
write(new_token, "new owner after lease expiry")
try:
    write(old_token, "late old owner")
except PermissionError:
    pass
else:
    raise AssertionError("stale writer accepted")
assert resource["value"] == "new owner after lease expiry"
```

This trusted-token resource model illustrates fencing after a newer accepted write, not a lock service or Redis lock implementation. Tokens must come from an authorized monotonic coordinator and cannot be caller-invented; token comparison and mutation must be atomic at the real resource.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not use lease expiry alone to guarantee no overlapping execution. Prefer database constraints/conditional writes when they directly enforce the invariant; lock-service partitions, clock/lease assumptions, and renewal add complexity.

## 6. How do I know I understand it?

**Blank-page check:** Draw a paused owner, expired lease, new owner, and late old write. Explain ownership token versus fencing token.

| Constraint change | Predict the failure and response |
| --- | --- |
| Old worker resumes after expiry | It may still execute; only resource-side fencing or another invariant guard prevents stale effects. |
| Protected provider cannot enforce fencing | A distributed lock alone cannot guarantee exactly-once remote effects. |
