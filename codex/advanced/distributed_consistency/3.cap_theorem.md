# CAP Theorem

[Lesson index](../../README.md) · [Previous](2.strong_consistency.md) · [Next](4.distributed_transactions.md)

## 1. What is it?

CAP says a partitioned asynchronous system cannot guarantee both linearizable consistency and formal availability for every request, like disconnected offices unable to both answer independently and always agree instantly.

## 2. Why do we need it?

Design discussions misuse CAP as 'pick any two' even during normal operation or confuse formal availability with an uptime percentage.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

In the theorem, consistency is atomic/linearizable behavior and availability requires every request to a nonfailed node eventually receive a valid response. During a partition, a node cannot know the remote latest write. Refusing or waiting sacrifices formal availability; answering stale sacrifices consistency. Network partitions are a failure condition, not a feature to switch off.

Reference: [Primary documentation](https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer2.pdf).

### 3b. Boundaries and lifecycle

Partition separates owners → choose which operations may proceed under which guarantees → preserve safety or allow defined stale/conflicting outcomes → repair after reconnection.

## 4. How to apply / implement / use it?

Save as `cap_theorem_demo.py`; run `python3 cap_theorem_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
latest, isolated_copy = 2, 1
partitioned = True
def read(require_fresh):
    if partitioned and require_fresh:
        raise ConnectionError("cannot establish fresh authority")
    return isolated_copy if partitioned else latest
try:
    read(require_fresh=True)
except ConnectionError:
    pass
else:
    raise AssertionError("freshness invented")
assert read(require_fresh=False) == 1
assert read(require_fresh=False) != latest
```

This single-read scenario illustrates the partition choice, not a proof or a complete CP/AP system. A fast error is not formal CAP availability, even if an uptime dashboard counts the HTTP endpoint as reachable.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not use CAP to justify arbitrary poor reliability or ignore normal-operation latency/consistency trade-offs. Classify operations and failure modes rather than labeling an entire product with two letters.
