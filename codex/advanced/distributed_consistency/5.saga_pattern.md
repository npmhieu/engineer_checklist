# Saga Pattern

[Lesson index](../../README.md) · [Previous](4.distributed_transactions.md) · [Next](6.compensation.md)

## 1. What is it?

A saga coordinates a business workflow through local commits and compensating actions, like a travel booking that cancels a reserved hotel if the flight cannot be bought.

## 2. Why do we need it?

Cross-service operations need recovery without pretending every service and provider shares one database transaction.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Persist step state, operation identity, outcomes, and compensation progress. Orchestration uses an explicit coordinator; choreography reacts through events. Intermediate committed states are visible, so reservations, semantic locks, and invariant design matter. Compensation can fail and is not isolation.

Reference: [Primary documentation](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-orchestration.html).

### 3b. Boundaries and lifecycle

Start → commit local step → record next intent → continue → on failure schedule compensations → retry/reconcile until completed, compensated, or manual intervention.

## 4. How to apply / implement / use it?

Save as `saga_pattern_demo.py`; run `python3 saga_pattern_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def run_saga(payment_ok, compensation_ok=True):
    state = {"reservation": "held", "payment": "pending", "saga": "running"}
    if payment_ok:
        state.update(payment="paid", saga="completed")
        return state
    state["payment"] = "rejected"
    if compensation_ok:
        state.update(reservation="released", saga="compensated")
    else:
        state["saga"] = "compensation-pending"
    return state
assert run_saga(True)["saga"] == "completed"
assert run_saga(False)["reservation"] == "released"
failed = run_saga(False, compensation_ok=False)
assert failed["saga"] == "compensation-pending"
assert failed["reservation"] == "held"
```

This deterministic workflow model demonstrates visible local state and failed compensation, not durable orchestration. Real steps and recovery decisions require persisted state/outbox intent, idempotent participants, timeouts, and reconciliation.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not use a saga where temporary invariant violations are forbidden without reservations or other domain coordination. Avoid a giant unobservable event chain or treating failed compensation as success.

## 6. How do I know I understand it?

**Blank-page check:** Draw forward and compensating steps, including crash/retry identities and a manual-resolution state.

| Constraint change | Predict the failure and response |
| --- | --- |
| Coordinator crashes after a step succeeds | Recover the recorded/queried outcome using stable identity rather than rerun blindly. |
| Compensation is unavailable | Keep recoverable pending state and ownership; the original effect remains committed. |
