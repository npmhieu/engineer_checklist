# Strong Consistency

[Lesson index](../../README.md) · [Previous](1.eventual_consistency.md) · [Next](3.cap_theorem.md)

## 1. What is it?

Strong consistency commonly means linearizable operations that appear to occur atomically in real-time order, like one authoritative counter every clerk must consult.

## 2. Why do we need it?

A client that sees a completed reservation must not later read an older available-stock value when the business depends on one current order of operations.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Define the model explicitly: linearizability is not the same as transaction serializability. A leader/consensus protocol can establish authoritative order, but unsafe stale followers or leader reads can violate it. Coordination adds network latency and may reject operations without sufficient authority.

Reference: [Primary documentation](https://etcd.io/docs/v3.6/learning/api_guarantees/).

### 3b. Boundaries and lifecycle

Route to authority → validate leadership/read barrier → order operation → commit under protocol → return a result consistent with completed predecessors.

## 4. How to apply / implement / use it?

Save as `strong_consistency_demo.py`; run `python3 strong_consistency_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from threading import Lock
class Register:
    def __init__(self):
        self.value = 0
        self.lock = Lock()
        self.authoritative = True
    def write(self, value):
        with self.lock:
            if not self.authoritative:
                raise ConnectionError("authority unavailable")
            self.value = value
    def read(self):
        with self.lock:
            if not self.authoritative:
                raise ConnectionError("authority unavailable")
            return self.value
register = Register()
register.write(7)
assert register.read() == 7
register.authoritative = False
try:
    register.read()
except ConnectionError:
    pass
else:
    raise AssertionError("stale fallback called strong")
```

This real synchronized local register models the chosen API policy, not distributed consensus. Replacing its lock with a majority count is not sufficient to implement linearizability; use a proven system and its documented read/write modes.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not pay global coordination cost for every cache or analytics read. Do not label an unspecified 'consistent' mode strong without identifying the exact model and failure behavior.

## 6. How do I know I understand it?

**Blank-page check:** Distinguish real-time order, serializable transactions, and session guarantees using concrete histories.

| Constraint change | Predict the failure and response |
| --- | --- |
| A stale follower serves the read | The strong guarantee is lost unless the protocol proves freshness. |
| Authority cannot be reached | Reject/wait within budget rather than silently return stale data under the same promise. |
