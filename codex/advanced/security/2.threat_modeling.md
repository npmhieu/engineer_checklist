# Threat Modeling

[Lesson index](../../README.md) · [Previous](1.security_architecture.md) · [Next](3.secrets_management.md)

## 1. What is it?

Threat modeling systematically asks what can go wrong in a specific design and how to reduce or accept that risk, like inspecting a building's access routes before choosing alarms.

## 2. Why do we need it?

Generic security checklists miss system-specific abuse paths such as one tenant reading another tenant's export or a worker fetching an attacker-controlled URL.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Model assets, actors, entry points, data flows, and trust boundaries; identify threats, rank context-sensitive risk, assign mitigations/owners, and validate with tests. STRIDE is one prompting framework, not a complete risk score or proof of safety. Update the model when architecture changes.

Reference: [Primary documentation](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html).

### 3b. Boundaries and lifecycle

Scope design → draw flows/boundaries → identify abuse scenarios → choose mitigation or explicit risk acceptance → implement/test → review changes and residual risk.

## 4. How to apply / implement / use it?

Save as `threat_modeling_demo.py`; run `python3 threat_modeling_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
threats = [
    {"id": "cross-tenant-export", "owner": "exports", "mitigation": "tenant authorization",
     "test": "reject other tenant", "status": "mitigated"},
    {"id": "worker-ssrf", "owner": "workers", "mitigation": "", "test": "",
     "status": "open"},
]
def ready(entries):
    return all(entry["owner"] and entry["mitigation"] and entry["test"]
               and entry["status"] == "mitigated" for entry in entries)
assert not ready(threats)
threats[1].update(mitigation="constrained egress and validated destinations",
                  test="blocked internal destination", status="mitigated")
assert ready(threats)
```

This traceability gate checks documented ownership/coverage fields only. A filled-in test name does not prove the control works; execute actual negative tests and review residual risk. Explicitly accepted risks need a separate approved policy rather than being mislabeled mitigated.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not treat threat modeling as one annual diagram or equate a numeric risk score with certainty. Avoid exhaustive speculation disconnected from real assets and flows.

## 6. How do I know I understand it?

**Blank-page check:** Threat-model an async export with upload, worker, storage, and download boundaries; link each high-priority threat to a control and executable test.

| Constraint change | Predict the failure and response |
| --- | --- |
| Worker gains arbitrary outbound HTTP access | Revisit SSRF, credential reachability, egress controls, redirects, and DNS/IP behavior. |
| A new public download endpoint appears | Review object authorization, link expiry, caching, and sensitive-data exposure. |
