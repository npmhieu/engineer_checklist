# Dependency / Supply-chain Security

[Lesson index](../../README.md) · [Previous](7.zero_trust_concepts.md) · [Next](../devops_delivery/1.infrastructure_as_code.md)

## 1. What is it?

Dependency/supply-chain security controls what code enters and produces a release, like verifying suppliers, sealed ingredients, and factory records rather than trusting the package label.

## 2. Why do we need it?

Typosquatted packages, compromised maintainers/builders, mutable tags, and stolen CI credentials can introduce malicious code without changing reviewed application source.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Use reviewed dependencies/lockfiles, integrity checks, controlled builders, least-privilege CI, artifact provenance/signatures, vulnerability response, and inventory/SBOMs. A digest identifies bytes but not who built them; a signature needs trusted identity and policy. An SBOM is an inventory, not proof of safety.

Reference: [Primary documentation](https://slsa.dev/spec/v1.2/).

### 3b. Boundaries and lifecycle

Review source/dependencies → build in controlled environment → record/verify provenance and artifact identity → enforce promotion policy → monitor and update vulnerabilities.

## 4. How to apply / implement / use it?

Save as `dependency_supply_chain_security_demo.py`; run `python3 dependency_supply_chain_security_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import hashlib
artifact = b"reviewed artifact"
digest = hashlib.sha256(artifact).hexdigest()
verified_statement = {"digest": digest, "builder": "trusted-builder",
                      "source": "reviewed-revision"}
def admit(payload, statement, signature_verified):
    if not signature_verified:
        raise PermissionError("signature verification required")
    if statement["builder"] != "trusted-builder" or statement["source"] != "reviewed-revision":
        raise PermissionError("provenance policy denied")
    if hashlib.sha256(payload).hexdigest() != statement["digest"]:
        raise ValueError("artifact mismatch")
    return True
assert admit(artifact, verified_statement, True)
try:
    admit(b"tampered", verified_statement, True)
except ValueError:
    pass
else:
    raise AssertionError("changed artifact accepted")
try:
    admit(artifact, verified_statement, False)
except PermissionError:
    pass
else:
    raise AssertionError("unverified provenance trusted")
```

This hashes real bytes but models signature verification as a trusted verifier result. Do not accept that Boolean or statement from the artifact uploader without cryptographic verification against trusted identity/source policy. Use maintained tooling such as Sigstore where appropriate.

Verification reference: [Sigstore signature verification](https://docs.sigstore.dev/cosign/verifying/verify/).

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not treat a matching hash, signed malicious build, clean scanner report, or SBOM as a complete guarantee. Pinning without an update process leaves known vulnerabilities in place.

## 6. How do I know I understand it?

**Blank-page check:** Trace one dependency through review, lockfile, builder, artifact, verification, deployment, and vulnerability response.

| Constraint change | Predict the failure and response |
| --- | --- |
| Attacker signs with an untrusted identity | Signature validity alone is insufficient; enforce authorized issuer/subject/builder policy. |
| A pinned dependency gains a disclosed vulnerability | Assess exposure and ship a reviewed update; reproducibility is not a reason to keep unsafe versions. |
