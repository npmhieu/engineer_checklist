# Advanced API Security

[Lesson index](../../README.md) · [Previous](5.key_management.md) · [Next](7.zero_trust_concepts.md)

## 1. What is it?

Advanced API security enforces identity, object/action/property permissions, abuse limits, and safe integration boundaries, like checking both who enters and which records and actions they may access.

## 2. Why do we need it?

A valid token does not prevent cross-tenant object access, mass assignment, resource exhaustion, SSRF, or unsafe third-party responses.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Validate credentials and claims under fixed policy, then authorize every action against trusted resource ownership. Allowlist writable fields, bound request/query costs, protect outbound destinations, and validate provider data. Rate limits supplement rather than replace access control; log only safe evidence.

Reference: [Primary documentation](https://api-security.owasp.org/editions/2023/en/0x11-t10/).

### 3b. Boundaries and lifecycle

Authenticate → constrain request → load resource within scope → authorize operation/properties → enforce cost budget → execute safely → return bounded/redacted output.

## 4. How to apply / implement / use it?

Save as `advanced_api_security_demo.py`; run `python3 advanced_api_security_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
tasks = {"task-1": {"tenant": "shop-1", "title": "old", "owner": "user-1"}}
def update(principal, task_id, patch):
    task = tasks[task_id]
    if principal["tenant"] != task["tenant"] or principal["user"] != task["owner"]:
        raise PermissionError("object access denied")
    if set(patch) != {"title"} or not isinstance(patch["title"], str) or not 1 <= len(patch["title"]) <= 80:
        raise ValueError("unsupported properties or title")
    task["title"] = patch["title"]
principal = {"tenant": "shop-1", "user": "user-1"}
update(principal, "task-1", {"title": "new"})
assert tasks["task-1"]["title"] == "new"
for patch in ({"owner": "attacker"}, {"title": "x" * 81}):
    try:
        update(principal, "task-1", patch)
    except ValueError:
        pass
    else:
        raise AssertionError("unsafe write accepted")
try:
    update({"tenant": "shop-2", "user": "user-1"}, "task-1", {"title": "stolen"})
except PermissionError:
    pass
else:
    raise AssertionError("cross-tenant object write")
```

This real object/property policy assumes verified principal context and a tiny fixture. It does not implement authentication, HTTP parsing, rate/cost limits, SSRF defense, database concurrency, or production error masking.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not rely on unguessable IDs, frontend-hidden fields, internal network placement, or one API gateway for all resource authorization. Avoid arbitrary outbound URL fetching.

## 6. How do I know I understand it?

**Blank-page check:** Describe negative tests for object, function, property, tenant, and resource-cost boundaries.

| Constraint change | Predict the failure and response |
| --- | --- |
| A new admin-only field appears in the database | It must not become writable through generic object binding. |
| One cheap HTTP request triggers a million-row export | Limit business/query cost and enqueue under admission policy, not just request count. |
