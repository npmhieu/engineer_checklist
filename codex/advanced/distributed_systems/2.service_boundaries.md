# Service Boundaries

[Lesson index](../../README.md) · [Previous](1.distributed_systems_fundamentals.md) · [Next](3.microservices_architecture.md)

## 1. What is it?

A service boundary assigns one capability's decisions and data to an owner, like a department with an explicit responsibility and service counter.

## 2. Why do we need it?

Splitting by table or technical layer creates chatty calls, shared writes, and changes that still require every team to deploy together.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Start with business invariants, language, access patterns, and independent change needs. Keep tightly coupled atomic decisions together where possible. A boundary crossing adds serialization, authentication, compatibility, latency, and uncertain outcomes; a shared database can defeat nominal ownership.

Reference: [Primary documentation](https://martinfowler.com/bliki/BoundedContext.html).

### 3b. Boundaries and lifecycle

Caller requests an owned capability → owner checks policy and mutates its data → other capabilities consume a contract or fact, not private tables.

## 4. How to apply / implement / use it?

Save as `service_boundaries_demo.py`; run `python3 service_boundaries_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
class Inventory:
    def __init__(self):
        self._stock = 1
    def reserve(self, quantity):
        if quantity <= 0 or quantity > self._stock:
            raise ValueError("invalid reservation")
        self._stock -= quantity
        return {"reserved": quantity}
inventory = Inventory()
assert inventory.reserve(1) == {"reserved": 1}
try:
    inventory.reserve(1)
except ValueError:
    pass
else:
    raise AssertionError("stock invariant bypassed")
```

This in-process owner illustrates a capability boundary, not a remote service, durable transaction, or concurrent reservation guarantee. Private attributes are a convention; deployment and database permissions need separate enforcement.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not extract services merely to match organization charts or nouns. If every operation needs cross-service atomicity, revisit the proposed ownership.

## 6. How do I know I understand it?

**Blank-page check:** Place the stock invariant and explain why checkout cannot decrement another owner's table directly.

| Constraint change | Predict the failure and response |
| --- | --- |
| Reservation and stock live under different writers | Atomic availability checks become distributed; consolidate ownership or design an explicit protocol. |
| Many calls occur per item | Offer a bounded coarse-grained capability instead of a remote getter loop. |
