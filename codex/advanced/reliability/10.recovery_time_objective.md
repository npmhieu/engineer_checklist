# Recovery Time Objective (RTO)

[Lesson index](../../README.md) · [Previous](9.recovery_point_objective.md) · [Next](11.multi_region_architecture.md)

## 1. What is it?

RTO is the targeted maximum time to restore the defined usable service after disruption, like a deadline for reopening the business rather than only replacing a disk.

## 2. Why do we need it?

Teams time file restoration but forget detection, approvals, provisioning, key access, verification, and traffic recovery.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Define start/end and acceptable degraded state. Recovery duration is a critical path through parallel/sequential work, not always the sum of every task. Exercises expose dependencies and manual delays; RTO is a target, not the observed result.

Reference: [Primary documentation](https://cloud.google.com/architecture/dr-scenarios-planning-guide).

### 3b. Boundaries and lifecycle

Incident begins → detect/declare → recover critical dependencies/data → validate business operation → reopen the defined service → compare elapsed time with target.

## 4. How to apply / implement / use it?

Save as `recovery_time_objective_demo.py`; run `python3 recovery_time_objective_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def sequential_recovery(phases):
    if any(duration < 0 for duration in phases.values()):
        raise ValueError("negative duration")
    return sum(phases.values())
phases = {"detect": 3, "approve": 4, "restore": 10, "verify": 3, "route": 2}
observed_minutes = sequential_recovery(phases)
assert observed_minutes == 22
assert observed_minutes > 20
phases["approve"] = 1
assert sequential_recovery(phases) == 19
try:
    sequential_recovery({"restore": -1})
except ValueError:
    pass
else:
    raise AssertionError("invalid measurement")
```

This arithmetic model explicitly assumes sequential phases. Real recovery needs measured start/end timestamps and a dependency graph where parallel tasks use critical-path timing.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not set RTO from the restore tool's speed alone or quietly redefine recovery as a booted VM while users still cannot transact.

## 6. How do I know I understand it?

**Blank-page check:** Draw the recovery critical path and choose the user-visible completion criterion.

| Constraint change | Predict the failure and response |
| --- | --- |
| Restore is fast but keys require a long approval | Approval remains on the critical path; automate safe access or change preparedness. |
| Some services recover in parallel | Use dependency/critical-path analysis instead of adding all durations. |
