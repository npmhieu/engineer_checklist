# Recovery Point Objective (RPO)

[Lesson index](../../README.md) · [Previous](8.backup_restore.md) · [Next](10.recovery_time_objective.md)

## 1. What is it?

RPO is the maximum targeted age of recoverable data after disruption, like deciding how many minutes of ledger entries the business can afford to lose.

## 2. Why do we need it?

Backup frequency or replica presence alone does not establish how much committed work survives a disaster.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Compare incident time with the latest independently verified recoverable point. Backup/log capture, transport, durability, replay validity, and key access all constrain that point. RPO is a target; observed recoverable-point age is evidence, not an automatic guarantee.

Reference: [Primary documentation](https://cloud.google.com/architecture/dr-scenarios-planning-guide).

### 3b. Boundaries and lifecycle

Define acceptable loss → design capture/replication/archive → monitor recoverable watermark → exercise recovery → compare observed exposure with target.

## 4. How to apply / implement / use it?

Save as `recovery_point_objective_demo.py`; run `python3 recovery_point_objective_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from datetime import datetime, timedelta, timezone
incident = datetime(2026, 10, 18, 10, 0, tzinfo=timezone.utc)
target = timedelta(minutes=5)
def exposure(recoverable):
    if recoverable > incident:
        raise ValueError("recoverable point cannot be in the future")
    return incident - recoverable
assert exposure(incident - timedelta(minutes=2)) <= target
assert exposure(incident - timedelta(minutes=12)) > target
try:
    exposure(incident + timedelta(seconds=1))
except ValueError:
    pass
else:
    raise AssertionError("invalid evidence accepted")
```

This timestamp calculation models recoverable-point age, not measured lost rows or a guaranteed bound. A timestamp is valid evidence only after the corresponding data/logs/keys are proven recoverable.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not confuse RPO with recovery duration or promise zero loss merely because backups run often. Zero-loss designs have explicit durability, availability, and distance costs.

## 6. How do I know I understand it?

**Blank-page check:** Explain target versus observed exposure and identify the exact recovery watermark, not merely the last job-start time.

| Constraint change | Predict the failure and response |
| --- | --- |
| Backup job ran but its output is corrupt | It does not advance the verified recoverable point. |
| Archive shipping lags 20 minutes | Actual exposure can exceed the target even while the primary is healthy. |
