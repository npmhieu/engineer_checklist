# High Availability

[Lesson index](../../README.md) · [Previous](4.fault_tolerance.md) · [Next](6.failover.md)

## 1. What is it?

High availability keeps a service usable through expected failures and maintenance, like several staffed lanes with enough spare capacity when one closes.

## 2. Why do we need it?

One instance, zone, or shared dependency can stop the entire user journey even when other components look healthy.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Availability is end-to-end and measured over an explicit objective/window. Remove single points, preserve spare capacity, and avoid correlated configuration or control-plane dependencies. Independent-failure formulas are planning approximations, not evidence that real failures are independent.

Reference: [Primary documentation](https://aws.amazon.com/builders-library/static-stability-using-availability-zones/).

### 3b. Boundaries and lifecycle

Distribute healthy capacity → route usable traffic → tolerate a defined loss → keep essential dependencies available → measure actual user outcomes.

## 4. How to apply / implement / use it?

Save as `high_availability_demo.py`; run `python3 high_availability_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def available(app_nodes, database_up, required_capacity):
    capacity = sum(node["capacity"] for node in app_nodes if node["healthy"])
    return database_up and capacity >= required_capacity
nodes = [{"healthy": True, "capacity": 60}, {"healthy": True, "capacity": 60}]
assert available(nodes, True, 100)
nodes[0]["healthy"] = False
assert available(nodes, True, 50)
assert not available(nodes, True, 100)
nodes[0]["healthy"] = True
assert not available(nodes, False, 50)
```

This capacity/critical-dependency model demonstrates why redundant instances alone are insufficient. It does not measure uptime, balance real traffic, or model correlated zone failures.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not buy replicas without testing failover capacity, dependency resilience, and maintenance behavior. HA is not protection from deleted data or a substitute for disaster recovery.

## 6. How do I know I understand it?

**Blank-page check:** Draw the full critical path and calculate whether remaining capacity survives the chosen failure.

| Constraint change | Predict the failure and response |
| --- | --- |
| One of two equal zones fails | The surviving zone needs enough usable capacity without depending on slow emergency provisioning. |
| Shared database fails | Healthy app instances cannot make a mandatory unavailable dependency disappear. |
