# Failover

[Lesson index](../../README.md) · [Previous](5.high_availability.md) · [Next](7.disaster_recovery.md)

## 1. What is it?

Failover moves responsibility to an eligible alternate after failure, like transferring incoming calls to a prepared backup team.

## 2. Why do we need it?

Redundant components provide no benefit if routing, credentials, data, or authority cannot move safely when the active component fails.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Separate detection from eligibility, ownership transfer, routing, client reconnects, and failback. DNS/cache/session delays affect convergence; stateful failover needs fencing and data eligibility beyond health. Frequent switching can flap and worsen incidents.

Reference: [Primary documentation](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_withstand_component_failures_failover2good.html).

### 3b. Boundaries and lifecycle

Detect under policy → establish safe alternate → transfer/fence ownership where needed → route → verify business outcomes → fail back deliberately.

## 4. How to apply / implement / use it?

Save as `failover_demo.py`; run `python3 failover_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
targets = {"primary": {"healthy": True, "eligible": True},
           "backup": {"healthy": True, "eligible": False}}
active = "primary"
def switch():
    global active
    candidate = targets["backup"]
    if not candidate["healthy"] or not candidate["eligible"]:
        raise RuntimeError("backup not ready for responsibility")
    active = "backup"
targets["primary"]["healthy"] = False
try:
    switch()
except RuntimeError:
    pass
assert active == "primary"
targets["backup"]["eligible"] = True
switch()
assert active == "backup"
```

This routing-policy model intentionally refuses an ineligible alternate. Eligibility is an externally verified fixture; it does not implement health detection, DNS, leader fencing, or data synchronization.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not fail over to an untested empty region or automate repeated toggling on noisy probes. General service failover and database promotion have different safety requirements.

## 6. How do I know I understand it?

**Blank-page check:** Explain what must be ready before traffic moves and which clients may still reach the previous endpoint.

| Constraint change | Predict the failure and response |
| --- | --- |
| DNS still points some clients at old target | Keep compatibility and safe ownership during convergence; TTL is not instantaneous cutover. |
| Original target recovers | Failback needs verification and policy, not an immediate reflex switch. |
