# Fan-out

[Lesson index](../../README.md) · [Previous](8.event_replay.md) · [Next](10.consumer_groups.md)

## 1. What is it?

Fan-out sends one input to multiple independent destinations, like distributing one notice to several departments.

## 2. Why do we need it?

A single competing queue does not ensure every independent application sees a fact, while synchronous broadcasting lets one slow destination block all others.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Each independent subscription needs progress, capacity, retry, authorization, and retention policy. Physical storage may be shared in log systems or copied across queues. With N subscribers, total processing work can approach N times the original volume.

Reference: [Primary documentation](https://www.rabbitmq.com/docs/exchanges).

### 3b. Boundaries and lifecycle

Publish once → route to subscriptions → each handles independently → observe lag/failure per destination without confusing partial completion with global success.

## 4. How to apply / implement / use it?

Save as `fan_out_demo.py`; run `python3 fan_out_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from collections import deque
inboxes = {"billing": deque(), "analytics": deque()}
def publish(event):
    for inbox in inboxes.values():
        if len(inbox) >= 1:
            raise OverflowError("subscriber capacity reached")
    for inbox in inboxes.values():
        inbox.append(dict(event))
publish({"id": "evt-1"})
assert inboxes["billing"].popleft()["id"] == "evt-1"
assert len(inboxes["analytics"]) == 1
try:
    publish({"id": "evt-2"})
except OverflowError:
    pass
else:
    raise AssertionError("slow subscriber ignored")
assert not inboxes["billing"]
```

This local all-capacity precheck makes overload visible but is not a broker's fan-out atomicity contract. Real brokers have product-specific routing, persistence, overflow, and subscriber isolation behavior.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not broadcast sensitive full records to every subscriber or let a noncritical subscriber consume unlimited retention. Specify whether slow subscribers block publication, drop, or retain separately.

## 6. How do I know I understand it?

**Blank-page check:** Draw independent subscriber state and calculate compute growth as subscribers increase.

| Constraint change | Predict the failure and response |
| --- | --- |
| Analytics stops for a week | Protect live consumers and define analytics retention/recovery instead of infinite accumulation. |
| A subscriber must see every event | Give it an independent durable subscription/group, not another worker in a competing group. |
