# Event-Driven Architecture at Scale

[Lesson index](../../README.md) · [Previous](4.inter_service_communication.md) · [Next](6.event_schema_versioning.md)

## 1. What is it?

Event-driven architecture at scale partitions and governs many independent fact streams, like a large dispatch network with regional sorting and separate recipient inboxes.

## 2. Why do we need it?

A single stream or unbounded fan-out becomes a throughput bottleneck, while uncontrolled schemas and replay can overwhelm downstream owners.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Partition work by stable business key, budget retention and replication bytes, and measure lag per partition. More consumers cannot remove a single hot key's serial invariant. Outbox/inbox recovery, schema governance, quotas, and isolation are operational prerequisites, not optional polish.

Reference: [Primary documentation](https://kafka.apache.org/43/design/design/).

### 3b. Boundaries and lifecycle

Commit fact → route partition → retain and replicate → independently consume/checkpoint → observe lag and skew → throttle, rebalance, or reconcile.

## 4. How to apply / implement / use it?

Save as `event_driven_architecture_at_scale_demo.py`; run `python3 event_driven_architecture_at_scale_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import hashlib
from collections import Counter
def partition(key, count):
    if count < 1:
        raise ValueError("positive partition count required")
    return int.from_bytes(hashlib.sha256(key.encode()).digest()[:8], "big") % count
keys = ["hot-order"] * 90 + ["other-" + str(number) for number in range(10)]
load = Counter(partition(key, 4) for key in keys)
assert sum(load.values()) == 100
assert max(load.values()) >= 90
assert partition("hot-order", 4) == partition("hot-order", 4)
try:
    partition("key", 0)
except ValueError:
    pass
else:
    raise AssertionError("invalid partition count")
```

This routing/skew model demonstrates a hot key, not Kafka placement, broker capacity, or safe partition expansion. Production partitioning must use the producer's supported algorithm and define key migration and ordering behavior.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not multiply partitions or subscribers without retention, ownership, and downstream capacity plans. Eventual projections are unsuitable as an unquestioned source for strict financial invariants.

## 6. How do I know I understand it?

**Blank-page check:** Estimate retained bytes and subscriber processing demand, then explain why one hot aggregate still limits throughput.

| Constraint change | Predict the failure and response |
| --- | --- |
| One account produces most events | Repartition only if its business invariant permits parallel work; otherwise optimize or bound that serial path. |
| A new subscriber replays a year | Isolate replay capacity and side effects from live processing. |
