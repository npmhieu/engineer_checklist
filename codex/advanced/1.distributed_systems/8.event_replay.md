# Event Replay

[Lesson index](../../README.md) · [Previous](7.event_ordering.md) · [Next](9.fan_out.md)

## 1. What is it?

Event replay reprocesses retained facts to rebuild or repair derived state, like recalculating a ledger from preserved entries.

## 2. Why do we need it?

A projection bug or new report cannot be repaired reliably from current rows alone when historical changes matter.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Use a separate projection namespace/checkpoint, deterministic handlers, historical decoders, and an explicit snapshot/offset boundary. Replay consumes storage bandwidth and downstream compute. Do not replay irreversible external effects unless their idempotency and business intent explicitly permit it.

Reference: [Primary documentation](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing).

### 3b. Boundaries and lifecycle

Select retained range → isolate rebuild → decode/upcast → apply facts without live side effects → catch up → verify totals and watermark → switch readers.

## 4. How to apply / implement / use it?

Save as `event_replay_demo.py`; run `python3 event_replay_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
events = [{"id": "one", "cents": 500}, {"id": "two", "cents": -100}]
sent_emails = []
def project(history, replay):
    total, seen = 0, set()
    for event in history:
        if event["id"] in seen:
            continue
        seen.add(event["id"])
        total += event["cents"]
        if not replay:
            sent_emails.append(event["id"])
    return total
assert project(events, replay=True) == 400
assert sent_emails == []
assert project(events + [events[0]], replay=True) == 400
assert project(events, replay=False) == 400
assert sent_emails == ["one", "two"]
```

This deterministic rebuild model deliberately suppresses replay notifications. In production, isolate side-effect handlers structurally as well as by policy; a forgotten replay flag must not resend real payments. Retention gaps and privacy deletion require explicit treatment.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not assume every queue retains acknowledged messages or that compacted streams preserve every intermediate fact. Avoid replay competing unboundedly with live traffic.

## 6. How do I know I understand it?

**Blank-page check:** Plan a projection rebuild, including historical schemas, catch-up watermark, validation, and reader cutover.

| Constraint change | Predict the failure and response |
| --- | --- |
| Historical events have been deleted | A full rebuild needs an appropriate snapshot/archive or must be declared impossible. |
| Replay invokes provider calls | Separate side-effect execution and use approved stable identities; replay is not blanket permission to act again. |
