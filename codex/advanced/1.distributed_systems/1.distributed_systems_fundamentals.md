# Distributed Systems Fundamentals

## 1. What is it?

A distributed system coordinates independent computers through messages, like offices cooperating by phone rather than sharing one desk.

## 2. Why do we need it?

A local program can inspect one process's state; separate machines can fail independently, messages can disappear, and a caller may not know whether remote work committed.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Separate safety (nothing invalid happens) from liveness (useful progress eventually happens). Networks introduce delay, loss, duplication, and partitions; clocks do not provide a universal event order. Timeouts detect lack of a timely answer, not proof of remote failure. Replication and coordination spend network hops, storage, and availability.

Reference: [Primary documentation](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf).

### 3b. Boundaries and lifecycle

Send intent → remote node may apply it → response may arrive or disappear → caller reconciles by stable identity instead of assuming timeout means rollback.

## 4. How to apply / implement / use it?

Save as `distributed_systems_fundamentals_demo.py`; run `python3 distributed_systems_fundamentals_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
effects = {}
def server(operation_id):
    effects.setdefault(operation_id, "committed")
    return effects[operation_id]
def call(operation_id, lose_reply=False):
    response = server(operation_id)
    if lose_reply:
        raise TimeoutError("reply lost")
    return response
try:
    call("purchase-1", lose_reply=True)
except TimeoutError:
    pass
assert effects["purchase-1"] == "committed"
assert call("purchase-1") == "committed"
assert len(effects) == 1
```

This deterministic message-loss model demonstrates an uncertain outcome, not a real network or durable idempotency store. A real implementation needs authenticated requests, atomic persistent identity/effect coordination, and bounded recovery.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not distribute a simple local invariant without a concrete isolation, ownership, or scale need. Remote calls add partial failures even on an internal network.

## 6. How do I know I understand it?

| Constraint change | Predict the failure and response |
| --- | --- |
| Response delay becomes unbounded | Stop waiting within budget, but reconcile rather than infer no effect. |
| One replica disagrees | Apply the declared consistency and conflict policy; another copy is not automatically authoritative. |
