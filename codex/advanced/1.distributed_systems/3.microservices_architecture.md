# Microservices Architecture

[Lesson index](../../README.md) · [Previous](2.service_boundaries.md) · [Next](4.inter_service_communication.md)

## 1. What is it?

Microservices architecture organizes independently deployable capability owners behind remote contracts, like specialist workshops with separate release schedules.

## 2. Why do we need it?

A large shared deployment can block independent changes or scaling, but splitting it without discipline replaces code coupling with network coupling.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Each service needs deployment ownership, compatible interfaces, observability, security, and data recovery. Independent deployability is not proven by separate processes. Cross-service consistency requires explicit coordination or eventual workflows; fleet connections, operational work, and network traffic grow.

Reference: [Primary documentation](https://martinfowler.com/bliki/MonolithFirst.html).

### 3b. Boundaries and lifecycle

Route to capability owner → authenticate/authorize → execute local transaction → communicate via bounded calls or durable events → observe and recover independently.

## 4. How to apply / implement / use it?

Save as `microservices_architecture_demo.py`; run `python3 microservices_architecture_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def inventory_v1(request):
    if request.get("quantity", 0) <= 0:
        return {"status": 422}
    return {"status": 200, "reservation_id": "r-1"}
def checkout(inventory, quantity):
    response = inventory({"quantity": quantity})
    if response["status"] != 200:
        raise ValueError("reservation rejected")
    return response["reservation_id"]
assert checkout(inventory_v1, 1) == "r-1"
try:
    checkout(inventory_v1, 0)
except ValueError:
    pass
else:
    raise AssertionError("downstream rejection ignored")
```

This contract-oriented composition runs locally; it proves neither independent deployment nor distributed fault tolerance. Replace the function boundary with a real client only after adding identity, deadlines, compatibility tests, and recovery.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not use microservices to avoid modular code design. A small team with simple workloads often gains more from a modular monolith than from a service fleet.
