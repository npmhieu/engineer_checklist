# Consumer Groups

[Lesson index](../../README.md) · [Previous](9.fan_out.md) · [Next](../2.messaging/1.message_delivery_semantics.md)

## 1. What is it?

A consumer group coordinates consumers sharing a stream workload and progress, like clerks sharing one department's numbered inbox.

## 2. Why do we need it?

Independent workers reading the same log without coordinated assignment either repeat every record or leave ownership and recovery ambiguous.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

In traditional Kafka consumer groups, partitions are assigned among members and committed offsets track group progress. Rebalancing changes ownership and can trigger repeats; commit order matters. More active members than partitions does not add processing parallelism in that model. Other group types/products differ.

Reference: [Primary documentation](https://kafka.apache.org/43/design/design/).

### 3b. Boundaries and lifecycle

Join group → receive assignment → process partition records → commit safe progress → revoke/drain on rebalance → resume from group checkpoints.

## 4. How to apply / implement / use it?

Save as `consumer_groups_demo.py`; run `python3 consumer_groups_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def assign(partitions, members):
    if not members:
        raise ValueError("members required")
    result = {member: [] for member in members}
    for index, partition in enumerate(partitions):
        result[members[index % len(members)]].append(partition)
    return result
assignment = assign([0, 1], ["worker-a", "worker-b", "worker-c"])
assert sorted(partition for owned in assignment.values() for partition in owned) == [0, 1]
assert assignment["worker-c"] == []
rebalanced = assign([0, 1], ["worker-a"])
assert rebalanced["worker-a"] == [0, 1]
try:
    assign([0], [])
except ValueError:
    pass
else:
    raise AssertionError("ownerless assignment accepted")
```

This round-robin assignment model is not Kafka's actual group protocol or a rebalance implementation. It omits leases, fencing, offset commits, partition revocation, and Kafka share-group semantics.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not place independent billing and analytics applications in the same traditional group if both need all facts. Avoid committing offsets beyond unfinished earlier records.

## 6. How do I know I understand it?

**Blank-page check:** Show two groups consuming the same topic and three workers sharing two partitions. Explain rebalance duplicates.

| Constraint change | Predict the failure and response |
| --- | --- |
| Worker dies after effect but before offset commit | New owner may reprocess; effects must be idempotent or transactionally coordinated. |
| Add a third worker to two assigned partitions | One member is idle in this group model; capacity needs more suitable partitions or faster processing. |
