# Performance Engineering

[Lesson index](../../README.md) · [Previous](../reliability/11.multi_region_architecture.md) · [Next](2.profiling.md)

## 1. What is it?

Performance engineering turns latency, throughput, and resource goals into a repeated design-and-measure process, like designing a bridge for a known traffic load rather than guessing after it jams.

## 2. Why do we need it?

Local speedups can fail to improve user latency, consume excessive memory, or move the bottleneck into a database or dependency.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Define workload, correctness, budgets, baseline, profiling, hypothesis, experiment, and regression gates. Include warm/cold paths, tail latency, errors, queueing, and cost. Measure the same semantic operation before and after; a faster wrong answer is not an optimization.

Reference: [Primary documentation](https://sre.google/sre-book/handling-overload/).

### 3b. Boundaries and lifecycle

Set objective → build representative workload → observe bottleneck → change one cause → compare correctness and cost → validate under load → keep evidence.

## 4. How to apply / implement / use it?

Save as `performance_engineering_demo.py`; run `python3 performance_engineering_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def evaluate(samples_ms, errors, requests, memory_mb):
    if requests <= 0 or len(samples_ms) != requests or errors < 0 or errors > requests:
        raise ValueError("invalid measurement")
    ordered = sorted(samples_ms)
    p95 = ordered[max(0, (95 * requests + 99) // 100 - 1)]
    return p95 <= 200 and errors / requests <= 0.01 and memory_mb <= 256
assert evaluate([100] * 100, 0, 100, 128)
assert not evaluate([100] * 90 + [800] * 10, 0, 100, 128)
assert not evaluate([100] * 100, 0, 100, 512)
try:
    evaluate([], 0, 0, 10)
except ValueError:
    pass
else:
    raise AssertionError("empty benchmark treated as success")
```

This executable budget gate uses synthetic measurements and a stated nearest-rank p95. It is not a benchmark or a recommended universal 200 ms/256 MB objective; set real budgets from your product and workload.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not optimize without a target, representative baseline, and correctness checks. Avoid comparing different machines/workloads as if only code changed.

## 6. How do I know I understand it?

**Blank-page check:** Design one experiment with workload, hypothesis, controls, success criteria, and rollback.

| Constraint change | Predict the failure and response |
| --- | --- |
| Average improves but p99 worsens | Check queueing, variance, errors, and resource contention before accepting the change. |
| Optimization doubles memory | Evaluate cost and capacity, not wall-clock time alone. |
