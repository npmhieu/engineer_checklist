# Large-scale Caching

[Lesson index](../../README.md) · [Previous](6.latency_optimization.md) · [Next](../observability_operations/1.advanced_distributed_tracing.md)

## 1. What is it?

Large-scale caching coordinates bounded reusable data across a fleet, like regional stockrooms that must agree when stored copies become stale.

## 2. Why do we need it?

One cache hit rate hides hot-key overload, stampedes, stale refills, cross-tenant leaks, and cache outages that flood the origin.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Design scoped keys, size/eviction budgets, TTL jitter, coalesced fills, invalidation/version rules, and safe fallback capacity. Cache-aside has a stale-fill race: a read begun before invalidation can repopulate old data afterward. Version/generation validation can reject that fill, but checks must be atomic at the real store.

Reference: [Primary documentation](https://redis.io/docs/latest/develop/reference/client-side-caching/).

### 3b. Boundaries and lifecycle

Read scoped cache → bound/coalesce miss → fetch authoritative version → publish only if generation still valid → invalidate/update on writes → observe origin and cache health.

## 4. How to apply / implement / use it?

Save as `large_scale_caching_demo.py`; run `python3 large_scale_caching_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
generation = {"task-1": 0}
cache = {}
def publish(key, captured_generation, value):
    if generation[key] != captured_generation:
        return False
    cache[key] = value
    return True
captured = generation["task-1"]
generation["task-1"] += 1
assert not publish("task-1", captured, "stale")
assert "task-1" not in cache
assert publish("task-1", generation["task-1"], "fresh")
assert cache["task-1"] == "fresh"
```

This single-process generation check models stale-fill rejection, not an atomic distributed cache protocol. Production needs atomic version/check-write behavior, tenant-safe keys, bounded memory, origin protection, and reliable invalidation policy.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not use caches as unquestioned authority for revocation or strict balances. Avoid unlimited cache-miss fallback during a cache outage and one TTL shared by millions of hot entries.

## 6. How do I know I understand it?

**Blank-page check:** Draw a stale-fill race and prove where generation is checked. Plan cache loss without overwhelming the database.

| Constraint change | Predict the failure and response |
| --- | --- |
| All entries expire together | Jitter TTLs, coalesce fills, and limit origin load rather than unleash a stampede. |
| Invalidation generation is lost on restart | The safety assumption changes; persist/version against authoritative state or tolerate explicit bounded staleness. |
