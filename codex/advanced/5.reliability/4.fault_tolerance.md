# Fault Tolerance

[Lesson index](../../README.md) · [Previous](3.graceful_degradation.md) · [Next](5.high_availability.md)

## 1. What is it?

Fault tolerance preserves specified service properties despite a defined set of faults, like a machine continuing safely after one component fails.

## 2. Why do we need it?

Individual retries or replicas do not guarantee correctness when faults combine or uncertain effects are repeated.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Define fault model, safety invariant, detection, redundancy, containment, and recovery. Mask only covered faults; fail safely outside the model. Redundancy costs capacity and complexity, while correlated failures can defeat multiple copies at once.

Reference: [Primary documentation](https://aws.amazon.com/builders-library/static-stability-using-availability-zones/).

### 3b. Boundaries and lifecycle

Detect symptom → contain → select safe recovery/masking action → preserve operation identity → verify invariant → reconcile incomplete outcomes.

## 4. How to apply / implement / use it?

Save as `fault_tolerance_demo.py`; run `python3 fault_tolerance_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
results = {}
def endpoint(operation_id, available):
    if not available:
        raise ConnectionError("endpoint down")
    return results.setdefault(operation_id, "accepted")
def resilient(operation_id):
    for available in (False, True):
        try:
            return endpoint(operation_id, available)
        except ConnectionError:
            continue
    raise ConnectionError("all endpoints unavailable")
assert resilient("op-1") == "accepted"
assert resilient("op-1") == "accepted"
assert len(results) == 1
try:
    endpoint("op-2", False)
except ConnectionError:
    pass
assert "op-2" not in results
```

This endpoint/fault model covers known pre-effect connection failure and a shared in-memory identity store. It does not cover unknown post-commit outcomes, independent replica stores, or real network failover.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not claim tolerance without naming covered faults and invariants. Repeated attempts against different providers can duplicate effects unless identity/reconciliation spans them.

## 6. How do I know I understand it?

**Blank-page check:** State one tolerated fault and one explicitly untolerated fault, then test both.

| Constraint change | Predict the failure and response |
| --- | --- |
| Both endpoints depend on one failed database | Redundancy at the endpoint layer does not remove the shared failure. |
| First endpoint commits before reply loss | Blind failover can repeat work; recover using a valid shared operation protocol. |
