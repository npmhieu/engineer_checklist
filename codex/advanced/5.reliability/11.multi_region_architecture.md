# Multi-Region Architecture

[Lesson index](../../README.md) · [Previous](10.recovery_time_objective.md) · [Next](../6.performance/1.performance_engineering.md)

## 1. What is it?

Multi-region architecture coordinates service and data placement across regions, like regional offices with explicit authority and disaster-transfer rules.

## 2. Why do we need it?

A regional outage, distant users, or residency requirements can exceed one region's capabilities, but copied deployments alone do not solve data authority.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Choose active/passive, regional ownership, or carefully specified multi-writer semantics. Cross-region replication adds latency, egress, lag, conflict, and key/access complexity. Routing, identity, data residency, failover fencing, and recovery must agree about who may write.

Reference: [Primary documentation](https://aws.amazon.com/builders-library/static-stability-using-availability-zones/).

### 3b. Boundaries and lifecycle

Assign regional authority → route eligible traffic → replicate under defined consistency → detect region failure → verify alternate/data/keys → transfer authority safely → reconcile.

## 4. How to apply / implement / use it?

Save as `multi_region_architecture_demo.py`; run `python3 multi_region_architecture_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
home = {"tenant-1": "region-a"}
healthy = {"region-a": True, "region-b": True}
def write_region(tenant, requested):
    if home[tenant] != requested:
        raise PermissionError("not the authoritative region")
    if not healthy[requested]:
        raise ConnectionError("home region unavailable")
    return requested
assert write_region("tenant-1", "region-a") == "region-a"
try:
    write_region("tenant-1", "region-b")
except PermissionError:
    pass
healthy["region-a"] = False
try:
    write_region("tenant-1", "region-a")
except ConnectionError:
    pass
else:
    raise AssertionError("availability invented")
```

This regional-ownership model fails closed rather than inventing safe cross-region promotion. Actual authority transfer requires fencing, eligible data, routing convergence, credentials, and tested recovery; changing home in a dictionary is not sufficient.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not add active/active writes without conflict/invariant design or assume zero RPO and low global write latency are free. Residency and privacy requirements need explicit review.

## 6. How do I know I understand it?

**Blank-page check:** Draw routing, write ownership, replication, and failure policy for a regional partition.

| Constraint change | Predict the failure and response |
| --- | --- |
| Regions cannot communicate | Choose safe restricted operations or defined conflict behavior; both cannot independently enforce one strict global invariant for free. |
| Traffic routes to backup but data/keys are absent | Service is not recovered despite healthy compute. |
