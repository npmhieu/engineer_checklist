# Graceful Degradation

[Lesson index](../../README.md) · [Previous](2.bulkhead.md) · [Next](4.fault_tolerance.md)

## 1. What is it?

Graceful degradation preserves an explicitly safe reduced experience when optional capabilities fail, like checkout continuing while recommendations are unavailable.

## 2. Why do we need it?

Failing a whole purchase because a noncritical widget is down converts a minor dependency issue into a major outage.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Classify mandatory versus optional behavior, define stale-data bounds and visible freshness, and budget fallback work. Fail closed for security and strict invariants. A fallback must be domain-approved; fabricated prices, bypassed authorization, or silent data loss are not graceful.

Reference: [Primary documentation](https://sre.google/sre-book/handling-overload/).

### 3b. Boundaries and lifecycle

Attempt optional capability within budget → classify failure → return approved reduced result with telemetry → recover normal behavior when safe.

## 4. How to apply / implement / use it?

Save as `graceful_degradation_demo.py`; run `python3 graceful_degradation_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def page(recommendations, authorized):
    if not authorized:
        raise PermissionError("access denied")
    try:
        items = recommendations()
        degraded = False
    except TimeoutError:
        items, degraded = [], True
    return {"checkout": "available", "recommendations": items, "degraded": degraded}
assert not page(lambda: ["item-1"], True)["degraded"]
def slow():
    raise TimeoutError("recommendations unavailable")
assert page(slow, True)["degraded"]
try:
    page(slow, False)
except PermissionError:
    pass
else:
    raise AssertionError("fallback bypassed authorization")
```

This real composition function models an optional read fallback without network effects. The returned degraded marker is deliberate; real applications need bounded calls, metrics, and product-approved degraded semantics.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not degrade mandatory authorization, ledger correctness, or consent checks into permissive defaults. Avoid a fallback that overloads another already-saturated dependency.

## 6. How do I know I understand it?

**Blank-page check:** List optional and mandatory capabilities for checkout and justify every fallback.

| Constraint change | Predict the failure and response |
| --- | --- |
| Cached price exceeds allowed freshness | Reject or revalidate rather than silently charge an unsupported amount. |
| Everyone falls back to the primary database | Fallback can trigger a second outage; reserve capacity and bound demand. |
