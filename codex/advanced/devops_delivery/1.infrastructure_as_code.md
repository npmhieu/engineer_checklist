# Infrastructure as Code

[Lesson index](../../README.md) · [Previous](../security/8.dependency_supply_chain_security.md) · [Next](2.blue_green_deployment.md)

## 1. What is it?

Infrastructure as code declares and reviews infrastructure changes through versioned definitions, like keeping an executable building plan instead of relying on remembered console clicks.

## 2. Why do we need it?

Manual infrastructure drifts across environments, lacks reviewable intent, and becomes difficult to reproduce or recover.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Declarative engines compare configuration, recorded state, and refreshed provider state to plan changes through a dependency graph. State maps resource identities and may contain secrets; locking and access control protect concurrent changes. Plans can become stale and apply can fail partially; IaC is not one global transaction.

Reference: [Primary documentation](https://developer.hashicorp.com/terraform/cli/commands/plan).

### 3b. Boundaries and lifecycle

Review configuration → initialize trusted providers/state → refresh/plan → review exact effects → approve/apply → reconcile partial failures/drift → preserve recovery evidence.

## 4. How to apply / implement / use it?

Save as `infrastructure_as_code_demo.py`; run `python3 infrastructure_as_code_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
actual = {"replicas": 2}
def plan(desired):
    if desired["replicas"] < 1:
        raise ValueError("unsafe capacity")
    return {"before": dict(actual), "after": dict(desired)}
def apply(change, approved):
    if not approved:
        raise PermissionError("approval required")
    if actual != change["before"]:
        raise RuntimeError("stale plan")
    actual.clear()
    actual.update(change["after"])
change = plan({"replicas": 3})
apply(change, True)
assert actual["replicas"] == 3
try:
    apply(change, True)
except RuntimeError:
    pass
else:
    raise AssertionError("stale plan reapplied")
```

This desired-state/approval model is not Terraform or cloud provisioning. Actual engines need provider credentials, protected state, concurrency locking, dependency handling, and partial-apply recovery. See the optional local-only exercise below.

### Optional real local-only Terraform exercise

Requires Terraform 1.4+; no cloud account or external provider. In a new disposable directory, create `main.tf`:

```hcl
terraform {
  required_version = ">= 1.4"
}
resource "terraform_data" "lesson" {
  input = "backend-learning"
}
```

Run `terraform init`, `terraform validate`, `terraform plan -out=lesson.tfplan`, inspect the plan, then optionally `terraform apply lesson.tfplan`. Applying changes only this exercise's Terraform state for the built-in terraform_data resource; it does not provision cloud infrastructure. A second plan should show no changes. Change input and review the next plan. This tool walkthrough is not part of the offline Python checks.

State reference: [Terraform state](https://developer.hashicorp.com/terraform/language/state).

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not store plaintext secrets in versioned configuration/state or run destructive plans blindly. Avoid assuming one reviewed speculative plan remains valid after other writers change resources.

## 6. How do I know I understand it?

**Blank-page check:** Explain configuration versus state versus actual provider objects, and diagnose a partially applied or stale plan.

| Constraint change | Predict the failure and response |
| --- | --- |
| Two pipelines change the same state | Use supported locking and ownership; last-write-wins state files can lose resource mappings. |
| Apply fails after creating some resources | Inspect actual/state evidence and recover idempotently; do not assume everything rolled back. |
