# Multi-environment Deployment

[Lesson index](../../README.md) · [Previous](6.kubernetes.md) · [Next](../../testing_acceptance/automated_testing/1.unit_test.md)

## 1. What is it?

Multi-environment deployment promotes verified artifacts through isolated configurations and access boundaries, like testing the same machine in a workshop before installing it on a live production line.

## 2. Why do we need it?

Rebuilding per environment changes tested bytes, while shared credentials or customer data let development mistakes damage production.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Promote immutable artifacts while validating environment-specific configuration, secrets references, identity, policies, and compatible migrations. Staging parity should cover relevant behavior, not require identical scale or unsafe production data copies. Environment protections and short-lived deployment identity limit privilege.

Reference: [Primary documentation](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).

### 3b. Boundaries and lifecycle

Build once → verify digest/provenance → test with isolated config → approve promotion → validate production config/access → deploy same artifact → observe/recover and record evidence.

## 4. How to apply / implement / use it?

Save as `multi_environment_deployment_demo.py`; run `python3 multi_environment_deployment_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
artifact = "sha256:" + "a" * 64
environments = {"staging": {"secret_ref": "staging/db", "approved": True},
                "production": {"secret_ref": "production/db", "approved": False}}
deployed = {}
def promote(environment, digest):
    config = environments[environment]
    if digest != artifact:
        raise ValueError("untested artifact")
    if not config["approved"] or not config["secret_ref"].startswith(environment + "/"):
        raise PermissionError("environment gate denied")
    deployed[environment] = digest
promote("staging", artifact)
try:
    promote("production", artifact)
except PermissionError:
    pass
assert "production" not in deployed
environments["production"]["approved"] = True
promote("production", artifact)
assert deployed["staging"] == deployed["production"]
```

This environment-gate model uses a fixture digest, not real artifact hashing, provenance verification, credentials, or deployment. Prefix checks only illustrate separate references; real access isolation must be enforced by identity/provider permissions.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not share production secrets with test runners, rebuild untracked dependencies for each environment, or copy raw sensitive production data into lower-trust environments.

## 6. How do I know I understand it?

**Blank-page check:** Draw artifact promotion separately from configuration/secret delivery and identify who may approve and deploy each environment.

| Constraint change | Predict the failure and response |
| --- | --- |
| Staging and production build independently | Same source revision may produce different bytes; promote the exact verified artifact. |
| A developer can resolve production secret references | Naming conventions are not isolation; fix actual permissions and audit access. |
