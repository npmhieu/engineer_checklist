## 1. What is it?

Kubernetes reconciles declared workload state onto a cluster, like a dispatcher continuously replacing and placing workers to match an operating plan.

## 2. Why do we need it?

Manual container placement, restart, service discovery, and rollout become difficult across many machines, but orchestration does not make application state safe automatically.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

The API server stores desired state through etcd; controllers reconcile; the scheduler assigns eligible Pods; kubelets manage node execution through the runtime. Deployments/ReplicaSets manage replicas, Services select endpoints, and requests/limits/probes influence placement and behavior. Reconciliation and startup are asynchronous and consume control/node resources.

Reference: [Primary documentation](https://kubernetes.io/docs/concepts/overview/components/).

### 3b. Boundaries and lifecycle

Submit desired objects → authenticate/authorize/admit → controller creates work → scheduler assigns → kubelet starts container → probes/endpoints reflect readiness → controllers react to changes/failures.

## 4. How to apply / implement / use it?

Save as `kubernetes_demo.py`; run `python3 kubernetes_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def reconcile(desired, observed, ready_nodes):
    if desired < 0 or observed < 0:
        raise ValueError("invalid replica count")
    missing = max(0, desired - observed)
    return {"create": min(missing, ready_nodes), "pending": max(0, missing - ready_nodes)}
assert reconcile(3, 1, 2) == {"create": 2, "pending": 0}
assert reconcile(3, 1, 0) == {"create": 0, "pending": 2}
try:
    reconcile(-1, 0, 2)
except ValueError:
    pass
else:
    raise AssertionError("invalid desired state")
```

This toy controller-capacity calculation is not Kubernetes scheduling: a node can run multiple Pods and real placement depends on resource requests, affinity, taints, quotas, and admission. It demonstrates asynchronous desired/observed reconciliation only. The optional Job below exercises real tooling when you provide a disposable cluster.

### Optional real Kubernetes Job exercise

Requires kubectl, a working container-pulling cluster, and permission to create a disposable namespace. Do not use an existing customer namespace. Save as `job.yaml`:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: backend-lesson
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: lesson
          image: python:3.13-slim
          command: ["python", "-B", "-c", "print('lesson complete')"]
          resources:
            requests:
              cpu: 25m
              memory: 32Mi
            limits:
              cpu: 100m
              memory: 64Mi
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
```

```sh
kubectl create namespace backend-lesson
kubectl apply -n backend-lesson -f job.yaml
kubectl wait -n backend-lesson --for=condition=complete job/backend-lesson --timeout=120s
kubectl logs -n backend-lesson job/backend-lesson
```

Proceed only if namespace creation succeeds and this is your newly created disposable namespace. Expected: Job completes and logs `lesson complete`. For the unhappy path, copy the manifest, change metadata.name to `backend-lesson-fail` and the Python command string to `raise SystemExit('expected demo failure')`. Apply that second manifest and run `kubectl wait -n backend-lesson --for=condition=failed job/backend-lesson-fail --timeout=120s`; with backoffLimit 0 it should become Failed rather than retry forever. Inspect logs/events for diagnosis.

When finished, delete **only the disposable namespace created for this exercise** with `kubectl delete namespace backend-lesson`; this deletes its resources. No cluster commands are executed by the offline checks. The mutable image tag is for the exercise; reviewed immutable digests are preferable for controlled production promotion.

Job reference: [Kubernetes Jobs](https://kubernetes.io/docs/concepts/workloads/controllers/job/).

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not adopt Kubernetes merely to run one simple service without operational need. It adds cluster security, upgrades, networking, storage, capacity, and incident responsibilities; it cannot create database backups or application idempotency for you.

## 6. How do I know I understand it?

**Blank-page check:** Trace a manifest through control plane, scheduler, kubelet, readiness, and Service endpoints. Explain Running versus Ready versus successful business behavior.

| Constraint change | Predict the failure and response |
| --- | --- |
| No node satisfies resource/placement requirements | Pods remain Pending; increasing desired replicas does not create usable capacity by itself. |
| Pod is restarted after an external effect | Application recovery/idempotency still determines correctness. |
