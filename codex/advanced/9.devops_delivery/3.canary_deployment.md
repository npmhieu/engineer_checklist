# Canary Deployment

[Lesson index](../../README.md) · [Previous](2.blue_green_deployment.md) · [Next](4.progressive_delivery.md)

## 1. What is it?

Canary deployment exposes a candidate to a limited representative workload before wider rollout, like trying a new checkout process in one supervised lane.

## 2. Why do we need it?

All-at-once release gives a hidden defect the full customer blast radius before it can be measured.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Choose traffic/cohort assignment, comparable control, minimum evidence, observation window, objectives, and abort rules. A fraction of pods is not necessarily the same fraction of requests. Cache, tenant, region, and long-running workload differences can bias results.

Reference: [Primary documentation](https://argo-rollouts.readthedocs.io/en/stable/features/canary/).

### 3b. Boundaries and lifecycle

Deploy candidate → route bounded traffic → compare user/error/latency/business evidence → hold, abort, or increase exposure → complete only with sufficient evidence.

## 4. How to apply / implement / use it?

Save as `canary_deployment_demo.py`; run `python3 canary_deployment_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def assess(errors, requests, ready):
    if not ready:
        return "abort"
    if not 0 <= errors <= requests:
        raise ValueError("invalid evidence")
    if requests < 100:
        return "hold"
    return "abort" if errors / requests > 0.02 else "eligible-to-expand"
assert assess(1, 200, True) == "eligible-to-expand"
assert assess(10, 200, True) == "abort"
assert assess(0, 4, True) == "hold"
assert assess(0, 200, False) == "abort"
try:
    assess(201, 200, True)
except ValueError:
    pass
else:
    raise AssertionError("invalid metrics accepted")
```

This deterministic gate uses illustrative sample/error limits, not a statistically complete canary analysis or traffic router. A passing sample is only eligibility evidence; real rollout decisions need representative windows, control comparison, and business checks.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not call one healthy request a canary success or expose an unrepresentative internal-only cohort then infer customer safety. Never duplicate non-idempotent effects through careless traffic mirroring.

## 6. How do I know I understand it?

**Blank-page check:** Specify cohort, traffic weight, control, observation duration, minimum evidence, and abort policy.

| Constraint change | Predict the failure and response |
| --- | --- |
| Canary gets only cache hits | Its latency evidence does not represent cold/miss-heavy live traffic. |
| Errors are rare and traffic is low | Wait or run safe representative probes; zero observed errors is weak evidence with tiny samples. |
