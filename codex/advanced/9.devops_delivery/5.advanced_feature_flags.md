# Advanced Feature Flags

[Lesson index](../../README.md) · [Previous](4.progressive_delivery.md) · [Next](6.kubernetes.md)

## 1. What is it?

Advanced feature flags govern versioned runtime behavior, targeting, and experiments across a fleet, like managed switches with stable cohorts, ownership, and emergency policy.

## 2. Why do we need it?

Simple booleans become stale distributed configuration, inconsistent tenant experiences, untested combinations, and permanent dead branches.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Use typed variants, validated evaluation context, deterministic assignment, config version/freshness, dependency rules, and explicit provider-failure policy. Separate rollout from authorization and record experiment exposure at the actual decision point. Caching reduces evaluation latency but delays emergency changes.

Reference: [Primary documentation](https://openfeature.dev/specification/sections/evaluation-context/).

### 3b. Boundaries and lifecycle

Publish reviewed config → distribute with version → evaluate trusted context → authorize independently → observe exposure/outcomes → disable or widen → remove obsolete flag.

## 4. How to apply / implement / use it?

Save as `advanced_feature_flags_demo.py`; run `python3 advanced_feature_flags_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import hashlib
config = {"version": 3, "percent": 100, "kill": False, "valid_until": 20}
def evaluate(tenant, now):
    if config["kill"] or now >= config["valid_until"]:
        return {"variant": "control", "reason": "safe-fallback"}
    if not 0 <= config["percent"] <= 100:
        raise ValueError("invalid rollout")
    digest = hashlib.sha256(("report-v2:" + tenant).encode()).digest()
    bucket = int.from_bytes(digest[:8], "big") % 100
    return {"variant": "new" if bucket < config["percent"] else "control",
            "reason": "config-" + str(config["version"])}
assert evaluate("tenant-1", 10)["variant"] == "new"
assert evaluate("tenant-1", 10) == evaluate("tenant-1", 10)
assert evaluate("tenant-1", 20)["variant"] == "control"
config["kill"] = True
assert evaluate("tenant-1", 10)["variant"] == "control"
```

This deterministic version/expiry model does not contact a provider or implement an experiment platform. The disabled fallback is a deliberate example, not universally safe. Tenant context must come from trusted identity, and authorization runs independently.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not leave emergency flags ownerless, assume every replica receives updates instantly, or use a feature flag to grant admin privileges. Test both branches and important interactions.

## 6. How do I know I understand it?

**Blank-page check:** Explain sticky assignment, typed variants, stale-config policy, exposure logging, kill-switch propagation, and removal.

| Constraint change | Predict the failure and response |
| --- | --- |
| Kill switch cannot reach an isolated replica | Its local freshness/fallback policy controls behavior; remote config is not instant global cancellation. |
| Business effect already committed | Disabling the flag prevents future exposure only; recovery needs its own workflow. |
