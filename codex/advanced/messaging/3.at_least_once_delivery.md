# At-least-once Delivery

[Lesson index](../../README.md) · [Previous](2.at_most_once_delivery.md) · [Next](4.effectively_once_processing.md)

## 1. What is it?

At-least-once delivery retries uncompleted delivery under stated durability and recovery assumptions, like retaining a ticket until completion is confirmed.

## 2. Why do we need it?

Important work must survive consumer crashes, but the transport cannot always distinguish unfinished work from a completed effect whose acknowledgement vanished.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Commit effects before acknowledging progress. If acknowledgement is lost, retry may repeat processing. Eventual successful delivery depends on recoverable infrastructure, retention, reachable consumers, and a message that can be handled; the label is not unconditional infinite availability.

Reference: [Primary documentation](https://www.rabbitmq.com/docs/reliability).

### 3b. Boundaries and lifecycle

Retain → deliver → commit effect → ack; crash before ack → redeliver same logical input → idempotent handler recognizes prior completion.

## 4. How to apply / implement / use it?

Save as `at_least_once_delivery_demo.py`; run `python3 at_least_once_delivery_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
pending = ["evt-1"]
effects = []
def attempt(lose_ack=False):
    message = pending[0]
    effects.append(message)
    if lose_ack:
        raise ConnectionError("ack lost")
    pending.pop(0)
try:
    attempt(lose_ack=True)
except ConnectionError:
    pass
assert pending == ["evt-1"] and effects == ["evt-1"]
attempt()
assert not pending
assert effects == ["evt-1", "evt-1"]
```

This model deliberately uses a non-idempotent handler to reveal duplicate effects. A real consumer needs atomic inbox/effect coordination or a naturally idempotent mutation, plus broker-specific acknowledgement configuration.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not apply repeated decrements, charges, or emails without duplicate protection. Infinite retries cannot repair permanent invalid data.

## 6. How do I know I understand it?

**Blank-page check:** Explain why this policy accepts duplicate attempts and how local effects can still happen once.

| Constraint change | Predict the failure and response |
| --- | --- |
| Retention expires before consumer recovery | Unconditional eventual delivery is no longer a valid assumption. |
| Effect commits but ack disappears | Redelivery is correct transport behavior; the handler must not repeat the business effect. |
