# Advanced Retry Strategies

[Lesson index](../../README.md) · [Previous](7.poison_messages.md) · [Next](9.dead_letter_queue_strategy.md)

## 1. What is it?

Advanced retry strategies coordinate safety, timing, ownership, and capacity across failures, like one dispatcher managing repeated attempts instead of every clerk redialing independently.

## 2. Why do we need it?

Layered retries multiply traffic; retries past a workflow deadline waste resources, and unknown outcomes can repeat irreversible work.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Use one retry owner, stable operation identity, classified failures, capped jitter, server delay guidance, attempt/elapsed budgets, and global retry capacity. Retry only if useful time remains. Reconcile uncertain effects; hedging is limited to operations safe to duplicate and increases load.

Reference: [Primary documentation](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/).

### 3b. Boundaries and lifecycle

Classify → check idempotency and remaining budget → reserve retry capacity → compute delay → schedule without holding scarce execution slots → stop or reconcile.

## 4. How to apply / implement / use it?

Save as `advanced_retry_strategies_demo.py`; run `python3 advanced_retry_strategies_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def decision(kind, attempt, remaining, retry_tokens, delay):
    if kind == "unknown-effect":
        return "reconcile"
    if kind == "permanent":
        return "reject"
    if kind != "transient":
        raise ValueError("unclassified failure")
    if attempt >= 3 or retry_tokens <= 0 or remaining <= delay + 0.2:
        return "stop"
    return "schedule"
assert decision("transient", 1, 5, 2, 1) == "schedule"
assert decision("transient", 3, 5, 2, 1) == "stop"
assert decision("transient", 1, 0.5, 2, 1) == "stop"
assert decision("unknown-effect", 1, 5, 2, 1) == "reconcile"
assert decision("permanent", 1, 5, 2, 1) == "reject"
```

This deterministic decision core does not reserve tokens atomically or perform retries. A production scheduler must persist retry identity/time, coordinate budgets, and apply actual deadline/cancellation behavior.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not hedge payments, retry at every layer, or hold a database connection during backoff. Retrying harder is not a substitute for admission control.

## 6. How do I know I understand it?

**Blank-page check:** Calculate the retry multiplier and design a bounded policy for timeout, rate limit, validation failure, and unknown provider outcome.

| Constraint change | Predict the failure and response |
| --- | --- |
| Every layer allows four attempts | Bottom-layer work can multiply exponentially; pick a coordinating retry owner. |
| Server advises waiting longer than the deadline | Stop/defer according to product policy rather than violating the budget. |
