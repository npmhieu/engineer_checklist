# At-most-once Delivery

[Lesson index](../../README.md) · [Previous](1.message_delivery_semantics.md) · [Next](3.at_least_once_delivery.md)

## 1. What is it?

At-most-once delivery permits loss while avoiding transport redelivery within its stated scope, like discarding a ticket before attempting the task.

## 2. Why do we need it?

Some disposable telemetry favors low overhead over recovery, but using the same policy for orders can silently lose important work.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Advancing progress before processing removes one retry window and creates a loss window. At-most-once is not a promise that an application cannot submit the same logical request twice; producer duplicates remain a separate concern.

Reference: [Primary documentation](https://kafka.apache.org/43/design/design/).

### 3b. Boundaries and lifecycle

Accept input → retire delivery/progress → attempt handler → success or unrecoverable loss under this policy.

## 4. How to apply / implement / use it?

Save as `at_most_once_delivery_demo.py`; run `python3 at_most_once_delivery_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from collections import deque
queue = deque(["one", "two"])
completed = []
def deliver(crash=False):
    message = queue.popleft()
    if crash:
        raise RuntimeError("consumer crashed after retirement")
    completed.append(message)
deliver()
try:
    deliver(crash=True)
except RuntimeError:
    pass
assert completed == ["one"]
assert not queue
```

The deque models retiring a delivery before an effect. It is non-durable and not a remote acknowledgement implementation. The failed second message is intentionally unrecoverable in this model.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not use for payments, required notifications, or other work whose loss needs recovery. Avoid claiming at-most-once transport prevents duplicate user intent.

## 6. How do I know I understand it?

**Blank-page check:** Prove where loss is possible and identify a workload where losing a sample is acceptable.

| Constraint change | Predict the failure and response |
| --- | --- |
| Handler crashes immediately after progress advances | The message is lost rather than redelivered. |
| Producer sends the same order under two IDs | Both can execute; this delivery policy is not business deduplication. |
