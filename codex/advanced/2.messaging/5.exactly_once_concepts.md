# Exactly-once Concepts

[Lesson index](../../README.md) · [Previous](4.effectively_once_processing.md) · [Next](6.message_ordering.md)

## 1. What is it?

Exactly-once concepts concern committing one logical outcome despite retries inside an explicitly coordinated scope, like advancing a ledger and its bookmark together.

## 2. Why do we need it?

Marketing labels can hide a gap between transactional stream output and an unrelated database, email, or payment provider.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Atomic processing can couple input progress, state changes, and outputs when one transaction protocol covers them. Kafka transactions can coordinate Kafka records and consumed offsets with suitable clients/isolation; an arbitrary external effect is outside that boundary. Execution attempts can still repeat.

Reference: [Primary documentation](https://kafka.apache.org/43/design/design/).

### 3b. Boundaries and lifecycle

Read input → start coordinated transaction → produce output/update covered state → commit progress and outputs together → readers observe committed results.

## 4. How to apply / implement / use it?

Save as `exactly_once_concepts_demo.py`; run `python3 exactly_once_concepts_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import sqlite3
database = sqlite3.connect(":memory:")
database.executescript("CREATE TABLE progress(next_offset INTEGER);"
                      "INSERT INTO progress VALUES(0);"
                      "CREATE TABLE output(offset INTEGER PRIMARY KEY, value TEXT);")
def process(offset, fail=False):
    with database:
        expected = database.execute("SELECT next_offset FROM progress").fetchone()[0]
        if offset != expected:
            return False
        database.execute("INSERT INTO output VALUES(?,?)", (offset, "result"))
        if fail:
            raise RuntimeError("transaction interrupted")
        database.execute("UPDATE progress SET next_offset=?", (offset + 1,))
    return True
try:
    process(0, fail=True)
except RuntimeError:
    pass
assert database.execute("SELECT COUNT(*) FROM output").fetchone()[0] == 0
assert process(0) and not process(0)
assert database.execute("SELECT next_offset FROM progress").fetchone()[0] == 1
database.close()
```

This real local transaction models atomic output/progress, not Kafka transactions or a global distributed exactly-once protocol. It deliberately excludes external providers and concurrent stream ownership.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not equate exactly-once committed output with one physical execution or one external side effect. Added coordination, abort/retry behavior, and scope restrictions must be justified.

**Blank-page check:** Name every resource inside the transaction and every excluded effect. Explain why the failed attempt can rerun safely.

| Constraint change | Predict the failure and response |
| --- | --- |
| Output goes to another uncoordinated database | Atomicity no longer spans both; use an appropriate sink protocol or idempotent recovery. |
| Readers include uncommitted output | They can observe aborted work; transactional reader isolation matters. |
