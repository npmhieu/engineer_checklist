# Effectively-once Processing

[Lesson index](../../README.md) · [Previous](3.at_least_once_delivery.md) · [Next](5.exactly_once_concepts.md)

## 1. What is it?

Effectively-once processing makes repeated attempts produce one intended observable effect within a defined boundary, like recording a receipt so copies do not charge again.

## 2. Why do we need it?

At-least-once transport is practical, but users care about the final business result rather than the number of handler invocations.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Use stable scoped identity, semantic fingerprint validation, and atomic deduplication plus local mutation/result. Retain identity long enough for the replay window. External effects need provider idempotency or a separate recoverable workflow; one local record is not global atomicity.

Reference: [Primary documentation](https://microservices.io/patterns/communication-style/idempotent-consumer.html).

### 3b. Boundaries and lifecycle

Receive → insert identity or load prior outcome → reject conflicting reuse → mutate/store result atomically → commit → acknowledge.

## 4. How to apply / implement / use it?

Save as `effectively_once_processing_demo.py`; run `python3 effectively_once_processing_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import sqlite3
database = sqlite3.connect(":memory:")
database.executescript("CREATE TABLE inbox(id PRIMARY KEY, amount INTEGER);"
                      "CREATE TABLE balance(value INTEGER);"
                      "INSERT INTO balance VALUES(0);")
def apply(event_id, amount):
    with database:
        prior = database.execute("SELECT amount FROM inbox WHERE id=?", (event_id,)).fetchone()
        if prior:
            if prior[0] != amount:
                raise ValueError("identity reused with different meaning")
            return "duplicate"
        database.execute("INSERT INTO inbox VALUES(?,?)", (event_id, amount))
        database.execute("UPDATE balance SET value=value+?", (amount,))
    return "applied"
assert apply("evt-1", 5) == "applied"
assert apply("evt-1", 5) == "duplicate"
try:
    apply("evt-1", 9)
except ValueError:
    pass
else:
    raise AssertionError("conflicting intent accepted")
assert database.execute("SELECT value FROM balance").fetchone()[0] == 5
database.close()
```

This real SQLite transaction covers one database and sequential fixture calls. Concurrent production handlers need uniqueness/conflict handling under their engine's isolation rules. Include tenant and consumer scope where IDs are not globally unique.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not advertise universal exactly-once behavior. Deduplication records, conflict checks, retention, and external-provider reconciliation have real cost.

## 6. How do I know I understand it?

**Blank-page check:** State precisely what effect is protected, which failures are covered, and how conflicting ID reuse is handled.

| Constraint change | Predict the failure and response |
| --- | --- |
| Inbox expires before an old replay | The old effect can happen again; align retention and replay policy. |
| Handler also calls an email provider | The database guarantee does not extend to that external call. |
