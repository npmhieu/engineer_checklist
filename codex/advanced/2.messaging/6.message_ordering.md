# Message Ordering

[Lesson index](../../README.md) · [Previous](5.exactly_once_concepts.md) · [Next](7.poison_messages.md)

## 1. What is it?

Message ordering specifies the transport sequence visible within a defined scope, like numbered envelopes on one conveyor rather than a universal timeline.

## 2. Why do we need it?

Parallel handlers can complete a later message before an earlier one even when the broker delivered them in order.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Distinguish enqueue, delivery, completion, and committed-effect order. Partitions, producer concurrency, retries, requeueing, and consumer parallelism affect each layer. Enforcing per-key sequential completion trades parallelism for predictable state transitions.

Reference: [Primary documentation](https://www.rabbitmq.com/docs/queues).

### 3b. Boundaries and lifecycle

Route by key → receive ordered stream → serialize conflicting handlers or validate sequence → commit → acknowledge only safe progress.

## 4. How to apply / implement / use it?

Save as `message_ordering_demo.py`; run `python3 message_ordering_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
delivered = [1, 2, 3]
completion_order = [2, 1, 3]
finished = set()
committed_through = 0
for sequence in completion_order:
    finished.add(sequence)
    while committed_through + 1 in finished:
        committed_through += 1
    if sequence == 2:
        assert committed_through == 0
assert committed_through == 3
assert delivered != completion_order
```

This contiguous-progress model prevents skipping an unfinished earlier record, but it does not reorder already executed business effects. Effects requiring strict sequence must also be serialized or guarded at the state boundary.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not commit the largest completed offset when earlier records remain unfinished. Do not demand global order for unrelated keys.

## 6. How do I know I understand it?

**Blank-page check:** Draw delivery order, handler completion order, and committed cursor separately; identify which one the invariant needs.

| Constraint change | Predict the failure and response |
| --- | --- |
| Record 1 hangs while 2 succeeds | Safe progress may stall; bound work, isolate keys, or recover the gap explicitly. |
| A failed record moves to a retry queue | Later records can overtake it; decide whether the business allows this. |
