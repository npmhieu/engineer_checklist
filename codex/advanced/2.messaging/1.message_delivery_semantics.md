# Message Delivery Semantics

[Lesson index](../../README.md) · [Previous](../1.distributed_systems/10.consumer_groups.md) · [Next](2.at_most_once_delivery.md)

## 1. What is it?

Message delivery semantics describe what a transport promises about delivery attempts, like postal rules about losing or resending a parcel.

## 2. Why do we need it?

Teams often confuse broker acceptance, consumer receipt, durable business effects, and a user's observed result, producing false exactly-once claims.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Name the boundary and failure assumptions. Publisher confirms concern broker acceptance; consumer acknowledgements concern delivery progress. Neither alone proves one business effect. Persistence, replication, retention, retries, and consumer transactions jointly determine what survives failures.

Reference: [Primary documentation](https://www.rabbitmq.com/docs/confirms).

### 3b. Boundaries and lifecycle

Publish → broker accepts → delivers → consumer commits → acknowledgement advances progress; inject a failure between each pair before claiming a guarantee.

## 4. How to apply / implement / use it?

Save as `message_delivery_semantics_demo.py`; run `python3 message_delivery_semantics_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def crash_window(ack_before_effect, crash):
    acknowledged, effects = False, 0
    if ack_before_effect:
        acknowledged = True
    if crash == "before-effect":
        return acknowledged, effects
    effects += 1
    if crash == "after-effect":
        return acknowledged, effects
    acknowledged = True
    return acknowledged, effects
assert crash_window(True, "before-effect") == (True, 0)
assert crash_window(False, "after-effect") == (False, 1)
assert crash_window(False, None) == (True, 1)
```

This state-transition model exposes loss and duplication windows; it is not a broker guarantee test. Acknowledged here means this model's delivery progress, not end-to-end customer success.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not select a delivery label without specifying storage, retention, failure scope, and effect boundary. Stronger transport guarantees can add coordination cost without covering an external provider.
