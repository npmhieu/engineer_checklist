# Key Management

[Lesson index](../../README.md) · [Previous](4.encryption.md) · [Next](6.advanced_api_security.md)

## 1. What is it?

Key management governs cryptographic key creation, permissions, versions, rotation, recovery, and destruction, like controlling master keys separately from the locked records.

## 2. Why do we need it?

Strong encryption is useless if every process can read the key, an old key is deleted prematurely, or recovery cannot access the right version.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Use a KMS/HSM or appropriate managed authority and separate key permissions. Envelope encryption encrypts data with data keys and protects those keys with a wrapping key. Rotation of a wrapping key does not automatically re-encrypt all data; key IDs, old-version decryption, rewrap/re-encryption, and revocation are distinct operations.

Reference: [Primary documentation](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html).

### 3b. Boundaries and lifecycle

Create protected key → authorize limited use → record key version with ciphertext → rotate new writes → retain/recover required old versions → retire only after verified migration/retention policy.

## 4. How to apply / implement / use it?

Save as `key_management_demo.py`; run `python3 key_management_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
keys = {"key-1": {"revoked": False}, "key-2": {"revoked": False}}
active = "key-1"
def resolve(key_id, action):
    if key_id not in keys or keys[key_id]["revoked"]:
        raise PermissionError("key unavailable")
    if action not in {"encrypt", "decrypt"}:
        raise ValueError("unsupported action")
    if action == "encrypt" and key_id != active:
        raise PermissionError("old key is decrypt-only")
    return key_id
assert resolve("key-1", "encrypt") == "key-1"
active = "key-2"
assert resolve("key-2", "encrypt") == "key-2"
assert resolve("key-1", "decrypt") == "key-1"
try:
    resolve("key-1", "encrypt")
except PermissionError:
    pass
else:
    raise AssertionError("old key used for new encryption")
keys["key-1"]["revoked"] = True
try:
    resolve("key-1", "decrypt")
except PermissionError:
    pass
else:
    raise AssertionError("revoked key accepted")
```

This key-policy model stores IDs only and performs no encryption, wrapping, KMS calls, or identity verification. Revoking key-1 intentionally makes its old ciphertext unavailable in the modeled policy; do not do that to real keys without a reviewed recovery/incident plan.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not implement a homegrown KMS or assume rotation erases prior exposure. Excessively broad decrypt privileges can bypass the value of protected storage.

## 6. How do I know I understand it?

**Blank-page check:** Draw data key, wrapping key, ciphertext metadata, permissions, and restore path; distinguish rotation from re-encryption and destruction.

| Constraint change | Predict the failure and response |
| --- | --- |
| Wrapping key rotates | Determine whether existing wrapped data keys need rewrapping; plaintext data need not always be rewritten. |
| An old key is destroyed while backups still need it | Those backups may become permanently unreadable. |
