# Eventual Consistency

[Lesson index](../../README.md) · [Previous](../2.messaging/10.queue_backpressure.md) · [Next](2.strong_consistency.md)

## 1. What is it?

Eventual consistency lets replicas temporarily disagree but converge under stated delivery/conflict assumptions once updates stop, like branch offices catching up with the same ledger.

## 2. Why do we need it?

Waiting for every distant copy on every write can harm latency and availability, but stale reads become a product and correctness concern.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Propagation, anti-entropy, version metadata, and conflict resolution determine convergence. Eventual consistency alone promises neither a time bound nor read-your-writes. Last-write-wins needs a defined total order and may discard valid concurrent changes; wall clocks are not perfect causality.

Reference: [Primary documentation](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf).

### 3b. Boundaries and lifecycle

Accept update → propagate asynchronously → replicas merge under one rule → repair missing state → expose freshness/consistency expectations.

## 4. How to apply / implement / use it?

Save as `eventual_consistency_demo.py`; run `python3 eventual_consistency_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
first = {"version": (1, "A"), "value": "old"}
second = dict(first)
def merge(local, incoming):
    return dict(max((local, incoming), key=lambda entry: entry["version"]))
first = {"version": (2, "A"), "value": "new"}
assert second["value"] == "old"
second = merge(second, first)
assert second == first
first = merge(first, {"version": (1, "B"), "value": "late-old"})
assert first["value"] == "new"
concurrent = {"version": (2, "B"), "value": "other"}
assert merge(first, concurrent) == merge(concurrent, first)
```

This deterministic version-order merge illustrates convergence and stale reads, not a complete replication protocol or conflict-free preservation of both edits. The chosen tie-break deliberately discards one competing value.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not use stale projections to enforce uniqueness, account limits, or inventory reservations without an authoritative coordination strategy. 'Eventually' is not a freshness SLA.

## 6. How do I know I understand it?

**Blank-page check:** Explain the convergence assumptions and distinguish eventual consistency from bounded staleness and read-your-writes.

| Constraint change | Predict the failure and response |
| --- | --- |
| Propagation stops permanently | The assumptions fail; replicas need repair before convergence can be claimed. |
| Two valid edits conflict | Choose domain merge, rejection, or explicit conflict handling rather than accidental clock priority. |
