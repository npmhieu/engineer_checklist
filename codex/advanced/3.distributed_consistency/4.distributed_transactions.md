# Distributed Transactions

[Lesson index](../../README.md) · [Previous](3.cap_theorem.md) · [Next](5.saga_pattern.md)

## 1. What is it?

A distributed transaction coordinates one commit decision across multiple transactional participants, like several ledgers waiting for the same signed approval.

## 2. Why do we need it?

Independent commits can leave money debited in one database but not credited in another after a partial failure.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Two-phase commit prepares participants, records a durable coordinator decision, then commits or rolls back. Prepared participants may hold locks/resources while in doubt. Coordinator recovery and participant durability are essential; consensus replication of a coordinator is a separate design concern. HTTP calls are not automatically transactional participants.

Reference: [Primary documentation](https://www.postgresql.org/docs/current/sql-prepare-transaction.html).

### 3b. Boundaries and lifecycle

Begin local work → prepare votes → durable global decision → notify/retry completion → recover unresolved participants from recorded decisions.

## 4. How to apply / implement / use it?

Save as `distributed_transactions_demo.py`; run `python3 distributed_transactions_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
participants = {"bank-a": "active", "bank-b": "active"}
decision = None
def prepare(name, accepts=True):
    participants[name] = "prepared" if accepts else "rejected"
def decide():
    global decision
    decision = "commit" if all(state == "prepared" for state in participants.values()) else "abort"
def finish(name):
    if decision is None:
        raise RuntimeError("in doubt")
    participants[name] = "committed" if decision == "commit" else "aborted"
prepare("bank-a")
try:
    finish("bank-a")
except RuntimeError:
    pass
prepare("bank-b")
decide()
for name in participants:
    finish(name)
assert set(participants.values()) == {"committed"}
```

This is a protocol state model, not a usable transaction manager. It omits durable logs, network failures, lock handling, rejection recovery tests, and participant recovery. Do not run PREPARE TRANSACTION manually in production without an appropriate coordinator and cleanup plan.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not use distributed transactions for arbitrary email/payment APIs or when their blocking/operational cost is unjustified. A saga changes the guarantee; it is not identical atomicity with cheaper syntax.

| Constraint change | Predict the failure and response |
