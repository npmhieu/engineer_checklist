# Distributed Idempotency

[Lesson index](../../README.md) · [Previous](7.distributed_locking.md) · [Next](../4.database_scaling/1.replication.md)

## 1. What is it?

Distributed idempotency gives repeated cross-process requests one stable operation meaning and outcome, like several branches consulting one authoritative receipt register.

## 2. Why do we need it?

Per-instance memory cannot deduplicate retries routed to another replica, and a process crash can separate an effect from its recorded result.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Scope keys by principal/tenant and operation; validate a semantic fingerprint; atomically claim/persist local effect/result. Pending work needs lease/fencing/reconciliation, not simply deletion on timeout. Each downstream boundary needs compatible identity handling; database uniqueness is not global provider atomicity.

Reference: [Primary documentation](https://docs.stripe.com/api/idempotent_requests).

### 3b. Boundaries and lifecycle

Verify caller → normalize semantic request → claim scoped key → perform/recover work → store outcome → replay same outcome or reject conflicting reuse.

## 4. How to apply / implement / use it?

Save as `distributed_idempotency_demo.py`; run `python3 distributed_idempotency_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import sqlite3
database = sqlite3.connect(":memory:")
database.execute("CREATE TABLE operations(tenant TEXT, key TEXT, amount INTEGER,"
                 " result TEXT, PRIMARY KEY(tenant,key))")
def execute(tenant, key, amount):
    with database:
        prior = database.execute("SELECT amount,result FROM operations WHERE tenant=? AND key=?",
                                 (tenant, key)).fetchone()
        if prior:
            if prior[0] != amount:
                raise ValueError("conflicting idempotency key")
            return prior[1]
        result = "accepted:" + str(amount)
        database.execute("INSERT INTO operations VALUES(?,?,?,?)",
                         (tenant, key, amount, result))
        return result
assert execute("shop-1", "op-1", 5) == execute("shop-1", "op-1", 5)
assert execute("shop-2", "op-1", 8) == "accepted:8"
try:
    execute("shop-1", "op-1", 9)
except ValueError:
    pass
else:
    raise AssertionError("changed intent accepted")
database.close()
```

This real SQLite identity/result boundary records acceptance only; no external effect occurs. It is a sequential local fixture, not a multi-replica service. Production needs concurrency-safe conflict handling and atomic inclusion of the actual local mutation, or a durable pending workflow for remote effects.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not make idempotency keys global authorization bypasses, delete uncertain pending operations, or reuse IDs with changed payloads. Retention and downstream limits constrain the guarantee.

## 6. How do I know I understand it?

**Blank-page check:** Trace a retry across two API replicas and a provider timeout. State which store owns the result and how ambiguity is resolved.

| Constraint change | Predict the failure and response |
| --- | --- |
| Retry reaches a different API replica | All replicas must consult the same authoritative operation store or equivalent consistency protocol. |
| Provider committed but response vanished | Recover with the same provider key/reconciliation; do not discard pending identity. |
