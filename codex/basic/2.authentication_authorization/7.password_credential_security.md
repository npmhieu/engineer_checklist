# Password / Credential Security

[Lesson index](../../README.md) · Previous: [JWT Basics](6.jwt_basics.md) · Next section: [Database Fundamentals](../3.database/1.database_fundamentals.md)

## 1. What is it?

Password and credential security protects the proofs used to access accounts and services, like protecting both a building's keys and the process for replacing a lost key.

It covers creation, storage, transport, verification, abuse prevention, recovery, rotation, revocation, and incident response—not only a password-length rule.

Credentials need different treatment:

| Credential | Typical handling |
| --- | --- |
| Human-chosen password verified by this service | Adaptive salted password hash; do not store recoverable plaintext |
| Random opaque API/session/reset token verified here | High entropy, bounded lifetime/purpose where appropriate, protected digest lookup |
| Outbound database/API secret this service must present | Secret manager and controlled retrieval; a one-way hash cannot recover the value to present |
| Signing private/shared key | Protected key management, narrowly scoped access, rotation and compromise response |
| Passkey public credential | Store public verification data; private authenticator material stays with its authenticator/provider design |

## 2. Why do we need it?

A database leak should not immediately expose every user's password. A reusable password from another breached service should not permit unlimited online guesses. Recovery must not be an easier takeover route than login.

Specific failures include plaintext credentials in logs, fast hashes cracked offline, silent password truncation, brute-force login causing CPU exhaustion, and a committed API key remaining usable after its repository history is cleaned up.

Password hashing limits offline guessing cost; it does not prevent phishing, malware, or replay of a password already known to an attacker. Transport protection, throttling, MFA/passkeys where appropriate, and recovery controls address different risks.

## 3. Under the hood / mechanism / system flow

### 3a. Salt, work factor, memory, and verification

A maintained password library generates a fresh random salt and computes an adaptive hash. The stored encoded record contains the algorithm/version, cost parameters, salt, and result. On login, the library uses those parameters to verify the complete submitted secret; there is no password decryption step.

- **Salt:** distinct per hash, not secret; prevents identical passwords from sharing one stored result and defeats shared precomputation.
- **Work factor:** makes each offline guess deliberately expensive. It must be benchmarked on the deployment hardware.
- **Memory hardness:** Argon2id uses a configured working-memory region and repeated passes, increasing the resources needed for bulk guessing.
- **Pepper:** an optional additional secret kept outside the password database; adds key-management and recovery obligations, not a replacement for salts or a good password hash.

Argon2's memory parameter is in KiB; parallelism does not multiply the configured total memory. Roughly, work grows with memory and passes, while each concurrent verification requires its working memory plus overhead. At 19 MiB per verification, 100 concurrent verifications can require about 1.9 GiB before other process costs. Bound request sizes and concurrent work, and rate-limit abusive attempts; do not “optimize” by switching to a fast hash.

[OWASP's password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) recommends Argon2id and lists a baseline configuration of 19 MiB, two passes, and parallelism one. The example uses that baseline for reproducibility, not as a guarantee that the cheapest listed configuration is ideal for your system. A mature framework/library's stronger calibrated policy may be appropriate. Parameter changes require review, not blind downgrades to match a sample.

### 3b. Credential lifecycle and surrounding systems

```text
Enrollment/change: bounded input → documented normalization + password policy
    → library hashes with fresh salt → atomically store credential state
Login: abuse controls → load trusted hash or dummy hash → library verify
    → current account checks → optional policy rehash → establish session
Recovery/compromise: prove recovery authority → replace/revoke credentials
    → invalidate access as required → notify/audit without leaking secrets
```

For a concrete human-password policy, [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver) requires at least 15 characters for single-factor passwords, allows a different minimum when used within MFA, favors allowing long passwords, requires checking commonly used/compromised values, and rejects arbitrary composition rules and routine periodic changes without evidence of compromise. These are guidance/profile requirements, not a statement that every product is legally governed by NIST.

Use a consistent Unicode-normalization policy when supported; do not silently trim, case-fold, or truncate the password used for verification. A blocklist lookup may compare normalized variants without changing the actual password hashed. Support password managers and paste rather than forcing predictable character patterns.

Recovery tokens need secure generation, purpose binding, expiry, one-use consumption, generic public responses, and deliberate session invalidation. A password reset must not automatically grant broader permissions. See [OWASP's recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

Machine-secret handling has another boundary: load protected secrets only where needed, restrict access, avoid plaintext logs/build artifacts, and prefer short-lived workload credentials where supported. Revoking a leaked secret matters even after deleting its file. See [OWASP's secrets management guidance](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html).

## 4. How to apply / implement / use it?

### Smallest runnable password-storage and login example

Save the Python block as `password_security_demo.py`. In a scratch directory:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install 'argon2-cffi>=23.1,<26'
.venv/bin/python password_security_demo.py
```

The package is **argon2-cffi**, imported as `argon2`. This example was checked with argon2-cffi 25.1.0. [Its API reference](https://argon2-cffi.readthedocs.io/en/stable/api.html) documents salt generation, verification errors, and checking for rehashes. Use a reviewed dependency lock/update policy in a real application.

This single-process fixture uses NFC normalization, 15–128 normalized code points for new passwords, and a tiny illustrative whole-password blocklist. A real service needs a maintained common/breached/context-specific blocklist and abuse controls. The sample phrase is public test data, not a password to use for any real account.

```python
import secrets
import unicodedata
from argon2 import PasswordHasher
from argon2.exceptions import InvalidHashError, VerificationError, VerifyMismatchError


class LoginFailed(Exception):
    pass


class CredentialStoreFailure(Exception):
    pass


hasher = PasswordHasher(time_cost=2, memory_cost=19456, parallelism=1)
blocked = {"passwordpassword", "correct horse battery staple"}
users = {}
dummy_hash = hasher.hash(secrets.token_urlsafe(32))


def normalize_password(password):
    if not isinstance(password, str) or len(password) > 1024:
        raise ValueError("INVALID_PASSWORD_INPUT")
    return unicodedata.normalize("NFC", password)


def create_account(username, password):
    normalized = normalize_password(password)
    if not 15 <= len(normalized) <= 128 or normalized.casefold() in blocked:
        raise ValueError("PASSWORD_POLICY_FAILED")
    if username in users:
        raise ValueError("ACCOUNT_EXISTS")
    users[username] = {
        "id": 7, "status": "active", "password_hash": hasher.hash(normalized),
    }


def authenticate_password(username, password):
    try:
        normalized = normalize_password(password)
    except ValueError:
        raise LoginFailed("INVALID_CREDENTIALS") from None
    account = users.get(username)
    encoded = dummy_hash if account is None else account["password_hash"]
    try:
        hasher.verify(encoded, normalized)
    except VerifyMismatchError:
        raise LoginFailed("INVALID_CREDENTIALS") from None
    except (VerificationError, InvalidHashError):
        raise CredentialStoreFailure("CREDENTIAL_VERIFICATION_UNAVAILABLE") from None
    if account is None or account["status"] != "active":
        raise LoginFailed("INVALID_CREDENTIALS")
    if hasher.check_needs_rehash(encoded):
        account["password_hash"] = hasher.hash(normalized)
    return {"subject_id": account["id"]}


phrase = "Learning-only long passphrase 7391"
create_account("learner", phrase)
stored = users["learner"]["password_hash"]
assert stored.startswith("$argon2id$") and stored != phrase
assert hasher.hash(phrase) != stored
assert authenticate_password("learner", phrase) == {"subject_id": 7}

for username, candidate in [("learner", "wrong password"), ("missing", phrase)]:
    try:
        authenticate_password(username, candidate)
    except LoginFailed as error:
        assert str(error) == "INVALID_CREDENTIALS"
    else:
        raise AssertionError("Invalid credentials were accepted")

users["learner"]["status"] = "suspended"
try:
    authenticate_password("learner", phrase)
except LoginFailed:
    pass
else:
    raise AssertionError("Suspended account authenticated")

for candidate in ["short", "passwordpassword"]:
    try:
        create_account("rejected", candidate)
    except ValueError:
        pass
    else:
        raise AssertionError("Weak password was accepted")
print("happy: salted Argon2id verification; unhappy: wrong/unknown/suspended/weak rejected")
```

`PasswordHasher` uses Argon2id by default and generates its own salts. Never accept a client-supplied encoded hash as the server's credential record: its parameters and provenance are not trusted. A damaged stored record is an internal verification failure, not a reason to authenticate the caller; an adapter returns a controlled server failure and records redacted diagnostics.

The dummy hash makes a missing-account path perform similar expensive work; it does **not** guarantee constant request timing or eliminate enumeration across all endpoints. Generic login responses also need careful HTTP behavior, throttling, recovery/registration behavior, and monitoring.

The fixture's `id=7` is deliberately fixed for its **one successful demonstration account**; a real registration service allocates unique stable IDs and enforces uniqueness transactionally. Username input is assumed normalized/validated by its input layer. Login verifies existing stored credentials without reapplying the current new-password blocklist/length policy to every attempt; account upgrades can use a deliberate migration/reset policy.

Successful rehash needs the submitted plaintext, so it commonly runs after a verified login. A real database implementation must coordinate replacement with concurrent password changes, for example using a compare-and-swap on the previous credential/version. `check_needs_rehash` detects a parameter mismatch, not proof that every different stored policy is weaker. Review the target policy and avoid accidental downgrades.

This is not a deployable login system: no TLS server, MFA, rate limiter, durable users, session creation, reset endpoint, or secret manager is supplied. Never print or log passwords, encoded hashes, tokens, or reusable keys. Use request IDs and redacted security events instead.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- If a trusted identity provider/passkey flow owns login, do not collect local passwords without a reason; still secure your local sessions, recovery/linking policy, and machine credentials.
- Do not use plaintext, reversible encryption for ordinary local password verification, MD5, or a single fast SHA-256 digest.
- Do not use a password hash when the application must retrieve an outbound secret; use controlled secret management for that separate requirement.
- Do not force arbitrary symbol mixtures or periodic password changes as a replacement for compromised-password blocking and appropriate incident response.
- Do not truncate passwords silently or assume a character count is a byte count when migrating legacy algorithms such as bcrypt.
- Do not force slow password verification onto every authenticated API call; establish a properly protected session afterward.

Slow hashing consumes resources for attackers and legitimate users alike. Benchmark under concurrent load and bound abuse without making account lockout an easy denial-of-service tool. Salts are not secret keys; peppers and signing keys require separate management. A stolen plaintext password or active session is not neutralized merely because the password database uses Argon2id.

## 6. How do I know I understand it?

**Blank-page check:** draw enrollment, stored hash components, login verification, policy rehash, recovery, and session revocation. Explain what a database-only attacker can try offline, what a phisher can still steal, and which defense addresses each.

| Constraint change | Predict the failure and response |
| --- | --- |
| Two users choose the same password | Fresh salts produce different encoded records; both still need a strong password policy |
| Login concurrency grows by 100 times | Memory/CPU can become the bottleneck; bound work, throttle abuse, and benchmark capacity |
| Hashing policy changes | Verify existing supported records and upgrade deliberately after successful proof or recovery |
| A machine API secret leaks into Git | Revoke/rotate it and investigate exposure; deleting the current file is insufficient |
| A password reset succeeds | Apply the intended session/refresh-token invalidation policy and notify/audit safely |
| A stored hash is malformed | Fail closed as a controlled internal problem; never treat it as a successful login |
| A Vietnamese password has equivalent Unicode encodings | Use the same documented normalization at enrollment and verification |

You understand credential security when storage, verification, transport, abuse prevention, recovery, and revocation remain distinct but coordinated defenses.
