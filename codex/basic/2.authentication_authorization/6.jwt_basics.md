# JWT Basics

## 1. What is it?

A JSON Web Token (JWT) carries structured claims that can be integrity-protected, like a signed event ticket whose issuer, holder, venue, and expiry can be checked without asking the ticket desk for that ticket's record.

JWT is a **format**, not a login protocol, browser-storage strategy, permission system, or guarantee of statelessness. This lesson uses the common signed/MAC-protected compact form, not encrypted JWTs. Signing/MAC protection prevents undetected changes when verified correctly; it does not hide the payload.

## 2. Why do we need it?

Several services may need to verify claims from a trusted issuer without making a central per-token lookup for every request. A structured, cryptographically protected token can support that boundary.

The problem is not that ordinary sessions are broken. JWT shifts responsibilities toward key distribution, validation policy, expiry, and claim freshness. Specific failures include accepting modified claims after merely decoding them, accepting a token intended for another API, and continuing to trust an old administrator role after revocation.

## 3. Under the hood / mechanism / system flow

### 3a. Encoded structure and cryptographic checks

The signed compact form has three base64url-encoded parts:

```text
base64url(header).base64url(payload).base64url(signature-or-MAC)
```

The integrity check covers the exact encoded header and payload joined by a dot. The header names parameters such as algorithm and optional key ID; the payload contains claims. Base64url is reversible encoding, not encryption. JWT also supports encrypted forms with a different structure; do not infer that every JWT always has three parts. See [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html).

| Claim | Meaning and validation boundary |
| --- | --- |
| `iss` | Issuer; match a configured trusted issuer |
| `aud` | Audience; token must be intended for this API/client context |
| `sub` | Subject identifier, interpreted within issuer scope |
| `exp` | Expiry time; expired tokens are rejected |
| `nbf` | Not usable before this time |
| `iat` | Issue time; not a substitute for expiry or a maximum-lifetime policy |
| `jti` | Token identifier; does not prevent replay unless a system tracks/enforces relevant state |

Numeric dates use seconds relative to the Unix epoch. Whether claims are mandatory is determined by the application/protocol profile; the generic format does not make all the fields above required. The example deliberately requires them.

For **HS256**, issuer and verifier share an HMAC secret, so any holder of that secret can mint tokens. With an asymmetric algorithm such as RS256 or ES256, the issuer signs using a private key while verifiers use an appropriate public key. Do not mix symmetric/asymmetric key interpretation or choose allowed algorithms from untrusted token data.

Parsing and HMAC processing scale with bounded token size; asymmetric verification has different cryptographic cost. Tokens are often larger than opaque IDs and travel on each request, consuming bandwidth and header space. Key retrieval can add I/O; cache trusted key sets with controlled refresh, unknown-key handling, and rotation policy. An arbitrary token-supplied URL or file path is not a safe key source.

### 3b. Validation before trust

```text
Bound input → configured algorithm + trusted key → signature/MAC verification
    → required claims + issuer/audience/time/type/profile validation
    → account/revocation freshness policy → principal → resource authorization
```

A successful signature alone is insufficient. Check intended token kind to avoid confusing ID tokens, access tokens, and another application's tokens. Use separate validation rules/keys where appropriate. A token's `kid` can select only among permitted keys from an already trusted context; it cannot choose your trust policy. [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html) describes algorithm verification, audience checks, explicit typing, and substitution defenses.

Expiry limits a credential's lifetime; it does not provide immediate logout or permission updates. A revoked-token list, account security version, online introspection, or short-lived credentials with a documented freshness window can address different requirements. They have different availability/state costs. A valid bearer JWT can normally be replayed by its holder until those controls reject it.

## 4. How to apply / implement / use it?

### Use a maintained verifier with explicit policy

Save the Python block as `jwt_basics_demo.py`. In a scratch directory, create an isolated environment and run:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install 'PyJWT>=2.10,<3'
.venv/bin/python jwt_basics_demo.py
```

Use the **PyJWT** package, imported as `jwt`, not a different package named `jwt`. See [PyJWT's API reference](https://pyjwt.readthedocs.io/en/stable/api.html) for required-claim and verification options. This example was checked with PyJWT 2.15.1; production dependencies need a reviewed lock/update policy.

The local fixture is both trusted issuer and verifier. It uses a random process-local HS256 key for a small demonstration, not a shared secret to distribute to arbitrary services. The custom `typ` and `ver` below define a local application profile, not a claim of implementing a complete OAuth/OIDC token profile. No real signing keys, passwords, or personal data should go into the example.

```python
import secrets
import time
import jwt


class Unauthenticated(Exception):
    pass


ISSUER = "https://identity.example.test"
AUDIENCE = "backend-learning-api"
TOKEN_TYPE = "backend-access+jwt"
signing_key = secrets.token_bytes(64)
accounts = {"user-7": {"status": "active", "auth_version": 1}}
now = int(time.time())
claims = {
    "iss": ISSUER, "aud": AUDIENCE, "sub": "user-7",
    "iat": now - 1, "nbf": now - 1, "exp": now + 120,
    "jti": secrets.token_urlsafe(16), "ver": 1,
}


def sign_fixture(payload, key=signing_key, algorithm="HS256", token_type=TOKEN_TYPE):
    return jwt.encode(payload, key, algorithm=algorithm, headers={"typ": token_type})


def verify_access_token(token):
    if not isinstance(token, str) or not token.isascii() or not 1 <= len(token) <= 4096:
        raise Unauthenticated("AUTHENTICATION_REQUIRED")
    try:
        verified = jwt.decode(
            token, signing_key, algorithms=["HS256"],
            issuer=ISSUER, audience=AUDIENCE, leeway=0,
            options={
                "require": ["iss", "aud", "sub", "iat", "nbf", "exp", "jti", "ver"],
                "strict_aud": True,
            },
        )
        if jwt.get_unverified_header(token).get("typ") != TOKEN_TYPE:
            raise jwt.InvalidTokenError("Wrong token kind")
        if any(type(verified[field]) is not int for field in ("iat", "nbf", "exp", "ver")):
            raise jwt.InvalidTokenError("Wrong numeric claim type")
        if not verified["sub"] or not verified["jti"]:
            raise jwt.InvalidTokenError("Empty identifier")
        if not 0 < verified["exp"] - verified["iat"] <= 300 or verified["nbf"] >= verified["exp"]:
            raise jwt.InvalidTokenError("Invalid lifetime")
    except jwt.InvalidTokenError:
        raise Unauthenticated("AUTHENTICATION_REQUIRED") from None
    account = accounts.get(verified["sub"])
    if account is None or account["status"] != "active" or account["auth_version"] != verified["ver"]:
        raise Unauthenticated("AUTHENTICATION_REQUIRED")
    return {"subject_id": verified["sub"]}


def expect_rejected(token):
    try:
        verify_access_token(token)
    except Unauthenticated:
        pass
    else:
        raise AssertionError("Untrusted JWT was accepted")


valid = sign_fixture(claims)
assert verify_access_token(valid) == {"subject_id": "user-7"}
for invalid in [
    "broken",
    sign_fixture(claims, key=secrets.token_bytes(64)),
    sign_fixture({**claims, "aud": "other-api"}),
    sign_fixture({**claims, "iss": "https://untrusted.example.test"}),
    sign_fixture({**claims, "exp": now - 60}),
    sign_fixture({**claims, "nbf": now + 60}),
    sign_fixture({field: value for field, value in claims.items() if field != "exp"}),
    sign_fixture(claims, algorithm="HS512"),
    sign_fixture(claims, key=None, algorithm="none"),
    sign_fixture(claims, token_type="JWT"),
    sign_fixture({**claims, "ver": True}),
]:
    expect_rejected(invalid)
accounts["user-7"]["auth_version"] += 1
expect_rejected(valid)
print("happy: verified principal; unhappy: signature/context/time/profile/version rejected")
```

Although `get_unverified_header` has “unverified” in its name, this code reads the type only **after** verifying that same token's signature with fixed policy; it does not select an algorithm or key from the header. The API fixes one issuer and account namespace; multi-issuer systems need a correct issuer/subject mapping and explicit trust configuration.

The `require` option enforces presence, while normal verification options and explicit profile checks enforce meaning. The account/version lookup intentionally adds current state for revocation: this demonstration is not fully stateless. Verification-store outages should fail closed with a controlled server error, not be interpreted as valid identity.

No HTTP server, login endpoint, refresh flow, key vault, key rotation, distributed revocation, or complete protocol implementation is supplied. A real protected bearer endpoint maps invalid credentials to a safe `401` with an applicable challenge and still performs action/resource authorization afterward.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- A simple browser app may be easier to secure with server-side sessions than a custom JWT/refresh-token system.
- Do not put passwords, secrets, or unnecessary personal data in a signed payload; readers can decode it.
- Do not disable signature verification, accept `alg=none`, or compute the allowed algorithm list from the token header.
- Do not accept a correctly signed token for the wrong issuer, audience, purpose, or account state.
- Do not treat a long-lived role claim as permanently current authorization or a `jti` as automatic replay protection.
- Do not distribute an HS256 signing secret to services that should only verify rather than issue tokens.

Signing-key compromise lets attackers mint trusted-looking tokens; expiry alone does not stop newly forged credentials. Incident response needs key retirement, trust distribution, and affected-session/token handling. Rotating keys also requires a deliberate overlap window for legitimately unexpired tokens, unless immediate invalidation is intended.

## 6. How do I know I understand it?

**Blank-page check:** draw the encoded parts and the verifier's trust inputs. Explain why readable claims are not trusted claims, why a valid signature is insufficient, and which checks require current server state.

| Constraint change | Predict the failure and response |
| --- | --- |
| An attacker changes `sub` without the key | Integrity verification must fail |
| Another API receives a valid token | Audience/profile checks reject substitution |
| `exp` is omitted | A verifier that only checks expiry when present is insufficient; require it |
| User is suspended before token expiry | Apply the defined current-state/revocation policy |
| Signing key is shared with a new verifier | Under HMAC that verifier can also mint tokens; reevaluate key/trust design |
| Server clocks differ | Define small intentional leeway and clock synchronization; do not disable time checks |

You understand JWTs when you can distinguish representation, cryptographic authenticity, protocol context, freshness, replay, and resource permissions.
