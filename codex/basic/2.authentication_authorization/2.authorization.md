# Authorization

[Lesson index](../../README.md) · Previous: [Authentication](1.authentication.md) · Next: [User Management](3.user_management.md)

## 1. What is it?

Authorization decides whether a verified caller may perform an action on a specific resource, like an employee badge opening only the rooms assigned to that employee.

Authentication identifies the badge holder; authorization decides which doors open. Knowing a task's ID or having a valid login does not grant access to it.

## 2. Why do we need it?

A backend that checks only “logged in” can let user 7 change `/tasks/43` even when task 43 belongs to someone else. Sequential IDs make this easy to discover, but replacing them with random IDs only makes guessing harder; it does not enforce permission.

Specific failures include cross-tenant data leaks, changing privileged fields through mass assignment, and background jobs bypassing checks that exist only in HTTP controllers.

Authorization makes the policy explicit: which **subject** may perform which **action** on which **resource**, under which **context**. Default denial means missing rules do not accidentally grant new capabilities. See [OWASP's authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

## 3. Under the hood / mechanism / system flow

### 3a. Policy inputs and enforcement costs

Common policy inputs are actor ID, tenant membership, permissions/roles, resource ownership, and relevant state. A policy can be a small predicate, a database query, or an external policy-engine decision. Regardless of implementation, it needs trusted inputs and a mandatory enforcement point.

In an in-memory policy, set membership is expected constant-time. Database membership/resource checks add query work and possibly network I/O; composite indexes help look up `(user_id, tenant_id)` efficiently. An external decision service adds latency and availability concerns. Per-row remote checks on a large list can become an N+1 bottleneck.

Permission caches trade lookup cost for stale access. Cache keys must include all relevant scope, and revocation needs invalidation or a documented freshness window. Never turn a failed policy lookup into an allow decision.

### 3b. Boundary and state-change flow

```text
Authenticate → derive trusted actor → validate requested action/input
    → resolve tenant/resource through policy scope
    → authorize → business checks → coordinated write → safe response
```

Enforce authorization server-side on reads, writes, lists, counts, exports, file downloads, and administrative operations. Hiding a frontend button is usability, not an access boundary. Filter collections to allowed records before pagination/counting so metadata does not leak inaccessible data.

A selected tenant ID may come from a URL, but it is only a selector; verify membership. A role in tenant A must not become global authority in tenant B. See [OWASP's multi-tenant security guidance](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html).

For state-changing operations, avoid checking ownership and then doing an unrelated unconditional update after ownership may have changed. Use a suitable transaction/lock or put relevant access predicates in the write itself. This protects that write's authorization boundary; it does not automatically cancel all work already in flight when permissions are revoked.

Choose public errors deliberately. A known authenticated denial can be `403`; a documented concealment policy can return `404` for both missing and inaccessible resources. Missing/invalid authentication remains a separate `401` path. A dependency failure is not an ordinary policy denial, even when access must be withheld.

## 4. How to apply / implement / use it?

### Define one small policy

For this lesson:

- A member may read tasks in that tenant.
- Only a member who owns a task may rename it.
- No membership, wrong tenant, wrong owner, or missing task means the resource is not visible for that operation.
- Public denial uses `404 TASK_NOT_FOUND` to conceal inaccessible task IDs.
- Writable input is only a validated title; callers cannot change ownership or tenant through this operation.

### Smallest runnable scoped read/write example

Save as `authorization_demo.py`; run `python3 authorization_demo.py`. Uses Python 3 and SQLite. `actor_id` is supplied by authentication, not from request JSON. A client may choose `tenant_id` and `task_id`, but every operation verifies the necessary membership/resource relationship.

```python
import sqlite3


class NotVisible(Exception):
    pass


database = sqlite3.connect(":memory:")
database.row_factory = sqlite3.Row
database.executescript("""
    CREATE TABLE memberships (
        user_id INTEGER NOT NULL, tenant_id INTEGER NOT NULL,
        PRIMARY KEY (user_id, tenant_id)
    );
    CREATE TABLE tasks (
        id INTEGER PRIMARY KEY, tenant_id INTEGER NOT NULL,
        owner_id INTEGER NOT NULL, title TEXT NOT NULL
    );
    INSERT INTO memberships VALUES (7, 1), (8, 1), (9, 2);
    INSERT INTO tasks VALUES
        (42, 1, 7, 'My task'), (43, 1, 8, 'Colleague task'), (44, 2, 9, 'Other tenant');
""")


def read_task(actor_id, tenant_id, task_id):
    row = database.execute(
        "SELECT id, title FROM tasks WHERE id = ? AND tenant_id = ? "
        "AND EXISTS (SELECT 1 FROM memberships "
        "WHERE user_id = ? AND memberships.tenant_id = tasks.tenant_id)",
        (task_id, tenant_id, actor_id),
    ).fetchone()
    if row is None:
        raise NotVisible("TASK_NOT_FOUND")
    return dict(row)


def rename_task(actor_id, tenant_id, task_id, title):
    if not isinstance(title, str) or not 1 <= len(title.strip()) <= 120:
        raise ValueError("INVALID_TITLE")
    with database:
        changed = database.execute(
            "UPDATE tasks SET title = ? WHERE id = ? AND tenant_id = ? AND owner_id = ? "
            "AND EXISTS (SELECT 1 FROM memberships "
            "WHERE user_id = ? AND memberships.tenant_id = tasks.tenant_id)",
            (title.strip(), task_id, tenant_id, actor_id, actor_id),
        )
        if changed.rowcount != 1:
            raise NotVisible("TASK_NOT_FOUND")


rename_task(7, 1, 42, "Renamed")
assert read_task(7, 1, 42) == {"id": 42, "title": "Renamed"}
assert read_task(7, 1, 43)["title"] == "Colleague task"

for operation in [
    lambda: rename_task(7, 1, 43, "Forbidden"),
    lambda: read_task(7, 2, 44),
    lambda: rename_task(7, 2, 44, "Forbidden"),
    lambda: read_task(7, 1, 999),
]:
    try:
        operation()
    except NotVisible as error:
        assert str(error) == "TASK_NOT_FOUND"
    else:
        raise AssertionError("Unauthorized or missing resource was accepted")

assert read_task(8, 1, 43)["title"] == "Colleague task"
with database:
    database.execute("DELETE FROM memberships WHERE user_id = 7 AND tenant_id = 1")
try:
    rename_task(7, 1, 42, "After revocation")
except NotVisible:
    pass
else:
    raise AssertionError("Revoked member retained access")
assert database.execute("SELECT title FROM tasks WHERE id = 42").fetchone()[0] == "Renamed"
print("happy: scoped access; unhappy: wrong owner/tenant/missing/revoked denied without writes")
database.close()
```

The SQL statement evaluates membership, tenant, and ownership as part of the update. Failed access changes zero rows; an adapter translates `NotVisible` to the chosen `404`, not to a success response. Reads return a public projection, not the full internal row.

The fixture assumes authentication has checked account status and that membership rows are current. Production code also needs account-lifecycle integration, safe administrative membership changes, suitable indexes, audits, and a concurrency policy for the chosen database. The final direct `SELECT` is test inspection, not an unprotected application endpoint.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not skip an access decision for protected data. Public access is an explicit policy, not a missing check.
- Do not introduce an external policy engine for three simple ownership checks unless its operational cost is justified.
- Do not scatter `if user.isAdmin` across handlers; centralize understandable policy while keeping enforcement unavoidable.
- Do not accept `ownerId`, `tenantId`, or `role` from a body as proof of permission.
- Do not assume a successful check at enqueue time grants a worker permanent authority; define execution-time checks and service identity/delegation.
- Do not expose every internal field after a successful row-level check; field-level disclosure and mutation need policy too.

Checking every operation costs complexity and sometimes I/O. Removing checks is not the optimization: use scoped queries, appropriate indexes, and carefully invalidated policy data. Database row-level security can add defense in depth, but requires correct connection/session context and does not replace every application-level decision.

## 6. How do I know I understand it?

**Blank-page check:** write a subject/action/resource/context matrix before code. For each allowed case, add a missing-login case, another owner, another tenant, missing membership, and a missing resource. State the public response and prove denied writes leave state unchanged.

| Constraint change | Predict the failure and response |
| --- | --- |
| IDs change from integers to UUIDs | Guessing becomes harder; authorization is still required |
| Feature adds an export route | Apply the same visibility policy to rows, counts, and files |
| Membership is cached for one hour | Revocation can lag for an hour unless invalidated or rechecked |
| A background worker invokes the service directly | It needs explicit identity/delegation and shared enforcement, not controller-only checks |
| Ownership changes during an edit | Couple authorization to the write using appropriate predicates/coordination |

You understand authorization when you can explain not only why an allowed request succeeds, but why every alternative entry point and cross-user/tenant request remains denied.
