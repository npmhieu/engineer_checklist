# Integration Test

[Lesson index](../../README.md) · Previous: [Unit Test](1.unit_test.md) · Next section: [Git](../7.development_operations/1.git.md)

## 1. What is it?

An integration test checks whether real components cooperate across a chosen boundary, like testing a cash register connected to its actual receipt printer rather than testing each separately.

The boundary must be named: repository plus database, HTTP router plus application, or client plus a provider sandbox are different scopes. Integration is not automatically full end-to-end testing.

## 2. Why do we need it?

A fake repository may accept values that the real database rejects, omit required transaction behavior, or return a different type. Unit tests can all pass while SQL uses the wrong column name.

Specific pain: a foreign key is declared but disabled on real connections, or an application returns success before a write is committed.

## 3. Under the hood / mechanism / system flow

### 3a. Real boundaries and fixtures

Use actual relevant libraries/engines, controlled schemas, isolated fixture data, and reliable cleanup. Containers or disposable databases can approximate production dependencies; SQLite is not proof of PostgreSQL-specific SQL, locking, or isolation semantics.

Setup and I/O make tests slower and failures less localized. Capture useful diagnostics without leaking secrets. Per-test transactions can help isolation but may hide behavior requiring separate connections or real commits. See [unittest fixture handling](https://docs.python.org/3/library/unittest.html) and [SQLite foreign-key requirements](https://www.sqlite.org/foreignkeys.html).

### 3b. Test lifecycle

```text
Create isolated dependency → initialize schema → seed known data
    → invoke real boundary → assert persisted result/failure → clean up
```

For concurrency tests, use independent connections/processes against shared storage; two independent `:memory:` databases do not test competing writes to one database. Avoid relying on random sleeps as synchronization.

## 4. How to apply / implement / use it?

Save as `integration_test_demo.py`; run `python3 integration_test_demo.py`. This tests real SQLite file persistence, uniqueness, foreign keys, and rollback; it does not contact a production database.

```python
from pathlib import Path
import sqlite3
import tempfile
import unittest

class DatabaseIntegrationTests(unittest.TestCase):
    def connect(self):
        connection = sqlite3.connect(self.path)
        connection.execute("PRAGMA foreign_keys = ON")
        return connection

    def setUp(self):
        self.directory = tempfile.TemporaryDirectory()
        self.path = Path(self.directory.name) / "test.sqlite"
        self.database = self.connect()
        self.database.executescript("""
            CREATE TABLE users (id INTEGER PRIMARY KEY, email TEXT UNIQUE NOT NULL);
            CREATE TABLE tasks (id INTEGER PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES users(id));
        """)

    def tearDown(self):
        self.database.close()
        self.directory.cleanup()

    def test_commit_survives_new_connection(self):
        with self.database:
            self.database.execute("INSERT INTO users VALUES (?, ?)", (7, "learner@example.test"))
        self.database.close()
        self.database = self.connect()
        self.assertEqual(self.database.execute("SELECT email FROM users WHERE id = 7").fetchone()[0], "learner@example.test")

    def test_batch_rolls_back_on_duplicate(self):
        with self.assertRaises(sqlite3.IntegrityError):
            with self.database:
                self.database.execute("INSERT INTO users VALUES (1, 'same@example.test')")
                self.database.execute("INSERT INTO users VALUES (2, 'same@example.test')")
        self.assertEqual(self.database.execute("SELECT COUNT(*) FROM users").fetchone()[0], 0)

    def test_missing_parent_is_rejected(self):
        with self.assertRaises(sqlite3.IntegrityError):
            with self.database:
                self.database.execute("INSERT INTO tasks VALUES (1, 999)")
        self.assertEqual(self.database.execute("SELECT COUNT(*) FROM tasks").fetchone()[0], 0)

if __name__ == "__main__":
    unittest.main(verbosity=2)
```

Each case gets its own database file. The first test deliberately closes/reopens so an uncommitted in-memory observation is insufficient. The constraint cases assert both the error and persistent state afterward.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Pure arithmetic does not need a database integration fixture.
- Do not run destructive tests against shared production data or real customer accounts.
- Do not replace the very dependency being tested with a mock and still claim its integration is proven.
- Do not depend on test order, shared mutable external accounts, or uncontrolled internet services.

Use provider sandboxes/contract tests intentionally and keep failure costs bounded. Select a small useful suite rather than treating every test as an all-system deployment.

## 6. How do I know I understand it?

**Blank-page check:** name the real boundary, fixture lifecycle, observable assertions, and what a successful run does not prove.

| Constraint change | Predict the failure and response |
| --- | --- |
| Production switches database engine | Add tests against that engine; SQLite compatibility is insufficient evidence |
| Two workers must compete | Use separate connections and deterministic synchronization |
| Tests run in parallel | Isolate data/schema/ports so cases cannot interfere |
| A migration upgrades old records | Test upgrades from representative previous state, not only clean setup |

You understand integration testing when a real boundary is exercised safely and its failure semantics are asserted, not assumed.
