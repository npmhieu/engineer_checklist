# File Storage

[Lesson index](../../README.md) · Previous: [File Upload](1.file_upload.md) · Next: [Notifications](3.notifications.md)

## 1. What is it?

File storage keeps and retrieves byte objects using controlled identities and metadata, like a warehouse locating parcels by inventory IDs rather than trusting labels supplied by visitors.

Storage is not the same as upload: files may also be generated by exports, jobs, or other services.

## 2. Why do we need it?

Saving attachments inside one container loses them on replacement and makes other replicas unable to serve them. Public raw paths can bypass ownership checks.

Specific pain: task metadata says a file exists, but its bytes are missing—or a user downloads another tenant's object by changing its key.

## 3. Under the hood / mechanism / system flow

### 3a. Filesystem versus object store

A filesystem uses paths/directories and filesystem operations; an object service exposes keys, byte objects, metadata, and service-specific request semantics. Object-key prefixes are not automatically POSIX directories. Large reads consume bandwidth/memory, and remote operations add latency and request costs. See [Amazon S3's storage overview](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html) for one concrete object model.

Metadata commonly stores owner/tenant, key, size, content type, digest, and lifecycle status. Integrity checks detect changed bytes, not whether the original upload was safe. Availability, durability, versioning, retention, backup, and disaster recovery are different properties.

### 3b. Metadata/object boundary

```text
Authorized producer → generated key → store bytes → mark metadata ready
Authorized reader → metadata lookup + policy → controlled byte retrieval
Delete/retire → coordinate metadata + object cleanup/reconciliation
```

A database transaction normally cannot roll back an independent object-store write. Pending states and reconciliation handle orphaned/missing objects. Signed URLs delegate limited access until their expiry; treat them as bearer capabilities, not permanent public identifiers.

## 4. How to apply / implement / use it?

Save as `file_storage_demo.py`; run `python3 file_storage_demo.py`. A private temporary directory stands in for storage; upload validation already happened.

```python
import hashlib
from pathlib import Path
import tempfile
import uuid

metadata = {}

def store(root, owner_id, content):
    key = uuid.uuid4().hex
    with (root / key).open("xb") as target:
        target.write(content)
    metadata[key] = {"owner": owner_id, "size": len(content), "digest": hashlib.sha256(content).hexdigest()}
    return key

def retrieve(root, actor_id, key):
    record = metadata.get(key)
    if record is None or record["owner"] != actor_id:
        raise LookupError("FILE_NOT_FOUND")
    content = (root / key).read_bytes()
    if len(content) != record["size"] or hashlib.sha256(content).hexdigest() != record["digest"]:
        raise OSError("STORAGE_INTEGRITY_FAILURE")
    return content

with tempfile.TemporaryDirectory() as directory:
    root = Path(directory)
    key = store(root, 7, b"validated content")
    assert retrieve(root, 7, key) == b"validated content"
    try:
        retrieve(root, 8, key)
    except LookupError:
        pass
    else:
        raise AssertionError("Ownership was bypassed")
    (root / key).write_bytes(b"corrupted")
    try:
        retrieve(root, 7, key)
    except OSError:
        pass
    else:
        raise AssertionError("Corruption was hidden")
print("happy: owner retrieves bytes; unhappy: wrong owner/corruption rejected")
```

Only server-generated keys enter metadata. A real implementation must protect metadata writes, persist it durably, stream large objects, and reconcile write failures. This in-memory catalog plus local file is not an atomic or replicated storage system; raw storage errors should become safe API failures, not filesystem-path disclosures.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- A small transactional blob may fit a database; do not force every byte into an object service without measuring.
- Do not make the whole bucket public to simplify private downloads.
- Do not rely on container-local files for shared persistent assets.
- Do not equate replication/versioning with tested backups or complete privacy erasure.

Remote storage introduces service permissions, network failures, lifecycle costs, and metadata consistency work. Select for access patterns and operational requirements.

## 6. How do I know I understand it?

**Blank-page check:** separate object identity, owner, integrity, publication state, and retrieval authorization. Draw failures between metadata and byte writes.

| Constraint change | Predict the failure and response |
| --- | --- |
| A second replica serves downloads | Use shared storage and authoritative metadata |
| Object write succeeds but DB commit fails | Reconcile the orphan instead of claiming cross-system rollback |
| Download link is forwarded | A bearer URL may work until expiry; scope and lifetime matter |
| Object becomes very large | Stream/range-read appropriately rather than buffering all bytes |

You understand storage when a file's existence, accessibility, integrity, and recovery story are independently clear.
