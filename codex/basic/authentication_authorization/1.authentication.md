# Authentication

[Lesson index](../../README.md) · Previous section: [Idempotency Basics](../api_application/12.idempotency_basics.md) · Next: [Authorization](2.authorization.md)

## 1. What is it?

Authentication verifies which identity a caller can prove control of, like a receptionist checking your badge before identifying you as an employee.

It answers **“Who is this caller?”**, not **“What may this caller do?”** A user ID, email address, or role written in a request is a claim, not proof. Authentication also does not necessarily establish a person's legal identity: control of an account and real-world identity proofing are different things.

| Concept | Example |
| --- | --- |
| Identification | Caller claims account `user-7` |
| Authentication, AuthN | Server verifies an authenticator bound to that account |
| Authorization, AuthZ | Server decides whether that account may rename task 42 |

## 2. Why do we need it?

Without a trusted identity boundary, anyone could send `{"userId":7}` and impersonate user 7. Audit records would identify whoever the caller claimed to be, rather than whoever demonstrated control of a credential.

Specific failures include account impersonation, stolen credentials remaining usable after suspension, and a backend treating an unverified token payload as established identity. Authentication creates trusted request context for subsequent policy checks; it does not replace those checks.

## 3. Under the hood / mechanism / system flow

### 3a. Authenticators and verification one layer down

Different authenticators provide different evidence:

- **Password:** compare against an adaptive, salted password hash using a maintained password-verification library. A salt distinguishes stored hashes; the work factor makes guessing deliberately expensive. Plain SHA-256 is not suitable password storage. See [OWASP's password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
- **Opaque bearer credential:** generate a high-entropy secret, store a lookup record bound to an identity, and verify possession, expiry, and current account state. A hash of a random secret can be stored instead of the secret itself.
- **Passkey:** a protocol verifies a signature over a challenge and relevant origin/relying-party context; the server stores a public credential rather than a shared password. Use a maintained protocol implementation.
- **Federated sign-in:** a trusted identity provider authenticates the user. An OpenID Connect client validates protocol responses and binds the verified identity to a local account; OAuth access delegation alone is not a substitute for an identity protocol. See [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html).

Password verification intentionally consumes CPU and sometimes substantial memory; login throttling is therefore also a capacity concern. Opaque credentials require a store/cache lookup, while signed credentials require cryptographic verification and potentially key retrieval. Cached identity/state data reduces I/O but delays suspension or revocation unless invalidation is designed explicitly.

The runnable example uses a random bearer credential. Hashing it is roughly linear in the bounded token length; an in-memory dictionary lookup is expected constant-time. A real shared store adds network/storage latency. Random high-entropy secrets are not human-chosen passwords: the fast token hash below must not be copied into password storage.

### 3b. Initial sign-in versus later requests

```text
Enrollment/provisioning → authenticator bound to identity
Initial sign-in → verify proof → establish authenticated session/context
Later request → verify session/credential + expiry + account state
    → trusted principal → authorization → business operation
```

A verified principal contains a stable server-side identity, not arbitrary client-supplied ownership or administrator flags. Authentication middleware may run before handlers, but workers and internal APIs also need trusted identities. An identity header is trustworthy only when an authenticated gateway sets it and the backend rejects spoofed/direct bypass traffic.

For protected HTTP bearer endpoints, missing/invalid credentials produce `401` with an applicable `WWW-Authenticate` challenge. An authenticated caller lacking a permission commonly receives `403`, or a documented `404` concealment response. [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html#section-3) describes bearer challenges and errors.

Use HTTPS for credentials. For browser cookie sessions, use appropriate `Secure`, `HttpOnly`, and `SameSite` settings plus a deliberate CSRF defense; authentication alone does not stop cross-site request forgery. Rotate session identifiers on authentication/privilege changes where appropriate. See [OWASP's session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

## 4. How to apply / implement / use it?

### Smallest runnable credential-verification example

Save as `authentication_demo.py`; run `python3 authentication_demo.py`. Requires Python 3 only. This demonstrates a **pre-provisioned machine-client bearer credential**, not a password login, identity-provider integration, or production token-issuance endpoint.

The fixture represents a trusted administrator provisioning a credential for an existing service account. Never expose an unauthenticated “give me a token for this user ID” route. The raw credential must reach its intended client through a secure provisioning channel and must not be logged.

```python
import hashlib
import secrets
import time
from dataclasses import dataclass


class Unauthenticated(Exception):
    pass


@dataclass(frozen=True)
class Principal:
    subject_id: int


accounts = {7: {"status": "active"}}
raw_credential = secrets.token_urlsafe(32)
credential_digest = hashlib.sha256(raw_credential.encode("ascii")).hexdigest()
credentials = {
    credential_digest: {"subject_id": 7, "expires_at": 2000},
}


def authenticate(authorization, now=None):
    if now is None:
        now = time.time()
    if not isinstance(authorization, str) or len(authorization) > 300:
        raise Unauthenticated("AUTHENTICATION_REQUIRED")
    scheme, separator, token = authorization.partition(" ")
    if scheme.lower() != "bearer" or not separator or not token:
        raise Unauthenticated("AUTHENTICATION_REQUIRED")
    if not token.isascii() or any(character.isspace() for character in token):
        raise Unauthenticated("AUTHENTICATION_REQUIRED")
    digest = hashlib.sha256(token.encode("ascii")).hexdigest()
    record = credentials.get(digest)
    if record is None or now >= record["expires_at"]:
        raise Unauthenticated("AUTHENTICATION_REQUIRED")
    account = accounts.get(record["subject_id"])
    if account is None or account["status"] != "active":
        raise Unauthenticated("AUTHENTICATION_REQUIRED")
    return Principal(subject_id=record["subject_id"])


def expect_rejected(header, now=1000):
    try:
        authenticate(header, now=now)
    except Unauthenticated as error:
        assert str(error) == "AUTHENTICATION_REQUIRED"
    else:
        raise AssertionError("Untrusted credential was accepted")


header = "Bearer " + raw_credential
assert authenticate(header, now=1000) == Principal(subject_id=7)
expect_rejected(None)
expect_rejected("Bearer incorrect")
expect_rejected(header, now=2000)
accounts[7]["status"] = "suspended"
expect_rejected(header)
accounts[7]["status"] = "active"
del credentials[credential_digest]
expect_rejected(header)
print("happy: verified principal; unhappy: missing/wrong/expired/suspended/revoked rejected")
```

Time is injected for deterministic expiry tests; callers of a real API cannot choose server time. The raw secret is never returned in the principal, printed, or stored as the lookup key. A bearer credential proves possession, so a stolen valid credential can impersonate its subject until rejected; hashing stored tokens does not stop theft from a client or network leak.

An HTTP adapter would translate `Unauthenticated` into a safe `401` and challenge. It must not turn a credential-store outage into successful authentication; unavailable verification infrastructure is a controlled server failure, not permission to trust the caller. The example has no server, persistence, rate limiter, secure provisioning channel, or production clock/revocation architecture.

For human login, prefer an established authentication framework or identity provider with appropriate MFA/passkey and recovery support. Return generic public authentication failures, limit automated guessing, and audit security events without passwords or bearer secrets. See [OWASP's authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Public content may intentionally permit anonymous access; do not require account creation without a product/security reason.
- Do not implement your own password hashing or passkey/OIDC protocol when maintained libraries cover the requirement.
- Do not treat a decoded JWT payload, client-provided user ID, or browser `isLoggedIn` flag as verified identity.
- Do not treat authentication as permission to every resource or as proof that a human is operating the client.
- Do not put reusable credentials into URLs, logs, or ordinary analytics events.
- Do not require password re-entry on every request; use an appropriate session mechanism and step-up authentication for sensitive actions.

Centralized identity adds dependency and configuration risk; local credentials add recovery, abuse prevention, and credential-storage responsibilities. Choose assurance appropriate to the threat model rather than assuming every credential proves the same thing.

## 6. How do I know I understand it?

**Blank-page check:** draw enrollment, initial proof verification, later credential verification, trusted principal creation, and authorization as distinct steps. Explain what an attacker gains by stealing a valid bearer credential and what the server must still check.

| Constraint change | Predict the failure and response |
| --- | --- |
| Caller changes `userId` in JSON | Ignore it as identity evidence; derive the actor from verified credentials |
| Credential remains cryptographically valid after suspension | Check current state or implement an explicit bounded revocation strategy |
| Verification store becomes unavailable | Fail closed; report a controlled server failure rather than grant access |
| Service runs on several replicas | Use shared credential/revocation state or a deliberate distributed verification design |
| A human login is now required | Add a real enrollment/login/recovery flow; the provisioning fixture is not a login system |

You understand authentication when you can identify the proof, its trusted verifier, its limitations, and where untrusted claims become trusted request context.
