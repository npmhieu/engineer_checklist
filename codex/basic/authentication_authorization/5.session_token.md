# Session / Token

[Lesson index](../../README.md) · Previous: [Role-Based Access Control](4.role_based_access_control.md) · Next: [JWT Basics](6.jwt_basics.md)

## 1. What is it?

A session preserves authenticated continuity across requests, while a token carries evidence used to resume that context or request access—like a hotel keeping your reservation while a key card lets you return to your room.

These terms describe different things, not competing technologies:

| Term | Meaning |
| --- | --- |
| Session | A continuing authenticated interaction, with lifecycle/state |
| Token | A value representing a credential, claim, reference, or limited-purpose proof |
| Cookie | A browser storage/transport mechanism that can carry a session token |
| Opaque token | An uninterpreted random reference; the server resolves its meaning |
| JWT | A structured token format; signing does not encrypt its claims |
| Access token | Credential presented to an intended resource/API |
| Refresh token | Credential used at an authorization service to obtain replacement access tokens |

A JWT can participate in a session, and a cookie can carry either an opaque identifier or a structured token. Not every token is a login session: email-verification and password-reset tokens have distinct purposes.

## 2. Why do we need it?

HTTP does not automatically remember a successful login. Sending a password on every request repeatedly exposes a valuable credential and makes expensive password verification part of every operation.

A session/token mechanism lets subsequent requests present a narrower, expiring credential. Specific failures it must handle include stolen credentials remaining valid after logout, attacker-chosen session IDs surviving login (session fixation), and one server replica rejecting sessions created by another.

Keeping a browser's `isLoggedIn` flag is not enough: every protected backend request must establish trusted context again from accepted evidence.

## 3. Under the hood / mechanism / system flow

### 3a. Storage and verification one layer down

For an opaque server-side session, a record commonly stores a token digest, user ID, creation time, last activity, absolute expiry, and security version. A cryptographically random token is given to the client; the server can store its digest instead of the reusable secret.

In memory, digest lookup is expected `O(1)`; an indexed database lookup is commonly logarithmic index work plus I/O. A remote cache/store adds network latency. Updating last activity on every request creates extra writes; reducing that frequency requires a carefully defined idle-timeout policy. Expired records also need cleanup—rejecting them during lookup does not reclaim all unused records automatically.

Structured signed tokens can avoid a per-token lookup for basic signature/claim verification, but current-account, policy, or revocation checks may still require state. Neither design makes authorization unnecessary.

Random high-entropy token digests can use a fast cryptographic hash; human-chosen passwords need a slow adaptive password hash. Do not copy a session-token hash into password storage. [OWASP's session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) explains identifier generation, storage, rotation, and expiry.

### 3b. Browser, server, and lifecycle boundaries

```text
Successful authentication → new session identifier → secure delivery
    → later request presents token → expiry/state/version check
    → trusted principal → current authorization → operation
Logout / expiry / revocation → reject future use of that credential
```

An **idle timeout** expires an inactive session; an **absolute timeout** expires it despite ongoing use. Identifier rotation replaces the bearer secret and invalidates its predecessor. Rotation should not silently restart an absolute lifetime unless a deliberate reauthentication policy permits a new lifetime.

For a same-site browser app, a server-managed cookie might be set as follows over HTTPS:

```http
Set-Cookie: __Host-session=<random-secret>; Path=/; Secure; HttpOnly; SameSite=Lax
Cache-Control: no-store
```

`__Host-` requires `Secure`, `Path=/`, and no `Domain`. `HttpOnly` prevents ordinary JavaScript reads, not authenticated requests made by injected scripts. `SameSite` reduces some cross-site cookie sending but is not a complete CSRF strategy for every deployment. Protect state-changing cookie-authenticated operations with appropriate CSRF defenses; do not mutate state through GET. Browser-session cookies still need server-enforced expiry.

Logout must invalidate server-side access where the design requires it and clear the matching browser cookie; deleting only local storage does not invalidate a copied bearer credential. Account-wide security versions can reject sessions issued before a password reset/suspension when each verifier actually checks them.

For OAuth refresh flows, refresh tokens go to their intended authorization endpoint, not arbitrary resource APIs. Rotation/reuse detection must be atomic and have explicit family-revocation and concurrency/recovery rules. [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14) describes refresh-token protections. Access-token expiry is not automatically refresh-token expiry.

## 4. How to apply / implement / use it?

### Smallest runnable opaque-session lifecycle

Save as `session_token_demo.py`; run `python3 session_token_demo.py`. Python 3 standard library only. This tests a single-process session store, not HTTP cookies, OAuth refresh tokens, or a login endpoint.

`create_session` is called **only after successful authentication** for an already trusted user ID; it must not become a public “issue a session for this ID” route. Test timestamps stand in for server time, never client-supplied time.

```python
import hashlib
import secrets


class Unauthenticated(Exception):
    pass


IDLE_SECONDS = 60
ABSOLUTE_SECONDS = 600
accounts = {7: {"status": "active", "auth_version": 0}}
sessions = {}


def digest_token(token):
    if not isinstance(token, str) or not 1 <= len(token) <= 256 or not token.isascii():
        raise Unauthenticated("AUTHENTICATION_REQUIRED")
    return hashlib.sha256(token.encode("ascii")).hexdigest()


def create_session(authenticated_user_id, now):
    account = accounts.get(authenticated_user_id)
    if account is None or account["status"] != "active":
        raise Unauthenticated("AUTHENTICATION_REQUIRED")
    token = secrets.token_urlsafe(32)
    sessions[digest_token(token)] = {
        "user_id": authenticated_user_id, "created_at": now, "last_seen": now,
        "auth_version": account["auth_version"],
    }
    return token


def verify_session(token, now):
    digest = digest_token(token)
    record = sessions.get(digest)
    if record is None:
        raise Unauthenticated("AUTHENTICATION_REQUIRED")
    account = accounts.get(record["user_id"])
    expired = now >= record["created_at"] + ABSOLUTE_SECONDS or now >= record["last_seen"] + IDLE_SECONDS
    invalid_account = account is None or account["status"] != "active"
    if expired or invalid_account or account["auth_version"] != record["auth_version"]:
        sessions.pop(digest, None)
        raise Unauthenticated("AUTHENTICATION_REQUIRED")
    record["last_seen"] = now
    return record["user_id"]


def rotate_session(token, now):
    verify_session(token, now)
    previous = digest_token(token)
    replacement = secrets.token_urlsafe(32)
    sessions[digest_token(replacement)] = dict(sessions[previous])
    del sessions[previous]
    return replacement


def logout(token):
    sessions.pop(digest_token(token), None)


def expect_rejected(token, now):
    try:
        verify_session(token, now)
    except Unauthenticated:
        pass
    else:
        raise AssertionError("Invalid session was accepted")


original = create_session(7, now=1000)
assert verify_session(original, now=1010) == 7
replacement = rotate_session(original, now=1020)
expect_rejected(original, now=1021)
assert verify_session(replacement, now=1030) == 7
expect_rejected(replacement, now=1090)

absolute = create_session(7, now=1000)
for now in range(1050, 1600, 50):
    assert verify_session(absolute, now=now) == 7
expect_rejected(absolute, now=1600)

logged_out = create_session(7, now=2000)
logout(logged_out)
expect_rejected(logged_out, now=2001)
revoked = create_session(7, now=2000)
accounts[7]["auth_version"] += 1
expect_rejected(revoked, now=2001)
expect_rejected("unknown", now=2001)
print("happy: resume and rotate; unhappy: old/idle/absolute/logout/version/unknown rejected")
```

Rotation copies `created_at`, preserving the absolute deadline. Tokens are never printed. A real adapter sends a safe authentication failure and applicable challenge for protected bearer routes, or follows its documented browser-login flow; it must not silently grant access when the store fails.

This dictionary implementation is single-threaded and non-durable. A shared implementation needs atomic verification/update/rotation and a revocation policy under races, shared state across replicas, secure clocks, cleanup, and transport protections. Cookie deletion and CSRF handling belong in an actual HTTP integration, not this function-only example.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Anonymous public endpoints may not need a session. Do not create persistent identity state without a reason.
- Do not store sessions only in one process when requests can land on several replicas; sticky routing alone does not solve restarts or revocation.
- Do not treat “cookie versus JWT” as “stateful versus stateless”: cookies are transport, JWT is a format, and either design may consult state.
- Do not put bearer secrets into URLs, logs, or analytics. Browser storage readable by JavaScript increases token-theft exposure under XSS.
- Do not refresh/rotate by issuing a replacement and deleting the predecessor in unrelated uncoordinated writes.
- Do not confuse a sliding activity timeout with infinite authenticated lifetime or a refresh token with permission to every API.

Server-side sessions add store dependency and cleanup work but can simplify centralized revocation. Signed-token approaches shift cost toward key lifecycle, claim validation, expiry, and freshness policy. Choose for client type, trust boundaries, and revocation needs—not fashion.

## 6. How do I know I understand it?

**Blank-page check:** draw the session record, client-held secret, verification path, idle/absolute deadlines, rotation, and logout. Explain which state changes reject a copied credential and which browser-only actions do not.

| Constraint change | Predict the failure and response |
| --- | --- |
| A second API replica receives the request | It needs the same session truth or an explicit distributed design |
| Requests arrive continuously | Idle expiry slides; absolute expiry must still apply |
| User deletes a cookie but attacker copied it | Server-side invalidation is still necessary under the logout contract |
| Two refresh/rotation requests race | Coordinate atomically and define replay/concurrency behavior |
| Permissions change during a session | Authentication continuity does not freeze authorization forever |

You understand sessions and tokens when you can separate identity continuity, credential representation, browser transport, authorization, and revocation.
