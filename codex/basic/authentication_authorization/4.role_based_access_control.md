# Role-Based Access Control (RBAC)

[Lesson index](../../README.md) · Previous: [User Management](3.user_management.md) · Next: [Session / Token](5.session_token.md)

## 1. What is it?

Role-based access control groups permissions into named roles and assigns those roles to users, like giving an editor a standard set of document tools instead of configuring each tool separately.

RBAC is one way to implement **authorization**, not authentication. A role is a bundle of permissions, not proof of identity and not automatically a global privilege.

```text
User → scoped role assignment → role permissions → allowed operation
```

## 2. Why do we need it?

Assigning every permission directly to every user becomes hard to review and update. If 100 editors all need a newly introduced edit permission, a role definition lets one controlled policy change express that intent.

Specific failures include inconsistent permission lists, forgotten access after job changes, and treating a tenant administrator as an administrator of the entire application. Roles provide an understandable administrative vocabulary, but only if their scope and meaning are explicit.

## 3. Under the hood / mechanism / system flow

### 3a. Relations and effective permissions

A typical relational model has users, roles, permissions, role-permission mappings, and **tenant-scoped user-role assignments**. Membership/account state is checked in addition to role mappings. Composite keys and foreign keys help prevent duplicate or dangling assignments.

With several assigned roles, a basic positive-grant policy computes the union of their permission sets. In-memory set membership is expected constant-time; building the effective set costs roughly the total number of assigned permission entries. Database joins or a policy service add storage/network work. Caching the union speeds repeated decisions but introduces revocation freshness and cache-key risks.

RBAC can include role hierarchies and separation-of-duty constraints; these are explicit policy features, not automatic consequences of naming a role `admin`. The [NIST RBAC project](https://csrc.nist.gov/projects/role-based-access-control) describes the model and its extensions. The example uses flat roles and positive grants only—no hierarchy or explicit-deny precedence.

### 3b. Decision and administrative lifecycle

```text
Verified actor + selected tenant → current account/membership
    → roles assigned in that tenant → effective permissions
    → resource tenant + ownership/context checks → operation

Role administration → separate authority check → assignment change + audit
    → invalidate affected policy/session caches as required
```

Permission labels such as `task.update` are server-owned capabilities. Clients may request an action but cannot select the role used to authorize it. “Admin in tenant 1” must be looked up as `(user, tenant 1)`, not cached as a global `isAdmin=true`.

RBAC alone does not express every relationship. “Editors can update only tasks they own” also needs an ownership predicate. “Do not approve your own expense” needs another constraint even when the role grants approval. These combine RBAC with contextual/attribute/relationship checks; creating a separate role for every record usually produces role explosion.

Removing a role changes future decisions only as quickly as the enforcement system observes it. Roles embedded in long-lived tokens can outlive a database reassignment. Use appropriate current-state checks, policy versions, invalidation, or bounded lifetimes according to the revocation requirement. [OWASP's authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) covers least privilege and permission checks throughout the application.

## 4. How to apply / implement / use it?

### Start with a small policy matrix

Within one tenant:

| Role | Read tasks | Update tasks | Manage members |
| --- | --- | --- | --- |
| Viewer | Yes | No | No |
| Editor | Yes | Own tasks only | No |
| Admin | Yes | Any task in that tenant | Yes |

Ownership limits are an additional policy check, not implied by `task.update`. All roles still require active account/membership and resource scope. The administrator role here is a **tenant administrator**, not an infrastructure/root operator.

### Smallest runnable role-and-resource checks

Save as `rbac_demo.py`; run `python3 rbac_demo.py`. Standard-library Python only. These dictionaries stand in for trusted server-managed policy storage; `actor_id` comes from authentication. There is no API that accepts role assignments from a profile request.

```python
class Denied(Exception):
    pass


ROLE_PERMISSIONS = {
    "viewer": frozenset({"task.read"}),
    "editor": frozenset({"task.read", "task.update"}),
    "admin": frozenset({"task.read", "task.update", "member.manage"}),
}
accounts = {7: "active", 8: "active", 9: "active", 10: "suspended"}
assignments = {
    (7, 1): {"viewer"}, (8, 1): {"editor"},
    (9, 1): {"admin"}, (9, 2): {"viewer"}, (10, 1): {"admin"},
}
tasks = {
    42: {"tenant_id": 1, "owner_id": 8, "title": "Editor task"},
    43: {"tenant_id": 1, "owner_id": 7, "title": "Viewer task"},
    44: {"tenant_id": 2, "owner_id": 9, "title": "Other tenant"},
}


def require_permission(actor_id, tenant_id, permission, task_id=None):
    if accounts.get(actor_id) != "active":
        raise Denied("FORBIDDEN")
    roles = assignments.get((actor_id, tenant_id), set())
    permissions = set()
    for role in roles:
        permissions.update(ROLE_PERMISSIONS.get(role, frozenset()))
    if permission not in permissions:
        raise Denied("FORBIDDEN")
    if permission in {"task.read", "task.update"}:
        task = tasks.get(task_id)
        if task is None or task["tenant_id"] != tenant_id:
            raise Denied("FORBIDDEN")
        if permission == "task.update" and "admin" not in roles and task["owner_id"] != actor_id:
            raise Denied("FORBIDDEN")


def rename_task(actor_id, tenant_id, task_id, title):
    if not isinstance(title, str) or not 1 <= len(title.strip()) <= 120:
        raise ValueError("INVALID_TITLE")
    require_permission(actor_id, tenant_id, "task.update", task_id)
    tasks[task_id]["title"] = title.strip()


require_permission(7, 1, "task.read", 42)
rename_task(8, 1, 42, "Edited by owner")
rename_task(9, 1, 43, "Edited by tenant admin")
require_permission(9, 1, "member.manage")

for operation in [
    lambda: rename_task(7, 1, 43, "Viewer escalation"),
    lambda: rename_task(8, 1, 43, "Not owner"),
    lambda: rename_task(9, 1, 44, "Cross tenant"),
    lambda: rename_task(9, 2, 44, "Admin elsewhere"),
    lambda: rename_task(10, 1, 42, "Suspended admin"),
    lambda: require_permission(9, 1, "unknown.permission"),
]:
    try:
        operation()
    except Denied:
        pass
    else:
        raise AssertionError("Policy granted forbidden access")

assignments[(8, 1)] = {"viewer"}
try:
    rename_task(8, 1, 42, "After role removal")
except Denied:
    pass
else:
    raise AssertionError("Removed edit permission remained usable")
assert tasks[42]["title"] == "Edited by owner"
assert tasks[43]["title"] == "Edited by tenant admin"
assert tasks[44]["title"] == "Other tenant"
print("happy: role plus resource policy; unhappy: escalation/cross-tenant/revoked denied")
```

Presence in the scoped assignment map represents current active membership in this simplified model. No assignment means no permissions; unknown roles grant nothing. A real data model should represent membership state explicitly if it supports pending/suspended memberships.

This single-threaded example checks immediately before an in-memory mutation. It is **not** a transaction/concurrency design: a database implementation must coordinate relevant policy/resource state with its writes, as discussed in the previous lessons. It intentionally omits authentication, role-administration endpoints, audit persistence, and policy caches.

An HTTP adapter can map `Denied` to `403`, or use a consistent concealment policy where appropriate. Administrative role changes need their own permission checks, allowed target/scope rules, and audits. If a product must never lose its last tenant admin, enforce that invariant under concurrency; the role matrix alone does not guarantee it.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- A tiny personal app may need ownership rules without named roles; do not add a role framework automatically.
- Do not use roles alone for document sharing, ownership, time limits, or separation-of-duty rules that need richer relationships/context.
- Do not create roles like `editor_of_task_42` for every object unless the product genuinely models such groups; this often becomes unmanageable.
- Do not trust `role=admin` from a request, UI state, or an unverified token payload.
- Do not conflate a tenant admin, a support operator, and a platform administrator.
- Do not let users change their roles through generic user/profile updates or assume a role-removal database write instantly invalidates every cached claim.

Roles simplify administration when people share stable responsibility bundles. They become expensive when exceptions dominate: role explosion, overlapping grants, migration of renamed permissions, audits, and stale access all need attention. An additive union policy is simple but cannot express an explicit deny that overrides another role without additional rules.

## 6. How do I know I understand it?

**Blank-page check:** draw user-role and role-permission relations, include tenant scope, and compute one user's effective permissions. Then explain why an editor with `task.update` still cannot rename a colleague's task under this lesson's policy.

| Constraint change | Predict the failure and response |
| --- | --- |
| User is admin in A and viewer in B | Evaluate scoped assignments; do not carry A's authority into B |
| Role loses an edit permission | Invalidate/recompute derived policy data according to the freshness requirement |
| Product adds “cannot approve own request” | Add a subject/resource constraint; the approval role alone is insufficient |
| One user has viewer and editor roles | Positive grants union; a viewer role is not an overriding deny |
| Last tenant admin is removed | Guard the administrative invariant with suitable transaction/locking semantics |
| Requirements create thousands of record-specific roles | Reevaluate ownership, sharing relations, or attribute-based policy |

You understand RBAC when you can explain grants, scope, contextual limits, controlled role administration, and revocation—not just check whether a string equals `admin`.
