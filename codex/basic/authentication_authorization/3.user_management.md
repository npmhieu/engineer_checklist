# User Management

[Lesson index](../../README.md) · Previous: [Authorization](2.authorization.md) · Next: [Role-Based Access Control](4.role_based_access_control.md)

## 1. What is it?

User management controls an account's lifecycle and related identity data, like a company's employee records tracking hiring, contact changes, suspension, and departure.

It includes registration/invitation, verification, profile changes, credential recovery, suspension, and retirement. Authentication verifies a caller; user management maintains which accounts exist and what state they are in. Neither replaces authorization for administrative actions.

## 2. Why do we need it?

A login form alone cannot answer who may register, whether an email was verified, how a lost credential is recovered, or how access stops when an account is suspended.

Specific failures include duplicate accounts created by concurrent signups, a verification link reactivating a suspended account, changing a profile field into `isAdmin=true`, and disabled users retaining existing sessions indefinitely.

Managing accounts as unrestricted CRUD hides these transitions. Registration, verification, changing an email, resetting a password, and suspension have different proof, permission, audit, and revocation requirements.

## 3. Under the hood / mechanism / system flow

### 3a. Data model and storage one layer down

A useful conceptual model separates concerns:

| Record | Responsibility |
| --- | --- |
| User | Stable ID, account state, public profile, security version |
| Login identity | Local credential or trusted provider `(issuer, subject)` binding |
| Verification/recovery token | Purpose, secret digest, user, expiry, consumed state |
| Session/credential | Authentication continuity and revocation |
| Tenant membership/role assignment | Access scope, separate from profile fields |
| Audit event | Who performed an administrative/security change |

Use a stable internal ID; an email can change. Unique constraints enforce whichever login-identifier policy the product defines, including its normalization and tenant scope. A pre-insert “email unused” query alone cannot prevent two concurrent inserts.

Indexed identity/token lookup is commonly logarithmic database work; profile writes, audit events, and token/session invalidation add I/O. Verification emails introduce another system boundary: database commit and mail delivery are not one atomic operation. A reliable delivery/outbox mechanism can coordinate retries; avoid sending mail while holding a long database lock.

For federation, do not merge accounts solely because two providers report the same email string. Use the trusted provider identity and an explicit secure linking flow. [OpenID Connect defines the issuer/subject identity relationship](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability).

### 3b. Account-state transitions

```text
Register/invite → pending → prove required control → active
active/pending → authorized suspension → suspended
suspended → separately authorized recovery/reactivation → active
eligible state → explicit retirement/deletion workflow
```

This is one product policy, not a mandatory universal state machine. An unverified user might be allowed limited actions in another product. What matters is that each operation checks allowed transitions; “email verified” must not override suspension.

Email verification proves access to that mailbox at verification time, not a legal identity or permanent account ownership. Recovery tokens must have an explicit purpose, expiry, secure generation/storage, and one-use consumption; verification and password-reset credentials must not be interchangeable. [OWASP's recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) explains token lifecycle and generic public responses.

Account suspension must affect later authentication/authorization, not merely hide the user in an admin screen. Checking current account state, revoking sessions, or comparing a session's security version to the user's current version are possible mechanisms. A self-contained token does not automatically learn about a database status change.

## 4. How to apply / implement / use it?

### Define operation-specific boundaries

| Operation | Required boundary |
| --- | --- |
| Register | Validated identifier, abuse controls, server-selected initial state |
| Verify email | Correct purpose, unexpired one-use proof, allowed account transition |
| Update profile | Authenticated self-service with an explicit writable-field allowlist |
| Change email/password | Appropriate recent proof, verification/recovery policy, notification and revocation decisions |
| Suspend/reactivate | Explicit administrative authority, state-transition rules, audit trail |
| Delete/retire | Ownership/authority, retention policy, related records and credentials handled deliberately |

Do not accept `role`, `status`, `email_verified`, or `auth_version` through a generic self-profile update. Public responses should not expose password hashes, token digests, or security-control fields.

### Smallest runnable account-lifecycle example

Save as `user_management_demo.py`; run `python3 user_management_demo.py`. Standard-library Python and SQLite only. This demonstrates pending registration, one-use email verification, administrative suspension, an audit record, and a security-version check—not a complete registration/login/recovery service.

The code uses already validated, bounded, normalized email strings from an input layer. It does not implement an email parser or prove deliverability by syntax. Returned raw verification tokens go only to a **trusted delivery adapter**, never a public signup response or logs. The fixture's verified operator ID `99` stands in for a real administrative authorization decision.

```python
import hashlib
import secrets
import sqlite3


class InvalidVerification(Exception):
    pass


database = sqlite3.connect(":memory:")
database.execute("PRAGMA foreign_keys = ON")
database.executescript("""
    CREATE TABLE users (
        id INTEGER PRIMARY KEY, email TEXT NOT NULL UNIQUE,
        status TEXT NOT NULL CHECK (status IN ('pending', 'active', 'suspended')),
        auth_version INTEGER NOT NULL DEFAULT 0
    );
    CREATE TABLE email_verifications (
        digest TEXT PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES users(id),
        expires_at INTEGER NOT NULL
    );
    CREATE TABLE audit_events (actor_id INTEGER, user_id INTEGER, action TEXT);
""")


def register(email, now):
    token = secrets.token_urlsafe(32)
    digest = hashlib.sha256(token.encode("ascii")).hexdigest()
    with database:
        created = database.execute(
            "INSERT INTO users (email, status) VALUES (?, 'pending')", (email,)
        )
        user_id = created.lastrowid
        database.execute(
            "INSERT INTO email_verifications VALUES (?, ?, ?)", (digest, user_id, now + 600)
        )
    return user_id, token


def verify_email(token, now):
    if not isinstance(token, str) or not token.isascii() or not 1 <= len(token) <= 256:
        raise InvalidVerification("INVALID_VERIFICATION")
    digest = hashlib.sha256(token.encode("ascii")).hexdigest()
    with database:
        database.execute("BEGIN IMMEDIATE")
        proof = database.execute(
            "SELECT user_id, expires_at FROM email_verifications WHERE digest = ?", (digest,)
        ).fetchone()
        if proof is None or now >= proof[1]:
            raise InvalidVerification("INVALID_VERIFICATION")
        changed = database.execute(
            "UPDATE users SET status = 'active' WHERE id = ? AND status = 'pending'",
            (proof[0],),
        )
        if changed.rowcount != 1:
            raise InvalidVerification("INVALID_VERIFICATION")
        database.execute("DELETE FROM email_verifications WHERE digest = ?", (digest,))
    return proof[0]


def suspend_user(actor_id, user_id):
    if actor_id != 99:
        raise PermissionError("FORBIDDEN")
    with database:
        changed = database.execute(
            "UPDATE users SET status = 'suspended', auth_version = auth_version + 1 "
            "WHERE id = ? AND status IN ('pending', 'active')", (user_id,)
        )
        if changed.rowcount != 1:
            raise ValueError("INVALID_ACCOUNT_TRANSITION")
        database.execute("DELETE FROM email_verifications WHERE user_id = ?", (user_id,))
        database.execute("INSERT INTO audit_events VALUES (?, ?, 'suspend')", (actor_id, user_id))


def account_allows_session(user_id, issued_version):
    row = database.execute("SELECT status, auth_version FROM users WHERE id = ?", (user_id,)).fetchone()
    return row is not None and row[0] == "active" and row[1] == issued_version


user_id, token = register("learner@example.test", now=1000)
assert not account_allows_session(user_id, issued_version=0)
assert verify_email(token, now=1100) == user_id
assert account_allows_session(user_id, issued_version=0)
assert not account_allows_session(user_id, issued_version=1)
try:
    suspend_user(7, user_id)
except PermissionError:
    pass
else:
    raise AssertionError("Unprivileged suspension succeeded")
assert account_allows_session(user_id, issued_version=0)
suspend_user(99, user_id)
assert not account_allows_session(user_id, issued_version=0)

pending_id, pending_token = register("pending@example.test", now=1000)
suspend_user(99, pending_id)
expired_id, expired_token = register("expired@example.test", now=1000)
for candidate, now in [(token, 1200), (pending_token, 1200), (expired_token, 1600), ("wrong", 1200)]:
    try:
        verify_email(candidate, now=now)
    except InvalidVerification:
        pass
    else:
        raise AssertionError("Used/suspended/expired/invalid proof was accepted")

try:
    register("learner@example.test", now=1200)
except sqlite3.IntegrityError:
    pass
else:
    raise AssertionError("Duplicate email bypassed uniqueness")
assert database.execute("SELECT COUNT(*) FROM users").fetchone()[0] == 3
assert database.execute("SELECT COUNT(*) FROM audit_events").fetchone()[0] == 2
print("happy: verify then suspend; unhappy: replay/expiry/state/authority/duplicate rejected")
database.close()
```

The unique email policy is exact equality on the normalized input provided to this layer. Other products may scope identifiers by tenant or allow several identities per account. The caught integrity exception is a test of this fixed schema; production code should classify the specific constraint, not relabel every database failure as “duplicate email.”

Verification consumes the proof and changes state together under a local transaction; [SQLite's write-transaction behavior](https://www.sqlite.org/lang_transaction.html) explains the serialization used here. Suspension also deletes outstanding verification proofs and increments `auth_version`. That version invalidates sessions **only if request verification actually compares it**; the integer is not a remote logout signal by itself. `issued_version` must come from a verified session/credential, not request JSON; this comparison supplements authentication and cannot replace proof of credential possession.

Internal results/errors above are not the public registration contract. A public response can say “If eligible, check your email” without revealing whether an account exists; response timing, rate limits, mail delivery, and recovery flows also need attention. This memory-only demo has no mail sender, stored password, durable sessions, actual reactivation/deletion operation, or production administrative policy.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not build an account system for data that can safely remain anonymous; user accounts create privacy, abuse, and support work.
- Do not implement every lifecycle feature yourself when an established identity system can own credentials and recovery; your application may still own profiles, memberships, and product account state.
- Do not use mutable email addresses as permanent foreign keys across the application.
- Do not let possession of an old verification link override an administrator's suspension.
- Do not assume soft deletion erases personal data, backups, audit events, external copies, or credentials.
- Do not link accounts or change recovery addresses solely on an unverified matching string.

Verification and recovery add friction and delivery dependencies. Retention versus erasure, administrative auditability, and account reactivation need explicit product/security policies. More account states require more allowed-transition tests; deleting rows is not a substitute for designing the lifecycle.

## 6. How do I know I understand it?

**Blank-page check:** draw the account state machine and separately draw credential/session state. For each transition, name the actor, required proof, allowed prior states, atomic writes, audit event, and effect on existing access.

| Constraint change | Predict the failure and response |
| --- | --- |
| Two concurrent signups choose the same identifier | A unique constraint decides the race; keep the public response policy consistent |
| Suspended user clicks an old verification link | Reject it; verification must not reactivate the account |
| Account is disabled while a signed token is still valid | Check state/version or enforce the documented revocation strategy |
| User changes email | Keep stable user ID; verify the new address under a deliberate transition policy |
| Mail delivery fails after registration commits | Retry delivery safely; do not assume the database transaction rolled back |
| External provider reports an existing email | Require secure identity linking rather than silently merging accounts |

You understand user management when accounts, proofs, permissions, and sessions remain consistent through every supported lifecycle transition—not just successful signup.
