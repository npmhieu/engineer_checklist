# Separation of Concerns

[Lesson index](../../README.md) · Previous: [Layered Architecture](2.layered_architecture.md) · Next: [Package / Folder Organization](4.package_folder_organization.md)

## 1. What is it?

Separation of concerns gives distinct responsibilities clear owners, like keeping a recipe separate from the delivery address and the payment terminal.

It is a design principle, not a requirement for one function/class/file per line of behavior.

## 2. Why do we need it?

If calculating an order total also parses HTTP, reads environment variables, and sends email, testing arithmetic requires all those systems. A small formatting change can unexpectedly affect persistence.

Specific pain: a background job copies controller logic and the two implementations slowly disagree about valid prices.

## 3. Under the hood / mechanism / system flow

### 3a. Cohesion, coupling, and effects

Keep closely related policy cohesive and isolate effects behind clear calls. A pure calculation takes values and returns a value; it does not secretly read the clock or network. That makes its cost and test inputs easier to reason about.

Separating policy from effectful adapters improves testability, but too many tiny abstractions increase indirection and navigation cost. Architectural layering is one possible application, not the definition of this principle. See [Microsoft's discussion of responsibilities and dependencies](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures).

### 3b. Shared meaning, separate interfaces

```text
HTTP parser / batch reader → common calculation or use case → chosen output/effect
```

Validation can exist at several boundaries for different reasons: transport checks shape; domain checks invariants. “Do not duplicate code” should not become “let a frontend be the only validator.”

## 4. How to apply / implement / use it?

Save as `concerns_demo.py`; run `python3 concerns_demo.py`. The same money calculation serves two inputs without importing a web framework or database.

```python
import json

def total_cents(quantity, unit_cents):
    if type(quantity) is not int or type(unit_cents) is not int or quantity <= 0 or unit_cents < 0:
        raise ValueError("INVALID_PRICE_INPUT")
    return quantity * unit_cents

def quote_http(body):
    if not isinstance(body, dict) or set(body) != {"quantity", "unit_cents"}:
        return 422, json.dumps({"code": "INVALID_FIELDS"})
    try:
        value = total_cents(body["quantity"], body["unit_cents"])
    except ValueError:
        return 422, json.dumps({"code": "INVALID_PRICE_INPUT"})
    return 200, json.dumps({"total_cents": value})

def quote_batch(rows):
    return [total_cents(quantity, price) for quantity, price in rows]

assert json.loads(quote_http({"quantity": 2, "unit_cents": 150})[1])["total_cents"] == 300
assert quote_batch([(2, 150), (1, 99)]) == [300, 99]
assert quote_http({"quantity": -1, "unit_cents": 150})[0] == 422
try:
    quote_batch([(True, 150)])
except ValueError:
    pass
else:
    raise AssertionError("Non-domain input bypassed shared rule")
print("happy: shared policy, distinct adapters; unhappy: invalid values rejected in both paths")
```

The fixture deliberately uses one currency/minor-unit policy and no tax/rounding engine. Adding persistence or notifications should not make `total_cents` depend on their availability.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not split tightly coupled invariants so no operation can enforce them coherently.
- Do not create a generic abstraction for unrelated logic just because both functions use strings.
- Do not fragment a small module into dozens of files without a change/testing benefit.
- Do not move complexity into a service locator that hides dependencies.

Separation should make change and ownership easier, not maximize the number of interfaces.

## 6. How do I know I understand it?

**Blank-page check:** list which concerns change for a new transport, a new tax policy, and a new email provider. Identify the minimal owner of each change.

| Constraint change | Predict the failure and response |
| --- | --- |
| A CLI replaces HTTP | Core arithmetic should remain usable |
| Currency scale changes | Change the explicit money policy, not a hidden formatter assumption |
| Mail service is down | Pure pricing should not fail because of unrelated delivery |
| Two values must change atomically | Keep their invariant coordinated despite separate adapters |

You understand the principle when boundaries reduce accidental coupling without scattering one invariant across unrelated owners.
