# Package / Folder Organization

[Lesson index](../../README.md) · Previous: [Separation of Concerns](3.separation_of_concerns.md) · Next: [Dependency Direction](5.dependency_direction.md)

## 1. What is it?

Package/folder organization groups code into discoverable modules with intended public boundaries, like labeled workshop drawers that also specify which tools other teams may borrow.

Folders aid navigation; import rules, exports, review, and tests enforce architecture. A directory name alone is not an isolation boundary.

## 2. Why do we need it?

A global `utils` folder becomes a dependency magnet, while one feature change touches controllers/services/models scattered everywhere. Circular imports and startup side effects make simple tests difficult to run.

Specific pain: importing a price function unexpectedly opens a database or starts a worker because an entry-point file also owns reusable logic.

## 3. Under the hood / mechanism / system flow

### 3a. Module loading and visibility

Python resolves modules on its import path, executes top-level code on initial import, and caches loaded modules. Imports can therefore perform unexpected I/O if modules do too much at the top level. Cycles can expose partially initialized modules. See [Python's module/package tutorial](https://docs.python.org/3/tutorial/modules.html).

Organizing by feature favors change locality; organizing by technical layer can clarify roles. A hybrid such as `tasks/domain.py`, `tasks/service.py`, and `tasks/adapters/` can express both. Neither pattern automatically prevents internal imports.

### 3b. Public API and composition root

```text
Entry point/composition root → supported feature interface → owned internals
Tests import reusable modules without starting the whole application
```

Keep server/worker startup behind explicit entry points. Avoid shadowing standard-library names such as `logging.py`, and avoid one feature importing another's private database details without a deliberate contract.

## 4. How to apply / implement / use it?

Save as `packages_demo.py`; run `python3 packages_demo.py`. It creates a temporary package, runs its entry point, and proves an invalid domain call fails. It writes no files into this repository.

```python
from pathlib import Path
import subprocess
import sys
import tempfile

sources = {
    "shop/__init__.py": "",
    "shop/domain.py": "def double_quantity(quantity):\n    if type(quantity) is not int or quantity <= 0:\n        raise ValueError('INVALID_QUANTITY')\n    return quantity * 2\n",
    "shop/service.py": "from .domain import double_quantity\n\ndef quote(quantity):\n    return double_quantity(quantity)\n",
    "shop/__main__.py": "from .service import quote\n\ndef main():\n    print(quote(21))\n\nif __name__ == '__main__':\n    main()\n",
}
with tempfile.TemporaryDirectory() as directory:
    root = Path(directory)
    for relative, content in sources.items():
        path = root / relative
        path.parent.mkdir(parents=True, exist_ok=True)
        path.write_text(content)
    success = subprocess.run([sys.executable, "-m", "shop"], cwd=root, capture_output=True, text=True, check=True)
    assert success.stdout.strip() == "42"
    imported = subprocess.run([sys.executable, "-c", "import shop.service"], cwd=root, capture_output=True, text=True, check=True)
    assert imported.stdout == ""
    failure = subprocess.run([sys.executable, "-c", "from shop.service import quote; quote(-1)"], cwd=root, capture_output=True, text=True)
    assert failure.returncode != 0 and "INVALID_QUANTITY" in failure.stderr
print("happy: module entry point and quiet imports; unhappy: domain rule still enforced")
```

One package is enough for this tiny example. The source dictionary is a fixture generator, not a recommendation to generate application source at runtime.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- A short script does not need a large application skeleton.
- Do not rename/move many files without updating imports, packaging, tests, and entry points.
- Do not create shared modules for domain-specific behavior merely to avoid choosing its owner.
- Do not assume leading underscores or folder labels prevent all cross-boundary access in Python.

Prefer structures that let a reader locate one feature and understand its dependencies. Enforce important boundaries with appropriate import/static checks and review.

## 6. How do I know I understand it?

**Blank-page check:** locate where a new task use case, SQLite adapter, CLI entry point, and unit test belong. Draw allowed imports.

| Constraint change | Predict the failure and response |
| --- | --- |
| A worker is added | Give it an explicit startup path; reuse import-safe feature code |
| Two packages import each other | Revisit ownership/contracts instead of hiding the cycle in more imports |
| A module is called `json.py` | It may shadow an expected import; choose unambiguous names |
| Feature extraction is planned | Identify public contracts and data ownership, not only folders |

You understand organization when readers can find owners and imports reflect the intended design.
