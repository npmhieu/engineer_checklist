# Notifications

[Lesson index](../../README.md) · Previous: [File Storage](2.file_storage.md) · Next: [Export / Import](4.export_import.md)

## 1. What is it?

A notification delivers relevant information through a channel such as email, push, SMS, or an in-app inbox, like sending a receipt after an order rather than making the customer repeatedly ask what happened.

An event is a fact; a notification is one possible reaction. Provider acceptance is not proof the recipient read it.

## 2. Why do we need it?

Sending email inside an order request makes checkout depend on mail-provider latency. Sending it after commit without recording intent can lose it if the process crashes first.

Specific pain: the business change commits but no notification is ever sent, or retries deliver several identical messages.

## 3. Under the hood / mechanism / system flow

### 3a. Intent, provider calls, and retries

Record a delivery intent with the business change in one local transaction, then let a worker contact the provider. An outbox provides a recoverable handoff; it does not make an external send atomic. A crash after provider acceptance but before marking sent can cause duplicates. See [AWS's transactional-outbox explanation](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).

Templates/rendering use CPU; provider calls add latency, quotas, cost, and failure modes. Attempts need bounded retries/backoff and permanent/transient error classification. Multi-worker delivery additionally needs atomic claiming/leases and recovery.

### 3b. Delivery lifecycle

```text
Business commit + pending intent → eligible worker claim → render/send
    → accepted / retry scheduled / permanently failed
    → provider callbacks or user read state, if supported
```

Check recipient visibility, channel preference, template escaping, and product-specific unsubscribe/security-message rules. Never place secrets or sensitive payloads indiscriminately into notification content or logs. Duplicate handling belongs to a defined message identity and provider/application policy.

## 4. How to apply / implement / use it?

Save as `notifications_demo.py`; run `python3 notifications_demo.py`. One worker and a simulated provider make retry behavior deterministic; no actual email is sent.

```python
import sqlite3

database = sqlite3.connect(":memory:")
database.executescript("""
    CREATE TABLE tasks (id INTEGER PRIMARY KEY, title TEXT);
    CREATE TABLE outbox (id INTEGER PRIMARY KEY, body TEXT, status TEXT, attempts INTEGER, next_at INTEGER);
""")
with database:
    database.execute("INSERT INTO tasks VALUES (1, 'Created')")
    database.execute("INSERT INTO outbox VALUES (1, 'Task created', 'pending', 0, 0)")
provider_attempts = []

def provider_send(body):
    provider_attempts.append(body)
    if len(provider_attempts) == 1:
        raise TimeoutError("SIMULATED_TRANSIENT_FAILURE")

def deliver_one(now):
    row = database.execute("SELECT id, body, attempts FROM outbox WHERE status = 'pending' AND next_at <= ? ORDER BY id LIMIT 1", (now,)).fetchone()
    if row is None:
        return False
    message_id, body, previous_attempts = row
    attempts = previous_attempts + 1
    with database:
        database.execute("UPDATE outbox SET attempts = ? WHERE id = ?", (attempts, message_id))
    try:
        provider_send(body)
    except TimeoutError:
        with database:
            database.execute("UPDATE outbox SET status = ?, next_at = ? WHERE id = ?", ("failed" if attempts >= 3 else "pending", now + 2**attempts, message_id))
        return False
    with database:
        database.execute("UPDATE outbox SET status = 'sent' WHERE id = ?", (message_id,))
    return True

assert not deliver_one(0)
assert not deliver_one(1)
assert deliver_one(2)
assert not deliver_one(3)
assert len(provider_attempts) == 2
assert database.execute("SELECT status, attempts FROM outbox").fetchone() == ("sent", 2)
database.close()
print("unhappy: transient failure retained; happy: delayed retry reaches accepted state")
```

`sent` here means the simulated provider call returned successfully, not end-user delivery. Real timeout outcomes can be uncertain; use provider idempotency where available and a duplicate-aware contract. This fixture does not solve multi-worker claims, crash recovery between steps, jitter, or preference changes.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not notify on every internal event; irrelevant messages create noise and cost.
- Do not block the core transaction on slow external delivery without a requirement.
- Do not retry permanent address/content errors forever or assume timeouts mean nothing was sent.
- Do not promise exactly-once user-visible delivery just because an outbox exists.

Some immediate low-risk notifications can be synchronous; choose their failure semantics deliberately. Critical communications need stronger delivery/reconciliation evidence than “function returned.”

## 6. How do I know I understand it?

**Blank-page check:** draw business commit, intent, provider acceptance, retry, and read/delivery evidence as separate states.

| Constraint change | Predict the failure and response |
| --- | --- |
| Provider times out after accepting | Outcome is uncertain; retries may duplicate |
| Two workers poll together | Add atomic claiming and recovery; the demo's SELECT is insufficient |
| Provider outage lasts hours | Bound attempts/backlog and monitor oldest pending age |
| User opts out before send | Apply the channel/product policy at the appropriate delivery boundary |

You understand notifications when intent is recoverable and delivery claims match the evidence actually available.
