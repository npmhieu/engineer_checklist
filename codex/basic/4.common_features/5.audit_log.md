# Audit Log

[Lesson index](../../README.md) · Previous: [Export / Import](4.export_import.md) · Next: [Reporting / Analytics](6.reporting_analytics.md)

## 1. What is it?

An audit log records attributable security or business actions and their relevant outcomes, like a signed maintenance ledger showing who changed a machine and when.

It differs from a debug log: its event contract, access controls, integrity, retention, and investigation value are deliberate.

## 2. Why do we need it?

The current row says a task is renamed but not who changed it or what it was before. Ordinary error logs may be sampled, rotated quickly, or omit successful actions.

Specific pain: an administrator changes access and no reliable evidence identifies the actor, target, or committed result.

## 3. Under the hood / mechanism / system flow

### 3a. Event records and storage costs

Common fields include event ID, server timestamp, trusted actor, action, resource/scope, outcome, and a bounded allowlist of changes. Append volume, indexes, retention, and investigation queries create storage/I/O costs.

Do not record passwords, bearer secrets, or whole sensitive request bodies. Restrict readers and writers; append-only application behavior is not proof against a privileged database operator. External immutable retention or tamper evidence has additional trust assumptions. See [OWASP logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).

### 3b. Committed fact versus attempted action

```text
Authorized business write + committed-change audit event → same local commit
Denied/failed attempts → separate security/operational event policy
```

If a committed change must always be audited, coordinate the local audit/outbox write with it. An external audit service cannot be included in the transaction just by calling it. A failed transaction should not leave an event falsely claiming the business change committed.

## 4. How to apply / implement / use it?

Save as `audit_log_demo.py`; run `python3 audit_log_demo.py`. Only title changes are retained; real titles may be personal data and require a specific retention/access policy.

```python
import sqlite3
import time
import uuid

database = sqlite3.connect(":memory:")
database.executescript("""
    CREATE TABLE tasks (id INTEGER PRIMARY KEY, owner_id INTEGER, title TEXT);
    CREATE TABLE audit (event_id TEXT PRIMARY KEY, at INTEGER, actor_id INTEGER, task_id INTEGER, old_title TEXT, new_title TEXT);
    INSERT INTO tasks VALUES (42, 7, 'Original');
""")

def rename(actor_id, title, fail=False):
    if not isinstance(title, str) or not 1 <= len(title) <= 120:
        raise ValueError("INVALID_TITLE")
    with database:
        database.execute("BEGIN IMMEDIATE")
        old = database.execute("SELECT title FROM tasks WHERE id = 42 AND owner_id = ?", (actor_id,)).fetchone()
        if old is None:
            raise PermissionError("FORBIDDEN")
        database.execute("UPDATE tasks SET title = ? WHERE id = 42", (title,))
        database.execute("INSERT INTO audit VALUES (?, ?, ?, 42, ?, ?)", (uuid.uuid4().hex, int(time.time()), actor_id, old[0], title))
        if fail:
            raise RuntimeError("SIMULATED_FAILURE")

rename(7, "Saved")
for actor_id, fail in [(8, False), (7, True)]:
    try:
        rename(actor_id, "Not committed", fail)
    except (PermissionError, RuntimeError):
        pass
    else:
        raise AssertionError("Expected failure did not occur")
assert database.execute("SELECT title FROM tasks").fetchone()[0] == "Saved"
assert database.execute("SELECT actor_id, old_title, new_title FROM audit").fetchall() == [(7, "Original", "Saved")]
database.close()
print("happy: attributable committed change; unhappy: denied/rolled-back changes not claimed")
```

The actor comes from authentication, not a body field. This local table is not tamper-proof; the demo proves transaction consistency, not immutable retention, privileged-user detection, or durable export.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not audit every low-value read with full payloads without a purpose/capacity policy.
- Do not use debug strings as the only evidence for important administrative actions.
- Do not claim a hash chain is tamper-proof if an attacker can rewrite the entire chain and its trust anchor.
- Do not confuse audit history with a complete event-sourced domain model or a backup.

Retention and availability policies can conflict with privacy and latency goals. Specify what must be audited, what happens if it cannot be recorded, and who can inspect it.

## 6. How do I know I understand it?

**Blank-page check:** define an event and its trust source for actor, time, target, and outcome. Separate an attempted action from a committed change.

| Constraint change | Predict the failure and response |
| --- | --- |
| External audit endpoint fails | Use durable handoff/recovery; do not assume remote delivery committed locally |
| User submits another actor ID | Ignore it as attribution evidence |
| Business transaction rolls back | Do not retain a false committed-change event |
| Privileged operator can edit audit rows | Local append convention alone cannot establish tamper resistance |

You understand auditing when evidence matches committed reality and its integrity/privacy limits are explicit.
