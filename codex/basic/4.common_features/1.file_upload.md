# File Upload

[Lesson index](../../README.md) · Previous section: [Migration Basics](../3.database/9.migration_basics.md) · Next: [File Storage](2.file_storage.md)

## 1. What is it?

File upload accepts client-supplied bytes into a controlled backend workflow, like a mailroom inspecting incoming parcels before placing them in storage.

Receiving bytes, validating content, authorizing ownership, and making an object available are separate steps.

## 2. Why do we need it?

A naive handler can buffer gigabytes, overwrite a server file using `../../...`, or serve active content as trusted HTML. Client filenames, extensions, MIME headers, and declared sizes are untrusted.

Specific pain: a small profile-image feature becomes a disk-exhaustion or stored-script endpoint. Upload limits and content policy belong at multiple boundaries, not only a frontend form.

## 3. Under the hood / mechanism / system flow

### 3a. Streaming, buffering, and storage I/O

HTTP parsers decode multipart/raw bodies into streams or temporary files. Full buffering uses memory proportional to upload size; bounded streaming limits memory but still needs total-size, time, concurrency, and disk quotas. Compression, archives, and image decoding can expand far beyond transferred bytes.

Content checks must match the accepted type: a header or extension is not proof. Complex formats may require maintained decoders, scanning, quarantine, and safe transformations. See [OWASP's upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

### 3b. Trust and lifecycle boundaries

```text
Authenticate/authorize → bounded read → validate supported content
    → generated storage key + private/quarantined object
    → required inspection → ready metadata → authorized download
```

Do not expose a half-uploaded object or trust a client-provided filesystem path. A direct-to-object-store upload still needs scoped permissions, limits, completion validation, and a publication decision. Failed uploads need cleanup/reconciliation.

## 4. How to apply / implement / use it?

Save as `file_upload_demo.py`; run `python3 file_upload_demo.py`. This intentionally accepts only nonempty UTF-8 `.txt` files up to 64 KiB; it is not a multipart parser, malware scanner, or general safe-document detector. The caller is assumed authorized to upload.

```python
from io import BytesIO
from pathlib import Path
import tempfile
import uuid

LIMIT = 64 * 1024

def accept_text(root, filename, stream):
    if not isinstance(filename, str) or len(filename) > 128 or any(part in filename for part in ("/", "\\", "\x00")):
        raise ValueError("INVALID_FILENAME")
    if Path(filename).suffix.lower() != ".txt":
        raise ValueError("UNSUPPORTED_TYPE")
    content = bytearray()
    while True:
        chunk = stream.read(min(4096, LIMIT + 1 - len(content)))
        if not chunk:
            break
        content.extend(chunk)
        if len(content) > LIMIT:
            raise ValueError("TOO_LARGE")
    if not content:
        raise ValueError("EMPTY_UPLOAD")
    content.decode("utf-8")
    key = uuid.uuid4().hex + ".txt"
    with (root / key).open("xb") as target:
        target.write(content)
    return key

with tempfile.TemporaryDirectory() as directory:
    root = Path(directory)
    key = accept_text(root, "notes.txt", BytesIO(b"Backend notes"))
    assert (root / key).read_bytes() == b"Backend notes"
    for name, data in [("../notes.txt", b"x"), ("app.html", b"x"), ("large.txt", b"x" * (LIMIT + 1)), ("bad.txt", b"\xff")]:
        try:
            accept_text(root, name, BytesIO(data))
        except (ValueError, UnicodeDecodeError):
            pass
        else:
            raise AssertionError("Disallowed upload was accepted")
    assert len(list(root.iterdir())) == 1
print("happy: bounded private text upload; unhappy: path/type/size/encoding rejected")
```

The temporary directory is private; production storage needs deliberate permissions and quotas. UTF-8 validity does not make embedded text trusted markup. Download as an attachment with a controlled `text/plain` content type and `nosniff`, rather than inserting it into HTML. The HTTP adapter must bound parser work and read timeouts before this function.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not accept every file type when the product needs one narrow format.
- Do not store executable content under a publicly executable web root.
- Do not load an entire large upload merely to check its declared size afterward.
- Do not claim extension/signature scanning alone proves a file safe.

Uploads create abuse, storage, scanning, privacy, and cleanup obligations. A URL to an existing trusted asset may be enough for some workflows, but fetching arbitrary URLs introduces separate server-side request-forgery risks.

## 6. How do I know I understand it?

**Blank-page check:** draw byte limits, trust checks, quarantine/publication, ownership, and failure cleanup separately.

| Constraint change | Predict the failure and response |
| --- | --- |
| Maximum grows to 2 GiB | Use bounded streaming/multipart storage, quotas, cancellation, and timeouts |
| ZIP archives are accepted | Bound expanded size/entry paths; transferred-byte limits are insufficient |
| Scan service is unavailable | Keep required inspection pending; do not publish as clean |
| User supplies a path-like name | Never use it as a trusted storage path |

You understand uploads when disallowed bytes never become publicly trusted objects and resource use stays bounded.
