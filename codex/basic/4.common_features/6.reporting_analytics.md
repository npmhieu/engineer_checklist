## 1. What is it?

Reporting presents defined summaries and analytics explores patterns in data, like totaling spreadsheet rows and comparing groups rather than inspecting one receipt at a time.

Every metric needs a definition: grain, numerator/denominator, scope, time window, timezone, inclusion rules, and freshness.

## 2. Why do we need it?

Individual CRUD records do not answer how many paid orders existed in a period or whether processing is slowing. A poorly defined report can confidently show the wrong number.

Specific bug: joining orders to several tags repeats an order amount and inflates a total. Another common error counts one midnight record in two date windows.

## 3. Under the hood / mechanism / system flow

### 3a. Grain, grouping, and computation

Aggregates such as COUNT/SUM group facts; joins can change their grain before aggregation. Grouping/scanning large datasets consumes CPU/I/O and may require sorts/hashes or temporary storage. Summary tables/materialized views reduce repeated work but add refresh and reconciliation responsibilities. See [PostgreSQL's aggregate introduction](https://www.postgresql.org/docs/current/tutorial-agg.html).

Use explicit units and types. A mean of group means is generally not the overall mean without weights. Null versus zero and refund/current-status rules change meaning. Analytical read replicas/warehouses can protect transactional load but may lag.

### 3b. From facts to decisions

```text
Authorized scoped facts → correct grain/time filter → aggregate
    → defined presentation + freshness → user decision
```

Use half-open intervals `[start, end)` for adjacent time windows. Convert business-local boundaries correctly, especially across daylight-saving changes. A report labeled “currently paid order amount” is not automatically accounting revenue or cash flow.

## 4. How to apply / implement / use it?

Save as `reporting_demo.py`; run `python3 reporting_demo.py`. This metric is the sum/count of currently paid order rows for one tenant in a UTC-second window; it intentionally makes no broader revenue claim.

```python
import sqlite3

database = sqlite3.connect(":memory:")
database.executescript("""
    CREATE TABLE orders (id INTEGER PRIMARY KEY, tenant_id INTEGER, at INTEGER, cents INTEGER, status TEXT);
    CREATE TABLE tags (order_id INTEGER, tag TEXT);
    INSERT INTO orders VALUES (1, 7, 100, 100, 'paid'), (2, 7, 150, 200, 'paid'),
        (3, 7, 200, 900, 'paid'), (4, 8, 100, 500, 'paid'), (5, 7, 120, 50, 'refunded');
    INSERT INTO tags VALUES (1, 'a'), (1, 'b'), (2, 'a');
""")
wrong = database.execute("SELECT SUM(orders.cents) FROM orders JOIN tags ON tags.order_id = orders.id WHERE tenant_id = 7 AND at >= 100 AND at < 200 AND status = 'paid'").fetchone()[0]
assert wrong == 400

def report(tenant_id, start, end):
    if end <= start:
        raise ValueError("INVALID_WINDOW")
    return database.execute("SELECT COUNT(*), COALESCE(SUM(cents), 0) FROM orders WHERE tenant_id = ? AND at >= ? AND at < ? AND status = 'paid'", (tenant_id, start, end)).fetchone()

assert report(7, 100, 200) == (2, 300)
assert report(7, 200, 300) == (1, 900)
assert report(99, 100, 200) == (0, 0)
try:
    report(7, 200, 100)
except ValueError:
    pass
else:
    raise AssertionError("Invalid time window accepted")
database.close()
print("unhappy: join duplicates money; happy: scoped fact-grain totals and disjoint windows")
```

Tenant selection must be authorized by the calling layer; a parameter alone is not permission. A database failure must not be converted into a zero report. This fixture has one currency, no historical status reconstruction, and no real warehouse/timezone layer.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not use a lagging dashboard as the authority for spending an account balance.
- Do not run unbounded analytical joins on a busy primary without workload analysis.
- Do not sum across currencies or average ratios without a defined weighting policy.
- Do not label a metric “daily active” without defining activity, identity, day, and deduplication.

Precomputation buys faster reads at the cost of stale/repairable derived data. Document freshness and reconcile against source facts.

## 6. How do I know I understand it?

**Blank-page check:** define the metric before SQL, then calculate a tiny fixture by hand including duplicates, refunds, missing data, and boundaries.

| Constraint change | Predict the failure and response |
| --- | --- |
| One order gains several tags | Preserve fact grain; do not sum duplicated join rows |
| Business day uses local time | Translate correct boundaries rather than assuming every day is 24 UTC hours |
| Dashboard moves to a replica | Publish/monitor freshness rather than imply immediate consistency |
| New currency appears | Separate/convert under an explicit metric policy |

You understand analytics when you can explain what a number means, what it excludes, and why the query computes that definition.
