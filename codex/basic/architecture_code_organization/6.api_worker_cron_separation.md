# API / Worker / Cron Separation

[Lesson index](../../README.md) · Previous: [Dependency Direction](5.dependency_direction.md) · Next section: [Unit Test](../testing/1.unit_test.md)

## 1. What is it?

API, worker, and cron separation gives request handling, queued execution, and scheduled triggering distinct entry points, like a reception desk, workshop, and calendar sharing the same operating rules.

They may share a codebase and domain services without sharing one runtime process or scaling policy.

## 2. Why do we need it?

Generating a five-minute report inside an HTTP handler ties up request capacity. Running a scheduler in every API replica can enqueue the same daily work several times.

Specific pain: web replicas scale from one to five and the “daily email” runs five times, while a slow export makes unrelated requests time out.

## 3. Under the hood / mechanism / system flow

### 3a. Process capacity and handoff

API processes optimize request latency; workers consume bounded concurrency and resource budgets; schedulers trigger work by time. Queues add serialization, storage, leases/acknowledgments, retries, and lag. A process split does not automatically create reliable delivery.

Long CPU/memory/disk work needs independent capacity control. Queue messages should contain bounded identifiers/context, not untrusted serialized executable objects. Scheduled jobs can be missed or duplicated; [Kubernetes CronJob documentation](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/) explicitly discusses scheduling limitations and idempotent jobs.

### 3b. Shared operation, different triggers

```text
HTTP → validate/authorize → durable job accepted → 202 + job identity
Cron → choose explicit period/timezone → enqueue intended work
Worker → establish allowed identity/context → shared use case → persist outcome → ack
```

Recheck permissions or use explicitly delegated authority according to policy. Do not trust arbitrary actor IDs placed in a message. Define business idempotency separately from job identity; two different jobs can represent one daily intent.

## 4. How to apply / implement / use it?

Save as `entry_points_demo.py`; run `python3 entry_points_demo.py`. This single-process queue demonstrates logical boundaries only; it is not durable messaging or multi-worker coordination.

```python
from datetime import date
from queue import Empty, Queue
import uuid

queue = Queue()
results = {}
outcomes = []

def generate_report(actor_id, period):
    if actor_id != 7:
        raise PermissionError("FORBIDDEN")
    canonical = date.fromisoformat(period).isoformat()
    if canonical != period:
        raise ValueError("INVALID_PERIOD")
    key = (actor_id, period)
    if key not in results:
        results[key] = "generated"
    return results[key]

def api_request(authenticated_actor, period):
    if authenticated_actor != 7:
        raise PermissionError("FORBIDDEN")
    if date.fromisoformat(period).isoformat() != period:
        raise ValueError("INVALID_PERIOD")
    job_id = uuid.uuid4().hex
    queue.put((job_id, authenticated_actor, period))
    return {"status": 202, "job_id": job_id}

def cron_trigger(period):
    return api_request(7, period)

def drain_worker():
    while True:
        try:
            job_id, actor_id, period = queue.get_nowait()
        except Empty:
            return
        try:
            generate_report(actor_id, period)
        except (PermissionError, ValueError):
            outcomes.append((job_id, "failed"))
        else:
            outcomes.append((job_id, "done"))

assert api_request(7, "2026-10-17")["status"] == 202
cron_trigger("2026-10-17")
queue.put(("untrusted-fixture", 8, "2026-10-17"))
drain_worker()
assert len(results) == 1
assert [state for _, state in outcomes] == ["done", "done", "failed"]
print("happy: two triggers share one business intent; unhappy: worker rejects unauthorized context")
```

The dictionary deduplication is not atomic/durable across processes. A production design needs persistent job/result state, correct business uniqueness, recovery, and authenticated message production. The cron fixture uses a trusted service identity and reuses enqueue validation, not an actual loopback HTTP call.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Cheap bounded work may remain synchronous; queues add complexity and delayed outcomes.
- Do not start an in-process scheduler independently in every replica without coordination.
- Do not return `202` before work is durably accepted when the contract promises recoverable execution.
- Do not acknowledge a real message before the required committed result unless loss is an explicit policy.

Separate entry points to isolate workloads and triggers, not to duplicate business logic or create unnecessary services.

## 6. How do I know I understand it?

**Blank-page check:** draw trigger, identity, durable handoff, operation, result state, acknowledgment, and retry boundaries.

| Constraint change | Predict the failure and response |
| --- | --- |
| API replicas multiply | Scheduler duplication must not multiply business effects |
| Worker crashes after commit before ack | Redelivery must not blindly repeat the effect |
| User loses access before execution | Apply the documented execution/delegation policy |
| Daylight-saving changes occur | Define schedule timezone and period identity explicitly |

You understand separation when triggers differ, rules stay shared, and crash/retry behavior is explicit.
