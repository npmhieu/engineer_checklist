# Layered Architecture

[Lesson index](../../README.md) · Previous: [Monolithic Architecture](1.monolithic_architecture.md) · Next: [Separation of Concerns](3.separation_of_concerns.md)

## 1. What is it?

Layered architecture separates responsibilities such as transport, application behavior, and persistence, like a restaurant separating the waiter, kitchen, and pantry.

Layers are logical code boundaries; they need not be separate network tiers. Their names and strictness vary between designs.

## 2. Why do we need it?

When HTTP parsing, permissions, SQL, and response formatting live in every handler, adding a worker duplicates business rules and changing storage touches transport code everywhere.

Specific pain: one endpoint enforces a title rule but an import path bypasses it. A shared service can own the rule while adapters handle their protocols.

## 3. Under the hood / mechanism / system flow

### 3a. Calls and data boundaries

An HTTP adapter parses input and translates results; an application service coordinates the use case; domain rules express meaning; a repository/adapter performs storage access. Extra local calls are usually cheap compared with I/O, but excessive object mapping and pass-through wrappers add maintenance and allocation cost.

Layering does not dictate that core logic must import a concrete database class. Dependency inversion can keep core policy independent of infrastructure. [Microsoft's architecture overview](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures) contrasts layered and clean arrangements.

### 3b. Request/error lifecycle

```text
Transport validation → shared use case → persistence port/adapter
    → domain result/error → transport status/body
```

Keep HTTP numbers out of domain rules; translate at the edge. Enforce authorization in a reusable operation, not solely a route decorator if other entry points invoke it. Transaction ownership must be explicit rather than split accidentally across repositories.

## 4. How to apply / implement / use it?

Save as `layered_demo.py`; run `python3 layered_demo.py`. A memory repository isolates responsibilities without requiring a framework.

```python
class StorageUnavailable(Exception):
    pass

class MemoryRepository:
    def __init__(self):
        self.items = []
        self.available = True

    def add(self, title):
        if not self.available:
            raise StorageUnavailable()
        self.items.append(title)
        return {"id": len(self.items), "title": title}

class TaskService:
    def __init__(self, repository):
        self.repository = repository

    def create(self, title):
        if not isinstance(title, str) or not 1 <= len(title.strip()) <= 120:
            raise ValueError("INVALID_TITLE")
        return self.repository.add(title.strip())

def handle(body, service):
    if not isinstance(body, dict) or set(body) != {"title"}:
        return 422, {"code": "INVALID_FIELDS"}
    try:
        return 201, service.create(body["title"])
    except ValueError:
        return 422, {"code": "INVALID_TITLE"}
    except StorageUnavailable:
        return 503, {"code": "TEMPORARILY_UNAVAILABLE"}

repository = MemoryRepository()
service = TaskService(repository)
assert handle({"title": " Learn "}, service) == (201, {"id": 1, "title": "Learn"})
assert handle({"title": 42}, service)[0] == 422
repository.available = False
assert handle({"title": "More"}, service)[0] == 503
assert repository.items == ["Learn"]
print("happy: layers compose; unhappy: input/storage failures translated without false success")
```

This tuple adapter is not a real HTTP server. Authorization is assumed before this narrow public-task fixture; a protected service needs an actor and shared policy enforcement. The `503` applies to the named simulated temporary outage, not every arbitrary exception.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- A one-off script may need functions rather than a class in every conceptual layer.
- Do not add a service/repository wrapper that merely forwards every method without a useful boundary.
- Do not place all business logic in controllers or let ORM entities leak everywhere by default.
- Do not confuse more folders with enforced dependency direction.

Choose enough structure to isolate likely change, not a mandatory ceremony for every line.

## 6. How do I know I understand it?

**Blank-page check:** assign parsing, title invariants, access checks, SQL, transaction ownership, and HTTP mapping to named boundaries.

| Constraint change | Predict the failure and response |
| --- | --- |
| Worker creates tasks | Reuse the use case without manufacturing an HTTP request |
| Database changes | Replace the persistence adapter without rewriting domain rules |
| Error response format changes | Change boundary translation, not business exceptions |
| Several writes must commit together | Coordinate one use-case transaction rather than unrelated repository commits |

You understand layers when a change has a predictable owner and rules remain shared across entry points.
