# Monolithic Architecture

[Lesson index](../../README.md) · Previous section: [Reporting / Analytics](../common_features/6.reporting_analytics.md) · Next: [Layered Architecture](2.layered_architecture.md)

## 1. What is it?

A monolith deploys an application's main capabilities together as one application unit, like several departments operating inside one building rather than in separate buildings connected by couriers.

One deployable does not mean one file, one server replica, no modules, or necessarily one database. A modular monolith preserves internal boundaries while sharing deployment.

## 2. Why do we need it?

Separate services introduce network failures, independent deployments, distributed data changes, and operational overhead. A small product can spend more effort coordinating services than implementing useful behavior.

Specific pain: checkout requires several network hops and recovery protocols before its domain boundaries are even stable. A monolith can keep related operations local and simplify transactions and debugging.

## 3. Under the hood / mechanism / system flow

### 3a. Local calls and shared resources

In-process module calls avoid network serialization/round trips but share memory, runtime resources, and process failure modes. Multiple replicas can scale the application; separating one hot feature's scaling is harder when the whole unit scales together.

A shared database transaction can coordinate local operations, though that does not make arbitrary external calls atomic. Large dependencies and accidental cross-module table access create coupling. [Fowler's Monolith First](https://martinfowler.com/bliki/MonolithFirst.html) discusses the trade-off and why later extraction is not automatically easy.

### 3b. Deployment and ownership boundaries

```text
One versioned application → internal module APIs → local/shared infrastructure
    → one coordinated release, possibly many running replicas
```

Use module contracts and ownership inside the deployable. A monolith can have API/worker process roles from the same codebase; deployment topology and source organization are distinct choices.

## 4. How to apply / implement / use it?

Save as `monolith_demo.py`; run `python3 monolith_demo.py`. Two logical capabilities share one process and an explicit transaction; real modules can live in separate files.

```python
import sqlite3

database = sqlite3.connect(":memory:")
database.executescript("""
    CREATE TABLE stock (sku TEXT PRIMARY KEY, available INTEGER CHECK (available >= 0));
    CREATE TABLE orders (id INTEGER PRIMARY KEY, sku TEXT);
    INSERT INTO stock VALUES ('BOOK', 1);
""")

class Inventory:
    def reserve(self, connection, sku):
        changed = connection.execute("UPDATE stock SET available = available - 1 WHERE sku = ? AND available > 0", (sku,))
        if changed.rowcount != 1:
            raise ValueError("SOLD_OUT")

class Orders:
    def __init__(self, inventory):
        self.inventory = inventory

    def place(self, sku):
        with database:
            self.inventory.reserve(database, sku)
            return database.execute("INSERT INTO orders (sku) VALUES (?)", (sku,)).lastrowid

orders = Orders(Inventory())
assert orders.place("BOOK") == 1
try:
    orders.place("BOOK")
except ValueError:
    pass
else:
    raise AssertionError("Oversold inventory")
assert database.execute("SELECT COUNT(*) FROM orders").fetchone()[0] == 1
database.close()
print("happy: local coordinated checkout; unhappy: sold-out request creates no order")
```

The connection parameter makes participation in one transaction visible. Authentication, durable deployment, payment, and module-access enforcement are omitted; the example does not claim these classes are separate services.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Independent trust, availability, ownership, or extreme scaling requirements may justify separate deployables.
- Do not equate a monolith with permission for every module to modify every table.
- Do not split into microservices merely to fix unclear code boundaries.
- Do not claim one release is risk-free: a defect can affect the shared application unit.

Choose boundaries from measured needs. Monolithic versus distributed is not a ranking of developer sophistication.

## 6. How do I know I understand it?

**Blank-page check:** draw code modules, deployment units, processes, replicas, and databases separately. Explain which calls cross a network and which changes share a transaction.

| Constraint change | Predict the failure and response |
| --- | --- |
| Report generation consumes all CPU | Isolate workload/process capacity; whole-app scaling may waste resources |
| One capability needs independent releases | Evaluate extraction with explicit contracts and data ownership |
| Two replicas are added | Shared state and external effects still need coordination |
| Inventory becomes a remote service | The local transaction no longer covers reservation automatically |

You understand monoliths when deployment unity and internal modularity remain distinct.
