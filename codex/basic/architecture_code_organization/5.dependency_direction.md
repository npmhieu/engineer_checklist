# Dependency Direction

[Lesson index](../../README.md) · Previous: [Package / Folder Organization](4.package_folder_organization.md) · Next: [API / Worker / Cron Separation](6.api_worker_cron_separation.md)

## 1. What is it?

Dependency direction defines which modules may know about which others, like designing a wall socket so the appliance needs an electrical contract rather than knowledge of the power station's machinery.

Runtime control flow and source-code dependency direction are not necessarily the same thing.

## 2. Why do we need it?

If business rules import a web framework and concrete database driver, testing a simple use case requires infrastructure startup. Replacing storage or reusing behavior from a worker becomes harder.

Specific pain: infrastructure changes force domain changes even when the product rule did not change.

## 3. Under the hood / mechanism / system flow

### 3a. Ports, adapters, and inversion

Core policy can define the capability it needs, such as `save_task(title)`. An outer adapter implements that port; a composition root connects them. This inverts the source dependency: infrastructure knows the core contract, while core code does not import that concrete implementation.

An interface call is local indirection, not inherently network I/O. Adapter behavior determines real latency, failure, and transaction semantics. Python protocols describe structural typing; they do not automatically validate all runtime behavior. See [Python Protocol documentation](https://docs.python.org/3/library/typing.html#typing.Protocol).

### 3b. Construction versus execution

```text
Source dependencies: adapter → core port; composition root → both
Runtime: entry point → use case → injected port implementation → infrastructure
```

Dependency injection is supplying dependencies, not necessarily installing a container framework. Keep transaction, timeout, and error contracts visible; an interface with misleading guarantees still creates coupling.

## 4. How to apply / implement / use it?

Save as `dependency_direction_demo.py`; run `python3 dependency_direction_demo.py`.

```python
from typing import Protocol

class TaskWriter(Protocol):
    def save(self, title: str) -> int:
        ...

class TaskService:
    def __init__(self, writer: TaskWriter):
        self.writer = writer

    def create(self, title):
        if not isinstance(title, str) or not title.strip():
            raise ValueError("INVALID_TITLE")
        return self.writer.save(title.strip())

class MemoryWriter:
    def __init__(self):
        self.items = []

    def save(self, title):
        self.items.append(title)
        return len(self.items)

class FailingWriter:
    def save(self, title):
        raise OSError("SIMULATED_STORAGE_FAILURE")

writer = MemoryWriter()
assert TaskService(writer).create(" Learn ") == 1 and writer.items == ["Learn"]
try:
    TaskService(FailingWriter()).create("Learn")
except OSError:
    pass
else:
    raise AssertionError("Storage failure became false success")
print("happy: injected adapter; unhappy: failed port propagates instead of pretending to save")
```

Classes share a file only for a runnable lesson. In an application, the core port/service should not import concrete outer adapters. A fake proves use-case behavior, not that a real database adapter honors its contract; integration tests address that boundary.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not invent an interface for every function without a meaningful boundary.
- Do not hide all dependencies in a global service locator.
- Do not make core interfaces mirror every method of a vendor SDK; define the capabilities the use case needs.
- Do not equate dependency inversion with removing all infrastructure knowledge from all code—the composition root must choose concrete adapters.

The payoff is independent policy and explicit effects; the cost is contracts, wiring, and adapter tests. Keep them narrow and useful.

## 6. How do I know I understand it?

**Blank-page check:** draw import arrows separately from runtime calls. Replace the persistence adapter without modifying the use-case rule.

| Constraint change | Predict the failure and response |
| --- | --- |
| Port moves from memory to network | Add explicit latency/timeouts/retry semantics; the signature alone is insufficient |
| Domain imports the concrete adapter | Independence is lost despite having an interface somewhere |
| Fake always succeeds | Unit tests do not prove real storage/error behavior |
| One use case needs atomic multi-write | Define a coherent unit-of-work/transaction contract |

You understand direction when policy can be tested without infrastructure and real effects remain explicit rather than hidden.
