# Schema / Data Modeling

[Lesson index](../../README.md) · Previous: [Database Fundamentals](1.database_fundamentals.md) · Next: [Relationships](3.relationships.md)

## 1. What is it?

Data modeling identifies entities, values, relationships, and rules, while a schema records their storage contract—like designing a form and deciding which fields and combinations are valid.

A conceptual model describes the domain; a logical model organizes entities/keys; a physical schema selects engine-specific types, constraints, and indexes. An API representation need not match a table one-to-one.

## 2. Why do we need it?

Without a model, one feature stores prices in dollars, another assumes cents, and duplicate product identifiers appear. “Just add a column” can hide an unclear distinction between a current product price and the historical price paid for an order.

Specific pain: floating-point rounding changes money totals or a required state is silently missing. Modeling makes units, identity, optionality, and invariants explicit before queries depend on them.

## 3. Under the hood / mechanism / system flow

### 3a. Representation and enforcement

Types affect storage width, comparison, encoding, and query behavior. Null is a missing/unknown value, not automatically zero or empty text; SQL comparisons with null require deliberate handling. Unique/check/not-null constraints enforce a subset of invariants at the final write boundary.

Use integer minor units or an appropriate fixed-precision decimal policy for money, with explicit currency and scale. Variable-length text and large blobs affect row/page and network costs. Schema choices also determine which joins and indexes will be needed. See [PostgreSQL's constraint documentation](https://www.postgresql.org/docs/current/ddl-constraints.html) for concrete enforcement mechanisms.

### 3b. From product rule to storage contract

```text
Example use cases → entities + units + allowed states → keys/relationships
    → schema constraints → validated write → compatible migration when rules change
```

Boundary validation provides helpful errors; constraints handle bypasses and races. Neither replaces authorization. Rules involving external systems or many rows may require more than a row-level CHECK.

## 4. How to apply / implement / use it?

Save as `schema_modeling_demo.py`; run `python3 schema_modeling_demo.py`. Prices below are USD cents; the product identifier is unique within a tenant, not globally.

```python
import sqlite3

database = sqlite3.connect(":memory:")
database.execute("""
    CREATE TABLE products (
        id INTEGER PRIMARY KEY,
        tenant_id INTEGER NOT NULL,
        sku TEXT NOT NULL CHECK (length(sku) > 0),
        price_cents INTEGER NOT NULL CHECK (typeof(price_cents) = 'integer' AND price_cents >= 0),
        currency TEXT NOT NULL CHECK (currency = 'USD'),
        UNIQUE (tenant_id, sku)
    )
""")
with database:
    database.execute("INSERT INTO products VALUES (1, 7, 'BOOK', 1299, 'USD')")
    database.execute("INSERT INTO products VALUES (2, 8, 'BOOK', 999, 'USD')")

for values in [(3, 7, "BOOK", 100, "USD"), (3, 7, "PEN", -1, "USD"), (3, 7, "PEN", 1.5, "USD")]:
    try:
        with database:
            database.execute("INSERT INTO products VALUES (?, ?, ?, ?, ?)", values)
    except sqlite3.IntegrityError:
        pass
    else:
        raise AssertionError("Schema invariant was bypassed")
assert database.execute("SELECT COUNT(*) FROM products").fetchone()[0] == 2
database.close()
print("happy: tenant-scoped identity and integer money; unhappy: duplicate/invalid money rejected")
```

SQLite has different type-affinity behavior from PostgreSQL; the explicit `typeof` check makes this fixture's stored integer rule visible. A real input layer should validate types before SQL. SKU case/normalization is a product contract; this example uses exact stored equality.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not design a universal entity-attribute-value system for ordinary known fields without a real requirement.
- Do not use one JSON blob merely to avoid thinking about identity, constraints, and query paths.
- Do not model historical facts as references to mutable current values when a snapshot is required.
- Do not overconstrain uncertain product rules so every small feature requires disruptive migration.

Flexible fields can be useful, but they move validation/indexing/versioning responsibilities elsewhere rather than eliminating them.

## 6. How do I know I understand it?

**Blank-page check:** model a product and an order line. Name identity, units, nullability, uniqueness scope, and which values must remain historical snapshots.

| Constraint change | Predict the failure and response |
| --- | --- |
| Multiple currencies arrive | Define currency-specific minor-unit/decimal rules; do not silently reuse USD assumptions |
| SKU becomes case-insensitive | Normalize and enforce the same equality policy, resolving existing collisions |
| Price changes after purchase | Preserve the order line's agreed price, not just current product price |
| New optional field becomes required | Plan compatible backfill and enforcement rather than rejecting all old rows |

You understand modeling when every field has meaning, units, ownership, and a change policy—not only a database type.
