## 1. What is it?

A database manages structured data and its safe retrieval and modification, like a shared spreadsheet with a query engine, access rules, and coordinated saving.

The **data** is not the same thing as the **database management system (DBMS)** that stores, queries, coordinates, and recovers it. A relational DBMS models tables and constraints; document, key-value, and graph systems make different modeling/access choices. “NoSQL” does not automatically mean “no schema” or “no transactions.”

## 2. Why do we need it?

An in-memory list disappears after restart. Concurrent rewrites of a JSON file can overwrite each other, and searching a huge file for one record becomes expensive. A DBMS supplies coordinated updates, queries, integrity controls, and recovery rather than requiring each feature to reinvent them.

Specific pain: two requests save the same file, one loses the other's task, then a process crash leaves a partly written file. Database guarantees address defined failure modes, not every possible application bug or hardware failure.

## 3. Under the hood / mechanism / system flow

### 3a. Pages, buffers, indexes, and recovery

Rows are typically stored in pages. A buffer/cache avoids repeated disk reads; indexes locate candidates; an optimizer chooses an execution plan. Writes affect cached pages and recovery structures such as a journal or write-ahead log before durable commit under the configured policy.

Scanning `n` rows costs roughly proportional to the data inspected; an appropriate tree index can reduce lookup work, but retrieving large results still costs CPU, memory, and I/O. Durability depends on engine settings, storage behavior, and successful synchronization—not merely calling a function named `save`. [SQLite's atomic-commit description](https://www.sqlite.org/atomiccommit.html) explains one concrete implementation and its assumptions.

### 3b. Application boundary

```text
Validated/authorized operation → connection → parameterized query
    → constraints + concurrency control → commit/rollback → application result
```

SQLite runs embedded in the application process; a client/server database adds network connections and server processes. Connection pooling reduces repeated setup but has capacity limits. Queries and database credentials must stay behind the backend's access boundary.

## 4. How to apply / implement / use it?

Save as `database_fundamentals_demo.py`; run `python3 database_fundamentals_demo.py`. Standard library only; a temporary file demonstrates persistence across connection reopen, not a power-loss test.

```python
from pathlib import Path
import sqlite3
import tempfile

with tempfile.TemporaryDirectory() as directory:
    path = Path(directory) / "learning.sqlite"
    database = sqlite3.connect(path)
    database.execute("CREATE TABLE tasks (id INTEGER PRIMARY KEY, title TEXT NOT NULL)")
    with database:
        database.execute("INSERT INTO tasks (title) VALUES (?)", ("Learn 'databases'",))
    database.close()

    database = sqlite3.connect(path)
    assert database.execute("SELECT title FROM tasks WHERE id = ?", (1,)).fetchone()[0] == "Learn 'databases'"
    try:
        with database:
            database.execute("INSERT INTO tasks (title) VALUES (?)", (None,))
    except sqlite3.IntegrityError:
        pass
    else:
        raise AssertionError("Required title was not enforced")
    assert database.execute("SELECT COUNT(*) FROM tasks").fetchone()[0] == 1
    database.close()
print("happy: committed data survives reopen; unhappy: invalid row rejected")
```

Placeholders bind values without concatenating SQL. A transaction context commits/rolls back; it does not close the connection. Keep backups and test restores separately: persistence is not a backup strategy.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- A tiny immutable configuration file may not need a DBMS.
- Do not choose a distributed database solely because the product might grow; operational complexity is real.
- Do not assume an ORM removes query cost, authorization, or transaction design.
- Do not store the only copy on ephemeral container storage or assume replication protects against accidental deletion.

Choose based on access patterns, correctness, availability, data volume, and operational skills. A database does not make an incorrect business operation correct automatically.

## 6. How do I know I understand it?

**Blank-page check:** draw application memory, database cache, recovery log, persistent file/storage, and backup. Explain what each survives and which component executes a query.

| Constraint change | Predict the failure and response |
| --- | --- |
| Process restarts | Uncommitted memory disappears; properly committed persistent data should remain |
| Dataset becomes 100 times larger | Scans and unbounded responses can dominate; inspect access paths |
| More clients write concurrently | Coordination/locking and connection capacity matter |
| Disk is lost | Commit durability on that disk is insufficient; use tested recovery/backup design |

You understand databases when you can separate data modeling, query execution, concurrency, durability, and recovery responsibilities.
