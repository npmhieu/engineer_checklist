# Primary / Foreign Key

[Lesson index](../../README.md) · Previous: [Normalization](4.normalization.md) · Next: [Indexes](6.indexes.md)

## 1. What is it?

A primary key identifies a row, while a foreign key requires a reference to an allowed parent key—like a library book ID and a loan record pointing to a real book.

Primary keys may contain several columns. Foreign keys can reference suitable unique keys as well as primary keys. Identification, reference integrity, and permission to access the row are different concerns.

## 2. Why do we need it?

Without stable identity, updating “the user named Alex” is ambiguous. Without referential checks, a task can point to a missing project—or a project from the wrong tenant if only part of a scoped reference is enforced.

Specific pain: an application pre-check passes, the parent is deleted concurrently, and the subsequent child insert creates an orphan. A database constraint protects the actual write boundary.

## 3. Under the hood / mechanism / system flow

### 3a. Uniqueness, nulls, and lookup work

An engine typically backs uniqueness with an index. Foreign-key enforcement checks parent existence on child writes and related children on parent changes/deletes. Supporting indexes on child references can avoid expensive scans; do not assume every engine creates those indexes automatically.

Nullable foreign-key columns can permit an absent reference under the engine's matching rules; add NOT NULL when the relationship is required. SQLite has historical primary-key/null quirks for some table forms, so explicitly declare non-integer composite components NOT NULL. See [SQLite foreign keys](https://www.sqlite.org/foreignkeys.html) and [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html).

### 3b. Creation/deletion lifecycle

```text
Create parent → insert child with valid scoped reference
    → parent update/delete applies RESTRICT/NO ACTION/CASCADE/SET NULL policy
```

Deferred checks, where supported/configured, shift the checking boundary; they do not waive integrity. Cascades are structural behavior, not authorization or an audit/retention policy.

## 4. How to apply / implement / use it?

Save as `keys_demo.py`; run `python3 keys_demo.py`. Composite references prevent a task in tenant 1 from pointing to tenant 2's project.

```python
import sqlite3

database = sqlite3.connect(":memory:")
database.execute("PRAGMA foreign_keys = ON")
database.executescript("""
    CREATE TABLE projects (
        tenant_id INTEGER NOT NULL, id INTEGER NOT NULL,
        PRIMARY KEY (tenant_id, id)
    );
    CREATE TABLE tasks (
        id INTEGER PRIMARY KEY, tenant_id INTEGER NOT NULL, project_id INTEGER NOT NULL,
        FOREIGN KEY (tenant_id, project_id) REFERENCES projects(tenant_id, id) ON DELETE RESTRICT
    );
    CREATE INDEX task_project ON tasks(tenant_id, project_id);
    INSERT INTO projects VALUES (1, 10), (2, 20);
    INSERT INTO tasks VALUES (42, 1, 10);
""")
for statement in [
    "INSERT INTO tasks VALUES (42, 1, 10)",
    "INSERT INTO tasks VALUES (43, 1, 20)",
    "DELETE FROM projects WHERE tenant_id = 1 AND id = 10",
]:
    try:
        with database:
            database.execute(statement)
    except sqlite3.IntegrityError:
        pass
    else:
        raise AssertionError("Key constraint was bypassed")
assert database.execute("SELECT COUNT(*) FROM tasks").fetchone()[0] == 1
database.close()
print("happy: scoped reference; unhappy: duplicate/cross-tenant/orphaning delete rejected")
```

The schema enforces scope consistency, not the caller's membership. Authorization remains mandatory. SQLite foreign-key enforcement must be enabled per connection outside an active transaction.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not remove referential integrity just to make import errors disappear; stage/validate imports instead.
- Do not use a mutable display name as identity without understanding rename propagation.
- Do not assume random/UUID primary keys provide authorization.
- Do not create local foreign keys across independently owned service databases; define integration consistency explicitly.

Constraints add write/checking work and influence deletion order. That cost buys enforceable integrity; measure before discarding it.

## 6. How do I know I understand it?

**Blank-page check:** write a composite parent key and matching child foreign key, then explain why referencing only the project ID is insufficient for this model.

| Constraint change | Predict the failure and response |
| --- | --- |
| Unassigned tasks become valid | Define nullable reference semantics deliberately |
| Project deletion should delete all tasks | Evaluate cascade, authorization, and retention consequences together |
| Child table grows to millions of rows | Index reference columns for relevant enforcement/query paths |
| IDs become externally visible | Keep access policy separate from identifier unpredictability |

You understand keys when identity, uniqueness scope, reference enforcement, and delete behavior are explicit.
