# Unit Test

[Lesson index](../../README.md) · Previous section: [API / Worker / Cron Separation](../architecture_code_organization/6.api_worker_cron_separation.md) · Next: [Integration Test](2.integration_test.md)

## 1. What is it?

A unit test checks a small behavior in controlled isolation, like testing one calculator operation before wiring it into a cash register.

The useful unit is a coherent behavior, not necessarily exactly one function. Isolation should make failures meaningful and execution deterministic.

## 2. Why do we need it?

Manual checking misses boundary cases after refactors. A wrong discount rule can survive while every HTTP endpoint still returns `200`.

Specific pain: a harmless-looking arithmetic change reverses rounding or accepts negative quantities, and the bug is discovered only after deployment. Fast targeted tests give early, localized evidence.

## 3. Under the hood / mechanism / system flow

### 3a. Arrange, act, assert, and isolation

The runner discovers cases, constructs fresh fixtures, invokes behavior, and reports assertion/exception failures with a nonzero result when appropriate. In-memory tests avoid database/network setup and usually run quickly; that speed does not prove external integrations work.

Inject clocks, randomness, and ports where they affect behavior. Fakes/stubs/mocks can control boundaries, but assertions about every internal method call often couple tests to implementation. [Python unittest](https://docs.python.org/3/library/unittest.html) provides cases, fixtures, assertions, and runners.

### 3b. Development feedback

```text
Behavior requirement → boundary examples → test → implementation/refactor
    → runner pass/fail → local/CI gate
```

An expected application error can be a passing test when the test asserts it. “Tests passed” means checked examples passed, not absence of all bugs. Coverage records execution, not adequacy of assertions.

## 4. How to apply / implement / use it?

Save as `unit_test_demo.py`; run `python3 unit_test_demo.py`. All tests should pass, including rejection cases. Money is integer cents; the chosen rule rounds the discount down to whole cents.

```python
import unittest

def discounted_total(subtotal_cents, percent):
    if type(subtotal_cents) is not int or type(percent) is not int:
        raise ValueError("INVALID_TYPE")
    if subtotal_cents < 0 or not 0 <= percent <= 100:
        raise ValueError("INVALID_RANGE")
    return subtotal_cents - subtotal_cents * percent // 100

class DiscountTests(unittest.TestCase):
    def test_normal_discount(self):
        self.assertEqual(discounted_total(1000, 10), 900)

    def test_boundaries_and_rounding(self):
        for inputs, expected in [((0, 50), 0), ((101, 10), 91), ((100, 0), 100), ((100, 100), 0)]:
            with self.subTest(inputs=inputs):
                self.assertEqual(discounted_total(*inputs), expected)

    def test_invalid_input(self):
        for inputs in [(-1, 10), (100, 101), (True, 10), (100, "10")]:
            with self.subTest(inputs=inputs), self.assertRaises(ValueError):
                discounted_total(*inputs)

if __name__ == "__main__":
    unittest.main(verbosity=2)
```

The example exercises real policy rather than mocking the multiplication operator. Change `//` rounding and consider which assertion should detect the altered contract. Avoid `sleep` or tight timing assertions for ordinary correctness.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not claim unit tests prove SQL constraints, HTTP routing, credentials, or actual provider behavior.
- Do not mock the implementation so completely that no useful behavior is exercised.
- Do not test private structure merely because it exists; prefer externally meaningful results and invariants.
- Do not use shared mutable fixtures that make test order significant.

Unit tests are one layer of evidence. Keep them small and useful, then cover real boundaries with integration/contract tests.

## 6. How do I know I understand it?

**Blank-page check:** write a rule's ordinary, boundary, invalid-type, and invalid-range examples. Explain what is isolated and what is not being proven.

| Constraint change | Predict the failure and response |
| --- | --- |
| Rounding policy changes | Update explicit behavior examples, not hidden assumptions |
| Function starts calling the clock | Inject/control time for reproducibility |
| Implementation is refactored but behavior stays | Tests should remain useful without rewriting every interaction expectation |
| All branches execute but assertions are empty | Coverage alone gives weak correctness evidence |

You understand unit tests when a failing case identifies a behavior regression rather than incidental implementation movement.
