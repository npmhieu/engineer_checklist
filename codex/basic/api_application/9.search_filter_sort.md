# Search / Filter / Sort

[Lesson index](../../README.md) · Previous: [HTTP Status Codes](8.http_status_codes.md) · Next: [Pagination](10.pagination.md)

## 1. What is it?

Search finds relevant records, filtering keeps records matching conditions, and sorting orders the results—like searching a spreadsheet, hiding completed rows, and ordering the rest by date.

These operations answer different questions:

| Operation | Question | Example |
| --- | --- | --- |
| Search | Which records match this text or meaning? | Tasks containing `Learn` |
| Filter | Which records satisfy these predicates? | `completed=false` |
| Sort | In what order should matches appear? | Newest first, then ID descending |

Our small example uses **case-sensitive literal substring search**, not fuzzy matching or relevance ranking. A production search contract must say which behavior it supports.

## 2. Why do we need it?

Downloading every task and filtering in the frontend wastes bandwidth and memory. It can also expose records the caller should never receive. Filtering only the currently displayed page gives incomplete results: a match may exist on another page.

Without explicit sorting, records can jump between responses when database plans change. Without a sort-field allowlist, using request text directly in SQL can allow injection or unexpectedly expensive expressions.

Specific pain: a user has 100,000 tasks but wants the newest 20 unfinished tasks about HTTP. The backend should apply access scope, matching conditions, ordering, and a result bound before returning data.

## 3. Under the hood / mechanism / system flow

### 3a. Query engine one layer down

A relational implementation usually maps filters to `WHERE`, ordering to `ORDER BY`, and a result bound to `LIMIT`. The optimizer chooses a physical plan; it need not execute operators in the exact order the SQL text suggests.

For `n` rows and `k` matches:

- A suitable B-tree index can locate equality/range matches with roughly `O(log n + k)` index work, plus row access and any additional filtering.
- A substring predicate may inspect many or all candidate strings. Cost includes the lengths of those strings, not just row count.
- A separate comparison sort over `k` candidates is commonly `O(k log k)`; large sorts can spill from memory to temporary disk. A matching index order or top-N strategy can reduce this work.
- Indexes consume disk/cache space and add write work. A composite index must fit actual access patterns; one index does not accelerate every filter/sort combination.

These are rough models, not latency guarantees. Inspect query plans and measure representative data. [PostgreSQL's index documentation](https://www.postgresql.org/docs/current/indexes-types.html) describes which operators B-trees support, including limitations for substring patterns.

Full-text engines go deeper: tokenize text, normalize terms, and maintain an inverted index mapping terms to matching document IDs. Ranking then scores candidates. That is different from looking for literal characters; language, stemming, and stop words change results. See [PostgreSQL's full-text search introduction](https://www.postgresql.org/docs/current/textsearch-intro.html).

### 3b. Request lifecycle and boundaries

```text
Query text → validate names/types/limits → trusted caller scope
    → search + filters → deterministic order → bounded page → public response
```

Always scope the query to records the caller can access. `ownerId=7` supplied by a client is not authentication. The examples receive `actor_id` from trusted server context.

Document how multiple conditions combine. Our different filters use AND. Repeated parameters are rejected rather than silently interpreted as OR, lists, or last-value-wins. Sorting uses a unique ID as a tie-breaker. Without `ORDER BY`, SQL does not promise a stable order; see [PostgreSQL's ordering rules](https://www.postgresql.org/docs/current/queries-order.html).

Clients should reset pagination when search, filters, or sort change. Unsupported inputs get our chosen `422`; no matches get `200` with an empty collection, not `404`.

## 4. How to apply / implement / use it?

### Define the contract

Illustrative request: `GET /tasks?q=Learn&completed=false&sort=-created_at`.

| Parameter | Contract |
| --- | --- |
| `q` | Optional literal, case-sensitive substring; at most 80 code points |
| `completed` | Optional exact string `true` or `false` |
| `sort` | `created_at`, `-created_at`, `title`, or `-title`; default newest first |
| Repeated/unknown parameters | Rejected |
| Result bound | At most 20 rows in this small example |

The next lesson replaces a fixed result bound with a continuation contract. Match normalization and collation deliberately: the example does not promise accent-insensitive matching or locale-aware alphabetical order.

### Smallest runnable example

Save as `search_filter_sort_demo.py`; run `python3 search_filter_sort_demo.py`. Uses Python 3's standard library and an in-memory SQLite database. This is a query-layer example, not an HTTP server; an adapter would map `ValueError` to the documented validation response.

```python
import sqlite3
from urllib.parse import parse_qs

database = sqlite3.connect(":memory:")
database.row_factory = sqlite3.Row
database.executescript("""
    CREATE TABLE tasks (
        id INTEGER PRIMARY KEY, owner_id INTEGER NOT NULL,
        title TEXT NOT NULL, completed INTEGER NOT NULL, created_at INTEGER NOT NULL
    );
    CREATE INDEX task_scope_order ON tasks (owner_id, completed, created_at, id);
    INSERT INTO tasks VALUES
        (1, 7, 'Learn HTTP', 0, 10),
        (2, 7, 'Learn SQL', 0, 20),
        (3, 7, 'Other work', 1, 30),
        (4, 8, 'Learn private material', 0, 40);
""")

SORTS = {
    "created_at": "created_at ASC, id ASC",
    "-created_at": "created_at DESC, id DESC",
    "title": "title ASC, id ASC",
    "-title": "title DESC, id DESC",
}


def list_tasks(actor_id, query):
    if len(query) > 1024:
        raise ValueError("QUERY_TOO_LONG")
    values = parse_qs(query, keep_blank_values=True, max_num_fields=10)
    if set(values) - {"q", "completed", "sort"}:
        raise ValueError("UNKNOWN_PARAMETER")
    if any(len(entries) != 1 for entries in values.values()):
        raise ValueError("REPEATED_PARAMETER")
    search = values.get("q", [""])[0]
    completed = values.get("completed", [None])[0]
    sort = values.get("sort", ["-created_at"])[0]
    if len(search) > 80 or completed not in (None, "true", "false") or sort not in SORTS:
        raise ValueError("INVALID_QUERY")
    predicates = ["owner_id = ?"]
    parameters = [actor_id]
    if search:
        predicates.append("instr(title, ?) > 0")
        parameters.append(search)
    if completed is not None:
        predicates.append("completed = ?")
        parameters.append(int(completed == "true"))
    statement = (
        "SELECT id, title, completed, created_at FROM tasks WHERE "
        + " AND ".join(predicates)
        + " ORDER BY " + SORTS[sort] + " LIMIT 20"
    )
    return [dict(row, completed=bool(row["completed"])) for row in database.execute(statement, parameters)]


assert [task["id"] for task in list_tasks(7, "q=Learn&completed=false")] == [2, 1]
assert list_tasks(7, "q=absent") == []
assert list_tasks(7, "q=private") == []
assert list_tasks(7, "q=%27%20OR%201%3D1--") == []

for query in ["sort=title;DROP%20TABLE%20tasks", "completed=no", "q=a&q=b", "ownerId=8"]:
    try:
        list_tasks(7, query)
    except ValueError:
        pass
    else:
        raise AssertionError("Invalid query was accepted")

print("happy: scoped, filtered, sorted results; unhappy: invalid queries rejected")
database.close()
```

SQLite's [`instr`](https://www.sqlite.org/lang_corefunc.html#instr) implements literal substring matching here. SQL values use placeholders. Column names and direction cannot be supplied as ordinary value parameters, so ordering comes only from the server-owned `SORTS` map. The string concatenation above does not insert raw user SQL.

This function assumes the HTTP layer has already bounded the request target and decoded valid query text. The in-memory fixture excludes durable disk I/O, authentication, and a full search index.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not build a separate search cluster for a handful of simple indexed filters. It adds synchronization, operations, and potentially stale results.
- Do not promise relevance, typo tolerance, or Unicode linguistic behavior from a basic substring query.
- Do not expose arbitrary database columns, operators, or sort expressions. Public query fields are an API contract, not a SQL console.
- Do not fetch all rows and filter/sort in application memory by default; the database can often reduce data earlier.
- Do not assume parameterized SQL makes a query cheap. A safe substring query can still scan millions of rows.
- Do not assume an external search index has current permissions. Enforce visibility and handle authorization changes deliberately.

More filter combinations mean more plans, indexes, test cases, and possible performance surprises. Bound query complexity and measure actual workloads rather than indexing every permutation.

## 6. How do I know I understand it?

**Blank-page check:** translate a request into authorization scope, predicates, ordering, and result bounds. Explain which inputs become SQL values and which must select server-owned identifiers.

| Constraint change | Predict the failure and response |
| --- | --- |
| Two tasks share a creation time | Add a unique tie-breaker so ordering remains deterministic |
| User searches `%` | Literal substring contract means `%` is ordinary text, not a wildcard |
| Dataset grows to 10 million rows | Substring scans can dominate; inspect plans, narrow candidates, or use a suitable search index |
| Product wants Vietnamese accent-insensitive matching | Define normalization/collation and test it; current literal matcher is insufficient |
| User changes sort between pages | Restart pagination or reject an incompatible continuation token |

You understand this item when you can explain both the correct result set and the work needed to produce it, without leaking another user's records.
