# Business Validation

[Lesson index](../../README.md) · Previous: [Request Validation](5.request_validation.md) · Next: [Error Handling](7.error_handling.md)

## 1. What is it?

Business validation enforces rules about what the application permits. An **invariant** is a condition that must remain true after an operation finishes.

For a task system, examples include “archived tasks cannot be renamed” and “a task may be completed only when its prerequisites are complete.” These are product rules, not JSON syntax rules.

Compare three questions:

| Check | Question | Example |
| --- | --- | --- |
| Request validation | Is the input acceptable? | Is `title` a non-empty string? |
| Authorization | May this actor perform the action? | Does this user own the task? |
| Business validation | Is this operation allowed in this state? | Is the task still editable? |

Business rules can be state-independent too: an end date preceding a start date is invalid even without a database lookup. State dependence is useful context, not the definition of business validation.

## 2. Why do we need it?

Well-formed requests can still cause incorrect behavior. `{"title":"New title"}` is valid JSON with valid fields, but must not rename an archived task under our example policy.

Rules must apply regardless of entry point: HTTP, background job, import, or administrative script. Keeping them only in controllers allows other entry points to bypass them.

Business validation also protects meaning: balances cannot become negative, paid invoices cannot be edited freely, and only allowed workflow transitions should occur. The exact rules come from the product, not from the framework.

## 3. How to apply / implement / use it?

### Express rules as examples

For renaming a task, define:

- Active task + allowed actor + valid title → rename succeeds.
- Archived task + allowed actor + valid title → `TaskArchived` failure; title unchanged.
- Active task + disallowed actor → access denied; title unchanged.

Represent expected failures with meaningful error types or result values. Keep HTTP numbers out of domain rules; the API boundary can map `TaskArchived` to this API's chosen `409` response.

### Enforce rules near the operation

Framework-neutral pseudocode:

```text
renameTask(actor, taskId, title):
    begin database transaction
    task = repository.findForUpdate(taskId)
    if missing:
        raise TaskNotFound
    require actor may edit task
    task.rename(title)       # checks archived state and title invariant
    repository.save(task)
    commit transaction

Task.rename(title):
    if archived:
        raise TaskArchived
    require valid task title
    self.title = title
```

Rollback on any failure. The HTTP adapter validates request shape before calling this function. The domain still enforces important invariants because non-HTTP callers can invoke it.

Simple rules concerning one object fit in that object. Rules involving several objects fit in an application/domain service with the required data. Small applications can use service functions without building a large domain framework.

### Make checks hold under concurrency

Consider one remaining seat and two simultaneous bookings:

```text
Unsafe: both read available = 1, both pass validation, both book.

Safer local database operation:
UPDATE events
SET available = available - 1
WHERE id = :eventId AND available > 0;
```

Check the affected-row count: zero means no decrement occurred. Persist the booking in the **same transaction**, so a failed insert rolls back the decrement. This protects that inventory operation; duplicate bookings may need an additional uniqueness rule.

A transaction alone is not enough if both requests can read stale state before unconditional writes. Choose atomic conditional writes, row locks, an appropriate isolation level, or version checks to match the invariant.

For uniqueness, a pre-check can improve feedback, but a database unique constraint must protect the final write. Translate that specific constraint violation into a known conflict. [PostgreSQL's constraint documentation](https://www.postgresql.org/docs/current/ddl-constraints.html) explains unique, check, and foreign-key constraints; an ordinary row CHECK is not a general mechanism for cross-row rules.

## 4. When should I NOT use this? Trade-offs and anti-patterns

Do not skip required business rules. Avoid using a heavy rule engine for a handful of straightforward conditions; named functions are often easier to inspect and change.

Other anti-patterns:

- Enforcing rules only in the frontend or HTTP handler.
- Reading “no duplicate exists” and assuming that protects a later insert.
- Treating an unavailable dependency as proof a business rule passed.
- Holding database locks while waiting for slow external services.
- Duplicating evolving rules across services without a clear owner.

Synchronous cross-service validation adds latency and can become stale immediately. For cross-service workflows, decide whether a reservation, pending state, or compensating action is needed. A local database transaction cannot make an external payment call atomic.

Strict consistency costs coordination; eventual consistency permits temporary gaps. Choose based on the invariant: a profile display can lag, while spending the same balance twice usually cannot.

## 5. How do I know I understand it?

Write “given / when / then” cases for the rename rule. Include a non-HTTP caller and simultaneous updates.

Answer checks:

| Scenario | Expected reasoning |
| --- | --- |
| Valid title, archived task | Business failure; request shape is valid |
| Valid title, wrong owner | Authorization failure |
| Two users claim one seat | One successful claim; enforce at atomic write/lock boundary |
| Two users choose one unique username | Database constraint resolves the race |
| Import renames archived task | Shared business operation must reject it too |

You understand business validation when you can name the invariant, identify who enforces it, and show why concurrent or alternative entry points cannot bypass it.
