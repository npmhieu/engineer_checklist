# Error Handling

[Lesson index](../../README.md) · Previous: [Business Validation](6.business_validation.md) · Next: [HTTP Status Codes](8.http_status_codes.md)

## 1. What is it?

Error handling detects failures, keeps state valid, and reports safe outcomes, like a failed bank transfer returning a clear receipt without leaving only half the transfer applied.

Two useful categories:

- **Expected failures:** invalid fields, missing tasks, forbidden actions, and business conflicts. They are normal branches of an application contract.
- **Unexpected failures:** programming bugs, unavailable infrastructure, or unhandled dependency behavior. They need controlled responses and diagnostic evidence.

An exception is one mechanism for propagating failure. A typed result such as `Success(task) | TaskArchived` is another. Error handling includes both; it is more than adding `try/catch`.

## 2. Why do we need it?

Clients need to decide whether to correct input, authenticate, refresh state, wait, or contact support. Operators need enough context to diagnose failures.

The application must also avoid partial writes and false success. If saving a task fails, returning a success body does not make the task exist.

For example, an archived-task conflict should tell the caller why renaming failed. An unexpected database failure should return a safe message while retaining internal diagnostics. [OWASP's error handling guidance](https://cheatsheetseries.owasp.org/cheatsheets/Error_Handling_Cheat_Sheet.html) explains separating public responses from internal error details.

## 3. Under the hood / mechanism / system flow

### 3a. Propagation and cleanup one layer down

An exception transfers control up the call stack to a matching handler; scoped cleanup runs as frames unwind. Typed results instead force callers to inspect a success/failure value and propagate it explicitly. Neither mechanism automatically reverses database writes, cancels external work, or prevents a process crash.

For a local transaction, a context manager can request rollback before the exception reaches the HTTP boundary. Files and connections also need cleanup. Stack traces, response serialization, and synchronous logging consume CPU, allocations, and I/O; an outage can turn unrestricted error logging or retries into another bottleneck.

### 3b. Error-to-response lifecycle

```text
Operation fails → service adds meaning or propagates
    → transaction rolls back / resources release
    → outer boundary classifies failure
    → safe status + stable code + request ID reach client
    → redacted diagnostics + metrics reach operators
```

The boundary is a translation point, not the owner of business rules. A known `TaskArchived` failure becomes a documented conflict; an unknown exception becomes a generic server failure. Clients branch on stable codes and decide whether to correct input, refresh state, or try later. Infrastructure sees the actual HTTP status, not an embedded JSON number.

Rollback only applies before a successful commit. If commit succeeds and response delivery fails, state remains changed even if the client sees a connection error. A timeout during commit can also leave the outcome uncertain. Use idempotency keys or reconciliation instead of assuming every error means “nothing happened.”

## 4. How to apply / implement / use it?

### Translate errors at the application boundary

Keep domain errors independent of HTTP. Map them in middleware or a shared HTTP adapter:

| Internal outcome | This API's response policy |
| --- | --- |
| Malformed JSON | `400`, `INVALID_JSON` |
| Invalid request fields | `422`, `VALIDATION_FAILED` |
| Task not found | `404`, `TASK_NOT_FOUND` |
| Archived task cannot be edited | `409`, `TASK_ARCHIVED` |
| Unexpected exception | `500`, `INTERNAL_ERROR` |

These mappings are contract choices. The next lesson covers the status semantics.

### Choose a consistent response envelope

The earlier lessons used a custom `error` object. A standardized alternative is **Problem Details**, defined by [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html). Use `application/problem+json`; add documented extensions for application codes and field errors.

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json
Cache-Control: no-store
X-Request-ID: req-8f31

{
  "type": "https://api.example.com/problems/task-archived",
  "title": "Task cannot be edited",
  "status": 409,
  "detail": "Archived tasks cannot be renamed.",
  "instance": "/requests/req-8f31",
  "code": "TASK_ARCHIVED",
  "requestId": "req-8f31"
}
```

The example URI identifies a problem type; in a real API, document that type. `instance` identifies this occurrence. `code` and `requestId` are application extensions. Clients should branch on stable identifiers, not human-readable message wording. The body's `status`, when present, must match the response status generated by the server.

Choose one public format for a given contract. Replacing an established format requires a compatibility plan; introducing Problem Details is not a reason to break existing clients.

### Preserve state and useful evidence

Framework-neutral pseudocode:

```text
HTTP error boundary(request):
    requestId = generateRequestId()
    try:
        return dispatch(request)
    catch expected application error:
        return mapped safe problem response with requestId
    catch unexpected error:
        log error, stack trace, route, and requestId securely
        return generic 500 problem response with requestId
```

Transaction code must roll back failed writes before the boundary sends a response. Release files, locks, and connections through scoped cleanup or `finally`. Log unexpected errors once at the responsible boundary, avoiding duplicate stack traces at every layer. Record expected failures at an appropriate severity rather than flooding error logs.

Never send stack traces, SQL statements, credentials, or database connection details to clients. Redact sensitive data in logs too; a request ID can correlate a safe response with restricted diagnostics.

### Recover only when justified

Retry transient operations with bounded attempts and backoff when their effects are safe to repeat. A lost response does not establish that a write failed. Payment or creation retries need idempotency or reconciliation.

If a response has already started streaming, middleware cannot reliably replace it with a new JSON status/body. Record the failure and end the stream according to its protocol.

### Smallest runnable boundary and rollback example

Save as `error_handling_demo.py`; run `python3 error_handling_demo.py`. This tests an HTTP-style adapter as a function returning `(status, body)`; it does not open a socket. The example uses Problem Details for errors and a normal resource body for success.

```python
import logging
import sqlite3
from http import HTTPStatus
from uuid import uuid4


class TaskArchived(Exception):
    pass


database = sqlite3.connect(":memory:")
database.executescript("""
    CREATE TABLE tasks (id INTEGER PRIMARY KEY, title TEXT, archived INTEGER);
    INSERT INTO tasks VALUES (1, 'Original', 0);
""")


def rename_task(title, fail_after_write=False):
    with database:
        archived = database.execute("SELECT archived FROM tasks WHERE id = 1").fetchone()[0]
        if archived:
            raise TaskArchived()
        database.execute("UPDATE tasks SET title = ? WHERE id = 1", (title,))
        if fail_after_write:
            raise RuntimeError("SIMULATED_STORAGE_FAILURE")
    return {"id": 1, "title": title}


def boundary(operation):
    request_id = uuid4().hex
    try:
        return 200, operation()
    except TaskArchived:
        status, code = 409, "TASK_ARCHIVED"
    except Exception as error:
        logging.error("request_id=%s failure_type=%s", request_id, type(error).__name__)
        status, code = 500, "INTERNAL_ERROR"
    return status, {
        "type": "about:blank", "title": HTTPStatus(status).phrase,
        "status": status, "code": code, "requestId": request_id,
    }


assert boundary(lambda: rename_task("Saved")) == (200, {"id": 1, "title": "Saved"})

with database:
    database.execute("UPDATE tasks SET archived = 1 WHERE id = 1")
status, body = boundary(lambda: rename_task("Forbidden change"))
assert status == 409 and body["code"] == "TASK_ARCHIVED"

with database:
    database.execute("UPDATE tasks SET archived = 0 WHERE id = 1")
status, body = boundary(lambda: rename_task("Uncommitted", fail_after_write=True))
assert status == 500 and body["code"] == "INTERNAL_ERROR"
assert "SIMULATED_STORAGE_FAILURE" not in str(body)
assert database.execute("SELECT title FROM tasks WHERE id = 1").fetchone()[0] == "Saved"
print("happy: saved; unhappy: conflict and safe 500; failed write rolled back")
database.close()
```

One `ERROR` log line is expected for the injected failure. The log deliberately records only an identifier and exception class, not exception text that might contain secrets. Production diagnostics can include restricted, redacted stack context. An HTTP implementation must additionally set the actual status, `Content-Type: application/problem+json`, request ID header, and deliberate cache headers; returning this tuple alone does not send a response.

This single-connection demo is about rollback and translation, not concurrent editing, full authentication, or every mapped error type.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Handle failure deliberately, but avoid catching an error where you cannot recover, add context, or translate it.

- Catching everything and returning `200` makes failures invisible.
- Returning an empty collection after a database failure falsely claims a successful read.
- Retrying validation failures wastes resources; the request needs correction.
- Retrying every dependency failure can amplify an outage or duplicate writes.
- Treating every database error as “duplicate record” hides real defects.
- Continuing after a failed invariant check can persist invalid state.

A generic fallback protects clients but is insufficient without logs and metrics. Detailed public errors improve usability but can disclose resource existence; access-denied responses may intentionally conceal it.

## 6. How do I know I understand it?

Describe or test four cases: invalid title, missing task, archived task, and an unexpected storage exception.

For every case, verify status, stable code, public message, diagnostic context, and persistent state.

| Scenario | Expected behavior |
| --- | --- |
| Storage fails before commit | No success response; transaction rolls back |
| Task is archived | Known conflict response; no stack trace exposed |
| Internal exception contains a password | Public response excludes it; logs redact it |
| Client loses response after commit | Outcome uncertain; no blind non-idempotent retry |

You understand error handling when failures remain visible, state remains valid, and clients receive enough safe information to choose their next action.

**Blank-page check:** draw a failure at each boundary: parsing, rule check, database write, commit, and response transmission. For each, state what the client knows, what persisted, what is logged, and whether retry is safe.

**Change a constraint:** a database write now also charges an external card. The local rollback no longer guarantees an undone charge; design idempotency and reconciliation. Responses now stream: after headers/body start, an outer handler cannot replace them with a fresh `500` JSON response.
