# Request Validation

[Lesson index](../../README.md) · Previous: [CRUD Resource](4.crud_resource.md) · Next: [Business Validation](6.business_validation.md)

## 1. What is it?

Request validation checks whether incoming input satisfies the API's input contract before application behavior uses it. Check path parameters, query parameters, headers, and bodies—not only JSON fields.

Examples: a task ID must be a positive integer; a title must be a string; `limit` must be between 1 and 100. Parsing answers “can I decode this?” Validation answers “does the decoded value satisfy the contract?”

For these lessons, **request validation** covers input shape, types, formats, and documented value limits. **Business validation** checks whether an operation is allowed by application rules and current state. The boundary is an organizational choice: a title length rule can be checked at the HTTP boundary and enforced again by the domain model.

## 2. Why do we need it?

Clients can be buggy, outdated, or hostile. A frontend form is not a trusted boundary; a caller can send requests directly.

Early validation gives callers useful feedback and prevents malformed data from reaching storage or expensive work. Input size and collection limits also bound resource consumption.

For example, rejecting `{"title":42}` near the API boundary is clearer than letting it cause a string-processing exception deep inside a service. [OWASP's input validation guidance](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html) covers server-side checks and allowlisting.

## 3. How to apply / implement / use it?

### Write a contract before writing checks

Example `POST /tasks` contract:

| Input | Rule |
| --- | --- |
| Media type | `application/json` |
| Body | JSON object; example size limit 16 KiB |
| `title` | Required string, 1–120 Unicode code points after trimming |
| `completed` | Optional boolean, defaults to `false` |
| Unknown fields | Rejected in this example |
| `id`, `ownerId` | Not accepted; assigned by server context |

Define what length means: bytes, code points, and visible characters differ. Keep application and database limits compatible.

### Validate cheaply before using data

Framework-neutral pseudocode:

```text
parseCreateTask(request):
    enforce body size limit while reading
    require supported JSON media type
    body = parse JSON or raise MalformedRequest
    require body is an object
    require keys are a subset of {title, completed}
    require title exists and is a string
    title = trim(body.title)
    require codePointLength(title) is between 1 and 120
    if completed exists:
        require completed is a boolean
    return CreateTaskInput(title, completed default false)
```

Use framework limits and a schema validator where available. Ensure exceptions from parsing and validation reach the error mapper. This example maps malformed JSON to `400`, unsupported media type to `415`, oversized content to `413`, and invalid decoded fields to `422`. A consistent `400` field-validation policy is also possible; document it.

For `GET /tasks?limit=20`, query values arrive as text. Parse an entire valid integer and apply bounds. Do not accept `20abc` because a permissive conversion reads its leading digits.

### Define updates separately

For PUT, require the documented replacement fields. For PATCH, omitted means unchanged; `false`, an empty string, and `null` are distinct values. Under the earlier JSON Merge Patch contract, `null` requests removal; reject removal of a required title. Do not use truthiness to decide whether a boolean was supplied.

### Return actionable field errors

An application-defined error body could be:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Request fields are invalid",
    "fields": [{"path":"title","code":"REQUIRED"}]
  }
}
```

Stable field paths and codes help clients highlight problems. Do not echo passwords, tokens, or full sensitive input. [Error Handling](7.error_handling.md) shows a standardized alternative envelope.

## 4. When should I NOT use this? Trade-offs and anti-patterns

Keep boundary validation; avoid treating it as the only correctness or security mechanism.

- Checking that `projectId` is an integer does not establish permission to use that project.
- Checking an email's format does not prove ownership or deliverability.
- Validation does not replace parameterized SQL, output encoding, or database constraints.
- Checking stock or uniqueness only here is vulnerable to concurrent requests.
- Giant regular expressions can be hard to maintain and expensive on hostile input.
- Silently coercing `"false"` to a truthy value can change meaning.

Rejecting unknown fields catches typos and unintended writes, but can hinder evolving clients. Ignoring unknown fields can improve compatibility, but must never allow automatic assignment to internal properties. Choose an explicit policy.

Do not “sanitize” arbitrary input by silently deleting characters until it passes. Normalize only documented transformations; reject input whose meaning would otherwise change.

## 5. How do I know I understand it?

Predict outcomes under the contract above:

| Input | Expected outcome |
| --- | --- |
| `{"title":" Learn "}` | Accepted; normalized title is `Learn` |
| `{"title":"   "}` | `422`, title too short after trimming |
| `{"title":12}` | `422`, wrong type |
| `{"title":"Learn","completed":"false"}` | `422`, string is not boolean |
| `{"title":"Learn","ownerId":99}` | `422`, forbidden/unknown input field |
| Broken JSON | `400`, parsing failed |
| Valid ID for another user's project | Shape may pass; authorization must still fail |

Implement or describe checks at the minimum, maximum, just outside each bound, missing values, nulls, and wrong types. You understand this item when accepted input has a clear typed shape and invalid input fails predictably before side effects.
