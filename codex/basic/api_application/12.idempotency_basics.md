# Idempotency Basics

[Lesson index](../../README.md) · Previous: [API Versioning](11.api_versioning.md)

## 1. What is it?

Idempotency means repeating the same operation has the same intended effect as doing it once, like pressing “set volume to 20” repeatedly instead of pressing “increase volume by 1.”

For an operation `f`, the state intuition is `f(f(state)) = f(state)`. Responses need not be identical. Deleting an existing task may return `204` first and `404` next while the intended final state remains “task absent.”

Request deduplication with an idempotency key is one way to make a retryable create safe. It is not the definition of every idempotent operation.

## 2. Why do we need it?

Networks fail after work succeeds. A server can commit a task, then lose its connection before the client receives the response. The client cannot tell whether the task exists and retries; a naive POST creates another task.

Disabling a submit button only reduces one source of duplicates. It does not stop network retries, timeouts, another browser tab, or repeated delivery by infrastructure.

Specific pain: one user intent becomes two records, two notifications, or two inventory deductions. Correct retry handling must recognize **the same intent**, not merely two requests with similar content.

## 3. Under the hood / mechanism / system flow

### 3a. Deduplication storage one layer down

A common record contains:

| Field | Purpose |
| --- | --- |
| Caller/tenant scope + operation + key | Identify one retryable intent without crossing users/endpoints |
| Request fingerprint | Reject reuse of that key for different semantic input |
| State/result | Distinguish in-progress work from a completed stored outcome |
| Stored status/body/relevant headers | Replay the documented result |
| Retention/expiry | Bound storage and define how long retries are protected |

The key needs an atomic uniqueness boundary, not an unsynchronized dictionary lookup. A lookup against an indexed record is typically logarithmic database work; hashing and serialization cost roughly the size of the normalized input/result. Retaining results consumes storage and may retain sensitive data. Expiry cleanup and additional writes are real costs.

For a short operation entirely inside one database, the business write and completed idempotency record can commit in the **same transaction**. Then there is no committed “task created but deduplication record missing” gap. Independent external effects cannot be included just by adding a local transaction.

### 3b. Retry lifecycle and HTTP semantics

```text
Client creates key for one intent → authenticates → sends request
    → server validates + scopes key + fingerprints normalized input
    → atomic lookup/claim
        existing same input: replay documented outcome
        existing different input: reject key reuse
        new input: perform operation + save outcome atomically
    → commit → response
Lost response? Client retries same intent with same key and same input.
```

Two simultaneous requests must coordinate. “Check key, run operation, store key” in independent commits is unsafe: both can see no key and both execute. Approaches include database uniqueness plus transactions/locking, or an explicit pending/completed protocol with recovery rules. Merely adding a cache lock with an expiry leaves crash/recovery gaps.

[RFC 9110 defines idempotent HTTP methods](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2). GET/HEAD are safe and idempotent by their defined semantics; PUT and DELETE are idempotent but not safe because they can mutate state. POST and PATCH are not inherently idempotent, though an individual operation can be designed that way. A PATCH that sets `completed=true` differs from one that increments a counter.

An idempotent method does not promise identical response bodies, no logs, or no audit records. It also does not solve conflicting edits from different intents; use concurrency control for that.

The exact key header, conflict status, retention period, and error-replay policy are API contracts, not universal behavior. For example, [Stripe's documented implementation](https://docs.stripe.com/api/idempotent_requests) compares parameters and can replay a stored result including a `500`. Our demonstration below deliberately stores only outcomes committed with its local operation.

## 4. How to apply / implement / use it?

### Define the contract before adding a key

Illustrative request:

```http
POST /v1/tasks HTTP/1.1
Content-Type: application/json
Idempotency-Key: 63c704c3-95b1-47cc-a149-7b5f936692e7

{"title":"Learn retries"}
```

Generate a new high-entropy key for each new user intent; reuse it only for retries of that intent. Do not generate a new key on every retry, and do not use one global key for all creates.

Our chosen policy:

- Authenticate and authorize before consulting/replaying a caller-scoped outcome. A key is not a credential.
- Accept a nonempty key of at most 128 characters and a valid title. The production input layer also bounds bytes and header format.
- Normalize title by documented trimming before fingerprinting.
- Same caller/operation/key and semantic input returns the original `201`, body, and `Location`.
- Same caller/operation/key with different input maps to `409 IDEMPOTENCY_KEY_REUSED`.
- Invalid input is rejected before a write. A failure before transaction commit leaves no task or completed key record.
- A different caller has a different key scope, even if the key text matches.

### Smallest runnable local transaction example

Save as `idempotency_demo.py`; run `python3 idempotency_demo.py`. Python 3 standard library only. This is an application operation returning an HTTP-style result, not a socket server. `actor_id` comes from trusted authentication context; task creation is assumed authorized for that caller.

```python
import hashlib
import json
import sqlite3


class KeyReused(Exception):
    pass


database = sqlite3.connect(":memory:")
database.executescript("""
    CREATE TABLE tasks (
        id INTEGER PRIMARY KEY, owner_id INTEGER NOT NULL, title TEXT NOT NULL
    );
    CREATE TABLE idempotency (
        actor_id INTEGER NOT NULL, operation TEXT NOT NULL, key TEXT NOT NULL,
        fingerprint TEXT NOT NULL, response TEXT NOT NULL,
        PRIMARY KEY (actor_id, operation, key)
    );
""")


def create_task(actor_id, key, title, fail_before_commit=False):
    if not isinstance(key, str) or not 1 <= len(key) <= 128 or not key.strip():
        raise ValueError("INVALID_IDEMPOTENCY_KEY")
    if not isinstance(title, str) or not 1 <= len(title.strip()) <= 120:
        raise ValueError("INVALID_TITLE")
    title = title.strip()
    operation = "POST /v1/tasks"
    encoded = json.dumps({"title": title}, sort_keys=True, separators=(",", ":"))
    fingerprint = hashlib.sha256(encoded.encode("utf-8")).hexdigest()
    with database:
        database.execute("BEGIN IMMEDIATE")
        existing = database.execute(
            "SELECT fingerprint, response FROM idempotency "
            "WHERE actor_id = ? AND operation = ? AND key = ?",
            (actor_id, operation, key),
        ).fetchone()
        if existing is not None:
            if existing[0] != fingerprint:
                raise KeyReused("IDEMPOTENCY_KEY_REUSED")
            return json.loads(existing[1])
        created = database.execute(
            "INSERT INTO tasks (owner_id, title) VALUES (?, ?)", (actor_id, title)
        )
        task_id = created.lastrowid
        response = {
            "status": 201, "headers": {"Location": f"/v1/tasks/{task_id}"},
            "body": {"id": task_id, "title": title},
        }
        database.execute(
            "INSERT INTO idempotency VALUES (?, ?, ?, ?, ?)",
            (actor_id, operation, key, fingerprint, json.dumps(response)),
        )
        if fail_before_commit:
            raise RuntimeError("SIMULATED_FAILURE_BEFORE_COMMIT")
        return response


first = create_task(7, "intent-1", "Learn retries")
retry = create_task(7, "intent-1", " Learn retries ")
assert retry == first
assert database.execute("SELECT COUNT(*) FROM tasks").fetchone()[0] == 1

try:
    create_task(7, "intent-1", "Different request")
except KeyReused as error:
    assert str(error) == "IDEMPOTENCY_KEY_REUSED"
else:
    raise AssertionError("Different input reused a key")

try:
    create_task(7, "intent-2", "Second task", fail_before_commit=True)
except RuntimeError:
    pass
else:
    raise AssertionError("Injected failure was not raised")
assert database.execute("SELECT COUNT(*) FROM tasks").fetchone()[0] == 1
assert database.execute("SELECT COUNT(*) FROM idempotency").fetchone()[0] == 1

second = create_task(7, "intent-2", "Second task")
other_caller = create_task(8, "intent-1", "Learn retries")
assert second["body"]["id"] != first["body"]["id"]
assert other_caller["body"]["id"] != first["body"]["id"]
assert database.execute("SELECT COUNT(*) FROM tasks").fetchone()[0] == 3
print("happy: replay one result; unhappy: key conflict and failed transaction stay safe")
database.close()
```

`BEGIN IMMEDIATE` acquires SQLite's write transaction before the lookup, serializing writers to the same database. Other connections can wait or receive a busy error; they must not bypass deduplication in response. See [SQLite transaction behavior](https://www.sqlite.org/lang_transaction.html). A different database needs its own correct claim/locking design, not a blind copy of this SQL.

The transaction context exits before the function actually returns its result to its caller; if commit fails, an exception propagates instead. The injected failure demonstrates rollback of both tables. A retry after an imagined lost successful response returns the same stored result without another task.

Limits: this single connection and `:memory:` fixture do not survive restarts and are not a concurrent-server implementation. Persistent retry protection needs a properly configured shared durable database and independent connections/transactions. The demo retains keys indefinitely and has no pending state because the complete local operation fits in one transaction. It does not charge a card, send a notification, or claim to make such effects atomic.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not add a result store to ordinary GET reads merely because clients retry them; preserve safe method semantics instead.
- Do not deduplicate only by body hash. Two intentionally identical task creates can be two legitimate intents.
- Do not store keys only in one API process's memory when retries can hit another replica or arrive after restart.
- Do not save a “completed” key before the business effect commits, or save it afterward in a separate uncoordinated commit.
- Do not keep a database lock open across a slow external request. Use an explicit recoverable workflow and downstream idempotency where available.
- Do not claim exactly-once execution for arbitrary distributed effects. A key protects only its documented scope and retention window.

When expired records are deleted, reusing the old key may execute the request again. Publish that window and set it according to realistic retry/recovery needs. Stored responses require access controls, redaction/retention policy, and storage limits. Replayed snapshots can differ from a resource's current state; the API should distinguish replaying the operation outcome from reading current state.

For async work, atomically creating one job is not the same as delivering one notification: the worker and its effects need their own duplicate-handling strategy. That belongs to advanced idempotency and idempotent consumers.

## 6. How do I know I understand it?

**Blank-page check:** draw failure points before write, after write/before commit, and after commit/before response. For each, explain what persisted and what a same-key retry does. Then draw two simultaneous requests and identify the atomic boundary that prevents two committed effects.

| Constraint change | Predict the failure and response |
| --- | --- |
| Retry generates a fresh key | Server sees a new intent; duplicates become possible |
| Same key carries a different title | Reject mismatch rather than return an unrelated result |
| Caller changes but key stays equal | Use separate authorization/key scope; never replay another user's body |
| Server restarts with memory-only keys | Protection is lost; use shared durable storage |
| Request includes an external payment | Local rollback cannot undo it; coordinate downstream keys and reconciliation |
| Key expires before a late retry | Request may execute again under the published retention policy |
| Two different keys update one task | Idempotency does not resolve their conflict; add concurrency control |

You understand idempotency when you can distinguish repeated intent, independent intent, retry-safe state changes, replayed responses, and uncertain distributed outcomes.
