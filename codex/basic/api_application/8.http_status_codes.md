# HTTP Status Codes

[Lesson index](../../README.md) · Previous: [Error Handling](7.error_handling.md)

## 1. What is it?

An HTTP status code is a three-digit response value describing the result of a request. It has protocol meaning independent of an application's JSON fields.

The first digit identifies its class: `1xx` informational, `2xx` successful, `3xx` redirection, `4xx` client-related error, and `5xx` server-related error. A request can receive informational responses before its final response.

The status is a broad outcome. An application code such as `TASK_ARCHIVED` explains the specific reason. A JSON body saying `"status":500` does not override an actual HTTP `200` response.

## 2. Why do we need it?

Clients, monitoring systems, caches, and gateways use status codes without needing to understand every application's response schema.

A task app can use them to decide whether to show new data, highlight a field, request login, or refresh stale state. Monitoring can distinguish expected rejected requests from server failures.

Status codes improve interoperability, but cannot express every product detail. Pair them with a documented body when useful, and with headers required by their semantics.

## 3. How to apply / implement / use it?

### Learn a practical set

The following compact meanings follow [RFC 9110's status definitions](https://www.rfc-editor.org/rfc/rfc9110.html#section-15). The task examples below apply those meanings to our learning API.

| Code | Meaning |
| --- | --- |
| `200 OK` | Request succeeded |
| `201 Created` | Resource created |
| `202 Accepted` | Accepted; processing incomplete |
| `204 No Content` | Success without response content |
| `304 Not Modified` | Cached representation can be reused after conditional retrieval |
| `400 Bad Request` | Invalid request |
| `401 Unauthorized` | Valid authentication credentials missing |
| `403 Forbidden` | Server refuses request |
| `404 Not Found` | Resource not found or existence concealed |
| `405 Method Not Allowed` | Method unsupported for target |
| `409 Conflict` | Conflict with current resource state |
| `412 Precondition Failed` | Request precondition failed |
| `413 Content Too Large` | Request content exceeds accepted size |
| `415 Unsupported Media Type` | Request content format unsupported |
| `422 Unprocessable Content` | Understood content cannot be processed as instructed |
| `500 Internal Server Error` | Unexpected server failure |
| `502 Bad Gateway` | Gateway received invalid upstream response |
| `503 Service Unavailable` | Service temporarily unavailable |
| `504 Gateway Timeout` | Gateway did not receive timely upstream response |

`429 Too Many Requests` indicates rate limiting and may include `Retry-After`; see [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html#section-4).

### Apply codes to concrete outcomes

Use `201` and `Location: /tasks/42` after creating a task. Use `200` for an empty list: `{"items":[]}`. Use `204` after deletion when no response body is needed.

For an export, return `202` with a job ID and status URL while work continues. Do not claim that the export has finished.

In this API, malformed JSON produces `400`, while a decoded but invalid title produces `422`. This separation is a contract policy; some APIs use `400` for both. An archived task produces `409` because renaming conflicts with its state.

A failed `If-Match` version precondition produces `412`. Do not relabel it `409` merely because both may involve concurrent updates.

### Include the right headers and content

- A `401` response must include an applicable `WWW-Authenticate` challenge.
- A `405` response must include `Allow` with supported methods.
- `204` and `304` have no response content. HEAD responses also have no content, even when the corresponding GET would return a body.
- A conditional GET can receive `304`; it does not mean “your update changed nothing.”
- For planned temporary unavailability, `503` can include `Retry-After`.

For the bearer-token example below, `WWW-Authenticate: Bearer realm="tasks"` supplies the authentication challenge. Detailed bearer authentication behavior is specified in [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html#section-3).

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="tasks"
Content-Type: application/json
Cache-Control: no-store

{"error":{"code":"AUTHENTICATION_REQUIRED"}}
```

Authentication answers who the caller is; authorization answers what they may do. A recognized user lacking permission commonly gets `403`. A privacy policy may return `404` to conceal a protected resource's existence.

Inspect actual response codes with `curl -i URL` or a browser's Network panel. In framework code, set the response status explicitly; serializing JSON alone often defaults to `200`.

## 4. When should I NOT use this? Trade-offs and anti-patterns

HTTP responses always have a status; the choice is how to use standard meanings appropriately.

- Do not encode every outcome as `200` for an ordinary HTTP resource API.
- Do not invent a different status for every business rule; use stable application codes.
- Do not return `401` merely because an authenticated user lacks access.
- Do not return `404` for every empty search result.
- Do not use `500` for a known field-validation failure.
- Do not assume every `5xx` can safely be retried or that a write was rolled back.

Use gateway codes when the component is acting as a gateway and the relevant upstream condition occurred. A database exception in application code is not automatically `502`.

Existing protocols can define different outcome conventions, such as RPC errors in a structured response. Follow their specifications instead of changing them to resemble this resource API. Inside business logic, use domain results; translate them to HTTP at the boundary.

Status choices and cache behavior interact. Protected or temporary error responses need deliberate cache headers, since some outcomes such as `404` can be cached.

## 5. How do I know I understand it?

Choose a response before reading the answer:

| Scenario | Answer under this contract |
| --- | --- |
| Task created immediately | `201`, created task, `Location` |
| Export queued | `202`, job ID/status URL |
| No matching tasks | `200`, empty collection |
| Invalid JSON | `400` |
| Missing bearer credentials | `401`, authentication challenge |
| Authenticated caller lacks access | `403`, or documented concealment policy |
| Archived task rename | `409` |
| `If-Match` fails | `412` |
| Too many calls | `429`, retry guidance when available |
| Unexpected implementation bug | `500`, safe error body |

You understand status codes when you can explain the meaning, choose matching headers and content, and distinguish protocol outcomes from application-specific reasons.
