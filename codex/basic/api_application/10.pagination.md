# Pagination

[Lesson index](../../README.md) · Previous: [Search / Filter / Sort](9.search_filter_sort.md) · Next: [API Versioning](11.api_versioning.md)

## 1. What is it?

Pagination splits an ordered result set into bounded pieces, like reading several pages of a book instead of receiving the entire book at once.

Unlike a printed book, a live database can change between page requests. Defining page size alone is not enough: define ordering, continuation, and consistency expectations too.

## 2. Why do we need it?

An unbounded list can exhaust server memory, saturate bandwidth, make clients slow to render, and keep database connections busy. A client asking for 20 records should not receive 2 million.

Pagination bounds response size and client work. It does **not** automatically bound database work: sorting a large candidate set, computing a total count, or skipping a deep offset can still be expensive.

Specific pain: page 50,000 gets slower than page 1, or newly inserted rows cause users to see the same task twice while scrolling.

## 3. Under the hood / mechanism / system flow

### 3a. Offset versus keyset access

| Strategy | SQL idea | Strength | Cost/limitation |
| --- | --- | --- | --- |
| Offset/page number | `ORDER BY ... LIMIT 20 OFFSET 1000` | Easy jump to a page | Must work through skipped rows; concurrent edits shift positions |
| Keyset/seek | `WHERE (created_at,id) < (?,?) ORDER BY created_at DESC,id DESC LIMIT 20` | Continue after a known position | Needs compatible ordering/index; arbitrary page jumps are harder |

With a matching index and simple predicates, keyset access is roughly `O(log n + page_size)` index work; offset access also traverses the skipped prefix. Actual plans, visibility checks, joins, and residual filters can add substantial work. [PostgreSQL's LIMIT/OFFSET documentation](https://www.postgresql.org/docs/current/queries-limit.html) explains both the skipped-row cost and the need for unique ordering.

A cursor is an API continuation token. It may encode a keyset position, an offset, or server-side state: “uses a cursor” does not prove keyset efficiency. SQLite documents a [row-value scrolling query](https://www.sqlite.org/rowvalue.html#scrolling_window_queries) illustrating keyset access.

Fetch `limit + 1` rows to detect another page, return only `limit`, and construct the next cursor from the **last returned row**, not the extra row. Otherwise the extra row can be skipped. Response buffering is roughly proportional to page size and row width. Large individual fields may still require separate projection or download endpoints.

### 3b. Continuation and changing state

```text
Validate limit + cursor → reapply authorization and filters
    → apply cursor boundary + stable order → fetch limit + 1
    → items + next_cursor → client repeats until next_cursor is null
```

For descending `(created_at, id)`, the next page uses `<`; ascending order uses `>`. Include all ordering components in the position. Null values, mixed directions, and collation need additional care; our example uses non-null integers and one direction.

Suppose the newest IDs are `[6,5,4,3]`. Page 1 returns `[6,5]`; someone inserts `7`. Offset 2 now starts at `5`, duplicating a row. Seeking after `5` still continues with older rows. However, keyset pagination is **not a snapshot**: new earlier rows may be absent, deleted rows disappear, and changing sort keys can move rows across the boundary.

Keep sort/filter context consistent across requests. Production opaque tokens can bind that context, a token format version, and expiry; integrity protection can detect tampering. Base64 alone is not signing or encryption, and a cursor never replaces authorization. A snapshot export needs a separate consistency strategy. See [Google's pagination guidance](https://google.aip.dev/158) for an example of an opaque-token API contract.

## 4. How to apply / implement / use it?

### Define the contract

Illustrative endpoint: `GET /tasks?limit=2&cursor=102:5`.

- Fixed sort: `created_at DESC, id DESC`; creation times do not change.
- `limit` is an integer from 1 through 100; default 2 for demonstration.
- A missing cursor means the first page; a returned cursor means continue.
- Success is `200` with `items` and `next_cursor`; an empty collection is still successful.
- Invalid limit/cursor maps to our chosen `422`, never an accidental unbounded query.
- No exact total count or page-number jump is promised.

### Smallest runnable keyset example

Save as `pagination_demo.py`; run `python3 pagination_demo.py`. Uses Python 3's SQLite module. The input layer passes an already parsed integer limit; a real HTTP adapter must parse query strings strictly.

```python
import re
import sqlite3

database = sqlite3.connect(":memory:")
database.row_factory = sqlite3.Row
database.executescript("""
    CREATE TABLE tasks (
        id INTEGER PRIMARY KEY, owner_id INTEGER NOT NULL, created_at INTEGER NOT NULL
    );
    CREATE INDEX task_page_order ON tasks (owner_id, created_at DESC, id DESC);
    INSERT INTO tasks VALUES
        (1, 7, 100), (2, 7, 100), (3, 7, 101),
        (4, 7, 101), (5, 7, 102), (6, 7, 102), (8, 8, 200);
""")


def page_tasks(actor_id, limit=2, cursor=None):
    if type(limit) is not int or not 1 <= limit <= 100:
        raise ValueError("INVALID_LIMIT")
    predicates = ["owner_id = ?"]
    parameters = [actor_id]
    if cursor is not None:
        if not isinstance(cursor, str) or len(cursor) > 40:
            raise ValueError("INVALID_CURSOR")
        if re.fullmatch(r"[0-9]+:[1-9][0-9]*", cursor) is None:
            raise ValueError("INVALID_CURSOR")
        created_at, task_id = map(int, cursor.split(":"))
        if max(created_at, task_id) > 2**63 - 1:
            raise ValueError("INVALID_CURSOR")
        predicates.append("(created_at, id) < (?, ?)")
        parameters.extend([created_at, task_id])
    parameters.append(limit + 1)
    rows = database.execute(
        "SELECT id, created_at FROM tasks WHERE " + " AND ".join(predicates)
        + " ORDER BY created_at DESC, id DESC LIMIT ?", parameters
    ).fetchall()
    items = [dict(row) for row in rows[:limit]]
    next_cursor = None
    if len(rows) > limit:
        last = items[-1]
        next_cursor = f"{last['created_at']}:{last['id']}"
    return {"items": items, "next_cursor": next_cursor}


first = page_tasks(7)
assert [task["id"] for task in first["items"]] == [6, 5]
with database:
    database.execute("INSERT INTO tasks VALUES (7, 7, 103)")
second = page_tasks(7, cursor=first["next_cursor"])
third = page_tasks(7, cursor=second["next_cursor"])
assert [task["id"] for task in second["items"]] == [4, 3]
assert [task["id"] for task in third["items"]] == [2, 1]
assert third["next_cursor"] is None
assert page_tasks(99) == {"items": [], "next_cursor": None}

for arguments in [{"limit": 0}, {"limit": True}, {"cursor": "broken"}, {"cursor": "9:0"}]:
    try:
        page_tasks(7, **arguments)
    except ValueError:
        pass
    else:
        raise AssertionError("Invalid pagination input was accepted")

print("happy: stable continuation despite insert; unhappy: invalid bounds/cursors rejected")
database.close()
```

The readable `timestamp:id` token is deliberately unsigned and has no expiration; clients should still treat it as a continuation token, not construct it themselves. Changing it can reposition a scan, but every query still restricts `owner_id`. This demo has no variable filters or sort; a production contract with either must bind/check their context as well. Sensitive positions need confidentiality in addition to integrity if they must not be exposed.

The example tests an insertion between requests, not concurrent transaction isolation. Row `7` is not included in this ongoing older-items traversal; restart from the first page to see it. The SQL ID is unique, so tied timestamps do not lose rows.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- A tiny, strictly bounded list such as seven weekdays may not need pagination.
- Offset pagination is reasonable for small datasets and page jumps; do not force keyset tokens into every admin table.
- Do not return an exact `COUNT(*)` automatically when clients only need “is there another page?” It can be more expensive than the page query.
- Do not sort only by a non-unique timestamp or use an inconsistent order on later pages.
- Do not implement a cursor by loading the entire dataset and slicing in memory.
- Do not hold a database transaction open for minutes while a human clicks Next merely to preserve a snapshot; long snapshots/locks have database-specific operational costs.

For complete exports, combine bounded processing with explicit snapshot/high-water-mark requirements. A high-water mark alone does not freeze updates and deletions. Keyset pagination improves traversal but does not provide exactly-once delivery of mutable records.

## 6. How do I know I understand it?

**Blank-page check:** write first-page and next-page SQL for both ascending and descending order, including a unique tie-breaker. Explain why the extra fetched row is not the cursor position and why authorization runs on every request.

| Constraint change | Predict the failure and response |
| --- | --- |
| Offset grows to one million | Work includes the skipped prefix; inspect the plan and consider keyset access |
| Many rows share one timestamp | Include ID in both ordering and cursor predicate |
| Sort field becomes editable | Rows can cross the cursor boundary; define live-list versus snapshot behavior |
| User changes filters mid-scroll | Restart or reject tokens whose context no longer matches |
| Legal export must reflect one instant | A live cursor is insufficient; use a suitable consistent snapshot/export design |

You understand pagination when you can predict both page contents and missing/duplicate possibilities under concurrent changes.
