# REST API

[Lesson index](../../README.md) · Previous: [API / Request-Response](api_request_response.md)

## 1. What is it?

REST means **Representational State Transfer**. It is an architectural style for distributed systems. In an HTTP API, a resource is an identifiable concept, such as a task, and a representation is data describing it, such as a JSON document.

Example: `/tasks/42` identifies a task; `{"id":42,"title":"Review REST"}` is one representation of that task. A resource does not have to correspond directly to a database row.

REST's constraints include client-server separation, stateless requests, cacheability, a uniform interface, layered systems, and optional code-on-demand. The uniform interface includes resource identification, manipulation through representations, self-describing messages, and hypermedia links that guide interactions. See [Fielding's original REST definition](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm).

Many APIs called “REST APIs” follow resource-oriented URLs and HTTP method conventions but omit hypermedia. That is a useful practical subset, rather than full adherence to REST. REST does not require JSON, and using HTTP plus JSON alone does not establish REST.

## 2. Why do we need it?

REST gives an API a consistent shape. Once a developer understands how tasks are listed, created, read, updated, and deleted, similar resources become easier to use.

For example, a resource-oriented API exposes `GET /tasks/42` and `DELETE /tasks/42`. Clients can understand the operation through the HTTP method instead of learning a different action name for every URL.

It also supports:

- Independent client and server changes behind a stable public interface.
- Caching where responses permit it.
- Server scaling when each request supplies its required context.
- Intermediaries such as gateways without clients knowing the full server topology.

REST is useful for resource-centered applications. It is not mandatory for every backend: an RPC-style API may fit operation-centered workflows, and event-driven communication may fit asynchronous reactions.

## 3. How do we apply / implement / use it?

### Identify resources and routes

Start with concepts users recognize. For our task app, use `/tasks` for a collection and `/tasks/{id}` for an individual resource. Plural nouns are a common naming convention, not a formal REST requirement.

| Request | Intended behavior | Example success |
| --- | --- | --- |
| `GET /tasks` | List tasks | `200` with a collection |
| `GET /tasks/42` | Read task 42 | `200` with a task |
| `POST /tasks` | Create a task | `201` with task and `Location` |
| `PUT /tasks/42` | Replace writable task fields | `200` with updated task |
| `PATCH /tasks/42` | Update selected fields | `200` with updated task |
| `DELETE /tasks/42` | Delete task 42 | `204` without a body |

For this example, PUT requires both `title` and `completed`, preserves the server-managed ID, and returns `404` when the task does not exist. Other APIs allow PUT to create at a known URI; document your choice.

### Define representations and update rules

GET response:

```json
{
  "id": 42,
  "title": "Review REST",
  "completed": false,
  "links": {
    "self": "/tasks/42",
    "collection": "/tasks"
  }
}
```

This is an application-defined JSON shape. Clients must understand what its link relations mean. Adding a `links` field alone does not fulfill every REST constraint; richer hypermedia can also describe available actions.

PATCH needs an explicit format and field policy. In this example, use JSON Merge Patch: `{"completed":true}` changes only `completed`. Allow only `title` and `completed`; validate their types; reject unknown fields and deletion of required fields. Merge Patch uses `null` to request field removal, which this task contract rejects for required fields. See [RFC 7396](https://www.rfc-editor.org/rfc/rfc7396.html).

These commands assume a local API on port 3000 implementing the documented routes and format:

```sh
# List incomplete tasks. Query names are part of our application contract.
curl -i 'http://localhost:3000/tasks?completed=false&limit=20'

# Mark task 42 complete using JSON Merge Patch.
curl -i -X PATCH http://localhost:3000/tasks/42 \
  -H 'Content-Type: application/merge-patch+json' \
  --data '{"completed":true}'

# Delete task 42.
curl -i -X DELETE http://localhost:3000/tasks/42
```

### Implement routes through shared business logic

Framework-neutral pseudocode:

```text
GET /tasks/{id}:
    validate ID
    load task through taskService
    return 404 if missing
    check access if tasks are private
    return 200 with public representation

PATCH /tasks/{id}:
    check media type and parse patch
    validate allowed fields and values
    check access if tasks are private
    update task through taskService
    return 404 if missing
    return 200 with updated representation
```

Each request must carry the authentication context it needs. Statelessness still allows persistent task data. For private task responses, choose deliberate cache rules; a beginner example can use `Cache-Control: no-store`. Public cacheable data may need a different policy.

### Avoid common mistakes

- Using GET for deletion or other business mutations.
- Treating PUT as an undocumented partial update.
- Returning `200` for failures or sending JSON with `204`.
- Assuming every POST can be safely retried without duplicates.
- Equating REST with database CRUD alone.

### Review practice

1. Design collection and item URLs for projects.
2. Explain how PUT differs from PATCH in the task contract.
3. Explain the difference between a resource and its representation.
4. Name the REST constraints and explain why noun-based routes alone are insufficient.

You understand this item when you can design predictable resource routes, explain their semantics, and distinguish practical HTTP conventions from the full REST style.
