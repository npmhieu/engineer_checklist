# Basic CI/CD

[Lesson index](../../README.md) · Previous: [Basic Monitoring](5.basic_monitoring.md) · Next level: [Advanced API Design](../../intermediate/1.api_application/1.advanced_api_design.md)

## 1. What is it?

CI/CD automates repeatable checks and release steps, like an assembly line that inspects a product before packaging and delivering the exact inspected build.

**Continuous integration** checks integrated changes frequently. **Continuous delivery** keeps validated releases deployable, often with an approval gate. **Continuous deployment** automatically releases changes that pass the required gates. Teams should state which meaning of CD they use.

## 2. Why do we need it?

“Works on my machine” omits dependencies, tests, configuration, and packaging differences. Manual deployment can ship a different artifact from the one tested or continue despite failed checks.

Specific pain: a developer ignores a failing command, builds from uncommitted edits, and deploys a package that cannot be traced to reviewed source.

## 3. Under the hood / mechanism / system flow

### 3a. Runners, gates, and artifacts

A runner checks out an identified source revision, prepares pinned/reviewed dependencies, runs checks, builds an artifact, and records outputs/provenance. Artifact digests identify bytes; a hash alone is not proof of trusted origin. Caches can save download/build time but must not allow untrusted inputs to poison trusted releases.

Build/test CPU, network, dependency availability, parallelism, and queue time determine feedback latency. Keep fast checks early. Untrusted pull requests must not receive deployment secrets or excessive permissions. [GitHub's secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use) discusses permissions, untrusted input, and action pinning; those concerns apply even when another CI provider is used.

### 3b. Release lifecycle

```text
Reviewed revision → validate/test → build immutable artifact → record digest
    → delivery approval/policy → deploy exact artifact + compatible config/schema
    → health/smoke verification → promote or recover deliberately
```

Do not rebuild independently for each environment and assume the result is identical. Serialize conflicting deployments as needed, protect release credentials, and define rollback/forward-fix behavior. Rolling back application bytes does not undo external effects or a destructive database migration.

## 4. How to apply / implement / use it?

Save as `ci_cd_demo.py`; run `python3 ci_cd_demo.py`. The example creates a disposable project and local pipeline: compile, real unit-test subprocess, package, then update a **simulated local release marker**. It never deploys anywhere or creates a repository/commit.

```python
import hashlib
from pathlib import Path
import subprocess
import sys
import tempfile
import zipfile

def pipeline(root):
    compiled = subprocess.run([sys.executable, "-m", "py_compile", "app.py"], cwd=root, capture_output=True)
    if compiled.returncode != 0:
        return False
    tested = subprocess.run([sys.executable, "-m", "unittest", "discover", "-p", "test_*.py"], cwd=root, capture_output=True)
    if tested.returncode != 0:
        return False
    artifact = root / "app.zip"
    with zipfile.ZipFile(artifact, "w") as package:
        package.write(root / "app.py", arcname="app.py")
    digest = hashlib.sha256(artifact.read_bytes()).hexdigest()
    (root / "release.sha256").write_text(digest)
    return True

with tempfile.TemporaryDirectory() as directory:
    root = Path(directory)
    (root / "app.py").write_text("def total(quantity, cents):\n    return quantity * cents\n")
    (root / "test_app.py").write_text("import unittest\nfrom app import total\n\nclass PriceTests(unittest.TestCase):\n    def test_total(self):\n        self.assertEqual(total(2, 150), 300)\n")
    assert pipeline(root)
    good_release = (root / "release.sha256").read_text()
    assert hashlib.sha256((root / "app.zip").read_bytes()).hexdigest() == good_release
    (root / "app.py").write_text("def total(quantity, cents):\n    return quantity + cents\n")
    assert not pipeline(root)
    assert (root / "release.sha256").read_text() == good_release
    assert hashlib.sha256((root / "app.zip").read_bytes()).hexdigest() == good_release
print("happy: checked artifact promoted; unhappy: failed tests preserve previous artifact/release marker")
```

The intentionally broken revision makes its test subprocess fail while the demonstration itself passes by asserting the gate blocks promotion. Real CI needs repository triggers, isolated immutable workspaces, dependency locks, artifact provenance, protected environments, approvals as applicable, and actual deployment/verification adapters. The marker is not a production atomic deployment mechanism.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- A small repository can start with checks only; automated production deployment is not mandatory.
- Do not use `continue-on-error` or ignored exit codes for required quality/security gates.
- Do not expose release credentials to arbitrary contributor code or interpolate untrusted event text into shell scripts.
- Do not replace safe migration/recovery planning with “we can rerun the pipeline.”

Automation makes both good and bad procedures repeatable. Keep permissions narrow, artifacts traceable, and production effects behind deliberate release policy.

## 6. How do I know I understand it?

**Blank-page check:** identify source revision, required gates, immutable artifact/digest, deployment authority, environment configuration, verification, and recovery path.

| Constraint change | Predict the failure and response |
| --- | --- |
| Tests fail | Required gates block release rather than emitting a warning and continuing |
| Untrusted fork opens a PR | Run safe checks without privileged production credentials |
| Two releases race | Coordinate promotion so an older job cannot accidentally overwrite a newer release |
| Schema change is irreversible | Application rollback alone cannot recover lost data |
| Dependency floats to a new version | Reviewed locking/provenance should make the change visible and reproducible |

You understand CI/CD when you can trace running bytes to checked source and explain exactly what prevents an unsafe promotion.
