# Health Check

[Lesson index](../../README.md) · Previous: [Logging](3.logging.md) · Next: [Basic Monitoring](5.basic_monitoring.md)

## 1. What is it?

A health check reports a narrowly defined ability of a running component, like checking whether a shop is open, staffed, and ready for customers rather than assuming its lights prove everything works.

**Liveness** asks whether restart might help; **readiness** asks whether this instance should receive traffic; **startup** accounts for initialization. They are not synonyms.

## 2. Why do we need it?

A process can exist while it is stuck or not yet initialized. Routing traffic to it creates failures, while restarting every replica during a shared database outage can amplify the outage.

Specific pain: a probe tests the database as “liveness,” the database slows, and all otherwise healthy application processes enter restart loops.

## 3. Under the hood / mechanism / system flow

### 3a. Probe execution and dependency cost

A supervisor/load balancer periodically calls a bounded HTTP/TCP/exec check and interprets failure thresholds/timeouts. Every probe consumes resources; an expensive deep check multiplied by replicas and frequency can load dependencies.

Liveness should target an instance-local recoverable problem, not every downstream fault. Readiness may include essential dependency/schema/startup state, but optional integrations may allow degraded service. [Kubernetes probe documentation](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/) describes these distinct actions and startup gating.

### 3b. Infrastructure reaction

```text
Start → initialization/startup gate → ready → receive traffic
Drain/unready → stop new routing → finish bounded in-flight work → terminate
Repeated liveness failure → supervisor restart under configured policy
```

Returning `200` in a JSON body is not enough; set the actual HTTP status. Keep public probe responses generic, protect deep diagnostics, and avoid logging every routine success. Readiness does not guarantee every future request will succeed.

## 4. How to apply / implement / use it?

Save as `health_check_demo.py`; run `python3 health_check_demo.py`. Functions return HTTP-style `(status, body)` values without opening a server.

```python
import sqlite3

def liveness():
    return 200, {"status": "alive"}

def readiness(database, startup_complete, draining=False):
    if not startup_complete or draining:
        return 503, {"status": "not_ready"}
    try:
        database.execute("SELECT 1").fetchone()
    except sqlite3.Error:
        return 503, {"status": "not_ready"}
    return 200, {"status": "ready"}

database = sqlite3.connect(":memory:")
assert readiness(database, startup_complete=False)[0] == 503
assert readiness(database, startup_complete=True)[0] == 200
assert readiness(database, startup_complete=True, draining=True)[0] == 503
database.close()
assert readiness(database, startup_complete=True)[0] == 503
assert liveness()[0] == 200
print("happy: initialized instance ready; unhappy: startup/drain/dependency not-ready without false liveness failure")
```

`SELECT 1` checks this fixture's connection only; it does not validate migrations, write capacity, or end-to-end business behavior. The startup flag represents an actual initialization decision in a real app. Real probes need bounded timeouts, sensible thresholds, and routing/shutdown integration. A trivial liveness function also cannot detect every event-loop/deadlock failure unless deployed in the relevant execution path.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- A short-lived batch process may communicate success with exit status rather than a permanent probe server.
- Do not use a deep all-dependencies check as every instance's restart signal.
- Do not let probes mutate business data or consume large resources.
- Do not expose hostnames, credentials, stack traces, or internal topology in public health bodies.

Health checks are control signals, not a substitute for monitoring, synthetic business checks, and clear incident diagnostics.

## 6. How do I know I understand it?

**Blank-page check:** assign a startup delay, local deadlock, shared DB outage, and graceful drain to the correct signal and infrastructure action.

| Constraint change | Predict the failure and response |
| --- | --- |
| Startup takes two minutes | Gate liveness with an appropriate startup policy, not endless premature restarts |
| Shared dependency fails | Withhold/degrade traffic as designed; restarting all replicas may not help |
| Instance begins shutdown | Remove readiness before terminating in-flight work |
| Probe rate multiplies with replicas | Bound check cost and avoid overloading the dependency being checked |

You understand health checks when the response causes the intended operational action instead of merely displaying green text.
