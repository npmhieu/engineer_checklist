# API Versioning

[Lesson index](../../README.md) · Previous: [Pagination](10.pagination.md) · Next: [Idempotency Basics](12.idempotency_basics.md)

## 1. What is it?

API versioning lets clients select a supported contract while that contract evolves, like keeping an old game controller adapter working after a new console connector appears.

A version identifies externally observable behavior: fields, types, defaults, errors, and semantics—not merely a code branch or database schema. `/v1` is an application API version; it is unrelated to HTTP/1.1 versus HTTP/2 or a server release such as `2.7.4`.

## 2. Why do we need it?

Clients do not all deploy with the server. A mobile app from last year, a partner integration, and today's frontend may all call the same backend.

Specific bug: the server renames `title` to `name`. An old client still reads `response.title`, gets nothing, and displays an empty task—even though the server returns `200` and its own tests pass. Changing an amount's unit from cents to dollars is another breaking change even when its JSON type stays numeric.

Compatibility-preserving changes avoid unnecessary migrations. When compatibility cannot be preserved, explicit versions let old and new clients coexist during a planned transition. They do not eliminate maintenance or make incompatible database changes safe automatically.

## 3. Under the hood / mechanism / system flow

### 3a. Adapters and shared implementation

Versioning is a contract/routing pattern, not a special engine. A router selects an adapter that validates version-specific input and renders version-specific output. Both adapters can invoke the same domain operation and storage model:

```text
v1 request → v1 input adapter ─┐
                             ├→ shared business rules → storage
v2 request → v2 input adapter ─┘
                                  ↓
client ← matching version's output/error adapter
```

Adapters add serialization and mapping work proportional to the representation size. The larger cost is operational: more contracts, tests, documentation, telemetry, and possibly data transformations. Duplicating the entire service per version multiplies fixes and can make behavior drift.

Shared logic is safe only when it preserves each supported contract's meaning. If an old operation cannot be mapped to a new model without changing meaning, it may need explicit compatibility logic or a migration deadline—not a misleading field rename adapter.

### 3b. Version selection, caches, and rollout

| Scheme | Example | Boundary consideration |
| --- | --- | --- |
| Path | `/v1/tasks/42` | Explicit routing; different URLs naturally separate cache keys |
| Query parameter | `/tasks/42?api-version=1` | Gateway/cache must preserve and key on the selected parameter |
| Custom request header | `API-Version: 1` | Header must reach the router; shared caches need an appropriate variation policy |
| Media-type negotiation | `Accept: application/vnd.example.task.v1+json` | Negotiation and cache handling are more involved; responses commonly vary on `Accept` |

There is no single HTTP requirement that every API use `/v1`. This lesson chooses path versions for clarity. Google's [AIP-185](https://google.aip.dev/185) is one concrete API-versioning policy, not a universal rule.

When a request header selects a cacheable representation, `Vary` tells compliant caches which request fields affect selection; configuring the cache correctly still matters. See [RFC 9110 on Vary](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.5). Versioning is not authorization: both versions still need equivalent permission checks.

Typical lifecycle:

1. Identify an observable incompatibility; first ask whether an additive change suffices.
2. Add new adapter/contract tests while keeping old behavior working.
3. Deploy storage changes compatible with both active implementations where needed.
4. Publish migration examples and a support/deprecation policy; measure usage by version.
5. Migrate clients, investigate remaining callers, and retire the old version deliberately.

Do not silently route an unsupported version to the newest contract. Return a documented error. Our small path router uses `404` for unknown routes; other selection schemes can have different error policies.

## 4. How to apply / implement / use it?

### Decide what is breaking

| Change | Compatibility question |
| --- | --- |
| Rename/remove a response field | Old readers generally break |
| Add a required request field | Existing requests no longer work |
| Change default sort or pagination meaning | Clients can get different behavior without a schema change |
| Add an optional response field | Often compatible for tolerant readers; strict decoders/signatures may still break |
| Add an enum value | Exhaustive client switches may fail |
| Make input validation stricter | Previously accepted requests may now fail |

Evaluate real supported clients and the written contract. “Additive” is not proof of compatibility in every ecosystem. [Google's compatibility guidance](https://google.aip.dev/180) distinguishes source, wire, and semantic compatibility.

### Smallest runnable version adapters

Save as `api_versioning_demo.py`; run `python3 api_versioning_demo.py`. Standard-library-only Python, with an in-memory task. `handle` simulates an HTTP adapter using parsed dictionaries and returns `(status, headers, body)`; it is not a socket server.

Both versions read task 42 and rename it. Version 1 uses `title` and `completed`; version 2 uses `name` and `state`. These are independent lesson contracts, not changes to the earlier examples. The actor is assumed authorized for this fixed task; a real application must enforce that in shared business logic.

```python
task = {"id": 42, "title": "Original", "completed": False}
ROUTES = {"/v1/tasks/42": "v1", "/v2/tasks/42": "v2"}


def rename_task(title):
    if not isinstance(title, str) or not 1 <= len(title.strip()) <= 120:
        raise ValueError("INVALID_TITLE")
    task["title"] = title.strip()


def represent(version):
    if version == "v1":
        return {"id": task["id"], "title": task["title"], "completed": task["completed"]}
    return {
        "id": task["id"], "name": task["title"],
        "state": "done" if task["completed"] else "open",
    }


def handle(method, path, body=None):
    version = ROUTES.get(path)
    if version is None:
        return 404, {}, {"error": {"code": "ROUTE_NOT_FOUND"}}
    if method not in {"GET", "PATCH"}:
        return 405, {"Allow": "GET, PATCH"}, {"error": {"code": "METHOD_NOT_ALLOWED"}}
    if method == "PATCH":
        field = "title" if version == "v1" else "name"
        if not isinstance(body, dict) or set(body) != {field}:
            return 422, {}, {"error": {"code": "INVALID_FIELDS"}}
        try:
            rename_task(body[field])
        except ValueError as error:
            return 422, {}, {"error": {"code": str(error)}}
    return 200, {}, represent(version)


assert handle("GET", "/v1/tasks/42")[2] == {
    "id": 42, "title": "Original", "completed": False
}
assert handle("GET", "/v2/tasks/42")[2] == {
    "id": 42, "name": "Original", "state": "open"
}
assert handle("PATCH", "/v2/tasks/42", {"name": "New name"})[0] == 200
assert handle("GET", "/v1/tasks/42")[2] == {
    "id": 42, "title": "New name", "completed": False
}
assert handle("PATCH", "/v1/tasks/42", {"name": "Wrong contract"})[0] == 422
assert handle("PATCH", "/v2/tasks/42", {"name": " "})[0] == 422
assert task["title"] == "New name"
assert handle("GET", "/v3/tasks/42")[0] == 404
assert handle("POST", "/v1/tasks/42")[0] == 405
print("happy: v1/v2 share rules and retain shapes; unhappy: invalid contracts rejected")
```

The adapter's PATCH contract accepts exactly the rename field, not arbitrary writable task properties; this is an application-defined partial update, not a general JSON Patch implementation. Real HTTP code also handles media types, JSON parsing, authentication, actual response headers, and a full route tree.

Keep a golden contract test for each supported version, including error shapes, defaults, and permissions—not only success JSON. For this example, a v2 rename must remain readable through v1 without exposing v2 field names to v1 clients.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not create a new public version for every internal refactor or compatible bug fix.
- Do not copy the whole backend into `v1/` and `v2/` when thin adapters suffice.
- Do not equate adding `/v2` with migrating clients; old callers continue using `/v1` until changed.
- Do not change the meaning of v1 behind its unchanged URL and call it compatible.
- Do not support versions forever without knowing the cost and security-maintenance obligations.
- Do not bypass shared authorization or validation merely to preserve an old implementation's unsafe behavior; security fixes may require coordinated client changes.

If every client is controlled and can migrate together, a planned compatible rollout or coordinated cutover may be simpler. Public or offline clients make that assumption much harder. API versioning also does not replace database migration discipline, feature flags, or release rollback planning.

## 6. How do I know I understand it?

**Blank-page check:** draw two adapters calling one domain operation. Define exactly what v1 clients may send and observe, and explain why a successful v2 deployment must not change that contract accidentally.

| Constraint change | Predict the failure and response |
| --- | --- |
| Response gains an enum value | A generated/exhaustive client may fail; evaluate compatibility instead of assuming safety |
| Version moves from URL to header | Update routing, forwarded headers, cache variation, docs, and tests |
| Old mobile clients cannot upgrade for six months | Plan an explicit support window and usage tracking |
| Domain replaces one title with several localized names | A field rename may no longer preserve v1 meaning; define compatibility behavior |
| Database drops a column still used by v1 | Both contracts cannot remain supported merely because both routes exist |

You understand API versioning when you can distinguish code changes from contract changes and explain how old and new clients coexist, migrate, and eventually retire a version.
