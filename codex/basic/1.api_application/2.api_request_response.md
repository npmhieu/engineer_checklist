# API / Request-Response

[Lesson index](../../README.md) · Previous: [HTTP Fundamentals](1.http_fundamentals.md) · Next: [REST API](3.rest_api.md)

## 1. What is it?

An API (Application Programming Interface) is a defined interface through which software uses another piece of software. It describes available operations, accepted inputs, outputs, and errors.

An API does not have to use the network: a library function is also an API. Here we focus on a backend HTTP API.

**Request-response** is an interaction pattern: a client sends a request, the server processes it, and the client receives a response. HTTP supplies the message semantics; your application defines what those messages mean for its users. See [RFC 9110's message exchange example](https://www.rfc-editor.org/rfc/rfc9110.html#section-3.9).

For a task app, an API contract could be:

| Contract part | Example |
| --- | --- |
| Operation | Create a task |
| Endpoint | `POST /tasks` |
| Input | JSON with a non-empty `title` |
| Success | `201`, a task object, and a `Location` header |
| Invalid JSON | `400` with an error object |
| Invalid title | `422` with an error object |

The `422` choice is this example's validation policy. Some APIs consistently use `400` instead; document the chosen contract.

## 2. Why do we need it?

An API lets clients use backend capabilities without knowing database tables or internal implementation details.

For example, a browser sends a title to create a task. The backend decides whether that title is valid, generates an ID, stores the task, and returns the result. The browser does not need database credentials or knowledge of how tasks are stored.

A clear contract helps frontend and backend developers work independently. It also makes testing possible: a test can send documented input and check the documented output.

Request-response works well when the client needs an immediate result, such as loading a profile or saving a small edit. Long-running work often needs a different flow: accept a job, return its identifier, and let the client retrieve progress later.

## 3. How do we apply / implement / use it?

### Define the contract first

For this learning example, `title` must be a string containing 1–120 characters after trimming. A created task starts with `completed: false`.

Request:

```http
POST /tasks HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json

{"title":"Review request-response"}
```

Success response:

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /tasks/42

{"id":42,"title":"Review request-response","completed":false}
```

Example error body for an invalid title, returned with `422`:

```json
{
  "error": {
    "code": "INVALID_TITLE",
    "message": "title must contain 1 to 120 characters"
  }
}
```

The machine-readable `code` lets clients react without depending on the exact wording of `message`.

### Follow the processing flow

```text
Client → Router → Handler → Business logic → Storage
Client ← HTTP response ← Handler ← Result ← Storage
```

1. The router matches the method and path.
2. Middleware and the handler perform relevant authentication and authorization checks.
3. The handler checks the content type, parses JSON, and validates input.
4. Business logic enforces application rules.
5. Storage persists the task.
6. The handler converts the result into the public response shape.

This is a conceptual flow; frameworks differ in where middleware and validation run.

### Implement a handler

Framework-neutral pseudocode, not runnable source:

```text
handleCreateTask(request):
    if request media type is not application/json:
        return 415 with UNSUPPORTED_MEDIA_TYPE

    input = parseJson(request.body)
    if parsing failed:
        return 400 with INVALID_JSON

    if input is not an object or input.title is not a string:
        return 422 with INVALID_TITLE

    title = trim(input.title)
    if length(title) < 1 or length(title) > 120:
        return 422 with INVALID_TITLE

    try:
        task = taskService.create(title)
    catch unexpected error:
        log internal error with request ID
        return 500 with INTERNAL_ERROR

    return 201
        headers: Location = "/tasks/" + task.id
        body: { id: task.id, title: task.title, completed: task.completed }
```

The service handles application behavior; the storage layer handles persistence. Return only fields clients should see. Do not expose stack traces, database errors, or private fields in the response.

### Handle the result on the client

The client should distinguish a received error response from a network failure or timeout. A timeout leaves the outcome uncertain, especially for writes. Retrying a create operation can produce duplicates unless the API defines deduplication, such as an idempotency key.

For a slow export, an alternative contract is `POST /exports` → `202 Accepted` plus a job ID and status URL. `202` means accepted, not completed. The client can poll the status URL. This behavior is described by [RFC 9110's 202 semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3).

### Review practice

- Describe the journey of a request from client to database and back.
- Decide where parsing, business rules, and persistence belong.
- Predict the results for a valid title, blank title, malformed JSON, and storage failure.
- Explain why a lost response makes blindly retrying POST risky.

You understand this item when you can define a small API contract and explain both its success and failure paths.
