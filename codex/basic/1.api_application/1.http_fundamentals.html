HTTP Fundamentals

Lesson index · Next: API / Request-Response

1. What is it?

HTTP (Hypertext Transfer Protocol) defines how clients and servers exchange messages. A client can be a browser, mobile app, command-line tool, or another backend. A server receives requests and sends responses.

An HTTP request contains a method, a target URL, headers, and sometimes a body. A response contains a status code, headers, and sometimes a body. These concepts are defined in HTTP Semantics, RFC 9110.

Think of a task app: the client asks for task 42; the backend returns its current details. 

GET /tasks/42 HTTP/1.1
Host: api.example.com
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{"id":42,"title":"Review HTTP","completed":false}

These examples show readable HTTP/1.1 message syntax. HTTP/2 and HTTP/3 encode messages differently while retaining the core meaning of methods, headers, and status codes.

Parts you should recognize

For https://api.example.com/tasks/42?include=owner:

Part Example Purpose
Scheme https HTTP communication protected by TLS
Host api.example.com Identifies the server
Path /tasks/42 Identifies the target resource
Query include=owner Supplies additional request options

Content-Type describes the body being sent. Accept describes response formats the client can handle. JSON is a common body format, but HTTP can also carry HTML, images, files, and other formats.

HTTP is stateless: application context must be supplied with each request as needed. This does not mean a backend cannot store data, users, or sessions. A client can send a session cookie or token so the backend can identify it.

2. Why do we need it?

HTTP gives independently built clients and servers a shared communication language. A mobile app written in Kotlin can call a backend written in Go because both understand the same protocol.

For a backend developer, knowing HTTP helps you:

  • Choose methods and response codes that clients understand.
  • Debug whether a failure comes from connectivity, authentication, input, or server code.
  • Inspect requests using browser developer tools or curl.
  • Use infrastructure such as gateways, reverse proxies, and caches correctly.

For example, a client receiving 404 should investigate the URL or missing resource. A 500 points toward an unexpected server failure. Returning 200 for every outcome hides that distinction.

3. How do we apply / implement / use it?

Choose the method and outcome

Method Typical task-app use
GET Read tasks
POST Create a task
PUT Replace a task's writable representation
PATCH Change selected task fields
DELETE Remove a task

GET must not request a business mutation such as deleting a task. PUT and DELETE are idempotent: repeating the same request has the same intended effect as sending it once. Responses can still differ, such as 204 on the first deletion and 404 on the next. POST and PATCH are not inherently idempotent. See RFC 9110 method properties.

Common response choices:

Status Meaning in this example
200 OK Read or update succeeded, with response content
201 Created New task created
204 No Content Operation succeeded; no response body
400 Bad Request Malformed request, such as invalid JSON
401 Unauthorized Valid authentication credentials are missing
403 Forbidden Server refuses access
404 Not Found Task or route was not found
500 Internal Server Error Unexpected server failure

Inspect real messages

The following commands assume you have implemented a local task API listening on port 3000. These lessons do not install or start a server. 

# Show response headers and body.
curl -i http://localhost:3000/tasks/42

# Send a JSON body to create a task.
curl -i http://localhost:3000/tasks \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json' \
  --data '{"title":"Review HTTP"}'

--data makes the second request use POST. Use HTTPS when communicating with a deployed API. Avoid putting passwords or tokens in URLs, which commonly appear in logs.

Implement the backend boundary

Your web framework normally handles network connections and message parsing. Your handler still needs to select the route, interpret input, invoke business logic, and send an appropriate status, headers, and body. Do not manually construct HTTP wire messages in ordinary application code.

Review practice

  1. Identify the method, path, headers, and body in the POST command.
  2. Explain how Content-Type differs from Accept.
  3. Explain why a successful DELETE might return 204 without JSON.
  4. Explain why a timeout does not prove that a write failed: the server may have committed it before the response was lost.

You understand this item when you can inspect a request and response and explain what each part means.
