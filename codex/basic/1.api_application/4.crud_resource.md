# CRUD Resource

[Lesson index](../../README.md) · Previous: [REST API](3.rest_api.md) · Next: [Request Validation](5.request_validation.md)

## 1. What is it?

CRUD Resource means managing an identifiable thing through **Create, Read, Update, Delete**, like adding, opening, editing, and removing a row in a spreadsheet.

A resource is something the application identifies and exposes, such as a task, project, or customer.

In our task app, `/tasks/42` identifies a task. Its JSON representation might contain `id`, `title`, and `completed`. The resource is an application concept; it need not match one database table. A task response might combine task data with an owner's display name.

CRUD describes operations. REST describes an architectural style. A CRUD API can use REST conventions, but the two terms are not interchangeable.

## 2. Why do we need it?

CRUD gives ordinary data management a predictable structure. A task app needs to save new tasks, retrieve existing tasks, edit details, and remove tasks.

This structure helps you define permissions and acceptance criteria: who may create, which records they may read, which fields they may update, and whether deletion is allowed. It also gives clients a stable interface while database implementation changes.

Example: a user can edit their task's title without receiving permission to change its owner or creation timestamp.

## 3. Under the hood / mechanism / system flow

### 3a. Storage one layer down

CRUD is a pattern, not a storage engine. A typical implementation translates resource operations into `INSERT`, `SELECT`, `UPDATE`, and `DELETE`. In a relational database, rows live on pages and indexes help locate them; SQLite, for example, stores tables and indexes in B-trees. See [SQLite's file format](https://www.sqlite.org/fileformat.html#b_tree_pages).

For `n` rows and `k` returned rows, an indexed lookup typically needs roughly `O(log n)` tree traversal plus row access; an unindexed filter may scan `O(n)` rows. Returning a collection also costs at least `O(k)` work and response memory if fully buffered. These are rough access costs, not latency guarantees: cached pages, query plans, network round trips, and disk reads matter.

Writes update rows and affected indexes. Durable storage also uses recovery mechanisms such as journals or write-ahead logs; commit can involve disk synchronization. Adding indexes can speed reads while increasing write work and storage. The in-memory example below deliberately excludes disk durability.

### 3b. Lifecycle and boundaries

```text
Client request → parse/validate → authorize → business operation
    → database write + constraints → commit → public representation/status
```

The visible state moves `absent → present → changed → absent` for create, update, and hard delete. Read should not change business state. Return success only after the required commit succeeds. A lost response after commit leaves the client uncertain; retrying a create without deduplication can make a second resource.

CRUD does not coordinate competing edits. If two requests read version 1 and both overwrite it, the later write can erase the earlier edit. A version condition such as `UPDATE ... WHERE id = ? AND version = ?` lets one writer detect that its view became stale.

## 4. How to apply / implement / use it?

### Define the resource and public contract

Example representation:

```json
{"id":42,"title":"Learn CRUD","completed":false}
```

The server generates `id`. Clients can create a title and update `title` or `completed`; they cannot assign arbitrary internal fields.

| Operation | Example request | Example result |
| --- | --- | --- |
| Create | `POST /tasks` with a title | `201`, created task, `Location: /tasks/42` |
| Read collection | `GET /tasks?limit=20` | `200` with tasks |
| Read item | `GET /tasks/42` | `200` with task, or `404` |
| Update | `PATCH /tasks/42` with selected changes | `200` with updated task |
| Delete | `DELETE /tasks/42` | `204`, no body |

This is our chosen contract. HTTP method semantics come from [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9); CRUD itself does not require HTTP.

### Keep responsibilities clear

```text
HTTP handler: parse request, validate shape, translate results
Application service: authorize operation, enforce business rules
Repository/database: read and persist data, enforce storage constraints
```

Framework-neutral pseudocode:

```text
renameTask(actor, taskId, newTitle):
    begin transaction
    task = repository.findForUpdate(taskId)
    if task is missing:
        raise TaskNotFound
    require actor may edit task
    require task may be renamed in its current state
    task.rename(newTitle)
    repository.save(task)
    commit transaction
    return publicTask(task)
```

Any failure rolls the transaction back. `findForUpdate` represents a database row lock; optimistic version checks are another option when concurrent updates matter. A plain read followed by an unconditional write can overwrite another user's changes.

For listing, enforce a maximum page size and scope results to records the caller may see. For deletion, choose hard deletion or soft deletion deliberately. Soft deletion records something like `deleted_at`; it also requires filtering, uniqueness, and retention rules. It is not automatic privacy erasure.

### Practice one lifecycle

Create a task, read it, rename it, read the new title, delete it, and confirm an item read returns `404`. An empty task collection should still return `200` with an empty collection, not an item-not-found error.

### Smallest runnable storage lifecycle

Save as `crud_demo.py`; run `python3 crud_demo.py`. This isolates persistence using Python's built-in SQLite driver. It is not an HTTP server; request validation and authorization belong around this layer. Titles below are trusted demonstration values.

```python
import sqlite3

database = sqlite3.connect(":memory:")
database.execute("CREATE TABLE tasks (id INTEGER PRIMARY KEY, title TEXT NOT NULL)")


def read_task(task_id):
    row = database.execute(
        "SELECT id, title FROM tasks WHERE id = ?", (task_id,)
    ).fetchone()
    if row is None:
        raise LookupError("TASK_NOT_FOUND")
    return {"id": row[0], "title": row[1]}


with database:
    created = database.execute("INSERT INTO tasks (title) VALUES (?)", ("Learn CRUD",))
    task_id = created.lastrowid
assert read_task(task_id)["title"] == "Learn CRUD"

with database:
    changed = database.execute(
        "UPDATE tasks SET title = ? WHERE id = ?", ("Practice CRUD", task_id)
    )
    assert changed.rowcount == 1
assert read_task(task_id)["title"] == "Practice CRUD"

with database:
    deleted = database.execute("DELETE FROM tasks WHERE id = ?", (task_id,))
    assert deleted.rowcount == 1

try:
    read_task(task_id)
except LookupError as error:
    assert str(error) == "TASK_NOT_FOUND"
    print("happy: create/read/update/delete; unhappy: deleted task is missing")
else:
    raise AssertionError("Deleted task must not be readable")

database.close()
```

Parameters keep values separate from SQL syntax. Each `with database` commits on success and rolls back on an exception; it does not close the connection. Replacing `:memory:` with a file enables persistence across runs, but this setup script would then need a deliberate initialization policy. See [Python's SQLite transaction context manager](https://docs.python.org/3/library/sqlite3.html#how-to-use-the-connection-context-manager).

## 5. When should I NOT use this? Trade-offs and anti-patterns

Use simple CRUD when the behavior is genuinely data management. Model business actions explicitly when changing fields alone would hide important rules.

For example, approving an expense may require authority checks, an audit record, and a notification. Exposing an unrestricted `PATCH {"approved":true}` can bypass that workflow. An explicit approval operation or approval resource can express it better; it still needs authorization and invariants.

Avoid these patterns:

- Automatically exposing every table and column as a public API.
- Saving a request body directly into an entity: callers could overwrite privileged fields.
- Providing DELETE when records must instead be retained or canceled.
- Assuming CRUD supplies concurrency control or audit history by itself.
- Adding generic repositories and abstractions before the application needs them.
