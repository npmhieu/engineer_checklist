# HTTP Status Codes

[Lesson index](../../README.md) · Previous: [Error Handling](7.error_handling.md) · Next: [Search / Filter / Sort](9.search_filter_sort.md)

## 1. What is it?

An HTTP status code is a three-digit label for a request's outcome, like a delivery tracker saying “delivered,” “address missing,” or “service unavailable.”

It has protocol meaning independent of an application's JSON fields.

The first digit identifies its class: `1xx` informational, `2xx` successful, `3xx` redirection, `4xx` client-related error, and `5xx` server-related error. A request can receive informational responses before its final response.

The status is a broad outcome. An application code such as `TASK_ARCHIVED` explains the specific reason. A JSON body saying `"status":500` does not override an actual HTTP `200` response.

## 2. Why do we need it?

Clients, monitoring systems, caches, and gateways use status codes without needing to understand every application's response schema.

A task app can use them to decide whether to show new data, highlight a field, request login, or refresh stale state. Monitoring can distinguish expected rejected requests from server failures.

Status codes improve interoperability, but cannot express every product detail. Pair them with a documented body when useful, and with headers required by their semantics.

## 3. Under the hood / mechanism / system flow

### 3a. Where the code travels

Status codes are protocol metadata, not an engine or a database operation. In HTTP/1.1 the response starts with a status line, such as `HTTP/1.1 404 Not Found`; HTTP/2 and HTTP/3 carry status through a `:status` pseudo-header instead. The numeric code carries the semantics; English reason text is not an application identifier. See [RFC 9110's response status overview](https://www.rfc-editor.org/rfc/rfc9110.html#section-15) and [HTTP/2 response control data](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.3.2).

Selecting a code is cheap compared with storage/network work. Its important cost is behavioral: retries can multiply traffic, cache choices can retain stale outcomes, and redirects can add round trips. Setting `500` does not execute a rollback, and setting `200` does not make a failed operation succeed.

### 3b. How surrounding systems react

```text
Service outcome → HTTP adapter chooses status + headers + optional body
    → gateway/proxy forwards or generates its own response
    → client interprets result; cache and monitoring apply configured rules
```

Examples of surrounding behavior:

- A client uses `201` plus `Location` to locate a created resource, or `202` plus a documented status URL to track incomplete work.
- A client handles `401` using the authentication challenge; `403` does not promise that logging in again will solve the problem.
- A conditional GET returning `304` lets a cache reuse its stored representation; an ordinary successful DELETE may return `204` with no content.
- Monitoring can count `5xx` as server-side failures, while gateways can generate `502`/`504` without your handler returning them.
- Retry behavior is client policy informed by method, status, headers, and idempotency; no status makes every write safe to repeat.

`404` and some other statuses can be heuristically cached when the HTTP cache rules allow it. A temporary or protected missing-resource result therefore needs deliberate cache policy, rather than assuming “errors are never cached.” See [RFC 9111's cache rules](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2.2).

## 4. How to apply / implement / use it?

### Learn a practical set

The following compact meanings follow [RFC 9110's status definitions](https://www.rfc-editor.org/rfc/rfc9110.html#section-15). The task examples below apply those meanings to our learning API.

| Code | Meaning |
| --- | --- |
| `200 OK` | Request succeeded |
| `201 Created` | Resource created |
| `202 Accepted` | Accepted; processing incomplete |
| `204 No Content` | Success without response content |
| `304 Not Modified` | Cached representation can be reused after conditional retrieval |
| `400 Bad Request` | Invalid request |
| `401 Unauthorized` | Valid authentication credentials missing |
| `403 Forbidden` | Server refuses request |
| `404 Not Found` | Resource not found or existence concealed |
| `405 Method Not Allowed` | Method unsupported for target |
| `409 Conflict` | Conflict with current resource state |
| `412 Precondition Failed` | Request precondition failed |
| `413 Content Too Large` | Request content exceeds accepted size |
| `415 Unsupported Media Type` | Request content format unsupported |
| `422 Unprocessable Content` | Understood content cannot be processed as instructed |
| `500 Internal Server Error` | Unexpected server failure |
| `502 Bad Gateway` | Gateway received invalid upstream response |
| `503 Service Unavailable` | Service temporarily unavailable |
| `504 Gateway Timeout` | Gateway did not receive timely upstream response |

`429 Too Many Requests` indicates rate limiting and may include `Retry-After`; see [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html#section-4).

### Apply codes to concrete outcomes

Use `201` and `Location: /tasks/42` after creating a task. Use `200` for an empty list: `{"items":[]}`. Use `204` after deletion when no response body is needed.

For an export, return `202` with a job ID and status URL while work continues. Do not claim that the export has finished.

In this API, malformed JSON produces `400`, while a decoded but invalid title produces `422`. This separation is a contract policy; some APIs use `400` for both. An archived task produces `409` because renaming conflicts with its state.

A failed `If-Match` version precondition produces `412`. Do not relabel it `409` merely because both may involve concurrent updates.

### Include the right headers and content

- A `401` response must include an applicable `WWW-Authenticate` challenge.
- A `405` response must include `Allow` with supported methods.
- `204` and `304` have no response content. HEAD responses also have no content, even when the corresponding GET would return a body.
- A conditional GET can receive `304`; it does not mean “your update changed nothing.”
- For planned temporary unavailability, `503` can include `Retry-After`.

For the bearer-token example below, `WWW-Authenticate: Bearer realm="tasks"` supplies the authentication challenge. Detailed bearer authentication behavior is specified in [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html#section-3).

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="tasks"
Content-Type: application/json
Cache-Control: no-store

{"error":{"code":"AUTHENTICATION_REQUIRED"}}
```

Authentication answers who the caller is; authorization answers what they may do. A recognized user lacking permission commonly gets `403`. A privacy policy may return `404` to conceal a protected resource's existence.

Inspect actual response codes with `curl -i URL` or a browser's Network panel. In framework code, set the response status explicitly; serializing JSON alone often defaults to `200`.

### Smallest runnable HTTP example

Save as `http_status_demo.py`; run `python3 http_status_demo.py`, then use another terminal for the curl commands below. Stop with Ctrl-C. Requires Python 3 only. This deliberately implements a small in-memory subset, not the full CRUD contract from lesson 4.

**Local learning only:** this server has no authentication, durable storage, TLS, or production protections. It binds only to `127.0.0.1`. Python explicitly warns that [`http.server` is not intended for production](https://docs.python.org/3/library/http.server.html).

```python
import json
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.parse import urlsplit

tasks = {42: {"id": 42, "title": "Learn status codes"}}


class Handler(BaseHTTPRequestHandler):
    def reply(self, status, payload=None, allow=None):
        content = b"" if payload is None else json.dumps(payload).encode("utf-8")
        self.send_response(status)
        self.send_header("Cache-Control", "no-store")
        if allow is not None:
            self.send_header("Allow", allow)
        if status != 204:
            self.send_header("Content-Type", "application/json")
            self.send_header("Content-Length", str(len(content)))
        self.end_headers()
        if self.command != "HEAD" and status != 204:
            self.wfile.write(content)

    def do_GET(self):
        path = urlsplit(self.path).path
        if path == "/tasks":
            self.reply(200, {"items": list(tasks.values())})
        elif path == "/tasks/42" and 42 in tasks:
            self.reply(200, tasks[42])
        else:
            self.reply(404, {"error": {"code": "TASK_NOT_FOUND"}})

    do_HEAD = do_GET

    def do_DELETE(self):
        path = urlsplit(self.path).path
        if path == "/tasks":
            self.reply(405, {"error": {"code": "METHOD_NOT_ALLOWED"}}, allow="GET, HEAD")
        elif path == "/tasks/42" and 42 in tasks:
            del tasks[42]
            self.reply(204)
        else:
            self.reply(404, {"error": {"code": "TASK_NOT_FOUND"}})

    def do_POST(self):
        path = urlsplit(self.path).path
        if path in {"/tasks", "/tasks/42"}:
            allowed = "GET, HEAD" if path == "/tasks" else "GET, HEAD, DELETE"
            self.reply(405, {"error": {"code": "METHOD_NOT_ALLOWED"}}, allow=allowed)
        else:
            self.reply(404, {"error": {"code": "TASK_NOT_FOUND"}})

    do_PUT = do_POST
    do_PATCH = do_POST


if __name__ == "__main__":
    with HTTPServer(("127.0.0.1", 3000), Handler) as server:
        server.serve_forever()
```

Run in this order against a freshly started server:

```sh
curl -i http://127.0.0.1:3000/tasks/42
curl -I http://127.0.0.1:3000/tasks/42
curl -i http://127.0.0.1:3000/missing
curl -i -X POST http://127.0.0.1:3000/tasks
curl -i -X DELETE http://127.0.0.1:3000/tasks/42
curl -i http://127.0.0.1:3000/tasks/42
curl -i http://127.0.0.1:3000/tasks
```

Expected: `200` with task; HEAD `200` with headers but no body; `404` with stable error; `405` with `Allow: GET, HEAD`; `204` with no body; `404` after deletion; `200` with `{"items":[]}`. Restart resets the task. These are observable happy and unhappy paths, not just JSON objects with a `status` field. The demo uses the earlier custom error envelope; production APIs can instead consistently implement lesson 7's Problem Details format.

## 5. When should I NOT use this? Trade-offs and anti-patterns

HTTP responses always have a status; the choice is how to use standard meanings appropriately.

- Do not encode every outcome as `200` for an ordinary HTTP resource API.
- Do not invent a different status for every business rule; use stable application codes.
- Do not return `401` merely because an authenticated user lacks access.
- Do not return `404` for every empty search result.
- Do not use `500` for a known field-validation failure.
- Do not assume every `5xx` can safely be retried or that a write was rolled back.

Use gateway codes when the component is acting as a gateway and the relevant upstream condition occurred. A database exception in application code is not automatically `502`.

Existing protocols can define different outcome conventions, such as RPC errors in a structured response. Follow their specifications instead of changing them to resemble this resource API. Inside business logic, use domain results; translate them to HTTP at the boundary.

Status choices and cache behavior interact. Protected or temporary error responses need deliberate cache headers, since some outcomes such as `404` can be cached.

## 6. How do I know I understand it?

Choose a response before reading the answer:

| Scenario | Answer under this contract |
| --- | --- |
| Task created immediately | `201`, created task, `Location` |
| Export queued | `202`, job ID/status URL |
| No matching tasks | `200`, empty collection |
| Invalid JSON | `400` |
| Missing bearer credentials | `401`, authentication challenge |
| Authenticated caller lacks access | `403`, or documented concealment policy |
| Archived task rename | `409` |
| `If-Match` fails | `412` |
| Too many calls | `429`, retry guidance when available |
| Unexpected implementation bug | `500`, safe error body |

You understand status codes when you can explain the meaning, choose matching headers and content, and distinguish protocol outcomes from application-specific reasons.

**Blank-page check:** write a decision tree for success, missing authentication, denied access, invalid input, state conflict, and infrastructure failure. For each leaf specify status, required headers, body/no-body, and what action the client can reasonably take.

**Change a constraint:** export processing grows from 50 ms to five minutes; model accepted work with `202` and a status resource instead of pretending the result is complete. A CDN starts caching responses: a cached `404` can hide a newly created task unless cache policy/invalidation handles it. A client retries every `5xx`: explain how a committed POST with a lost response can create duplicates without idempotency.
