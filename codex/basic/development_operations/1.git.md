## 1. What is it?

Git is a distributed version-control system that records project snapshots and their history, like a branching save-game system where changes can be compared and integrated.

A local repository, a branch, a working directory, and a hosted remote such as GitHub are different concepts.

## 2. Why do we need it?

Copying folders as `final_v2_fixed` loses why changes happened and makes collaboration error-prone. A teammate's work can be overwritten without a reviewable history.

Specific pain: a regression appears and there is no reliable way to compare versions, identify its introduction, or prepare a small reviewed correction.

## 3. Under the hood / mechanism / system flow

### 3a. Objects, references, and three states

Git stores content-addressed objects: blobs for file content, trees for directory snapshots, and commits referencing trees and parents. Commits form a graph; branches are movable references, not complete folder copies. Packing/delta compression is an implementation optimization, not proof Git's conceptual model stores only diffs.

The working tree holds current files; the index/staging area describes the next snapshot; HEAD names the current checkout/reference. Hashing reads content and uses CPU/I/O; large changing binary files can grow repositories substantially. See the [official Git reference](https://git-scm.com/docs/git).

### 3b. Change and collaboration flow

```text
Edit → inspect working diff → stage selected changes → inspect staged diff
    → commit staged snapshot → review/share → integrate compatible history
```

Fetch updates remote-tracking information; pull additionally integrates under configured behavior. Merge/rebase have different history effects; conflicts require understanding the intended combined behavior. A local commit is not automatically pushed or backed up remotely.

## 4. How to apply / implement / use it?

Save as `git_demo.py`; run `python3 git_demo.py`. Requires Git on PATH. It uses an isolated temporary repository, creates no commits, touches no project repository, and demonstrates staging plus a failed command safely.

```python
import os
from pathlib import Path
import subprocess
import tempfile

environment = {name: value for name, value in os.environ.items() if not name.startswith("GIT_")}
environment.update({"GIT_CONFIG_GLOBAL": os.devnull, "GIT_CONFIG_NOSYSTEM": "1"})

with tempfile.TemporaryDirectory() as directory:
    root = Path(directory)

    def git(*arguments, check=True):
        return subprocess.run(["git", "-C", str(root), *arguments], env=environment, check=check, capture_output=True, text=True)

    git("init", "--quiet")
    path = root / "notes.txt"
    path.write_text("first version\n")
    git("add", "notes.txt")
    path.write_text("second version\n")
    assert git("show", ":notes.txt").stdout == "first version\n"
    assert path.read_text() == "second version\n"
    assert git("status", "--porcelain").stdout.startswith("AM ")
    assert "second version" in git("diff", "--", "notes.txt").stdout
    failed = git("add", "missing.txt", check=False)
    assert failed.returncode != 0
    assert git("show", ":notes.txt").stdout == "first version\n"
print("happy: index differs from working tree; unhappy: missing path fails without changing staged content")
```

In your own intended workflow, `git diff --cached` reviews what a subsequent `git commit` would record. Unstaged edits are not silently included in that snapshot. The example intentionally stops before committing or creating collaboration history.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not commit credentials, runtime databases, dependencies, or huge generated artifacts without a deliberate policy.
- `.gitignore` does not remove a secret already tracked or present in history; revoke leaked credentials first.
- Do not rewrite shared history or use destructive reset/clean commands without understanding data-loss and collaborator impact.
- Do not treat a versioned repository as the only backup for all application data.

Git is valuable for source/history; object storage, artifact registries, and database backups serve different needs. Prefer focused commits and reviewed changes over one opaque accumulated snapshot.

## 6. How do I know I understand it?

**Blank-page check:** draw working tree, index, HEAD, commit graph, local branch, remote-tracking reference, and remote repository separately.

| Constraint change | Predict the failure and response |
| --- | --- |
| File changes after staging | Commit still uses the staged content until staged again |
| Secret is removed in a new commit | Historical copies and credential validity remain concerns |
| Two developers edit the same behavior | Resolve semantics, not only conflict markers |
| Local machine is lost before push/backup | Unshared history can be lost despite having local commits |

You understand Git when you can predict exactly what a command will compare or record before using it.
