# Logging

[Lesson index](../../README.md) · Previous: [Environment / Configuration](2.environment_configuration.md) · Next: [Health Check](4.health_check.md)

## 1. What is it?

Logging records selected execution events for diagnosis, like a flight recorder that preserves useful observations without copying every passenger's private belongings.

Operational logs, durable audit evidence, metrics, and traces overlap but serve different contracts.

## 2. Why do we need it?

After a request fails, the current database row cannot explain which dependency timed out. Unstructured “something went wrong” messages give no route or correlation context.

Specific pain: the client has a generic `500`, operators cannot find its cause, or debug logs expose the very password involved in the incident.

## 3. Under the hood / mechanism / system flow

### 3a. Events, handlers, and cost

An application emits an event and context; formatters encode it; handlers write to streams/files/collectors. Synchronous I/O can slow requests; asynchronous queues need bounds, shutdown flush, and overflow policy. Volume, indexing, retention, and cardinality affect cost.

Structured JSON enables machine parsing and escaping. It does not automatically redact secrets, and raw exception text can contain sensitive data. Use meaningful severity, stable event names, and bounded allowlisted context. See [Python logging](https://docs.python.org/3/library/logging.html) and [OWASP's logging controls](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).

### 3b. Request-to-investigation lifecycle

```text
Trusted request ID → boundary/use-case events → redacted structured sink
    → restricted search/retention → investigation/alert evidence
```

Log unexpected failures at an owning boundary rather than duplicating a stack trace at every layer. Logging a failure does not roll back a transaction or send the correct response. Define behavior when the collector or disk fails; ordinary diagnostic logging and mandatory audit recording may need different policies.

## 4. How to apply / implement / use it?

Save as `logging_demo.py`; run `python3 logging_demo.py`. A strict event formatter demonstrates bounded safe fields, not a universal sanitizer for arbitrary log messages.

```python
import io
import json
import logging
import re

class SafeFormatter(logging.Formatter):
    def format(self, record):
        event = record.msg if record.msg in {"task_saved", "storage_failed"} else "unclassified"
        request_id = getattr(record, "request_id", "missing")
        if not isinstance(request_id, str) or re.fullmatch(r"[A-Za-z0-9-]{1,64}", request_id) is None:
            request_id = "invalid"
        route = getattr(record, "route", "other")
        if route not in {"/tasks", "/tasks/{id}"}:
            route = "other"
        return json.dumps({"event": event, "level": record.levelname, "request_id": request_id, "route": route})

output = io.StringIO()
handler = logging.StreamHandler(output)
handler.setFormatter(SafeFormatter())
logger = logging.getLogger("learning.safe")
logger.handlers = [handler]
logger.setLevel(logging.INFO)
logger.propagate = False
logger.info("task_saved", extra={"request_id": "server-001", "route": "/tasks/{id}", "access_token": "SECRET_TOKEN"})
logger.error("storage_failed", extra={"request_id": "bad\nline", "error": "PASSWORD_SECRET"})
lines = output.getvalue().splitlines()
assert len(lines) == 2
assert json.loads(lines[0])["request_id"] == "server-001"
assert json.loads(lines[1])["request_id"] == "invalid"
assert "SECRET_TOKEN" not in output.getvalue() and "PASSWORD_SECRET" not in output.getvalue()
print("happy: correlated structured events; unhappy: secret extras and invalid context excluded")
```

The logger is configured once for this standalone process. Production setup should avoid replacing framework handlers casually. Server-generated IDs and canonical route templates are used; this fixture intentionally excludes all exception text and needs a separate restricted/redacted diagnostic strategy for deeper failures.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not log passwords, authorization headers, complete request bodies, or connection strings by default.
- Do not use logs as an unbounded substitute for metrics or transactional audit history.
- Do not mark every expected validation rejection as a critical error.
- Do not assume JSON formatting alone prevents sensitive disclosure or unlimited volume.

Logging every detail can hurt performance and investigations by creating noise. Record actionable context with retention/access controls and a defined failure policy.

## 6. How do I know I understand it?

**Blank-page check:** design one safe failure event with an owner, severity, correlation ID, fields, destination, retention, and explicit excluded secrets.

| Constraint change | Predict the failure and response |
| --- | --- |
| Exception contains SQL credentials | Do not blindly serialize it; redact/restrict diagnostics |
| Collector becomes slow | Bound queues/backpressure and choose loss/failure behavior deliberately |
| One error occurs in five layers | Preserve context without five duplicate stack traces |
| User input contains newlines | Encode/validate context to prevent forged multiline events |

You understand logging when a failure is investigable without turning diagnostics into a data leak or another outage.
