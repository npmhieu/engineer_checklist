# Basic Monitoring

[Lesson index](../../README.md) · Previous: [Health Check](4.health_check.md) · Next: [Basic CI/CD](6.basic_ci_cd.md)

## 1. What is it?

Monitoring observes defined system signals over time so problems become visible, like a dashboard tracking engine temperature and fuel rather than waiting for the car to stop.

Collecting measurements, retaining/querying them, displaying dashboards, and alerting are separate parts of the system.

## 2. Why do we need it?

A process can pass a health check while error rate, tail latency, connection saturation, or queue age steadily worsens. A single successful manual request can hide many failures.

Specific pain: average latency looks fine while the slowest users time out, or a worker is running but its oldest pending job is hours late.

## 3. Under the hood / mechanism / system flow

### 3a. Counters, gauges, histograms, and cardinality

Counters accumulate events and need rates/deltas over a window; gauges represent current state; histograms count observations in buckets. Percentiles describe distributions; averaging per-instance percentiles does not generally yield a fleet percentile. Cumulative histogram buckets include all observations at or below their boundary.

Every label combination can create another time series, increasing memory, storage, query cost, and ingestion work. Use bounded canonical routes/status classes—not user IDs, tokens, or raw URLs. [Prometheus instrumentation guidance](https://prometheus.io/docs/practices/instrumentation/) discusses useful signals and cardinality.

### 3b. Signal-to-action flow

```text
Instrument operations → collect/scrape/export → retain/query time windows
    → dashboard + actionable alert → investigation/runbook → recovery verification
```

Start with request rate, error rate, duration, and resource saturation; add backlog age/failure for async work. Define what counts as an error, window/minimum traffic, and business impact. No observations means “unknown/no traffic,” not proof of zero failures. Monitor the monitoring pipeline itself.

## 4. How to apply / implement / use it?

Save as `monitoring_demo.py`; run `python3 monitoring_demo.py`. This bounded in-memory fixture represents one measurement window, not a production metrics server or time-series database.

```python
import math

routes = {"/tasks", "/tasks/{id}"}
bounds = (0.1, 0.5, 1.0, math.inf)
metrics = {route: {"count": 0, "errors": 0, "buckets": [0] * len(bounds)} for route in routes}

def observe(route, status, seconds):
    if route not in routes or type(status) is not int or not 100 <= status <= 599:
        raise ValueError("INVALID_LABEL_OR_STATUS")
    if type(seconds) not in (int, float) or not math.isfinite(seconds) or seconds < 0:
        raise ValueError("INVALID_DURATION")
    record = metrics[route]
    record["count"] += 1
    record["errors"] += int(status >= 500)
    for position, upper in enumerate(bounds):
        if seconds <= upper:
            record["buckets"][position] += 1

def window_error_rate(route):
    record = metrics[route]
    return None if record["count"] == 0 else record["errors"] / record["count"]

assert window_error_rate("/tasks") is None
for status, seconds in [(200, 0.01), (200, 0.2), (500, 0.8), (503, 1.2), (200, 0.3)]:
    observe("/tasks", status, seconds)
assert window_error_rate("/tasks") == 0.4
assert metrics["/tasks"]["buckets"] == [1, 3, 4, 5]
alert = metrics["/tasks"]["count"] >= 5 and window_error_rate("/tasks") > 0.05
assert alert
for route, duration in [("/tasks/secret-user-id", 0.2), ("/tasks", math.nan)]:
    try:
        observe(route, 200, duration)
    except ValueError:
        pass
    else:
        raise AssertionError("Unbounded label or invalid duration accepted")
assert metrics["/tasks"]["count"] == 5
print("happy: bounded counters/distribution; unhappy: elevated errors detected and bad observations rejected")
```

The 5%/five-request threshold is a teaching fixture, not an operational recommendation. Real counter-based error rates use a defined time window and handle process resets; latency uses an appropriate monotonic timer. Configure actual collection, retention, routing, and runbooks separately.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not instrument every variable or attach high-cardinality/private data to labels.
- Do not alert on every transient fluctuation without impact, duration, or ownership.
- Do not equate CPU utilization alone with user-visible health.
- Do not use averages to hide a distribution's slow tail or treat missing telemetry as success.

Too many alerts create fatigue; too many metrics create cost. Start with actionable symptoms and sufficient context, then expand based on real diagnostic needs.

## 6. How do I know I understand it?

**Blank-page check:** choose signals for an API and a worker. Define labels, windows, error meaning, collection failure behavior, and the action for one alert.

| Constraint change | Predict the failure and response |
| --- | --- |
| User IDs become metric labels | Time-series count grows with users; avoid that label design |
| One replica restarts | Counter reset must not become a negative request rate |
| Average latency stays low but p99 worsens | Inspect tail distribution and affected workload |
| Scrapes stop arriving | Alert on missing monitoring evidence rather than reporting zero errors |

You understand monitoring when measurements answer operational questions and alerts have a clear owner and response.
