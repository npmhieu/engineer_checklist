# Relationships

[Lesson index](../../README.md) · Previous: [Schema / Data Modeling](2.schema_data_modeling.md) · Next: [Normalization](4.normalization.md)

## 1. What is it?

A relationship records how entities connect, like one customer having several orders or several students enrolling in several courses.

**Cardinality** describes one-to-one, one-to-many, or many-to-many; **optionality** says whether participation is required. A drawing alone does not enforce either.

## 2. Why do we need it?

Comma-separated user IDs cannot reliably enforce valid memberships or store per-membership roles. Duplicated ownership columns can disagree about who owns a record.

Specific pain: deleting a project leaves orphan memberships, or the same user is added to the same project twice. Explicit relationships give integrity and query paths a consistent meaning.

## 3. Under the hood / mechanism / system flow

### 3a. Keys, link rows, and joins

A foreign key on the many side commonly models one-to-many. A foreign key plus uniqueness can model at most one related row. Many-to-many uses a junction table with one row per association; that row can carry attributes such as membership role or enrollment date.

Joins connect matching keys; they can multiply rows. Joining one project to ten members yields ten result rows, not ten projects. Indexes influence lookup cost; fetching related data one object at a time can create N+1 queries. Foreign keys need correct engine configuration; [SQLite requires enabling foreign-key enforcement on each relevant connection](https://www.sqlite.org/foreignkeys.html).

### 3b. Relationship lifecycle

```text
Create parent identities → create valid associations → join for a use case
    → change/remove association → apply deliberate parent-deletion policy
```

Membership existence does not automatically grant every action. Authorization interprets relationships; the database enforces structural references. Deleting a parent can restrict, cascade, or null related references under a chosen policy.

## 4. How to apply / implement / use it?

Save as `relationships_demo.py`; run `python3 relationships_demo.py`.

```python
import sqlite3

database = sqlite3.connect(":memory:")
database.execute("PRAGMA foreign_keys = ON")
database.executescript("""
    CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
    CREATE TABLE profiles (user_id INTEGER PRIMARY KEY REFERENCES users(id), bio TEXT);
    CREATE TABLE projects (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
    CREATE TABLE memberships (
        user_id INTEGER NOT NULL REFERENCES users(id),
        project_id INTEGER NOT NULL REFERENCES projects(id),
        role TEXT NOT NULL,
        PRIMARY KEY (user_id, project_id)
    );
    INSERT INTO users VALUES (7, 'Learner');
    INSERT INTO projects VALUES (42, 'Backend');
    INSERT INTO profiles VALUES (7, 'Learning');
    INSERT INTO memberships VALUES (7, 42, 'editor');
""")
row = database.execute("""
    SELECT users.name, projects.name, memberships.role
    FROM memberships JOIN users ON users.id = memberships.user_id
    JOIN projects ON projects.id = memberships.project_id
""").fetchone()
assert row == ("Learner", "Backend", "editor")
for statement in [
    "INSERT INTO memberships VALUES (7, 42, 'viewer')",
    "INSERT INTO memberships VALUES (99, 42, 'viewer')",
    "INSERT INTO profiles VALUES (7, 'Duplicate profile')",
]:
    try:
        with database:
            database.execute(statement)
    except sqlite3.IntegrityError:
        pass
    else:
        raise AssertionError("Invalid relationship was accepted")
database.close()
print("happy: joined association; unhappy: duplicate/orphan/extra profile rejected")
```

The profile schema permits zero or one profile per user; it does not force every user to have a profile. Requiring that total participation needs an additional creation/workflow design.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not force cross-service relationships into local foreign keys when another service owns the identity; define integration/consistency behavior instead.
- Do not use a junction table for a field that is genuinely a single bounded value.
- Do not cascade-delete important history without a product retention policy.
- Do not mistake an ORM relationship for a guarantee that its generated queries are efficient.

Relationships add joins and deletion/change coordination, but removing them does not remove the domain's consistency requirements.

## 6. How do I know I understand it?

**Blank-page check:** draw users, projects, profiles, and memberships with cardinality and optionality. Translate each line into constraints or identify what the schema does not enforce.

| Constraint change | Predict the failure and response |
| --- | --- |
| Membership gains a role | Store it on the association, not the user globally |
| A user may have several profiles | Remove/rethink the uniqueness rule deliberately |
| Project is deleted | Define restrict/cascade/history behavior before shipping DELETE |
| Report counts projects after joining members | Avoid counting multiplied association rows as distinct projects |

You understand relationships when you can enforce multiplicity and reason about join results and deletion behavior.
