# Basic Query Optimization

[Lesson index](../../README.md) · Previous: [Indexes](6.indexes.md) · Next: [Transactions](8.transactions.md)

## 1. What is it?

Query optimization reduces the work needed to return the correct data, like planning one shopping route instead of making a separate trip for each item.

At the application level this includes query shape, round trips, selected columns, result bounds, and suitable indexes—not only rewriting SQL syntax.

## 2. Why do we need it?

A list endpoint can execute one query for ten tasks and then ten more for their owners. Each query looks fast in isolation, yet network latency accumulates. An index cannot remove those avoidable round trips by itself.

Specific pain: ORM N+1 loading makes latency rise with page size while database logs show many small queries rather than one obviously slow query.

## 3. Under the hood / mechanism / system flow

### 3a. Plans, cardinality, and I/O

The optimizer estimates row counts and chooses scans, seeks, joins, and sorts from available statistics/access paths. Bad estimates can choose poor plans. Runtime includes connection waits, round trips, page reads, CPU, temporary spills, and serialization; SQL character count is not a cost model.

Start with rows examined versus returned, query count per request, and plan operators. Select only needed columns, bound result sizes, avoid repeated per-row lookups, and make filters compatible with useful indexes where possible. See [SQLite query planning](https://www.sqlite.org/queryplanner.html).

### 3b. Evidence-driven loop

```text
Slow real operation → representative baseline → inspect query count/plan
    → one targeted change → verify identical results → measure again
```

Do not remove tenant/permission predicates to get a faster plan. A join rewrite can change multiplicity or null behavior; preserve semantics before comparing speed. Production `EXPLAIN ANALYZE`-style commands can execute the statement—know the engine and avoid casually running mutating statements as diagnostics.

## 4. How to apply / implement / use it?

Save as `query_optimization_demo.py`; run `python3 query_optimization_demo.py`. It counts SELECT statements, avoiding unreliable wall-clock assertions on a tiny fixture.

```python
import sqlite3

database = sqlite3.connect(":memory:")
database.executescript("""
    CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT);
    CREATE TABLE tasks (id INTEGER PRIMARY KEY, owner_id INTEGER);
    INSERT INTO users VALUES (1, 'A'), (2, 'B');
""")
with database:
    database.executemany("INSERT INTO tasks VALUES (?, ?)", [(number, 1 + number % 2) for number in range(1, 11)])
queries = []
database.set_trace_callback(lambda statement: queries.append(statement) if statement.lstrip().upper().startswith("SELECT") else None)

slow = []
for task_id, owner_id in database.execute("SELECT id, owner_id FROM tasks ORDER BY id LIMIT 10").fetchall():
    owner = database.execute("SELECT name FROM users WHERE id = ?", (owner_id,)).fetchone()[0]
    slow.append((task_id, owner))
assert len(queries) == 11
queries.clear()
fast = database.execute("""
    SELECT tasks.id, users.name FROM tasks JOIN users ON users.id = tasks.owner_id
    ORDER BY tasks.id LIMIT 10
""").fetchall()
assert fast == slow and len(queries) == 1
database.close()
print("unhappy: N+1 uses 11 queries; happy: same result with one joined query")
```

All fixture tasks have valid owners. If owners could be absent, an inner join would drop tasks; use the correct relationship/outer-join behavior rather than assuming every rewrite preserves results. Batching related data is another option when one giant join would multiply rows.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not optimize guesses before locating the actual bottleneck.
- Do not create a huge join that returns a Cartesian explosion instead of bounded batches.
- Do not test only hot-cache tiny fixtures or use “under 1 ms” assertions as correctness tests.
- Do not hide a database outage behind a cache merely to make latency look better.

Some expensive queries belong in background reporting, read models, or dedicated analytical systems. That is a workload decision after measurement, not the first response to any slow query.

## 6. How do I know I understand it?

**Blank-page check:** explain an endpoint's query count, expected result cardinality, main plan operators, and what measurement would prove an improvement.

| Constraint change | Predict the failure and response |
| --- | --- |
| Page size doubles | N+1 round trips grow; batching/joining changes that scaling |
| Some owners disappear | Preserve intended null/missing behavior when rewriting joins |
| Production distribution differs | Reevaluate estimates/plans with representative data |
| DB is fast but response is slow | Inspect pool wait, network, serialization, and external dependencies too |

You understand optimization when an evidence-backed change preserves meaning while reducing measured work.
