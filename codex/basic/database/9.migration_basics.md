# Migration Basics

[Lesson index](../../README.md) · Previous: [Transactions](8.transactions.md) · Next section: [File Upload](../common_features/1.file_upload.md)

## 1. What is it?

A migration is an ordered, recorded change to database structure or data, like versioned renovation instructions rather than manually altering each building differently.

Application code version, database migration version, and public API version are separate compatibility concerns.

## 2. Why do we need it?

Manual ALTER commands drift between developer machines and production. A new application expects a column that is absent, or a failed change is marked complete even though its schema update never committed.

Specific pain: a deployment succeeds on an empty database but fails on existing rows or when old and new application replicas run together.

## 3. Under the hood / mechanism / system flow

### 3a. History, DDL, and data work

A migration tool commonly stores ordered IDs, checksums, and execution history, acquires a migration lock, and executes pending changes. DDL can be metadata-only or rewrite/scan/lock large tables depending on engine and operation. Backfills also generate I/O, logs, replication lag, and contention.

Transactional DDL support varies. Do not assume one DBMS's ALTER or rollback behavior applies elsewhere. [SQLite's ALTER TABLE documentation](https://www.sqlite.org/lang_altertable.html) lists its supported operations and constraints.

### 3b. Deployment compatibility

```text
Inspect current schema/data → apply reviewed expansion → deploy compatible code
    → backfill/verify → switch reads/writes → remove obsolete structures later
```

Keep already applied migrations immutable; add a new corrective migration instead of editing history. A down migration is not a backup: dropping a column can destroy data that reversal cannot reconstruct. Test backups/restores and rehearse realistic upgrades before destructive production work.

## 4. How to apply / implement / use it?

Save as `migration_demo.py`; run `python3 migration_demo.py`. This small SQLite runner illustrates history/checksum atomicity, not a general production migration framework.

```python
import hashlib
import sqlite3

database = sqlite3.connect(":memory:")
database.executescript("""
    CREATE TABLE tasks (id INTEGER PRIMARY KEY, title TEXT NOT NULL);
    INSERT INTO tasks VALUES (1, 'Existing task');
    CREATE TABLE migrations (version INTEGER PRIMARY KEY, checksum TEXT NOT NULL);
""")

def migrate(version, statement):
    checksum = hashlib.sha256(statement.encode()).hexdigest()
    with database:
        database.execute("BEGIN IMMEDIATE")
        existing = database.execute("SELECT checksum FROM migrations WHERE version = ?", (version,)).fetchone()
        if existing:
            if existing[0] != checksum:
                raise ValueError("APPLIED_MIGRATION_CHANGED")
            return
        database.execute(statement)
        database.execute("INSERT INTO migrations VALUES (?, ?)", (version, checksum))

change = "ALTER TABLE tasks ADD COLUMN completed INTEGER NOT NULL DEFAULT 0 CHECK (completed IN (0, 1))"
migrate(1, change)
migrate(1, change)
assert database.execute("SELECT completed FROM tasks").fetchone()[0] == 0
try:
    migrate(2, "ALTER TABLE missing ADD COLUMN value TEXT")
except sqlite3.OperationalError:
    pass
else:
    raise AssertionError("Invalid migration succeeded")
try:
    migrate(1, "ALTER TABLE tasks ADD COLUMN unrelated TEXT")
except ValueError:
    pass
else:
    raise AssertionError("Edited migration history was accepted")
assert database.execute("SELECT version FROM migrations").fetchall() == [(1,)]
database.close()
print("happy: upgrade existing row once; unhappy: invalid change/history edit rejected")
```

This runner assumes externally ordered migrations; it does not enforce a complete ordered manifest, branch conflict handling, or every DDL recovery case. Its explicit transaction coordinates this SQLite DDL and history entry. Prefer an established migration tool in an application.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not auto-run destructive schema synchronization at every application startup.
- Do not test only creation from an empty database; upgrade realistic old data too.
- Do not combine removal of a column and deployment of readers that still need it.
- Do not run an unbounded backfill in a peak-traffic deployment transaction without capacity/lock analysis.

For disposable fixtures, rebuilding may be simpler. Persistent user data needs deliberate migration, compatibility, verification, and recovery plans.

## 6. How do I know I understand it?

**Blank-page check:** write an expansion/backfill/switch/contraction sequence for renaming a required field while old and new replicas coexist.

| Constraint change | Predict the failure and response |
| --- | --- |
| Old rows violate a new NOT NULL rule | Backfill/resolve data before enforcing the constraint |
| Two deployers migrate together | Use the tool's correct shared locking/coordination mechanism |
| Change rewrites a huge table | Rehearse runtime/locks and choose engine-appropriate online strategies |
| Rollback code needs a removed column | Schema rollback is not automatically safe; preserve compatibility or restore/reconcile |

You understand migrations when schema, data, running code, and recovery remain compatible across the transition—not only at its final state.
