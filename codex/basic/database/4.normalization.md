# Normalization

[Lesson index](../../README.md) · Previous: [Relationships](3.relationships.md) · Next: [Primary / Foreign Key](5.primary_foreign_key.md)

## 1. What is it?

Normalization organizes relational facts according to what determines them, like keeping one address-book entry instead of copying the same contact details onto every order.

It reduces unnecessary duplication and update/insert/delete anomalies. It does not mean “split every field into another table.”

## 2. Why do we need it?

If a department name appears on every employee row, renaming the department requires many writes. Updating only some rows makes the name contradictory; deleting the last employee can accidentally erase the only record of the department.

Specific pain: a report shows two names for the same department because identical facts have several independent storage locations.

## 3. Under the hood / mechanism / system flow

### 3a. Functional dependencies and normal forms

A functional dependency `X → Y` means one X value determines one Y value under the domain's rules. Candidate keys identify rows minimally; normalization reasons about all relevant candidate keys, not just the chosen primary key.

- **1NF:** represent values in appropriate atomic domains without repeating groups; what counts as one value depends on the modeled domain.
- **2NF:** 1NF plus no non-prime attribute depending on only a proper subset of a candidate key. With `(order_id, product_id)`, product name depends on product ID, not the whole order-line identity.
- **3NF:** for each nontrivial dependency `X → A`, X is a superkey or A is a prime attribute. In common simple models, this removes non-key facts depending transitively on other non-key facts.

Adding a surrogate ID does not magically remove business dependencies. Decomposition should preserve facts and support a lossless reconstruction through joins. [Microsoft's normalization explanation](https://learn.microsoft.com/en-us/previous-versions/troubleshoot/microsoft-365/microsoft-365-apps/access/database-normalization-description) illustrates anomalies and basic normal forms.

### 3b. Write/read lifecycle and costs

```text
Identify fact owner + dependencies → decompose tables → enforce references
    → write each fact in its owner → join/projection for readers
```

Normalization can reduce repeated storage and multi-row updates while increasing joins. Query plans and indexes determine actual I/O. Deliberate denormalized read models require a clear source of truth and refresh/reconciliation policy.

## 4. How to apply / implement / use it?

Save as `normalization_demo.py`; run `python3 normalization_demo.py`.

```python
import sqlite3

duplicated = [{"employee": "A", "department": 1, "name": "Ops"}, {"employee": "B", "department": 1, "name": "Ops"}]
duplicated[0]["name"] = "Platform"
assert len({row["name"] for row in duplicated}) == 2

database = sqlite3.connect(":memory:")
database.execute("PRAGMA foreign_keys = ON")
database.executescript("""
    CREATE TABLE departments (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
    CREATE TABLE employees (
        id INTEGER PRIMARY KEY, name TEXT NOT NULL,
        department_id INTEGER NOT NULL REFERENCES departments(id)
    );
    INSERT INTO departments VALUES (1, 'Ops');
    INSERT INTO employees VALUES (1, 'A', 1), (2, 'B', 1);
""")
with database:
    database.execute("UPDATE departments SET name = ? WHERE id = ?", ("Platform", 1))
rows = database.execute("""
    SELECT employees.name, departments.name FROM employees
    JOIN departments ON departments.id = employees.department_id ORDER BY employees.id
""").fetchall()
assert rows == [("A", "Platform"), ("B", "Platform")]
database.close()
print("unhappy: duplicated fact diverges; happy: one update gives consistent joined names")
```

The two representations store different ownership structures; the first assertion deliberately demonstrates the anomaly. Historical order prices or shipping-address snapshots are separate historical facts, not necessarily bad copies of a current mutable fact.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not normalize a historical snapshot into a reference that rewrites history whenever current data changes.
- Do not add lookup tables for every boolean or tiny stable domain without need.
- Do not use analytical denormalization as an excuse to create conflicting sources of truth.
- Do not assume more normal forms always yield the fastest reporting query.

Transactional models and analytical star/read models serve different access patterns. Denormalization should name its owner, refresh lag, and recovery path.

## 6. How do I know I understand it?

**Blank-page check:** list candidate keys and functional dependencies for an order line, product, and category. Predict an anomaly before proposing a table split.

| Constraint change | Predict the failure and response |
| --- | --- |
| Department name changes | One owned fact should change, not independent employee copies |
| Last employee is deleted | Department existence should not accidentally disappear |
| An order must retain its agreed price | Store a historical fact instead of reading today's product price |
| Reporting joins become expensive | Measure/index first; consider an explicitly maintained read model |

You understand normalization when you can explain which fact is duplicated, which dependency causes the anomaly, and why the decomposition preserves meaning.
