# Transactions

## 1. What is it?

A transaction groups database operations into one coordinated commit or rollback boundary, like a bank transfer that must not debit one account without crediting the other.

It is not automatically a transaction across a database, payment provider, mail server, and filesystem.

## 2. Why do we need it?

If a process debits a balance and crashes before crediting the destination, money appears lost. Separate successful statements do not guarantee a valid combined operation.

Specific bug: an error halfway through an operation leaves earlier writes committed, or two callers pass the same stale balance check. Transactions provide a boundary, while correct statements and appropriate isolation/locking protect the actual invariant.

## 3. Under the hood / mechanism / system flow

### 3a. ACID and coordination

- **Atomicity:** commit the transaction's changes together or undo them.
- **Consistency:** declared constraints and correctly designed operations preserve intended invariants; the engine cannot infer every business rule.
- **Isolation:** concurrent work interacts according to the chosen engine/isolation rules, not necessarily as if every read used a global latest state.
- **Durability:** a successful commit survives defined failures under configured storage/recovery guarantees.

Locks, versioned data/snapshots, journals/logs, and commit synchronization implement these properties. Long transactions retain locks/versions and connections, increasing contention and cleanup costs. [SQLite's transaction documentation](https://www.sqlite.org/lang_transaction.html) describes its one-writer behavior; do not copy that concurrency model onto every DBMS.

### 3b. Commit boundary and uncertain outcomes

```text
Begin → coordinated checks/writes → commit → return success
Any pre-commit failure → rollback → report failure
```

A network failure around commit can leave the caller uncertain even when changes persisted. Do not assume an error response proves rollback; use idempotency/reconciliation where needed. A transaction alone does not fix stale read-then-unconditional-write logic.

## 4. How to apply / implement / use it?

Save as `transactions_demo.py`; run `python3 transactions_demo.py`. Integer cents and a conditional debit protect this local invariant.

```python
import sqlite3

database = sqlite3.connect(":memory:")
database.executescript("""
    CREATE TABLE accounts (id INTEGER PRIMARY KEY, cents INTEGER NOT NULL CHECK (cents >= 0));
    INSERT INTO accounts VALUES (1, 100), (2, 0);
""")

def transfer(source, destination, cents):
    if type(cents) is not int or cents <= 0:
        raise ValueError("INVALID_AMOUNT")
    with database:
        debit = database.execute("UPDATE accounts SET cents = cents - ? WHERE id = ? AND cents >= ?", (cents, source, cents))
        if debit.rowcount != 1:
            raise ValueError("INSUFFICIENT_OR_MISSING_SOURCE")
        credit = database.execute("UPDATE accounts SET cents = cents + ? WHERE id = ?", (cents, destination))
        if credit.rowcount != 1:
            raise LookupError("DESTINATION_NOT_FOUND")

transfer(1, 2, 40)
assert database.execute("SELECT cents FROM accounts ORDER BY id").fetchall() == [(60,), (40,)]
for destination, amount in [(99, 10), (2, 100)]:
    try:
        transfer(1, destination, amount)
    except (LookupError, ValueError):
        pass
    else:
        raise AssertionError("Invalid transfer succeeded")
assert database.execute("SELECT cents FROM accounts ORDER BY id").fetchall() == [(60,), (40,)]
database.close()
print("happy: balanced transfer; unhappy: missing destination/overdraft leave balances unchanged")
```

The operation assumes an already authorized caller and fixed currency. The missing-destination failure occurs after the debit, proving rollback of that debit. This is not a concurrent-load, crash-durability, ledger, or external-payment implementation.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- A single atomic statement already has a database boundary; avoid unnecessary multi-step work.
- Do not hold locks while waiting for HTTP calls, human input, or long report generation.
- Do not catch an error inside a transaction and continue blindly after partial work.
- Do not assume default isolation prevents all lost updates, write skew, or overselling.

Local transactions are powerful but cannot roll back independent external effects. Use explicit workflows/outbox/compensation when those boundaries matter.

## 6. How do I know I understand it?

**Blank-page check:** mark every write, constraint, lock/conditional predicate, and commit boundary in a transfer. Place a failure after each step and predict persistent state.

| Constraint change | Predict the failure and response |
| --- | --- |
| Two requests spend one remaining balance | Use a coordinated conditional write/locking strategy, not an independent pre-check |
| Destination insert fails | Earlier debit must roll back under the same transaction |
| Commit response is lost | Outcome can be uncertain; do not blindly repeat a non-idempotent operation |
| Transfer calls an external provider | A local rollback cannot undo that provider's completed effect |

You understand transactions when you can explain both their guarantees and what lies outside their boundary.
