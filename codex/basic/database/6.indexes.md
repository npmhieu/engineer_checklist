# Indexes

## 1. What is it?

An index is an auxiliary structure that helps a database locate or order data, like a book's index pointing to relevant pages instead of reading the whole book.

It is not a second independent source of truth maintained by application code; the engine normally updates it with the indexed data.

## 2. Why do we need it?

Looking up one user's newest tasks by scanning every task wastes CPU and page reads as data grows. Sorting the candidate set separately can add memory use and temporary-disk I/O.

Specific bottleneck: an endpoint that was fast at 100 rows becomes slow at ten million despite returning only 20 rows.

## 3. Under the hood / mechanism / system flow

### 3a. Ordered structures and access paths

A common B-tree/B+tree family organizes ordered keys into pages with high branching factors. A seek is roughly `O(log n)` tree work, followed by traversal of matching entries and possibly table-page lookups. Returning `k` rows still costs at least proportional work in `k`.

A composite index on `(owner_id, created_at, id)` can support owner equality followed by ordered traversal. Column order matters; it is not equivalent to any permutation. A covering index can supply selected values without some table accesses, depending on engine/visibility rules. Leading-wildcard or transformed predicates may not use an ordinary index as hoped.

Indexes consume storage/cache and increase insert/update/delete work. Low-selectivity conditions may still favor a scan. The optimizer chooses; existence alone does not force use. [SQLite's query-planner explanation](https://www.sqlite.org/queryplanner.html) illustrates searches, multi-column indexes, and sorting.

### 3b. Query and write lifecycle

```text
Observed query pattern → candidate index → plan inspection + measurement
Writes → table change + index maintenance in the transaction
```

Creating an index on production data can consume resources and block work depending on engine/DDL mode. Uniqueness indexes additionally enforce a constraint and may fail to build when existing rows conflict.

## 4. How to apply / implement / use it?

Save as `indexes_demo.py`; run `python3 indexes_demo.py`. This proves an access-plan change, not a benchmark or a promise about another engine's optimizer.

```python
import sqlite3

database = sqlite3.connect(":memory:")
database.execute("CREATE TABLE tasks (id INTEGER PRIMARY KEY, owner_id INTEGER, created_at INTEGER)")
with database:
    database.executemany("INSERT INTO tasks VALUES (?, ?, ?)", [(number, number % 20, number) for number in range(1, 2001)])
query = "SELECT id FROM tasks WHERE owner_id = ? ORDER BY created_at DESC, id DESC LIMIT 5"

def plan():
    return [row[3] for row in database.execute("EXPLAIN QUERY PLAN " + query, (7,))]

before = plan()
expected = database.execute(query, (7,)).fetchall()
database.execute("CREATE INDEX task_owner_date ON tasks(owner_id, created_at DESC, id DESC)")
after = plan()
assert database.execute(query, (7,)).fetchall() == expected
assert any("SCAN" in detail for detail in before)
assert any("task_owner_date" in detail and "SEARCH" in detail for detail in after)
database.close()
print("unhappy: scan before index; happy: indexed search preserves results")
```

Plan text is engine/version-specific; this assertion intentionally targets SQLite. Read the complete plan and test representative distributions rather than relying only on one keyword.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not index every column or every possible filter combination.
- Do not expect a low-selectivity boolean index alone to solve every query.
- Do not ignore write amplification, larger backups, and cache pressure.
- Do not keep redundant indexes forever without usage/workload review.

Tiny tables and broad analytical scans may not benefit. Indexes accelerate particular access patterns, not poorly bounded API responses or slow external calls.

## 6. How do I know I understand it?

**Blank-page check:** propose an index for tenant equality, status equality, and newest-first pagination. Explain column order, returned-row cost, and write overhead.

| Constraint change | Predict the failure and response |
| --- | --- |
| Query drops the leading equality condition | Reevaluate the available access path; the old index may be less useful |
| Most rows match | A scan may be rational despite index existence |
| Writes grow tenfold | Extra index maintenance can become expensive |
| Sorting changes to another column | Existing index order may no longer avoid sorting |

You understand indexes when you can explain both saved read work and added maintenance work using a real query plan.
