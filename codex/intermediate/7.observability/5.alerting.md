# Alerting

[Lesson index](../../README.md) · [Previous](4.monitoring.md) · [Next](6.request_id.md)

## 1. What is it?

Alerting notifies an owner when a condition needs timely action, like a fire alarm rather than a wall of temperature readings.

## 2. Why do we need it?

Without routing and thresholds, outages go unnoticed; indiscriminate notifications create fatigue and teach responders to ignore real incidents.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Separate condition evaluation from notification delivery, grouping, silencing, and escalation. Use persistence/windowing to suppress flaps while preserving fast detection for serious failures. Every page needs user impact, owner, severity, evidence, and a runbook.

Reference: [Primary documentation](https://prometheus.io/docs/practices/alerting/).

### 3b. Boundaries and lifecycle

Evaluate → pending → firing → routed notification → acknowledged investigation → resolved; test delivery as well as the expression.

## 4. How to apply / implement / use it?

Save as `alerting_demo.py`; run `python3 alerting_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
state = {"since": None, "firing": False}
def evaluate(now, bad):
    if not bad:
        state.update(since=None, firing=False)
        return "healthy"
    if state["since"] is None:
        state["since"] = now
    state["firing"] = now - state["since"] >= 60
    return "firing" if state["firing"] else "pending"
assert evaluate(0, True) == "pending"
assert evaluate(30, False) == "healthy"
assert evaluate(40, True) == "pending"
assert evaluate(99, True) == "pending"
assert evaluate(100, True) == "firing"
assert evaluate(101, False) == "healthy"
```

The fake-clock state machine demonstrates sustained-condition timing. It assumes uninterrupted evaluations and supplies no actual notifications, durable alert state, missing-data policy, inhibition, or escalation.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not page for conditions with no useful immediate action. Avoid one page per replica, no-owner alerts, and permanent silences that hide unresolved failure.

## 6. How do I know I understand it?

**Blank-page check:** Write an alert containing impact, owner, threshold/window, evidence, and runbook. Explain detection delay versus noise trade-offs.

| Constraint change | Predict the failure and response |
| --- | --- |
| One dependency fails across 50 replicas | Group related symptoms and route a useful incident, not 50 independent pages. |
| Notifications cannot be delivered | Use independent delivery monitoring/escalation; a firing rule alone does not summon a human. |
