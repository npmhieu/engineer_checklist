# Monitoring

[Lesson index](../../README.md) · [Previous](3.error_tracking.md) · [Next](5.alerting.md)

## 1. What is it?

Monitoring continuously evaluates system signals against expected behavior, like checking dashboard instruments throughout a journey rather than only after a breakdown.

## 2. Why do we need it?

A healthy process can serve errors, stop consuming jobs, or display stale reports; isolated logs do not automatically reveal these conditions.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Combine user-visible probes with internal request, error, latency, saturation, and freshness signals. Collection, storage, query evaluation, and dashboarding are separate failure points. Missing telemetry is unknown, not automatically healthy or zero traffic.

Reference: [Primary documentation](https://prometheus.io/docs/practices/instrumentation/).

### 3b. Boundaries and lifecycle

Collect timestamped signals → check freshness and objectives → display trends → trigger actionable investigation or alerts; monitor the monitoring path too.

## 4. How to apply / implement / use it?

Save as `monitoring_demo.py`; run `python3 monitoring_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def assess(sample, now):
    if sample is None or now - sample["time"] > 30:
        return "unknown"
    if sample["requests"] == 0:
        return "no-traffic"
    if sample["errors"] / sample["requests"] > 0.05:
        return "degraded"
    return "healthy"
assert assess({"time": 90, "requests": 100, "errors": 1}, 100) == "healthy"
assert assess({"time": 90, "requests": 100, "errors": 20}, 100) == "degraded"
assert assess({"time": 10, "requests": 100, "errors": 0}, 100) == "unknown"
assert assess({"time": 90, "requests": 0, "errors": 0}, 100) == "no-traffic"
```

This deterministic evaluator uses pre-aggregated fixture windows, not a real collector or monitoring backend. Production must validate signal timestamps, denominator semantics, clock behavior, and expected traffic patterns.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not build dashboards with no operational question or equate green CPU with user success. Avoid alerting on every raw metric before defining ownership and objectives.

## 6. How do I know I understand it?

**Blank-page check:** Design a view that distinguishes healthy, degraded, no traffic, and missing data. Name an external probe that catches a failure internal metrics might miss.

| Constraint change | Predict the failure and response |
| --- | --- |
| Collector stops sending samples | Show unknown and monitor freshness; zero errors is not evidence of success. |
| Requests succeed but reports stop updating | Monitor business freshness/queue age, not HTTP status alone. |
