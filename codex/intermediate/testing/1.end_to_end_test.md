# End-to-End (E2E) Test

[Lesson index](../../README.md) · [Previous](../architecture/9.shared_platform_infrastructure.md) · [Next](2.contract_test.md)

## 1. What is it?

An end-to-end test exercises a complete supported user workflow through its public entry point, like buying an item at checkout instead of testing the till's buttons separately.

## 2. Why do we need it?

Unit tests can pass while routing, serialization, wiring, authorization, and persistence fail when assembled.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Define the actual system boundary and use real components inside it. Isolate fixtures, run through the public interface, and assert externally visible results. Real dependencies increase setup and diagnosis cost; replacing a provider narrows what the test proves.

Reference: [Primary documentation](https://docs.python.org/3/library/unittest.html).

### 3b. Boundaries and lifecycle

Arrange isolated environment → invoke public entry point → observe response and durable state through another public operation → clean up.

## 4. How to apply / implement / use it?

Save as `end_to_end_test_demo.py`; run `python3 end_to_end_test_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from pathlib import Path
import subprocess
import sys
import tempfile
application = '''
import json
import sqlite3
import sys
database = sqlite3.connect(sys.argv[1])
database.execute("CREATE TABLE IF NOT EXISTS tasks(title TEXT)")
if sys.argv[2] == "add":
    title = sys.argv[3].strip()
    if not title:
        print("title required", file=sys.stderr)
        raise SystemExit(2)
    with database:
        database.execute("INSERT INTO tasks VALUES (?)", (title,))
    print(json.dumps({"created": title}))
else:
    print(json.dumps(database.execute("SELECT title FROM tasks").fetchall()))
database.close()
'''
with tempfile.TemporaryDirectory() as directory:
    script = Path(directory) / "app.py"
    script.write_text(application)
    database = str(Path(directory) / "tasks.db")
    def invoke(*arguments):
        return subprocess.run([sys.executable, str(script), database, *arguments],
                              capture_output=True, text=True, timeout=5)
    assert invoke("add", "learn").returncode == 0
    assert invoke("list").stdout.strip() == '[["learn"]]'
    rejected = invoke("add", " ")
    assert rejected.returncode == 2 and "title required" in rejected.stderr
    assert invoke("list").stdout.strip() == '[["learn"]]'
```

This is a genuine end-to-end test of the supplied tiny CLI through subprocess and file-backed SQLite. It is not browser/API E2E, production database parity, login coverage, or external-provider coverage.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not replace every unit test with slow E2E flows. Avoid shared mutable accounts, fixed sleeps, order-dependent fixtures, and assertions on private implementation details.

## 6. How do I know I understand it?

**Blank-page check:** Name every real boundary the test crosses and every excluded dependency. Diagnose whether failure is in setup, transport, policy, or persistence.

| Constraint change | Predict the failure and response |
| --- | --- |
| Database becomes a remote service | The fixture and cleanup must cover credentials, readiness, isolation, and network failures. |
| UI selectors change | Stable public test hooks reduce brittleness; test business behavior, not layout trivia. |
