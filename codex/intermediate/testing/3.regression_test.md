# Regression Test

[Lesson index](../../README.md) · [Previous](2.contract_test.md) · [Next](4.smoke_test.md)

## 1. What is it?

A regression test preserves previously correct behavior against future changes, like keeping a repaired fault on a permanent inspection checklist.

## 2. Why do we need it?

A bug fixed once can return through refactoring, an alternate input path, or a dependency update when nobody records the failure condition.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Regression is a purpose, not a test scope: unit, integration, contract, or E2E tests can prevent recurrence. Capture the smallest reproducible failing input and assert the intended invariant rather than the original implementation.

Reference: [Primary documentation](https://docs.python.org/3/library/unittest.html).

### 3b. Boundaries and lifecycle

Reproduce failure → add a test that fails on the old behavior → fix the root cause → keep the test in the appropriate suite.

## 4. How to apply / implement / use it?

Save as `regression_test_demo.py`; run `python3 regression_test_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import unittest
def normalize_title(title):
    normalized = title.strip()
    if not normalized:
        raise ValueError("title required")
    return normalized
def old_normalize(title):
    if not title:
        raise ValueError("title required")
    return title.strip()
class TitleRegression(unittest.TestCase):
    def test_whitespace_only_is_rejected(self):
        with self.assertRaises(ValueError):
            normalize_title(" \t ")
    def test_useful_title_is_preserved(self):
        self.assertEqual(normalize_title(" learn "), "learn")
assert old_normalize(" \t ") == ""
unittest.main()
```

The script demonstrates the old counterexample and two passing tests of the fix. In a real repository, first run the new test against the old implementation to observe failure; do not permanently ship duplicate old implementations.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not add a broad slow workflow when a narrow deterministic test captures the bug. Avoid encoding accidental buggy behavior as an expected result.

## 6. How do I know I understand it?

**Blank-page check:** Explain why the old function accepts invalid state and identify the smallest invariant the regression protects.

| Constraint change | Predict the failure and response |
| --- | --- |
| Another entry point skips normalization | Move validation to the responsible shared boundary and add appropriate coverage. |
| Whitespace rules change intentionally | Update the specified contract and tests together, not merely silence the failing test. |
