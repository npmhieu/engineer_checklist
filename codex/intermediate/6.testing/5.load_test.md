# Load Test

[Lesson index](../../README.md) · [Previous](4.smoke_test.md) · [Next](6.basic_performance_test.md)

## 1. What is it?

A load test measures system behavior under a defined traffic workload, like testing a checkout lane with many shoppers rather than timing one purchase.

## 2. Why do we need it?

Single-request tests miss contention, queue growth, exhausted pools, tail latency, and error rates near capacity.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Specify request mix, dataset, arrival model, concurrency, duration, and success criteria. Closed-loop generators wait for responses and can hide overload as offered load falls. Measure offered/completed rate, percentiles, errors, and resource saturation; generator capacity can be the bottleneck.

Reference: [Primary documentation](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/).

### 3b. Boundaries and lifecycle

Establish baseline → increase controlled workload → observe latency/errors/queues → find limiting resource → stop safely → compare against service objectives.

## 4. How to apply / implement / use it?

Save as `load_test_demo.py`; run `python3 load_test_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from concurrent.futures import ThreadPoolExecutor
from time import perf_counter
import hashlib
def request(number):
    started = perf_counter()
    try:
        if number % 17 == 0:
            raise RuntimeError("injected service failure")
        hashlib.pbkdf2_hmac("sha256", b"input", b"fixture", 1000)
        ok = True
    except RuntimeError:
        ok = False
    return ok, perf_counter() - started
started = perf_counter()
with ThreadPoolExecutor(max_workers=4) as executor:
    outcomes = list(executor.map(request, range(40)))
elapsed = perf_counter() - started
durations = sorted(duration for ok, duration in outcomes)
errors = sum(not ok for ok, duration in outcomes)
assert errors == 3 and len(outcomes) == 40
assert elapsed > 0 and all(duration >= 0 for duration in durations)
print({"completed_per_second": 40 / elapsed,
       "p95_seconds": durations[int(0.95 * (len(durations) - 1))],
       "errors": errors})
```

This bounded closed-loop local workload validates measurement and error counting, not HTTP capacity or production throughput. It deliberately injects three failures and excludes executor queue wait from per-operation durations. Real end-to-end latency should include relevant admission/queue delays.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not load-test production without authorization, guardrails, and abort thresholds. Avoid extrapolating tiny local measurements or reporting only averages and successful requests.

## 6. How do I know I understand it?

**Blank-page check:** Design a workload with offered rate, realistic data, p95/p99 objectives, and stop conditions. Explain how the generator can under-report an overloaded service.

| Constraint change | Predict the failure and response |
| --- | --- |
| Service slows under closed-loop load | Clients send less traffic while waiting; apparent stability can hide unmet demand. |
| Only successful timings are reported | Fast failures and dropped requests can make the result falsely reassuring. |
