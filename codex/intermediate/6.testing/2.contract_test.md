# Contract Test

[Lesson index](../../README.md) · [Previous](1.end_to_end_test.md) · [Next](3.regression_test.md)

## 1. What is it?

A contract test checks that communicating components agree on observable request/response or message behavior, like checking both ends use the same plug shape and voltage.

## 2. Why do we need it?

Provider unit tests and consumer mocks can both pass while disagreeing on field names, nullability, error shape, or meaning.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

A contract captures required fields, types, status/error behavior, and relevant semantics. Provider verification checks actual output against those expectations. Consumer-driven systems add publication, versioning, and compatibility gates; a static schema alone is not proof every consumer works.

Reference: [Primary documentation](https://docs.pact.io/getting_started/how_pact_works).

### 3b. Boundaries and lifecycle

Consumer defines expectations → provider is exercised in controlled states → verification reports compatibility → deployment considers supported consumer versions.

## 4. How to apply / implement / use it?

Save as `contract_test_demo.py`; run `python3 contract_test_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def consumer_contract(response):
    if response["status"] != 200:
        raise AssertionError("expected success")
    body = response["body"]
    if not isinstance(body, dict):
        raise AssertionError("object required")
    if type(body.get("id")) is not int or not isinstance(body.get("title"), str):
        raise AssertionError("id and title contract changed")
def provider(task_id):
    return {"status": 200, "body": {"id": task_id, "title": "learn",
                                  "extra_optional": True}}
consumer_contract(provider(1))
try:
    consumer_contract({"status": 200, "body": {"id": "1", "name": "learn"}})
except AssertionError:
    pass
else:
    raise AssertionError("breaking provider accepted")
```

This minimal executable contract checks a supplied provider function, not HTTP encoding, authentication, a registry, or Pact verification. Tolerating extra fields is deliberate; money units and authorization semantics need additional assertions.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not confuse schema validation with business correctness or mock-only tests with provider verification. Over-specifying optional details can block harmless changes.

## 6. How do I know I understand it?

**Blank-page check:** Write consumer expectations for success, not-found, and invalid input. Explain which provider changes are additive versus breaking.

| Constraint change | Predict the failure and response |
| --- | --- |
| Provider adds an optional field | A tolerant consumer contract can still pass. |
| Provider changes integer cents to decimal dollars | Type-compatible output may still be semantically breaking; test units. |
