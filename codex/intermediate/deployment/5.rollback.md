# Rollback

[Lesson index](../../README.md) · [Previous](4.database_migration_strategy.md) · [Next](6.feature_flags.md)

## 1. What is it?

A rollback returns to a previously compatible release state, like switching traffic back to an inspected spare lane rather than erasing all trips already taken.

## 2. Why do we need it?

A bad release needs fast recovery, but replacing code alone cannot undo committed data, provider calls, or an incompatible schema contraction.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Record artifact/config/flag identities and compatibility requirements. Reversing traffic is often quick; undoing data may require a compensating business operation or verified restore. A backup restore has recovery-point loss and recovery-time costs and is not interchangeable with application rollback.

Reference: [Primary documentation](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).

### 3b. Boundaries and lifecycle

Detect failure → stop harmful changes → check old-version compatibility with current state → revert traffic/artifact/config where safe → reconcile effects → verify user outcomes.

## 4. How to apply / implement / use it?

Save as `rollback_demo.py`; run `python3 rollback_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
supported = {"v1": {"open"}, "v2": {"open", "archived"}}
records = [{"id": 1, "state": "open"}]
running = "v2"
def rollback(target):
    global running
    if target not in supported:
        raise ValueError("unknown release")
    if any(record["state"] not in supported[target] for record in records):
        raise RuntimeError("current data incompatible with target")
    running = target
rollback("v1")
assert running == "v1"
running = "v2"
records.append({"id": 2, "state": "archived"})
try:
    rollback("v1")
except RuntimeError:
    pass
else:
    raise AssertionError("unsafe rollback allowed")
assert running == "v2" and records[1]["state"] == "archived"
```

This release-compatibility model intentionally refuses a code rollback after incompatible data appears. It neither deploys artifacts nor repairs data. Recovery then needs an explicit safe forward fix, compatible build, compensation, or tested restore plan.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not promise rollback after irreversible external effects or incompatible data writes. Do not delete valid customer changes merely to make an old binary start.
