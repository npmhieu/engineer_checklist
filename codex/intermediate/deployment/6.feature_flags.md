# Feature Flags

[Lesson index](../../README.md) · [Previous](5.rollback.md) · [Next](../../advanced/distributed_systems/1.distributed_systems_fundamentals.md)

## 1. What is it?

A feature flag selects behavior at runtime without necessarily shipping new code, like a switch enabling a newly installed circuit.

## 2. Why do we need it?

Deploying and exposing a feature simultaneously makes targeted rollout, fast disabling, and controlled experiments harder.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Evaluate a named typed flag using approved context and a documented fallback. Stable hashing gives deterministic cohorts; configuration propagation can lag. A flag does not replace authorization or undo effects already committed. Record owner, expiry, and cleanup plan.

Reference: [Primary documentation](https://openfeature.dev/specification/sections/flag-evaluation/).

### 3b. Boundaries and lifecycle

Deploy compatible paths → evaluate flag per use case → expose to controlled cohort → monitor outcomes → widen or disable → remove obsolete branch and flag.

## 4. How to apply / implement / use it?

Save as `feature_flags_demo.py`; run `python3 feature_flags_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import hashlib
def enabled(tenant, percent, available=True):
    if not 0 <= percent <= 100:
        raise ValueError("invalid rollout percentage")
    if not available:
        return False
    key = ("new-report:" + tenant).encode()
    bucket = int.from_bytes(hashlib.sha256(key).digest()[:8], "big") % 100
    return bucket < percent
assert enabled("tenant-1", 100)
assert not enabled("tenant-1", 0)
assert enabled("tenant-1", 30) == enabled("tenant-1", 30)
assert not enabled("tenant-1", 100, available=False)
try:
    enabled("tenant-1", 101)
except ValueError:
    pass
else:
    raise AssertionError("invalid rollout accepted")
```

This deterministic local rollout example uses a deliberate disabled fallback and no provider/network. Real flags require typed evaluation, protected targeting context, config freshness, auditing, tests of both branches, and a fallback suitable for the feature. A disabled fallback is not universally the safest choice.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not use flags as access control, leave temporary flags forever, or let many flags create an untested combinatorial state space. A kill switch cannot undo irreversible work already started.

## 6. How do I know I understand it?

**Blank-page check:** Explain stable cohorting, provider failure fallback, owner/expiry, and removal. Show authorization runs independently of rollout choice.

| Constraint change | Predict the failure and response |
| --- | --- |
| Flag provider is unavailable | Use the documented last-known/default policy and expose stale config; avoid inconsistent safety assumptions. |
| Feature already created new data | Disabling the UI/code path does not reverse those records or restore old-version compatibility. |
