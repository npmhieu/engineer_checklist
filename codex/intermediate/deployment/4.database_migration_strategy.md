# Database Migration Strategy

[Lesson index](../../README.md) · [Previous](3.production_deployment.md) · [Next](5.rollback.md)

## 1. What is it?

A database migration strategy coordinates compatible schema/data changes across application versions, like replacing a bridge while keeping a safe lane open.

## 2. Why do we need it?

A migration can succeed technically yet break old replicas, queued workers, rollback readers, or restore procedures.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Plan expand, dual-compatible reads/writes, bounded backfill, convergence checks, switch, and delayed contract. Migration runners need serialized ownership and recorded progress; each DDL operation has engine-specific lock/rewrite behavior. A reverse migration is not proof of safe data recovery.

Reference: [Primary documentation](https://www.postgresql.org/docs/current/sql-altertable.html).

### 3b. Boundaries and lifecycle

Rehearse on representative data → expand → deploy compatible writers → backfill and verify → switch readers → drain old versions and queued contracts → contract only after the rollback window closes.

## 4. How to apply / implement / use it?

Save as `database_migration_strategy_demo.py`; run `python3 database_migration_strategy_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import sqlite3
database = sqlite3.connect(":memory:")
database.executescript("CREATE TABLE users(id PRIMARY KEY, name TEXT);"
                      "INSERT INTO users VALUES(1, 'Mai');")
database.execute("ALTER TABLE users ADD COLUMN display_name TEXT")
with database:
    database.execute("UPDATE users SET display_name=name")
active_versions = {"v1", "v2"}
def contract():
    if "v1" in active_versions:
        raise RuntimeError("old readers still active")
    database.execute("ALTER TABLE users DROP COLUMN name")
assert database.execute("SELECT name FROM users").fetchone()[0] == "Mai"
assert database.execute("SELECT display_name FROM users").fetchone()[0] == "Mai"
try:
    contract()
except RuntimeError:
    pass
else:
    raise AssertionError("incompatible contraction allowed")
active_versions.remove("v1")
contract()
try:
    database.execute("SELECT name FROM users")
except sqlite3.OperationalError:
    pass
else:
    raise AssertionError("old reader unexpectedly compatible")
database.close()
```

This real SQLite DDL demo requires SQLite 3.35+ for DROP COLUMN and uses a fixed dataset. It demonstrates a compatibility guard, not production online DDL, dual-write correctness, lock duration, backups, or old worker detection. Do not contract a real schema based only on this in-memory version set.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not run destructive migrations automatically on every replica startup or assume a DOWN script can reconstruct dropped data. Avoid one giant backfill or contracting before all rollback and queued-client needs are resolved.

## 6. How do I know I understand it?

**Blank-page check:** Build a version/schema read-write matrix and state the evidence required before dropping an old representation.

| Constraint change | Predict the failure and response |
| --- | --- |
| Old writer remains after backfill | New representation can diverge; maintain compatible writes and verify convergence before switching. |
| Rollback needs the removed column | Rollback is no longer compatible; retain expanded schema longer or plan a tested forward recovery. |
