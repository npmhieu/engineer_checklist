# Consumer

[Lesson index](../../README.md) · [Previous](5.message_queue.md) · [Next](7.worker.md)

## 1. What is it?

A consumer receives messages and applies a handler, like a clerk opening queued tickets and recording outcomes.

## 2. Why do we need it?

A broker can deliver data successfully while the application fails before persisting the intended effect.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

The consumer controls validation, effect transaction, and acknowledgement order. Acknowledge after durable success; acknowledge before it and a crash may lose work. Commit before acknowledgement and a crash may cause a duplicate, so the handler needs idempotency.

Reference: [Primary documentation](https://www.rabbitmq.com/docs/confirms).

### 3b. Boundaries and lifecycle

Receive → validate → apply or recognize previous completion → commit → acknowledge; classify permanent failures separately from retryable failures.

## 4. How to apply / implement / use it?

Save as `consumer_demo.py`; run `python3 consumer_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
effects, acknowledgements = [], []
def consume(message):
    if message["amount"] <= 0:
        raise ValueError("invalid amount")
    effects.append(message["id"])
    acknowledgements.append(message["id"])
consume({"id": "ok", "amount": 4})
try:
    consume({"id": "bad", "amount": -1})
except ValueError:
    pass
assert effects == ["ok"]
assert acknowledgements == ["ok"]
```

The lists expose the effect-before-ack boundary only. They are neither durable nor atomic. A real consumer uses a database transaction/inbox and a broker acknowledgement API; poison messages need bounded handling.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not acknowledge in an unconditional finally block or requeue permanent errors forever. Consumer concurrency must respect database and downstream capacity.

## 6. How do I know I understand it?

**Blank-page check:** Explain the crash just before commit and the crash just after commit. Which causes redelivery, and how do effects remain correct?

| Constraint change | Predict the failure and response |
| --- | --- |
| Connection closes before ack | Delivery can recur; stable deduplication identity is required. |
| Schema is unsupported | Quarantine with safe diagnostics; repeating immediately will not fix it. |
