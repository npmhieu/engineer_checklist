# Event-Driven Architecture

[Lesson index](../../README.md) · [Previous](9.event.md) · [Next](11.queue_vs_topic.md)

## 1. What is it?

Event-driven architecture connects components through published facts and reactions, like independent departments reading the same change bulletin.

## 2. Why do we need it?

Synchronous chains make upstream latency and availability depend on every downstream service, even for work that can finish later.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Producers, transport, and subscribers form distributed state machines. Eventual consistency means each projection can lag. Outbox/inbox patterns, ordering scopes, retries, and reconciliation replace assumptions supplied by one local call stack.

Reference: [Primary documentation](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/event-driven).

### 3b. Boundaries and lifecycle

Commit fact → publish → subscribers update their own states → observe lag and repair failures. Cross-service workflows need explicit compensation or orchestration, not imaginary global rollback.

## 4. How to apply / implement / use it?

Save as `event_driven_architecture_demo.py`; run `python3 event_driven_architecture_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from collections import deque
events = deque()
orders, report = {}, {}
def place(order_id):
    if order_id in orders:
        raise ValueError("duplicate order")
    orders[order_id] = "placed"
    events.append(("OrderPlaced", order_id))
place(7)
assert 7 not in report
kind, order_id = events.popleft()
assert kind == "OrderPlaced"
report[order_id] = "visible"
assert report[7] == "visible"
try:
    place(7)
except ValueError:
    pass
assert not events
```

This intentionally non-durable model illustrates projection lag only. The separate writes are unsafe across crashes; a production implementation needs transactional publication intent and idempotent subscribers.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not introduce distributed eventual consistency for a simple local invariant. Costs include harder debugging, schema ownership, replay privacy, failure recovery, and operational tooling.

## 6. How do I know I understand it?

**Blank-page check:** Draw authoritative state and two projections. Label what a user sees before every projection catches up.

| Constraint change | Predict the failure and response |
| --- | --- |
| Subscriber is offline | Original operation can succeed while projection freshness degrades. |
| Business requires immediate cross-service invariant | Redesign ownership or coordination; asynchronous facts alone cannot enforce it. |
