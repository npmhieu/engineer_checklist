# Duplicate Processing

[Lesson index](../../README.md) · [Previous](16.dead_letter_queue.md) · [Next](18.idempotent_consumer.md)

## 1. What is it?

Duplicate processing means the same logical input is handled more than once, like two clerks acting on photocopies of one request.

## 2. Why do we need it?

Retry after a lost acknowledgement is normal, but duplicate charges, emails, or stock decrements are not acceptable side effects.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Duplicates arise from producer retries, relay crashes, redelivery, and recovery. Stable business identity matters more than payload equality; distinct valid orders may have identical payloads. Delivery flags and in-memory sets are not durable proof of uniqueness.

Reference: [Primary documentation](https://www.rabbitmq.com/docs/confirms).

### 3b. Boundaries and lifecycle

Receive repeated identity → verify operation meaning and scope → recognize prior outcome or safely reapply → acknowledge without multiplying effects.

## 4. How to apply / implement / use it?

Save as `duplicate_processing_demo.py`; run `python3 duplicate_processing_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
messages = [{"id": "order-1", "amount": 5},
            {"id": "order-1", "amount": 5},
            {"id": "order-2", "amount": 5}]
naive_total = sum(message["amount"] for message in messages)
seen, safe_total = set(), 0
for message in messages:
    if message["id"] not in seen:
        seen.add(message["id"])
        safe_total += message["amount"]
assert naive_total == 15
assert safe_total == 10
assert len(seen) == 2
```

This deliberately contrasts unsafe repeated effects with process-local deduplication. The set is not restart-safe or atomic with durable effects; use the next lesson's transactional inbox for that boundary.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not deduplicate by amount, timestamp alone, or a random ID generated on each retry. Do not keep unbounded IDs forever without a defined replay/retention window.

## 6. How do I know I understand it?

**Blank-page check:** List three duplicate-producing crash windows. Explain why identical payloads can still represent two legitimate operations.

| Constraint change | Predict the failure and response |
| --- | --- |
| Deduplication retention ends before redelivery | An old input may execute again; align retention with replay guarantees. |
| Producer creates a new ID on every retry | Receiver cannot recognize one logical operation without another stable key. |
