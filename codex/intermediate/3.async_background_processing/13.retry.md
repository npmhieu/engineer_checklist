# Retry

[Lesson index](../../README.md) · [Previous](12.job_status_lifecycle.md) · [Next](14.exponential_backoff.md)

## 1. What is it?

A retry repeats an operation after a classified failure, like redialing a temporarily busy number without placing a second purchase.

## 2. Why do we need it?

Transient outages can fail otherwise valid work, but retrying every failure can amplify an outage or repeat an already committed charge.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Classify retryable failures, bound attempts and elapsed time, and preserve operation identity. An unknown outcome requires reconciliation or idempotency. Retries at multiple layers multiply total attempts, so choose one coordinating budget.

Reference: [Primary documentation](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/).

### 3b. Boundaries and lifecycle

Attempt → success, permanent rejection, known transient failure, or uncertain result → retry only when safe and within remaining budget.

## 4. How to apply / implement / use it?

Save as `retry_demo.py`; run `python3 retry_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
def retry(operation, attempts):
    if attempts < 1:
        raise ValueError("positive attempt count required")
    for attempt in range(attempts):
        try:
            return operation()
        except ConnectionError:
            if attempt + 1 == attempts:
                raise
calls = 0
def flaky():
    global calls
    calls += 1
    if calls == 1:
        raise ConnectionError("temporary")
    return "ok"
assert retry(flaky, 2) == "ok" and calls == 2
def invalid():
    raise ValueError("bad input")
try:
    retry(invalid, 3)
except ValueError:
    pass
else:
    raise AssertionError("permanent error swallowed")
```

This demonstrates classification and attempt limits only, with an operation whose fixture has no external effect. Add backoff, deadlines, cancellation, and stable downstream identities for real network work.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not retry authorization errors, malformed input, or non-idempotent unknown outcomes blindly. Immediate retry loops consume capacity during the outage they are meant to survive.

## 6. How do I know I understand it?

**Blank-page check:** Classify four failures and choose retry, reject, quarantine, or reconcile. Calculate the attempt multiplier across three retrying layers.

| Constraint change | Predict the failure and response |
| --- | --- |
| Three layers each allow three attempts | A request can cause up to 27 bottom-layer attempts. |
| Response is lost after a charge | Use a stable provider idempotency key or reconcile; loss of response is not rollback. |
