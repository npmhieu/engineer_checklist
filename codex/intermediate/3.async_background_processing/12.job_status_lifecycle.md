# Job Status / Lifecycle

[Lesson index](../../README.md) · [Previous](11.queue_vs_topic.md) · [Next](13.retry.md)

## 1. What is it?

A job lifecycle is an explicit state machine for work, like a parcel moving through accepted, in transit, delivered, or failed.

## 2. Why do we need it?

Free-form status strings allow impossible transitions and stale workers overwriting a newer result.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Persist permitted transitions and an ownership/version token. Claim queued work atomically; finish only while ownership still matches. Cancellation requested and cancellation completed are different facts. Terminal states require a deliberate retry/reset policy.

Reference: [Primary documentation](https://docs.aws.amazon.com/batch/latest/userguide/job_states.html).

### 3b. Boundaries and lifecycle

queued → running → succeeded or failed; retryable failures may schedule another attempt. Lease expiry permits recovery but does not stop the old worker.

## 4. How to apply / implement / use it?

Save as `job_status_lifecycle_demo.py`; run `python3 job_status_lifecycle_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
job = {"state": "queued", "version": 0}
allowed = {"queued": {"running"}, "running": {"succeeded", "failed"}}
def transition(expected_version, target):
    if expected_version != job["version"]:
        raise ValueError("stale owner")
    if target not in allowed.get(job["state"], set()):
        raise ValueError("invalid transition")
    job.update(state=target, version=expected_version + 1)
transition(0, "running")
try:
    transition(0, "succeeded")
except ValueError:
    pass
else:
    raise AssertionError("stale completion accepted")
transition(1, "succeeded")
assert job == {"state": "succeeded", "version": 2}
```

Single-process version checks illustrate the rule. Replace them with database compare-and-swap or equivalent atomic persistence; a Python dictionary does not prevent concurrent workers racing.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not overload one status with progress, cancellation intent, retry schedule, and error cause. Explicit fields cost more design but prevent misleading UI and unsafe recovery.
