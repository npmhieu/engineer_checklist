# Feature / Domain-oriented Architecture

[Lesson index](../../README.md) · [Previous](../4.application_features/5.batch_processing.md) · [Next](2.modular_monolith.md)

## 1. What is it?

Feature/domain-oriented architecture groups code around business capabilities, like keeping each department's tools together instead of sorting the whole company by tool type.

## 2. Why do we need it?

A small business change scattered across global controllers, services, and repositories forces unrelated teams to edit the same areas and hides ownership.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

A feature slice can contain transport, application, domain, and adapters while exposing a narrow interface. Grouping by feature does not remove dependency rules. Domain ownership is about business decisions and data, not merely URL names.

Reference: [Primary documentation](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/ddd-oriented-microservice).

### 3b. Boundaries and lifecycle

Entry point calls a feature use case → that feature applies policy and owns persistence → other features use explicit interfaces or integration events.

## 4. How to apply / implement / use it?

Save as `feature_domain_oriented_architecture_demo.py`; run `python3 feature_domain_oriented_architecture_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import ast
def allowed(source):
    for node in ast.walk(ast.parse(source)):
        if isinstance(node, ast.ImportFrom):
            module = node.module or ""
            if module.startswith("billing.") and module != "billing.api":
                return False
        if isinstance(node, ast.Import):
            for alias in node.names:
                if alias.name.startswith("billing.") and alias.name != "billing.api":
                    return False
    return True
assert allowed("from billing.api import invoice_total")
assert not allowed("from billing.repository import invoice_table")
assert not allowed("import billing.repository")
```

This executable lint rule illustrates a boundary for a hypothetical orders feature. It is not a complete import checker: relative imports, dynamic imports, aliases accessing internals, and runtime data access need additional enforcement.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not create one package per endpoint regardless of shared invariants. Avoid a universal shared folder that gradually owns every business concept.

## 6. How do I know I understand it?

**Blank-page check:** Place the files for a refund feature and explain which module owns refund policy, persistence, and public contracts.

| Constraint change | Predict the failure and response |
| --- | --- |
| Two features need one invariant atomically | Reconsider ownership or define explicit coordination; folders do not supply atomicity. |
| A caller imports another feature's repository | Depend on its public capability instead of bypassing policy. |
