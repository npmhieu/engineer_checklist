# Modular Monolith

[Lesson index](../../README.md) · [Previous](1.feature_domain_oriented_architecture.md) · [Next](3.ddd_basics.md)

## 1. What is it?

A modular monolith is one deployable application with enforced internal module boundaries, like several disciplined departments in one building.

## 2. Why do we need it?

A big unstructured application couples unrelated changes, while premature network services add deployment, latency, and consistency costs before boundaries are understood.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Calls remain in-process and may share local transaction facilities, but each module owns its data and public API. Enforce imports and database access deliberately. A single runtime still shares crash fate, memory pressure, and release cadence.

Reference: [Primary documentation](https://martinfowler.com/bliki/MonolithFirst.html).

### 3b. Boundaries and lifecycle

One composition root wires module APIs → modules collaborate through contracts → one artifact deploys; extraction remains a later design option, not a guaranteed free conversion.

## 4. How to apply / implement / use it?

Save as `modular_monolith_demo.py`; run `python3 modular_monolith_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
class Inventory:
    def __init__(self):
        self._available = 1
    def reserve(self):
        if self._available == 0:
            raise ValueError("sold out")
        self._available -= 1
        return "reservation-1"
def checkout(reserve):
    return {"state": "reserved", "reference": reserve()}
inventory = Inventory()
assert checkout(inventory.reserve)["state"] == "reserved"
try:
    checkout(inventory.reserve)
except ValueError:
    pass
else:
    raise AssertionError("inventory rule bypassed")
```

This one-process example uses an explicit inventory capability instead of accessing its storage. Python underscores are conventions, not security. Durable atomic checkout across modules needs an explicit unit of work; a failed payment after reserve needs rollback or compensation policy.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not mistake one repository for modularity. Independent scaling, isolation, or release requirements may justify services, but shared tables and hidden calls can also create a distributed monolith after extraction.

## 6. How do I know I understand it?

**Blank-page check:** Draw module ownership and allowed calls, then name one benefit retained and one limitation imposed by one deployment.

| Constraint change | Predict the failure and response |
| --- | --- |
| A module exhausts process memory | Other modules can fail too; internal APIs do not isolate resource failure. |
| Extract inventory to a service | An in-process call becomes a failure-prone remote boundary with different transaction semantics. |
