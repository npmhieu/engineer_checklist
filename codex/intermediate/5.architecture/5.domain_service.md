# Domain Service

[Lesson index](../../README.md) · [Previous](4.bounded_context.md) · [Next](6.application_service.md)

## 1. What is it?

A domain service expresses business policy that does not naturally belong to one entity or value object, like a pricing rule comparing several offers.

## 2. Why do we need it?

Putting cross-object policy in controllers duplicates rules, while forcing it into an unrelated entity obscures ownership.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

A domain service speaks domain language and takes domain inputs or narrow domain-facing abstractions. It does not become an all-purpose coordinator for HTTP, transactions, email, and storage. Pure calculations cost CPU proportional to their input; effects need explicit boundaries.

Reference: [Primary documentation](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/ddd-oriented-microservice).

### 3b. Boundaries and lifecycle

Application loads relevant facts → domain service decides → aggregate applies valid change → application persists and coordinates effects.

## 4. How to apply / implement / use it?

Save as `domain_service_demo.py`; run `python3 domain_service_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from dataclasses import dataclass
@dataclass(frozen=True)
class Offer:
    seller: str
    cents: int
def cheapest(offers):
    if not offers or any(offer.cents <= 0 for offer in offers):
        raise ValueError("valid offers required")
    return min(offers, key=lambda offer: (offer.cents, offer.seller))
assert cheapest([Offer("B", 900), Offer("A", 900)]).seller == "A"
try:
    cheapest([])
except ValueError:
    pass
else:
    raise AssertionError("empty decision accepted")
```

This pure domain policy makes a deterministic choice in O(number of offers) time without I/O. It assumes offers are authorized, comparable, and in one currency; freshness and reservation belong in the surrounding use case.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not extract every entity method into a service or turn DomainService into a database/network utility. Anemic entities and god-services both hide invariants.

## 6. How do I know I understand it?

| Constraint change | Predict the failure and response |
| --- | --- |
| Offers are in different currencies | Reject or use an explicit exchange policy; raw integer comparison is invalid. |
| Chosen offer expires before purchase | Revalidate/reserve under the correct concurrency boundary. |
