# Batch Processing

[Lesson index](../../README.md) · [Previous](4.reporting_architecture.md) · [Next](../architecture/1.feature_domain_oriented_architecture.md)

## 1. What is it?

Batch processing handles work in bounded groups, like moving boxes on a pallet instead of one trip per box.

## 2. Why do we need it?

One operation per row wastes round trips, but processing the entire dataset at once exhausts memory, creates long locks, and makes recovery expensive.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Batch size trades overhead against memory, transaction duration, log volume, and retry work. Use a stable ordered cursor or explicit snapshot; persist each chunk's checkpoint with effects. Parallel chunks need nonoverlapping ownership and duplicate-safe recovery.

Reference: [Primary documentation](https://www.postgresql.org/docs/current/sql-declare.html).

### 3b. Boundaries and lifecycle

Select bounded chunk after checkpoint → validate/transform → commit effects and progress → repeat → reconcile counts and failures.

## 4. How to apply / implement / use it?

Save as `batch_processing_demo.py`; run `python3 batch_processing_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import sqlite3
database = sqlite3.connect(":memory:")
database.executescript("CREATE TABLE source(id INTEGER PRIMARY KEY);"
                      "INSERT INTO source VALUES(1),(2),(3),(4),(5);"
                      "CREATE TABLE result(id INTEGER PRIMARY KEY);"
                      "CREATE TABLE progress(last_id INTEGER);"
                      "INSERT INTO progress VALUES(0);")
def chunk(fail=False):
    with database:
        last_id = database.execute("SELECT last_id FROM progress").fetchone()[0]
        rows = database.execute("SELECT id FROM source WHERE id>? ORDER BY id LIMIT 2",
                                (last_id,)).fetchall()
        for row in rows:
            database.execute("INSERT INTO result VALUES (?)", row)
        if fail:
            raise RuntimeError("before checkpoint")
        if rows:
            database.execute("UPDATE progress SET last_id=?", rows[-1])
        return len(rows)
assert chunk() == 2
try:
    chunk(fail=True)
except RuntimeError:
    pass
assert database.execute("SELECT COUNT(*) FROM result").fetchone()[0] == 2
while chunk():
    pass
assert database.execute("SELECT COUNT(*) FROM result").fetchone()[0] == 5
database.close()
```

This real transaction couples chunk effects and checkpoint for a fixed source. New rows with older IDs, edited/deleted rows, concurrent owners, and external effects require additional snapshot or reconciliation rules.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not choose huge batches merely to minimize statement count. Small latency-sensitive work may be better handled individually; avoid OFFSET scanning over a mutating dataset as a recovery cursor.
