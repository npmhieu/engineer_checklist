# Advanced API Design

[Lesson index](../../README.md) · Previous level: [Basic CI/CD](../../basic/development_operations/6.basic_ci_cd.md) · Next: [Backward Compatibility](2.backward_compatibility.md)

## 1. What is it?

Advanced API design makes an interface predictable under concurrency, retries, growth, and partial failure, like designing traffic rules for a busy junction rather than drawing roads alone.

The advance beyond CRUD is explicit behavior when conditions stop being ideal—not longer URLs or more endpoints.

## 2. Why do we need it?

Two editors can overwrite each other's changes; a bulk request can partially succeed; a slow operation can time out after committing. An endpoint returning the right JSON once does not answer what clients should do next.

Specific bug: client B submits a stale title after client A's edit and silently erases A's work. The contract needs a concurrency policy, not merely input validation.

## 3. Under the hood / mechanism / system flow

### 3a. Mechanisms behind the contract

Optimistic concurrency uses a version/precondition and an atomic conditional write. A successful write advances the version; a stale writer is rejected instead of overwriting newer state. This adds comparison/update work, not permission to split checking and writing into unrelated operations.

An ETag identifies a representation. A strong tag must change when the represented bytes/variant change; a row version is suitable only if the implementation preserves that invariant. A deployment/serializer/encoding change can matter too. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-13) defines conditional request evaluation and strong comparison for `If-Match`.

Other mechanisms include bounded cursor queries, durable asynchronous operation records, request deduplication, and explicit batch result models. They add storage, coordination, and lifecycle cost; none is automatically supplied by naming an API RESTful.

### 3b. Lifecycle and client behavior

```text
Authorize → validate ordinary request → evaluate preconditions
    → coordinated state change → commit → representation/status/next action
```

| Design decision | Client-visible contract |
| --- | --- |
| Require current representation | Read ETag, submit `If-Match`, refresh/reconcile after `412` |
| Require a precondition | Missing condition can produce `428`; do not cache that response |
| Long-running operation | Durable acceptance → `202` plus an authorized status resource, not a false completed result |
| Bulk changes | Define atomic all-or-nothing versus per-item outcomes and retry identities |
| Collection growth | Bound page size, filter complexity, response fields, and continuation semantics |

`428 Precondition Required` is defined in [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html#section-3). Preconditions do not replace authorization or idempotency: two separate valid intents can still conflict, and a lost successful response still needs a recovery policy.

## 4. How to apply / implement / use it?

Save as `advanced_api_design_demo.py`; run `python3 advanced_api_design_demo.py`. Standard-library SQLite only. Functions return HTTP-style tuples, not socket responses. `actor_id` comes from authentication.

The HTTP adapter is assumed to parse `If-Match` correctly into either `"*"` or a tuple of entity-tag strings. The example does not implement HTTP header grammar. Weak tags do not equal the strong tags issued here.

```python
import sqlite3

database = sqlite3.connect(":memory:")
database.executescript("""
    CREATE TABLE tasks (id INTEGER PRIMARY KEY, owner_id INTEGER, title TEXT, version INTEGER);
    INSERT INTO tasks VALUES (42, 7, 'Original', 1);
""")

def representation(row):
    task_id, title, version = row
    return {"ETag": f'"task-{task_id}-v{version}"', "Cache-Control": "no-store"}, {"id": task_id, "title": title, "version": version}

def read_task(actor_id, task_id):
    row = database.execute("SELECT id, title, version FROM tasks WHERE id = ? AND owner_id = ?", (task_id, actor_id)).fetchone()
    if row is None:
        return 404, {}, {"code": "TASK_NOT_FOUND"}
    headers, body = representation(row)
    return 200, headers, body

def rename_task(actor_id, task_id, title, if_match=None):
    with database:
        database.execute("BEGIN IMMEDIATE")
        row = database.execute("SELECT id, title, version FROM tasks WHERE id = ? AND owner_id = ?", (task_id, actor_id)).fetchone()
        if row is None:
            return 404, {}, {"code": "TASK_NOT_FOUND"}
        if not isinstance(title, str) or not 1 <= len(title.strip()) <= 120:
            return 422, {}, {"code": "INVALID_TITLE"}
        headers, body = representation(row)
        if if_match is None:
            return 428, {"Cache-Control": "no-store"}, {"code": "PRECONDITION_REQUIRED"}
        if if_match != "*" and (not isinstance(if_match, tuple) or not all(isinstance(tag, str) for tag in if_match)):
            return 400, {}, {"code": "INVALID_PARSED_PRECONDITION"}
        if if_match != "*" and headers["ETag"] not in if_match:
            return 412, {"Cache-Control": "no-store"}, {"code": "STALE_REPRESENTATION"}
        changed = database.execute("UPDATE tasks SET title = ?, version = version + 1 WHERE id = ? AND owner_id = ? AND version = ?", (title.strip(), task_id, actor_id, row[2]))
        if changed.rowcount != 1:
            raise RuntimeError("CONDITIONAL_WRITE_FAILED")
        new_headers, new_body = representation((task_id, title.strip(), row[2] + 1))
        return 200, new_headers, new_body

observed = read_task(7, 42)[1]["ETag"]
assert rename_task(7, 42, "First edit", (observed,))[0] == 200
assert rename_task(7, 42, "Stale edit", (observed,))[0] == 412
assert rename_task(7, 42, "No condition")[0] == 428
assert rename_task(8, 42, "Wrong owner")[0] == 404
assert read_task(7, 42)[2]["title"] == "First edit"
database.close()
print("happy: versioned edit; unhappy: stale/missing-condition/unauthorized writes blocked")
```

SQLite's explicit write transaction serializes this fixture; production databases need their own appropriate isolation/conditional-write design. Only this representation's controlled fields/version are modeled. `If-Match: *` means “exists,” not “unchanged since I read it,” so it does not provide the same lost-update protection as a specific tag.

For an async API, separately define operation ownership, pending/running/succeeded/failed states, cancellation semantics, result expiry, and recovery after duplicate submission. Do not add a queue without also defining these observable behaviors.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Simple bounded CRUD does not need a custom workflow engine or elaborate batch protocol.
- Do not add async processing when predictable short synchronous work suffices.
- Do not require clients to retry conflicts blindly; their intent may need merging or user confirmation.
- Do not use field selection, batching, or caching to bypass field/resource authorization.
- Do not expose arbitrary SQL-like filtering without complexity/capacity limits.

Every option becomes a compatibility, test, and operational commitment. Start with real client workflows and failure modes, not a collection of fashionable API features.

## 6. How do I know I understand it?

**Blank-page check:** design an edit and a long-running export, including permissions, preconditions, retry identity, status transitions, failure bodies, and client next steps.

| Constraint change | Predict the failure and response |
| --- | --- |
| Two editors share an old ETag | One conditional edit succeeds; the other must refresh/reconcile |
| Serializer changes bytes without advancing tags | Strong-validator promise breaks; update variant/version strategy |
| Export grows from milliseconds to minutes | Introduce durable acceptance/status lifecycle, not a larger timeout alone |
| Batch item 7 fails | Outcome depends on the documented atomic/per-item contract |

You understand advanced design when clients can predict state and safe next actions after failures, not just successful requests.
