# Rate Limiting

[Lesson index](../../README.md) · Previous: [Advanced Idempotency](4.advanced_idempotency.md) · Next: [Webhook](6.webhook.md)

## 1. What is it?

Rate limiting bounds how much work a caller or workload may start over time, like a ticket gate admitting a controlled flow instead of letting everyone enter at once.

It differs from a concurrency limit on in-flight work, a lifetime/billing quota, and queue backpressure. A service often needs several of these controls.

## 2. Why do we need it?

A fast loop, abusive client, or synchronized retries can exhaust database connections and starve other tenants. Authentication identifies the caller but does not make its demand safe.

Specific bottleneck: one tenant's export requests monopolize worker capacity while ordinary interactive traffic fails.

## 3. Under the hood / mechanism / system flow

### 3a. Algorithms, storage, and atomicity

| Algorithm | Mechanism | Important trade-off |
| --- | --- | --- |
| Fixed window | Count requests in a time bucket | Can permit a large burst across adjacent boundaries |
| Sliding log/window | Track/reconstruct recent arrivals | More memory/state or approximation |
| Token bucket | Refill tokens over time; consume per operation | Explicit burst capacity plus average admission rate |
| Leaky-bucket-style pacing | Drain/space work at a defined rate | Waiting/queue behavior must be bounded |

A token bucket computes `tokens = min(capacity, tokens + elapsed * refill_rate)` then atomically checks/deducts cost. Read-check-write in independent operations lets concurrent callers overspend. Local lock/state is cheap but only local; shared enforcement needs an atomic store operation/script or coordinated service. [Redis's rate-limiter example](https://redis.io/docs/latest/commands/incr/#pattern-rate-limiter) illustrates counter patterns and race considerations.

Keys need bounded lifecycle/cardinality and trustworthy scope. Raw spoofable IP headers or arbitrary user-supplied account IDs are not authenticated identities. NAT makes IP-only limits coarse. Separate cost classes for expensive endpoints; do not let clients choose their own cost.

### 3b. Admission and client reaction

```text
Identify trusted scope + operation class → atomic admission decision
    → admit business work / reject before expensive work
```

A quota rejection can return `429` with documented retry guidance; [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html#section-4) defines that status. `Retry-After` is guidance, not a reservation that guarantees admission later. Clients should back off safely rather than synchronize another burst. A limiter-store outage is a different condition from exhausted quota: choose an explicit fail-open/fail-closed/degraded policy and appropriate failure response.

## 4. How to apply / implement / use it?

Save as `rate_limiting_demo.py`; run `python3 rate_limiting_demo.py`. Standard library only. A lock protects one process's buckets; the fixture allows only known scope keys and injects a monotonic-style server clock.

```python
from concurrent.futures import ThreadPoolExecutor
import math
import threading

class TokenBucket:
    def __init__(self, capacity, refill_rate, scopes):
        if type(capacity) is not int or capacity <= 0 or not math.isfinite(refill_rate) or refill_rate <= 0:
            raise ValueError("INVALID_POLICY")
        self.capacity = capacity
        self.refill_rate = refill_rate
        self.scopes = frozenset(scopes)
        self.buckets = {}
        self.lock = threading.Lock()

    def admit(self, scope, now, cost=1):
        if scope not in self.scopes or type(cost) is not int or not 1 <= cost <= self.capacity or not math.isfinite(now):
            raise ValueError("INVALID_ADMISSION_INPUT")
        with self.lock:
            tokens, updated = self.buckets.get(scope, (float(self.capacity), now))
            if now < updated:
                raise ValueError("CLOCK_MOVED_BACKWARD")
            tokens = min(self.capacity, tokens + (now - updated) * self.refill_rate)
            allowed = tokens >= cost
            if allowed:
                tokens -= cost
            self.buckets[scope] = (tokens, now)
            retry_after = 0 if allowed else math.ceil((cost - tokens) / self.refill_rate)
            return {"allowed": allowed, "remaining": math.floor(tokens), "retry_after": retry_after}

scope = (7, "task-write")
limiter = TokenBucket(5, 2.0, {scope})
assert all(limiter.admit(scope, now=0)["allowed"] for attempt in range(5))
rejected = limiter.admit(scope, now=0)
assert not rejected["allowed"] and rejected["retry_after"] == 1
assert limiter.admit(scope, now=0.5)["allowed"]

parallel = TokenBucket(5, 2.0, {scope})
with ThreadPoolExecutor(max_workers=16) as executor:
    decisions = list(executor.map(lambda attempt: parallel.admit(scope, now=0), range(64)))
assert sum(decision["allowed"] for decision in decisions) == 5
try:
    limiter.admit((999, "task-write"), now=1)
except ValueError:
    pass
else:
    raise AssertionError("Unknown scope created unbounded state")
print("happy: burst/refill admission; unhappy: concurrent overspend and unknown scopes prevented")
```

An HTTP adapter maps a quota decision to `429` plus `Retry-After: <seconds>` without starting expensive work. The 5-token/2-per-second policy is arbitrary teaching data, not a recommended production quota. This fixture has no multi-replica consistency, persistence, eviction, fairness scheduler, concurrency semaphore, or outage policy implementation.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not use rate limits instead of authentication, authorization, request-size limits, or input-complexity bounds.
- Do not expect per-process buckets on ten replicas to enforce one global quota.
- Do not return `429` for every downstream/database failure just because work cannot proceed.
- Do not retain one bucket for every attacker-chosen key forever.
- Do not queue unlimited waiting requests to hide admission failures.

Strict shared limits add latency and store dependency; approximate/local limits may be sufficient for some protections. Define burst, fairness, scope, clock, and availability requirements before choosing enforcement.

## 6. How do I know I understand it?

**Blank-page check:** calculate a token bucket by hand for a burst, partial refill, rejection, and concurrent arrivals. Distinguish admission rate from in-flight capacity.

| Constraint change | Predict the failure and response |
| --- | --- |
| Replicas increase from one to ten | Local enforcement can multiply allowed aggregate demand |
| One operation costs 100 times more | Use workload-aware cost/concurrency controls rather than request count alone |
| Limiter backend fails | Follow a defined outage policy; it is not proof the caller exceeded quota |
| Clock moves backward | Do not mint tokens from an invalid elapsed-time calculation |

You understand limiting when you can prove the bound under the chosen concurrency/scope model and explain how legitimate clients recover.
