# Event

[Lesson index](../../README.md) · [Previous](8.cronjob.md) · [Next](10.event_driven_architecture.md)

## 1. What is it?

An event records a fact that already happened, like a receipt saying an order was placed rather than an instruction to place it.

## 2. Why do we need it?

Commands disguised as facts couple consumers to hidden requirements; mutable event meanings break replay and historical interpretation.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Use past-tense semantics, stable occurrence identity, aggregate identity, occurred-at time, and an evolution strategy. Processing time can differ greatly from occurrence time. Events need not expose private domain objects or every internal change.

Reference: [Primary documentation](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/event-driven).

### 3b. Boundaries and lifecycle

Domain action commits → immutable fact becomes publishable → independent consumers react; a consumer failure does not undo the original fact.

## 4. How to apply / implement / use it?

Save as `event_demo.py`; run `python3 event_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from dataclasses import dataclass, FrozenInstanceError
@dataclass(frozen=True)
class OrderPlaced:
    event_id: str
    order_id: int
    total_cents: int
    def __post_init__(self):
        if self.total_cents < 0:
            raise ValueError("negative total")
event = OrderPlaced("evt-1", 7, 1200)
assert event.order_id == 7
try:
    OrderPlaced("evt-2", 8, -1)
except ValueError:
    pass
else:
    raise AssertionError("invalid fact")
try:
    event.total_cents = 0
except FrozenInstanceError:
    pass
else:
    raise AssertionError("event mutated")
```

This immutable in-memory value models event semantics, not durable event storage, event sourcing, or publication. Frozen dataclasses do not recursively freeze nested mutable objects.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not emit events for every field assignment or use a fact as an implicit demand that exactly one specific service must comply. Not every event-driven design needs event sourcing.
