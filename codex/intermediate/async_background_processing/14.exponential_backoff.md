# Exponential Backoff

[Lesson index](../../README.md) · [Previous](13.retry.md) · [Next](15.timeout.md)

## 1. What is it?

Exponential backoff increases retry delays after repeated failures, like waiting longer between checks when a shop remains closed.

## 2. Why do we need it?

Thousands of clients retrying at the same fixed instant create synchronized load spikes that delay recovery.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Calculate a capped delay from base times a power of two, then jitter it. Full jitter samples between zero and that cap. Track total deadline as well as per-attempt count; schedule delayed work without occupying a scarce worker slot where possible.

Reference: [Primary documentation](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/).

### 3b. Boundaries and lifecycle

Transient failure → compute bounded jittered delay → check remaining deadline → schedule next eligible attempt → stop on success or exhausted budget.

## 4. How to apply / implement / use it?

Save as `exponential_backoff_demo.py`; run `python3 exponential_backoff_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import random
randomizer = random.Random(7)
def delay(attempt, base=1.0, cap=8.0):
    if not 0 <= attempt <= 20 or base <= 0 or cap <= 0:
        raise ValueError("invalid backoff")
    ceiling = min(cap, base * (2 ** attempt))
    return randomizer.uniform(0, ceiling)
delays = [delay(attempt) for attempt in range(6)]
assert all(0 <= value <= min(8, 2 ** attempt)
           for attempt, value in enumerate(delays))
remaining = 0.1
assert max(delays) > remaining
try:
    delay(-1)
except ValueError:
    pass
else:
    raise AssertionError("negative attempt accepted")
```

This computes deterministic test samples; it does not sleep or schedule durable retries. Jittered individual delays need not increase monotonically. Real retry logic must honor provider delay guidance and the total deadline.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not back off permanent errors or use unlimited exponential growth. Too-long delays violate freshness requirements; too-short caps keep overloading a recovering dependency.

## 6. How do I know I understand it?

**Blank-page check:** Derive capped full jitter from memory. Explain why the third sampled wait can be shorter than the second.

| Constraint change | Predict the failure and response |
| --- | --- |
| All clients use identical production random seeds | Their retries synchronize again; fixed seeds belong in tests. |
| Remaining deadline is less than next wait | Stop or reschedule under an explicit workflow budget. |
