# Queue vs Topic

[Lesson index](../../README.md) · [Previous](10.event_driven_architecture.md) · [Next](12.job_status_lifecycle.md)

## 1. What is it?

A work queue shares deliveries among competing receivers, while pub/sub gives independent subscriptions their own view, like one service desk versus separate department inboxes.

## 2. Why do we need it?

Putting billing and analytics on the same competing queue can send each event to only one department instead of both.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Subscription state determines independent consumption. In RabbitMQ a topic exchange routes by binding patterns to queues; in Kafka a topic is a partitioned retained log with consumer-group offsets. Neither term universally promises global order or one execution.

Reference: [Primary documentation](https://www.rabbitmq.com/docs/exchanges).

### 3b. Boundaries and lifecycle

Choose one work stream per competing group; create independent subscriptions for independent reactions. Ordering and replay depend on product and configuration.

## 4. How to apply / implement / use it?

Save as `queue_vs_topic_demo.py`; run `python3 queue_vs_topic_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from collections import deque
work = deque(["evt-1", "evt-2"])
first_worker = work.popleft()
second_worker = work.popleft()
assert {first_worker, second_worker} == {"evt-1", "evt-2"}
subscriptions = {name: deque() for name in ("billing", "analytics")}
for subscription in subscriptions.values():
    subscription.append("evt-3")
assert subscriptions["billing"].popleft() == "evt-3"
assert subscriptions["analytics"].popleft() == "evt-3"
assert not work
try:
    work.popleft()
except IndexError:
    pass
else:
    raise AssertionError("work duplicated")
```

These deques illustrate delivery topology, not a broker. The independent inbox copies are a model of subscriptions, not Kafka's physical storage implementation.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not add a subscriber to a competing consumer group when it needs every event independently. Fan-out multiplies downstream work, retention, and recovery obligations.
