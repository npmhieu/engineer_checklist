# Idempotent Consumer

[Lesson index](../../README.md) · [Previous](17.duplicate_processing.md) · [Next](../application_features/1.async_export_import.md)

## 1. What is it?

An idempotent consumer preserves the intended result under repeated delivery, like stamping a paid invoice so another copy cannot trigger another payment.

## 2. Why do we need it?

Commit-before-ack avoids lost work but permits redelivery after a crash, so handling twice must not apply the business mutation twice.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

A unique inbox key scoped by consumer, tenant, and event is inserted in the same database transaction as the local effect. Duplicate insertion skips the effect. External providers need their own stable idempotency key or another outbox; a local inbox cannot atomically cover arbitrary remote effects.

Reference: [Primary documentation](https://microservices.io/patterns/communication-style/idempotent-consumer.html).

### 3b. Boundaries and lifecycle

Receive → begin → claim inbox identity → change local state → commit → ack. Failure before commit rolls both back; failure after commit safely redelivers.

## 4. How to apply / implement / use it?

Save as `idempotent_consumer_demo.py`; run `python3 idempotent_consumer_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import sqlite3
database = sqlite3.connect(":memory:")
database.executescript("CREATE TABLE inbox(consumer TEXT, event TEXT,"
                      " PRIMARY KEY(consumer,event));"
                      "CREATE TABLE totals(value INTEGER);"
                      "INSERT INTO totals VALUES (0);")
def consume(event, crash=False):
    with database:
        inserted = database.execute(
            "INSERT OR IGNORE INTO inbox VALUES ('billing', ?)", (event,)).rowcount
        if not inserted:
            return "duplicate"
        database.execute("UPDATE totals SET value = value + 5")
        if crash:
            raise RuntimeError("before commit")
    return "applied"
try:
    consume("evt-1", crash=True)
except RuntimeError:
    pass
assert database.execute("SELECT value FROM totals").fetchone()[0] == 0
assert consume("evt-1") == "applied"
assert consume("evt-1") == "duplicate"
assert database.execute("SELECT value FROM totals").fetchone()[0] == 5
database.close()
```

This uses a real SQLite transaction for one local effect. The fixture has one tenant; include tenant in production keys when event IDs are not globally unique. It does not model broker acknowledgements, cross-database effects, concurrent PostgreSQL locks, or ID reuse with conflicting payloads.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not commit the inbox marker separately before the effect or deduplicate only in memory. Inbox growth, retention, schema evolution, and conflicting payload reuse need explicit policies.

## 6. How do I know I understand it?

**Blank-page check:** Draw crashes before commit and after commit/before ack. Prove why each path ends with one local increment.

| Constraint change | Predict the failure and response |
| --- | --- |
| Payment happens through a remote API | Forward a stable provider key or persist a separate recoverable intent; local atomicity does not extend to the provider. |
| A retry reuses ID with a different payload | Reject or investigate using stored semantic identity/fingerprint instead of silently treating it as equivalent. |
