# Producer

[Lesson index](../../README.md) · [Previous](3.message.md) · [Next](5.message_queue.md)

## 1. What is it?

A producer creates and publishes messages, like the sender who packages and hands over a parcel.

## 2. Why do we need it?

Committing a database change and publishing separately creates a gap: the order exists but no downstream notification ever arrives.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

A transactional outbox stores business state and publish intent in the same local transaction. A relay publishes later, records progress, and may resend after a crash. Publisher confirmation concerns broker acceptance under configured guarantees, not completion by consumers.

Reference: [Primary documentation](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).

### 3b. Boundaries and lifecycle

Application transaction → outbox row → relay publish → confirmation → mark sent. Consumers must still handle repeats and unauthorized or invalid content.

## 4. How to apply / implement / use it?

Save as `producer_demo.py`; run `python3 producer_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import sqlite3
database = sqlite3.connect(":memory:")
database.executescript("CREATE TABLE orders(id PRIMARY KEY);"
                      "CREATE TABLE outbox(id PRIMARY KEY, body TEXT);")
def place(order_id, crash=False):
    with database:
        database.execute("INSERT INTO orders VALUES (?)", (order_id,))
        if crash:
            raise RuntimeError("before outbox")
        database.execute("INSERT INTO outbox VALUES (?, ?)",
                         (order_id, "OrderPlaced"))
place(1)
try:
    place(2, crash=True)
except RuntimeError:
    pass
assert database.execute("SELECT id FROM orders").fetchall() == [(1,)]
assert database.execute("SELECT id FROM outbox").fetchall() == [(1,)]
database.close()
```

This is the real atomic local producer boundary. No relay or broker is supplied. Test relay crash-after-publish separately; marking sent before publishing risks loss.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not use an outbox to claim a distributed transaction or global exactly-once effects. It adds storage, cleanup, relay lag, and duplicate handling.

## 6. How do I know I understand it?

**Blank-page check:** Show both dual-write failure windows, then show which one the outbox removes and which duplicate window remains.

| Constraint change | Predict the failure and response |
| --- | --- |
| Relay crashes after publish | Outbox is resent; consumers deduplicate stable event identity. |
| Outbox is never drained | Business writes succeed but downstream state stalls; alert on oldest unsent age. |
