# Application Service

[Lesson index](../../README.md) · [Previous](5.domain_service.md) · [Next](7.infrastructure_layer.md)

## 1. What is it?

An application service coordinates a use case without owning its business rules, like a dispatcher arranging people and tools to fulfill one request.

## 2. Why do we need it?

Controllers, workers, and cron handlers otherwise duplicate authorization, transaction handling, persistence, and side-effect sequencing.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

It defines the use-case boundary: load facts, enforce access, call domain behavior, commit, and arrange reliable publication. It can depend on ports, not concrete transports. Domain policy remains testable independently of orchestration.

Reference: [Primary documentation](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/microservice-application-layer-implementation-web-api).

### 3b. Boundaries and lifecycle

Adapter parses input → application service checks caller and starts unit of work → domain decides → repository/outbox persist → adapter maps result.

## 4. How to apply / implement / use it?

Save as `application_service_demo.py`; run `python3 application_service_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import sqlite3
database = sqlite3.connect(":memory:")
database.executescript("CREATE TABLE tasks(id PRIMARY KEY, owner TEXT, done INTEGER);"
                      "INSERT INTO tasks VALUES (1, 'user-1', 0);")
def can_complete(done):
    return not done
def complete_task(actor, task_id):
    with database:
        row = database.execute("SELECT owner, done FROM tasks WHERE id=?",
                               (task_id,)).fetchone()
        if row is None:
            raise LookupError("missing task")
        if row[0] != actor:
            raise PermissionError("not owner")
        if can_complete(row[1]):
            database.execute("UPDATE tasks SET done=1 WHERE id=?", (task_id,))
try:
    complete_task("user-2", 1)
except PermissionError:
    pass
assert database.execute("SELECT done FROM tasks").fetchone()[0] == 0
complete_task("user-1", 1)
assert database.execute("SELECT done FROM tasks").fetchone()[0] == 1
database.close()
```

This real local transaction illustrates orchestration with a tiny domain predicate. SQL is inline to keep the example runnable; larger code should inject repository/unit-of-work ports. The single connection does not prove concurrent authorization or update safety.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not make the application service another HTTP controller or hide core rules in transport handlers. Avoid opening transactions across slow provider calls.

## 6. How do I know I understand it?

**Blank-page check:** List orchestration responsibilities separately from domain decisions. Invoke the same use case from API and worker without duplicating rules.

| Constraint change | Predict the failure and response |
| --- | --- |
| Task ownership changes concurrently | Check authorization and mutation under a suitable atomic/concurrency strategy. |
| A notification is required after commit | Persist outbox intent with the state change rather than sending inside a retryable transaction. |
