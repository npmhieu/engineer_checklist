# DDD Basics

[Lesson index](../../README.md) · [Previous](2.modular_monolith.md) · [Next](4.bounded_context.md)

## 1. What is it?

Domain-driven design models software around business language and rules, like learning a shop's real workflow before drawing its forms.

## 2. Why do we need it?

Database-shaped objects and scattered conditionals make rules inconsistent across API, worker, and import paths.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

An entity has identity over time; a value object is defined by its values; an aggregate is a consistency boundary with a root guarding invariants. Repositories load/save aggregates, while domain events describe meaningful facts. Strategic boundaries matter more than adopting every tactical class.

Reference: [Primary documentation](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-model-layer-validations).

### 3b. Boundaries and lifecycle

Clarify language with domain experts → identify invariants and ownership → invoke aggregate behavior → persist atomically → publish committed facts safely.

## 4. How to apply / implement / use it?

Save as `ddd_basics_demo.py`; run `python3 ddd_basics_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from dataclasses import dataclass, field
@dataclass(frozen=True)
class Quantity:
    value: int
    def __post_init__(self):
        if type(self.value) is not int or self.value <= 0:
            raise ValueError("positive integer quantity required")
@dataclass
class Order:
    order_id: str
    _lines: list = field(default_factory=list, repr=False)
    state: str = "draft"
    def add(self, quantity):
        if self.state != "draft":
            raise ValueError("order is closed")
        self._lines.append(quantity)
order = Order("order-1")
order.add(Quantity(2))
order.state = "submitted"
try:
    order.add(Quantity(1))
except ValueError:
    pass
else:
    raise AssertionError("closed order changed")
assert Quantity(2) == Quantity(2)
assert Order("order-2").order_id != order.order_id
```

This small domain model demonstrates value equality, identity, and guarded behavior. Its state is publicly mutable and not a hardened aggregate API; production should encapsulate transitions and enforce persistence/concurrency invariants too.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not force rich aggregates onto simple CRUD or create a giant aggregate spanning the business. Modeling effort pays off where language and rules are genuinely complex.

## 6. How do I know I understand it?

**Blank-page check:** Define entity, value object, aggregate, repository, and domain event using one business example, without referring to database tables.

| Constraint change | Predict the failure and response |
| --- | --- |
| Two aggregate instances are edited concurrently | In-memory guards alone fail; add version checks, locks, or constraints at persistence. |
| Business meaning differs by department | Use distinct bounded-context models instead of one universal object. |
