# Production Deployment

[Lesson index](../../README.md) · [Previous](2.ci_cd_pipeline.md) · [Next](4.database_migration_strategy.md)

## 1. What is it?

Production deployment introduces a version into real traffic under controlled checks, like opening one newly serviced checkout lane before switching the whole store.

## 2. Why do we need it?

Starting a process does not prove it is ready, compatible with the current database, or safe under customer traffic.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Rolling, canary, blue/green, and recreate strategies trade capacity, overlap, and rollback speed. Startup, readiness, and liveness answer different questions. Graceful shutdown stops intake before draining; mixed versions require compatible APIs, messages, schema, and configuration.

Reference: [Primary documentation](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).

### 3b. Boundaries and lifecycle

Prepare compatible dependencies → start candidate → readiness and smoke checks → route limited traffic → observe objectives → promote or halt → drain old instances.

## 4. How to apply / implement / use it?

Save as `production_deployment_demo.py`; run `python3 production_deployment_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
fleet = {"stable": {"version": "v1", "ready": True},
         "candidate": {"version": "v2", "ready": False}}
traffic = {"stable": 100, "candidate": 0}
def promote():
    if not fleet["candidate"]["ready"]:
        raise RuntimeError("candidate not ready")
    traffic.update(stable=90, candidate=10)
try:
    promote()
except RuntimeError:
    pass
assert traffic == {"stable": 100, "candidate": 0}
fleet["candidate"]["ready"] = True
promote()
assert sum(traffic.values()) == 100 and traffic["candidate"] == 10
canary_errors = 0.2
if canary_errors > 0.05:
    traffic.update(stable=100, candidate=0)
assert traffic["candidate"] == 0
```

This deterministic rollout policy model does not start instances, configure a load balancer, or validate Kubernetes manifests. Real traffic weighting, health checks, metrics windows, sample sizes, and rollback require platform-specific tooling.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not deploy all replicas simultaneously without an accepted outage plan. Avoid dependency-heavy liveness probes that restart otherwise healthy processes during a shared database incident.

## 6. How do I know I understand it?

| Constraint change | Predict the failure and response |
| --- | --- |
| Candidate passes readiness but corrupts business output | Add critical workflow checks and business signals; readiness is necessary, not sufficient. |
| Old and new versions overlap | Keep schema/contracts compatible across both until old instances and jobs drain. |
