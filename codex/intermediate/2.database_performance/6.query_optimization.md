# Query Optimization

[Lesson index](../../README.md) · [Previous](5.pessimistic_locking.md) · [Next](7.database_migration_in_production.md)

## 1. What is it?

Query optimization reduces measured work while preserving results, like choosing an efficient delivery route without dropping any addresses.

## 2. Why do we need it?

An index alone may not fix bad cardinality estimates, spills, fan-out joins, N+1 round trips, or excessive returned data.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Inspect estimated versus actual rows, scan/join choices, loops, buffers, sorting, and spills on representative distributions. PostgreSQL EXPLAIN ANALYZE executes the query; a mutating statement can cause real effects. Plan cost units are not milliseconds. Statistics, cache state, data skew, and prepared-plan behavior influence choices.

Reference: [Primary documentation](https://www.postgresql.org/docs/current/using-explain.html).

### 3b. Boundaries and lifecycle

Baseline workload → inspect plan and request-level cost → one change → verify semantics and repeat measurement. Preserve authorization predicates and result grain.

## 4. How to apply / implement / use it?

Save as `query_optimization_demo.py`; run `python3 query_optimization_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import sqlite3
database = sqlite3.connect(":memory:")
database.execute("CREATE TABLE tasks (id INTEGER PRIMARY KEY, owner INTEGER)")
with database:
    database.executemany("INSERT INTO tasks VALUES (?,?)", [(number, number % 10) for number in range(1000)])
query = "SELECT id FROM tasks WHERE owner=? ORDER BY id LIMIT 5"
before = database.execute(query, (7,)).fetchall()
scan = [row[3] for row in database.execute("EXPLAIN QUERY PLAN " + query, (7,))]
database.execute("CREATE INDEX task_owner ON tasks(owner,id)")
search = [row[3] for row in database.execute("EXPLAIN QUERY PLAN " + query, (7,))]
assert database.execute(query, (7,)).fetchall() == before
assert any("SCAN" in detail for detail in scan)
assert any("SEARCH" in detail for detail in search)
database.close()
```

Real SQLite plans demonstrate access-path change, not PostgreSQL planner parity or a latency benchmark. Production experiments need representative distributions and controlled warm/cold-cache conditions.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not optimize only toy data, use elapsed-time assertions as correctness tests, or create huge joins that multiply facts. Precomputation has freshness and repair costs.

## 6. How do I know I understand it?

**Blank-page check:** Explain estimated/actual cardinality, loops, rows examined/returned, round trips, and the evidence supporting an improvement.

| Constraint change | Predict the failure and response |
| --- | --- |
| A hot tenant owns most rows | Skew can invalidate assumptions about selectivity. |
| A join adds several matches per fact | Verify multiplicity before celebrating faster totals. |
