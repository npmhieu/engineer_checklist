# Caching

[Lesson index](../../README.md) · [Previous](7.database_migration_in_production.md) · [Next](9.redis.md)

## 1. What is it?

Caching retains reusable derived results to avoid repeating expensive work, like keeping a frequently consulted map beside the desk instead of fetching it every time.

## 2. Why do we need it?

Repeated reads waste database/network capacity, but stale or incorrectly scoped entries can expose data or mislead decisions.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Cache-aside reads cache, loads on miss, and fills with a bounded TTL. Keys include tenant, identity/policy where needed, query/version, and representation context. Invalidation races, negative caching, stampedes, and eviction all affect behavior. Hit latency is cheap; misses, serialization, and coordination still cost work.

Reference: [Primary documentation](https://redis.io/docs/latest/develop/use/client-side-caching/).

### 3b. Boundaries and lifecycle

Authorize → scoped cache lookup → authoritative load on miss → fill → coordinated invalidation/expiry after writes. Treat cache failure separately from a genuine missing record.

## 4. How to apply / implement / use it?

Save as `caching_demo.py`; run `python3 caching_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
source = {(7, 42): "old"}
cache = {}
def read(tenant, task, now):
    key = (tenant, task)
    entry = cache.get(key)
    if entry and now < entry[1]:
        return entry[0]
    value = source.get(key)
    cache[key] = (value, now + 5)
    return value
assert read(7,42,0) == "old"
source[(7,42)] = "new"
assert read(7,42,1) == "old"
assert read(7,42,5) == "new"
assert read(8,42,5) is None
cache.pop((7,42))
assert read(7,42,6) == "new"
```

This models TTL/scoping in one process; it does not implement atomic invalidation across replicas, stampede control, or production policy caching. The stale assertion intentionally reveals the freshness trade-off.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not use a lagging cache as the authority for spending inventory/balance. Avoid caching secrets or permission-sensitive data without explicit scope and revocation policy.

## 6. How do I know I understand it?

**Blank-page check:** Draw read/write/invalidation races, define acceptable staleness, and calculate the miss load when many keys expire together.

| Constraint change | Predict the failure and response |
| --- | --- |
| TTL expires for every hot key together | Jitter/refresh coordination can avoid a stampede. |
| Access is revoked | Invalidate or recheck policy; TTL alone defines a lag window. |
