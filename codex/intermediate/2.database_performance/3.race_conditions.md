# Race Conditions

[Lesson index](../../README.md) · [Previous](2.concurrency.md) · [Next](4.optimistic_locking.md)

## 1. What is it?

A race condition makes correctness depend on uncontrolled timing, like two people both taking the last numbered ticket after separately checking availability.

## 2. Why do we need it?

A valid check followed by a later write can become invalid between steps. Tests that happen to run sequentially miss lost updates and overselling.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Read-modify-write consists of several events even when source code looks compact. Visibility and interleavings matter; a language runtime lock does not make arbitrary workflows atomic. Use atomic database predicates, uniqueness, locks, or versions at the shared authority.

Reference: [Primary documentation](https://docs.python.org/3/library/threading.html).

### 3b. Boundaries and lifecycle

Identify invariant → force an unsafe interleaving → protect the check-and-effect boundary → test the resulting committed state.

## 4. How to apply / implement / use it?

Save as `race_conditions_demo.py`; run `python3 race_conditions_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from concurrent.futures import ThreadPoolExecutor
import threading
state = {"count": 0}
barrier = threading.Barrier(2)
def unsafe():
    observed = state["count"]
    barrier.wait(timeout=2)
    state["count"] = observed + 1
with ThreadPoolExecutor(max_workers=2) as executor:
    list(executor.map(lambda number: unsafe(), range(2)))
assert state["count"] == 1
state["count"] = 0
lock = threading.Lock()
def safe():
    with lock:
        state["count"] += 1
with ThreadPoolExecutor(max_workers=2) as executor:
    list(executor.map(lambda number: safe(), range(2)))
assert state["count"] == 2
```

The barrier deterministically exposes a lost update without relying on sleeps. The lock only protects this process; separate API replicas need shared coordination.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not fix races by sleeping or hoping requests rarely overlap. Do not hold a local lock and assume it protects another process's writes.

## 6. How do I know I understand it?

**Blank-page check:** Write the exact read/check/write schedule that violates one invariant, then identify the smallest authoritative atomic boundary.

| Constraint change | Predict the failure and response |
| --- | --- |
| Workers become separate processes | A thread lock no longer protects shared database state. |
| Check uses cached data | Validate the final authoritative write, not just the earlier cache read. |
