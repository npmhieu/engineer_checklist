# Notification Architecture

[Lesson index](../../README.md) · [Previous](1.async_export_import.md) · [Next](3.audit_activity_history.md)

## 1. What is it?

Notification architecture turns business intent into controlled per-channel delivery, like a dispatch desk choosing postal mail, email, or text from one request.

## 2. Why do we need it?

Sending email inline delays transactions; retries duplicate messages; shared templates can leak tenant data or ignore user preferences.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Separate notification intent, recipient resolution, preferences, template version, delivery attempt, and provider response. Store business intent transactionally; apply channel-specific rate limits and permanent/transient classification. Provider acceptance is not human receipt.

Reference: [Primary documentation](https://learn.microsoft.com/en-us/azure/architecture/patterns/queue-based-load-leveling).

### 3b. Boundaries and lifecycle

Business event → intent/outbox → policy and template → channel job → provider attempt → callback or reconciliation → delivery history.

## 4. How to apply / implement / use it?

Save as `notification_architecture_demo.py`; run `python3 notification_architecture_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
intents, attempts = {}, []
def request(notification_id, recipient, enabled):
    if not enabled:
        return "suppressed"
    if notification_id in intents:
        return "duplicate"
    intents[notification_id] = {"recipient": recipient, "state": "pending"}
    return "queued"
def deliver(notification_id, provider):
    intent = intents[notification_id]
    result = provider(intent["recipient"], notification_id)
    attempts.append((notification_id, result))
    intent["state"] = "accepted"
assert request("notice-1", "user-1", True) == "queued"
assert request("notice-1", "user-1", True) == "duplicate"
assert request("notice-2", "user-2", False) == "suppressed"
def unavailable(recipient, key):
    raise ConnectionError("provider unavailable")
try:
    deliver("notice-1", unavailable)
except ConnectionError:
    pass
assert intents["notice-1"]["state"] == "pending"
deliver("notice-1", lambda recipient, key: "provider-accepted")
assert intents["notice-1"]["state"] == "accepted"
```

This offline fixture neither sends messages nor guarantees durable delivery. It passes a stable key but does not prove a provider supports idempotency; provider timeouts can leave unknown outcomes. Production needs protected recipient data, consent policy, callback verification, and durable attempts.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not treat delivery as one boolean or use unbounded retries for bounces and revoked consent. Security-critical alerts may have different policy from marketing preferences.

## 6. How do I know I understand it?

**Blank-page check:** Trace one event to two channels and identify independent attempt identities, suppression decisions, and unknown provider outcomes.

| Constraint change | Predict the failure and response |
| --- | --- |
| Provider accepts but response disappears | Reconcile or use provider idempotency; blind resend can duplicate notifications. |
| Template changes before retry | Record version/inputs deliberately so retry behavior is auditable. |
