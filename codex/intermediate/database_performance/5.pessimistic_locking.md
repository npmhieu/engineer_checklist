# Pessimistic Locking

[Lesson index](../../README.md) · [Previous](4.optimistic_locking.md) · [Next](6.query_optimization.md)

## 1. What is it?

Pessimistic locking reserves access before a critical decision, like taking the only storeroom key before counting and removing stock.

## 2. Why do we need it?

Competing operations may need a consistent read and coordinated multi-step write. Optimistic retries can become expensive under heavy conflict.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

In PostgreSQL SELECT FOR UPDATE locks selected rows until transaction end; competing lock modes may wait or fail. Acquire multiple locks consistently, set bounded waits, and recover deadlock victims. Locks add queueing and consume connections. SKIP LOCKED suits some work queues, not a general consistent reporting query.

Reference: [Primary documentation](https://www.postgresql.org/docs/current/explicit-locking.html).

### 3b. Boundaries and lifecycle

Begin → acquire appropriate lock → check invariant → write → commit/rollback releases lock. Never wait for user input or slow external calls while holding it.

## 4. How to apply / implement / use it?

Save as `pessimistic_locking_demo.py`; run `python3 pessimistic_locking_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from pathlib import Path
import sqlite3
import tempfile
with tempfile.TemporaryDirectory() as directory:
    path = Path(directory) / "locks.sqlite"
    first = sqlite3.connect(path, timeout=0)
    second = sqlite3.connect(path, timeout=0)
    first.execute("CREATE TABLE stock (amount INTEGER)")
    first.execute("BEGIN IMMEDIATE")
    try:
        second.execute("BEGIN IMMEDIATE")
    except sqlite3.OperationalError as error:
        assert "locked" in str(error).lower()
    else:
        raise AssertionError("Competing writer was not blocked")
    first.rollback()
    second.execute("BEGIN IMMEDIATE")
    second.rollback()
    first.close()
    second.close()
```

This is SQLite's database-writer lock, NOT a PostgreSQL row-lock simulation. The PostgreSQL application form is BEGIN; SELECT ... FOR UPDATE; checked UPDATE; COMMIT. Test that form against PostgreSQL with independent connections.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not lock entire broad result sets casually or assume locking existing rows protects every missing-row/range invariant. Lock order and isolation must fit the rule.

## 6. How do I know I understand it?

**Blank-page check:** Draw lock ownership, waiting, timeout/deadlock handling, and release on rollback. Distinguish row and database locks.

| Constraint change | Predict the failure and response |
| --- | --- |
| Two operations lock rows in reverse order | A deadlock can occur; consistent order and retry policy matter. |
| Provider call takes seconds | Move it outside the lock or redesign a reservation workflow. |
