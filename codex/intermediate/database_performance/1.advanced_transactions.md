# Advanced Transactions

[Lesson index](../../README.md) · [Previous](../api_application/8.service_to_service_communication.md) · [Next](2.concurrency.md)

## 1. What is it?

Advanced transactions coordinate invariants under competing operations and failures, like several cashiers sharing one correctly balanced till.

## 2. Why do we need it?

Atomic statements alone do not prevent write skew, stale decisions, or incorrect retries. A transfer can be internally atomic while a cross-row rule still fails.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

MVCC snapshots, predicate/row locks, constraints, and isolation determine allowed histories. Serializable execution may abort a transaction; retry its complete decision with fresh reads, bounded attempts, and no repeated external effects. Savepoints support partial rollback, not independent durable subtransactions. Long snapshots retain versions; locks and retries add contention.

Reference: [Primary documentation](https://www.postgresql.org/docs/current/transaction-iso.html).

### 3b. Boundaries and lifecycle

Begin → read/check/write under chosen isolation → commit or classify failure. Commit-time communication failure can leave an uncertain outcome; recovery differs from a known serialization abort.

## 4. How to apply / implement / use it?

Save as `advanced_transactions_demo.py`; run `python3 advanced_transactions_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import sqlite3
database = sqlite3.connect(":memory:")
database.execute("CREATE TABLE items (id INTEGER PRIMARY KEY, name TEXT UNIQUE)")
with database:
    database.execute("INSERT INTO items VALUES (1, 'kept')")
    database.execute("SAVEPOINT optional")
    try:
        database.execute("INSERT INTO items VALUES (2, 'kept')")
    except sqlite3.IntegrityError:
        database.execute("ROLLBACK TO optional")
    database.execute("RELEASE optional")
    database.execute("INSERT INTO items VALUES (3, 'also kept')")
assert database.execute("SELECT id FROM items ORDER BY id").fetchall() == [(1,), (3,)]
database.close()
```

This demonstrates real SQLite savepoints, not PostgreSQL serializable concurrency. A savepoint does not commit independently; failure of the outer transaction would undo both surviving inserts.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not retry every database exception or put provider calls inside retryable transactions. Choose the weakest isolation that actually preserves the invariant, not the weakest by habit.

## 6. How do I know I understand it?

**Blank-page check:** Draw two competing histories and identify which constraint, lock, or abort prevents invalid committed state. Explain savepoint versus commit.

| Constraint change | Predict the failure and response |
| --- | --- |
| A serialization failure occurs | Restart the whole decision from fresh state, with bounded retries. |
| Commit response disappears | Reconcile using durable operation identity; do not assume rollback. |
