# Optimistic Locking

[Lesson index](../../README.md) · [Previous](3.race_conditions.md) · [Next](5.pessimistic_locking.md)

## 1. What is it?

Optimistic locking rejects updates based on an outdated version, like editing a shared document only if nobody changed its revision since you opened it.

## 2. Why do we need it?

Last-write-wins silently erases another editor's work. Holding a lock while a human edits is impractical.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Read version N; update with WHERE identity/version=N and advance the version atomically. Zero affected rows means the assumption no longer held; distinguish deletion/authorization as appropriate. Conflicts cost rejected work and reconciliation, not a waiting lock held during user think-time.

Reference: [Primary documentation](https://www.postgresql.org/docs/current/sql-update.html).

### 3b. Boundaries and lifecycle

Read → edit outside transaction → authorize and conditional update → success or conflict. Every relevant mutation must advance the version.

## 4. How to apply / implement / use it?

Save as `optimistic_locking_demo.py`; run `python3 optimistic_locking_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
import sqlite3
database = sqlite3.connect(":memory:")
database.executescript("CREATE TABLE tasks (id INTEGER PRIMARY KEY, title TEXT, version INTEGER); INSERT INTO tasks VALUES (1, 'old', 1);")
def rename(title, expected):
    with database:
        changed = database.execute("UPDATE tasks SET title=?, version=version+1 WHERE id=1 AND version=?", (title, expected))
        if changed.rowcount != 1:
            raise ValueError("STALE_VERSION")
rename("first", 1)
try:
    rename("second", 1)
except ValueError:
    pass
else:
    raise AssertionError("Lost update accepted")
assert database.execute("SELECT title,version FROM tasks").fetchone() == ("first", 2)
database.close()
```

This uses a real conditional SQLite write but not simultaneous connections. HTTP If-Match preconditions can expose this policy; domain version conflicts and HTTP header semantics remain distinct.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not blindly retry a user edit over new data. High contention may make retries wasteful; consider serialization or a different operation shape.
