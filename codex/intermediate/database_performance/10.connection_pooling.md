# Connection Pooling

[Lesson index](../../README.md) · [Previous](9.redis.md) · [Next](../async_background_processing/1.background_task.md)

## 1. What is it?

A connection pool lends a bounded set of reusable connections, like a small taxi fleet instead of buying a car for every trip.

## 2. Why do we need it?

Repeated connection/TLS/auth setup costs latency, while unlimited connections exhaust database resources. Slow borrowers can starve everyone else.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Acquisition waits for an idle connection or capacity; checkout has a deadline and returns the resource after commit/rollback/reset. Leaked transactions and session state contaminate later borrowers. Total demand multiplies by replicas/processes; more connections can increase contention instead of throughput.

Reference: [Primary documentation](https://www.psycopg.org/psycopg3/docs/advanced/pool.html).

### 3b. Boundaries and lifecycle

Acquire with budget → use scoped transaction → cleanup/reset in finally/context → return. Distinguish acquisition timeout from query timeout and broken-connection replacement.

## 4. How to apply / implement / use it?

Save as `connection_pooling_demo.py`; run `python3 connection_pooling_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from contextlib import contextmanager
from queue import Empty, Queue
pool = Queue(maxsize=1)
pool.put({"connection": 1})
@contextmanager
def borrow():
    try:
        connection = pool.get(timeout=0.01)
    except Empty:
        raise TimeoutError("POOL_EXHAUSTED") from None
    try:
        yield connection
    finally:
        pool.put(connection)
with borrow() as connection:
    try:
        with borrow():
            raise AssertionError("Capacity bypassed")
    except TimeoutError:
        pass
with borrow() as connection:
    assert connection["connection"] == 1
```

This resource-pool fixture is not a database driver pool. Real pools must reset transactions/session settings, validate/replace dead connections, and use correct thread/process ownership.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not share one checked-out connection concurrently or create a pool per request. Avoid queues so long requests expire before useful work starts.

## 6. How do I know I understand it?

**Blank-page check:** Calculate fleet-wide connection demand and trace acquisition, transaction cleanup, release, timeout, and replacement.

| Constraint change | Predict the failure and response |
| --- | --- |
| Replicas double | The database may receive twice the configured per-replica maximum. |
| A query leaves a transaction open | Rollback/reset before reuse or contaminate the next request. |
