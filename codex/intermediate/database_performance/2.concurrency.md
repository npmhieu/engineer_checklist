# Concurrency

[Lesson index](../../README.md) · [Previous](1.advanced_transactions.md) · [Next](3.race_conditions.md)

## 1. What is it?

Concurrency lets operations overlap in progress, like several cooks sharing a kitchen even when they are not all using the stove simultaneously.

## 2. Why do we need it?

Serializing every request wastes waiting time; uncoordinated overlap corrupts shared state. More concurrent requests can also overwhelm a finite database pool.

## 3. Under the hood / mechanism / system flow

### 3a. Implementation, state, and cost

Threads/tasks/processes have different scheduling and memory boundaries. Concurrency is not necessarily parallel CPU execution; async I/O does not make blocking code nonblocking. Locks/semaphores bound critical sections or admission. Queueing, context switches, memory, and contention can dominate throughput.

Reference: [Primary documentation](https://docs.python.org/3/library/threading.html).

### 3b. Boundaries and lifecycle

Admit bounded work → execute/wait → release resources on every outcome. A local lock coordinates only participants in that process.

## 4. How to apply / implement / use it?

Save as `concurrency_demo.py`; run `python3 concurrency_demo.py`. Standard library only. Assertions cover successful behavior and a rejected, failed, or unsafe case.

```python
from concurrent.futures import ThreadPoolExecutor
import threading
capacity = threading.BoundedSemaphore(2)
inside = 0
peak = 0
guard = threading.Lock()
def work(number):
    global inside, peak
    with capacity:
        with guard:
            inside += 1
            peak = max(peak, inside)
        try:
            if number == 3:
                raise ValueError("EXPECTED_FAILURE")
            return number * 2
        finally:
            with guard:
                inside -= 1
with ThreadPoolExecutor(max_workers=8) as executor:
    futures = [executor.submit(work, number) for number in range(8)]
    outcomes = []
    for future in futures:
        try:
            outcomes.append(future.result(timeout=2))
        except ValueError:
            outcomes.append("failed")
assert outcomes.count("failed") == 1 and inside == 0 and peak <= 2
```

The bound is proven for this thread fixture; it is not a distributed quota or a CPU scalability benchmark. Scheduling may keep the measured peak below two.

## 5. When should I NOT use this? Trade-offs and anti-patterns

Do not increase concurrency without measuring downstream capacity. Avoid blocking an event loop or holding locks across slow network work.

## 6. How do I know I understand it?

**Blank-page check:** Separate tasks in flight, threads running, CPU parallelism, and downstream connection demand. Account for cleanup after errors.

| Constraint change | Predict the failure and response |
| --- | --- |
| Replicas multiply | Per-process admission multiplies aggregate demand. |
| Dependency slows | Bound waiting queues/deadlines rather than creating unlimited tasks. |
