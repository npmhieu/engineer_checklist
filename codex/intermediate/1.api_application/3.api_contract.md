# API Contract

[Lesson index](../../README.md) · Previous: [Backward Compatibility](2.backward_compatibility.md) · Next: [Advanced Idempotency](4.advanced_idempotency.md)

## 1. What is it?

An API contract defines what callers may send and what the service promises in return, like an order form plus delivery terms rather than a picture of the finished parcel.

It covers protocol, shapes, permissions, semantics, errors, limits, and lifecycle expectations. OpenAPI describes many HTTP interface details; it does not automatically specify every business invariant or reliability promise.

## 2. Why do we need it?

Frontend and backend teams can each implement a plausible but incompatible interpretation: one sends `name`, another requires `title`; one expects creation, another only queues work.

Specific pain: tests exercise one hard-coded success body while the deployed provider omits required fields or changes an error format. A versioned contract can drive validation, documentation, client generation, and executable checks.

## 3. Under the hood / mechanism / system flow

### 3a. Description, schema validation, and behavior tests

[OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html) uses a JSON Schema-based schema dialect. JSON Schema can check object shape, required fields, types, bounds, and configured formats. Format checking and schema-dialect support depend on validator configuration; listing a property does not necessarily require it or reject other properties.

Validation walks data and can add CPU/allocation work, especially with complex alternatives, references, or regexes. Bound input before parsing/validation. Generated SDKs/mocks are derived artifacts and can drift when not tied to the same source version.

Schema validation cannot prove account authorization, exact side effects, isolation, freshness, or a safe retry policy. Provider tests verify implementation against the description; consumer tests capture real usage assumptions. Both are useful and neither replaces integration/security tests.

### 3b. Contract lifecycle

```text
Review use cases/failures → version one description → validate/check compatibility
    → generate/test provider + clients → release → detect drift
```

Write semantics beside the schema: normalization, null/omitted behavior, status/headers, authentication scheme, resource/field permissions, pagination, retry keys, quotas, and async transitions. A valid response schema is only one part of a valid response.

## 4. How to apply / implement / use it?

Save the Python block as `api_contract_demo.py`. In a scratch directory:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install 'jsonschema>=4.18,<5'
.venv/bin/python api_contract_demo.py
```

The example was checked with jsonschema 4.26.0. It uses [Draft202012Validator](https://python-jsonschema.readthedocs.io/en/stable/validate/) for the simple schemas in one in-memory OpenAPI description. It is not a full OpenAPI-document/HTTP protocol validator or a web server. Production dependencies need reviewed locking/updates.

```python
from jsonschema import Draft202012Validator, ValidationError

spec = {
    "openapi": "3.1.1",
    "info": {"title": "Learning Tasks", "version": "1.0.0"},
    "paths": {"/tasks": {"post": {
        "requestBody": {"required": True, "content": {"application/json": {"schema": {"$ref": "#/components/schemas/CreateTask"}}}},
        "responses": {
            "201": {"description": "Created", "headers": {"Location": {"schema": {"type": "string"}}}, "content": {"application/json": {"schema": {"$ref": "#/components/schemas/Task"}}}},
            "422": {"description": "Input validation failure"},
        },
    }}},
    "components": {"schemas": {
        "CreateTask": {"type": "object", "required": ["title"], "additionalProperties": False,
            "properties": {"title": {"type": "string", "minLength": 1, "maxLength": 120, "pattern": r"\S"}}},
        "Task": {"type": "object", "required": ["id", "title", "completed"],
            "properties": {"id": {"type": "integer", "minimum": 1}, "title": {"type": "string", "minLength": 1}, "completed": {"type": "boolean"}}},
    }},
}
schemas = spec["components"]["schemas"]
for schema in schemas.values():
    Draft202012Validator.check_schema(schema)
request_validator = Draft202012Validator(schemas["CreateTask"])
response_validator = Draft202012Validator(schemas["Task"])

def provider(body):
    if not request_validator.is_valid(body):
        return 422, {}, {"code": "VALIDATION_FAILED"}
    return 201, {"Location": "/tasks/1"}, {"id": 1, "title": body["title"].strip(), "completed": False}

def check_creation_response(response):
    status, headers, body = response
    if status != 201:
        raise AssertionError("Wrong success status")
    response_validator.validate(body)
    if headers.get("Location") != f"/tasks/{body['id']}":
        raise AssertionError("Missing or inconsistent Location")

check_creation_response(provider({"title": " Learn contracts "}))
for body in [{}, {"title": " "}, {"title": 42}, {"title": "Learn", "ownerId": 99}]:
    assert provider(body)[0] == 422
try:
    check_creation_response((201, {"Location": "/tasks/1"}, {"id": 1, "title": "Learn"}))
except ValidationError:
    pass
else:
    raise AssertionError("Missing required response field escaped")
try:
    check_creation_response((201, {}, {"id": 1, "title": "Learn", "completed": False}))
except AssertionError:
    pass
else:
    raise AssertionError("Missing required application header escaped")
print("happy: contract-aligned creation; unhappy: invalid requests and provider drift detected")
```

This fixture reuses its actual schema objects rather than copying separate validators. Its simple schemas do not use the full OpenAPI dialect or external references. The request has strict unknown-field rejection, while the response deliberately permits extension fields. The header requirement is an additional executable application assertion, not something the body validator enforces.

Title length is measured before documented trimming; only this fixture's title-only public creation route is modeled. The provider has no persistent ID allocation or authentication; a protected real API must describe and enforce both security and ownership rather than treating documentation as enforcement.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Do not maintain a giant hand-written specification that nobody checks against implementation.
- Do not claim schema-valid means authorized, transactionally correct, or semantically compatible.
- Do not generate clients from an unreviewed schema and assume all target languages handle enums/nulls identically.
- Do not expose validation diagnostics containing sensitive input or internal schema paths indiscriminately.
- Do not turn every example value into an accidental promise without stating defaults and allowed variability.

Small internal interfaces can use smaller executable contracts; independent consumers and releases increase the value of formal descriptions. Contract tooling has a cost, but conflicting sources of truth have one too.

## 6. How do I know I understand it?

**Blank-page check:** specify one route's method, path, auth, input, normalization, success/error status/body/headers, limits, side effects, and retry behavior. Mark which parts your schema checker actually verifies.

| Constraint change | Predict the failure and response |
| --- | --- |
| Provider omits `completed` | Response contract test fails even if HTTP status is `201` |
| Header disappears but body stays valid | Separate header/protocol assertion is necessary |
| Client adds an internal `ownerId` | Request allowlist rejects it under this contract |
| Behavior changes units without changing type | Schema-only checks miss the semantic break |

You understand contracts when the description, executable checks, and real consumer expectations agree—and their unverified gaps are explicit.
