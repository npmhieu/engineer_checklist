# Advanced Idempotency

[Lesson index](../../README.md) · Previous: [API Contract](3.api_contract.md) · Next: [Rate Limiting](5.rate_limiting.md)

## 1. What is it?

Advanced idempotency makes repeated intent recoverable across concurrency, crashes, and external effects, like a tracked payment order that can be resumed without charging again after a lost receipt.

It builds on [Idempotency Basics](../../basic/1.api_application/12.idempotency_basics.md): a local deduplication record alone cannot make an independent provider effect atomic with your database.

## 2. Why do we need it?

A worker can charge a provider, crash before saving the result, and then run again after its lease expires. Holding a database lock while calling the provider is slow and still does not eliminate the crash gap.

Specific pain: a retry sees “pending” and repeats an external charge, or an old worker overwrites a newer recovery worker's completed state.

## 3. Under the hood / mechanism / system flow

### 3a. Intent records, leases, fencing, and downstream keys

Persist caller/tenant + operation + key, a canonical semantic-input fingerprint, stable operation ID, state/result, and recovery ownership. A lease permits takeover after a deadline; a monotonically increasing generation/fence prevents an outdated owner from committing where the conditional write enforces it.

Lease expiry does **not** prove the previous worker stopped. A fencing number protects only boundaries that check it. For an external side effect, reuse a stable downstream idempotency identity or query/reconcile a provider operation; without provider support, strict duplicate prevention may be impossible in an uncertain-outcome window.

Indexed coordination adds reads/writes and contention. Stored results need retention/privacy policy; backlog scans need bounded indexes. Lease renewal/recovery needs an authoritative time policy and protection against stale owners. [AWS's retry-safe API discussion](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) explains caller intent and safe retries across failures.

### 3b. Recoverable state machine

```text
Validated authorized intent → durable pending operation + stable provider key
    → claim generation/lease → external call outside local transaction
    → conditional completion → replay stored result
Crash → expired lease → new generation → same provider key → recover outcome
```

Do not delete a pending record merely because its lease expired. Lease duration and deduplication retention are different contracts. New intents receive new keys; the same key with different input is a conflict. Provider retention and reconciliation windows must cover realistic local retries, or a late retry can create a new external effect.

## 4. How to apply / implement / use it?

Save as `advanced_idempotency_demo.py`; run `python3 advanced_idempotency_demo.py`. Python standard library only. Two separate temporary SQLite files represent the application and an **independent simulated provider with an idempotent API**. No payment or network call occurs.

The crash is an injected exception after provider commit, followed by closing/reopening both connections. Tenant context and worker calls are trusted fixture inputs; real APIs need authorization for submit/status/replay and authenticated workers.

```python
import hashlib
import json
from pathlib import Path
import sqlite3
import tempfile
import uuid

class KeyConflict(Exception):
    pass

class InProgress(Exception):
    pass

class LeaseLost(Exception):
    pass

def submit(tenant_id, key, cents):
    if type(tenant_id) is not int or tenant_id <= 0 or type(cents) is not int or cents <= 0 or not isinstance(key, str) or not 1 <= len(key) <= 128:
        raise ValueError("INVALID_REQUEST")
    fingerprint = hashlib.sha256(json.dumps({"cents": cents}, sort_keys=True).encode()).hexdigest()
    with local:
        local.execute("BEGIN IMMEDIATE")
        existing = local.execute("SELECT id, fingerprint FROM operations WHERE tenant_id = ? AND action = 'charge' AND request_key = ?", (tenant_id, key)).fetchone()
        if existing:
            if existing[1] != fingerprint:
                raise KeyConflict("IDEMPOTENCY_KEY_REUSED")
            return existing[0]
        operation_id = uuid.uuid4().hex
        local.execute("INSERT INTO operations VALUES (?, ?, 'charge', ?, ?, ?, 'pending', 0, 0, NULL)", (operation_id, tenant_id, key, fingerprint, cents))
    return operation_id

def claim(operation_id, now):
    with local:
        local.execute("BEGIN IMMEDIATE")
        state, generation, lease_until = local.execute("SELECT state, generation, lease_until FROM operations WHERE id = ?", (operation_id,)).fetchone()
        if state == "succeeded":
            return None
        if lease_until > now:
            raise InProgress("LEASE_HELD")
        generation += 1
        local.execute("UPDATE operations SET generation = ?, lease_until = ? WHERE id = ?", (generation, now + 10, operation_id))
    return generation

def provider_charge(operation_id, cents):
    with provider:
        provider.execute("BEGIN IMMEDIATE")
        previous = provider.execute("SELECT cents FROM charges WHERE operation_id = ?", (operation_id,)).fetchone()
        if previous:
            if previous[0] != cents:
                raise ValueError("PROVIDER_KEY_REUSED")
        else:
            provider.execute("INSERT INTO charges VALUES (?, ?)", (operation_id, cents))
    return {"provider_id": operation_id, "cents": cents}

def complete(operation_id, generation, result, now):
    with local:
        changed = local.execute("UPDATE operations SET state = 'succeeded', result = ? WHERE id = ? AND state = 'pending' AND generation = ? AND lease_until > ?", (json.dumps(result), operation_id, generation, now))
        if changed.rowcount != 1:
            raise LeaseLost("STALE_OR_EXPIRED_OWNER")

def execute(operation_id, generation, now, crash=False):
    cents = local.execute("SELECT cents FROM operations WHERE id = ?", (operation_id,)).fetchone()[0]
    result = provider_charge(operation_id, cents)
    if crash:
        raise RuntimeError("CRASH_AFTER_PROVIDER_COMMIT")
    complete(operation_id, generation, result, now)
    return result

with tempfile.TemporaryDirectory() as directory:
    local_path = Path(directory) / "application.sqlite"
    provider_path = Path(directory) / "provider.sqlite"
    local = sqlite3.connect(local_path)
    provider = sqlite3.connect(provider_path)
    local.execute("CREATE TABLE operations (id TEXT PRIMARY KEY NOT NULL, tenant_id INTEGER, action TEXT, request_key TEXT, fingerprint TEXT, cents INTEGER, state TEXT, generation INTEGER, lease_until INTEGER, result TEXT, UNIQUE(tenant_id, action, request_key))")
    provider.execute("CREATE TABLE charges (operation_id TEXT PRIMARY KEY NOT NULL, cents INTEGER)")
    operation_id = submit(7, "intent-a", 500)
    assert submit(7, "intent-a", 500) == operation_id
    try:
        submit(7, "intent-a", 600)
    except KeyConflict:
        pass
    else:
        raise AssertionError("Changed input reused a key")
    first_generation = claim(operation_id, now=100)
    try:
        claim(operation_id, now=101)
    except InProgress:
        pass
    else:
        raise AssertionError("Active lease was ignored")
    try:
        execute(operation_id, first_generation, now=102, crash=True)
    except RuntimeError:
        pass
    else:
        raise AssertionError("Crash injection did not execute")
    local.close()
    provider.close()
    local = sqlite3.connect(local_path)
    provider = sqlite3.connect(provider_path)
    recovered_generation = claim(operation_id, now=111)
    result = execute(operation_id, recovered_generation, now=112)
    try:
        complete(operation_id, first_generation, result, now=113)
    except LeaseLost:
        pass
    else:
        raise AssertionError("Stale owner changed completion")
    assert provider.execute("SELECT COUNT(*) FROM charges").fetchone()[0] == 1
    assert json.loads(local.execute("SELECT result FROM operations WHERE id = ?", (operation_id,)).fetchone()[0]) == result
    assert claim(operation_id, now=114) is None
    local.close()
    provider.close()
print("happy: crash recovery reuses one provider effect; unhappy: mismatch/busy/stale owner rejected")
```

The provider's uniqueness is a deliberately supplied guarantee, not something an HTTP timeout or local lease creates. Local fencing stops stale **local completion**; it does not cancel an earlier external request. Production code reads fresh authoritative completion time, bounds attempts, renews/reconciles leases, handles permanent/unknown outcomes, and indexes recovery scans. This fixture has no retention cleanup or real multi-worker/provider integration test.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- A short operation wholly inside one database may need only the simpler atomic result-store pattern.
- Do not replace pending operations with success merely because their lease expired.
- Do not regenerate downstream keys on retry or use a body hash alone to identify user intent.
- Do not allow stored results from one caller/tenant to be replayed to another.
- Do not promise universal exactly-once effects across arbitrary systems or keep retrying after downstream deduplication has expired without reconciliation.

Explicit states and recovery are operational work. Sometimes returning an uncertain/pending state and reconciling is safer than automatically retrying a non-idempotent provider action.

## 6. How do I know I understand it?

**Blank-page check:** place crashes before intent commit, before provider call, after provider commit, and before/after local completion. Explain the next owner's action and the identity protecting each effect.

| Constraint change | Predict the failure and response |
| --- | --- |
| Old worker runs after lease takeover | Fence local writes; downstream protection must exist independently |
| Provider has no key/query guarantee | A timeout can leave an irreducibly uncertain outcome; design reconciliation/manual recovery |
| Key retention ends before retry | Late execution may repeat the effect; align windows and policy |
| Payload changes under the same key | Reject conflict rather than return an unrelated stored result |

You understand advanced idempotency when the recovery protocol, not just the happy path, explains every committed effect.
