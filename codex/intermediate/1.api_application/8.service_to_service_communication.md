# Service-to-Service Communication

[Lesson index](../../README.md) · Previous: [Third-party API Integration](7.third_party_api_integration.md) · Next: [Advanced Transactions](../2.database_performance/1.advanced_transactions.md)

## 1. What is it?

Service-to-service communication exchanges requests or messages across independently running application components, like departments in separate buildings using verified couriers and agreed forms instead of assuming a local conversation.

It can use synchronous HTTP/RPC or asynchronous messaging. Splitting code into services creates network, identity, deployment, and data-consistency boundaries.

## 2. Why do we need it?

Independent capabilities may need separate ownership, scale, release cadence, or trust isolation. But a formerly local function call can now time out, execute twice, or succeed after the caller gives up.

Specific security bug: an internal API trusts any `X-User-ID` header and lets an otherwise legitimate service act as an unauthorized user—the confused-deputy problem.

## 3. Under the hood / mechanism / system flow

### 3a. Transport, identity, contracts, and resource costs

Synchronous calls add discovery/load balancing, DNS, connection pools, TLS, serialization, deadlines, and independent failure. Async messages add durable handoff, delivery/ordering/acknowledgment semantics, schema evolution, and backlog capacity. A service mesh can assist transport but does not infer all business permissions.

Normal TLS authenticates the server to the client under its trust policy; mutual TLS additionally authenticates the client certificate. Workload identity still needs correct trust roots, intended identity mapping, rotation, and authorization. Service tokens require verified issuer/audience/purpose/scopes, not merely a decoded payload. [OWASP's microservices security guidance](https://cheatsheetseries.owasp.org/cheatsheets/Microservices_Security_Cheat_Sheet.html) discusses service identity and authorization boundaries.

Distinguish **workload identity** from **delegated end-user authority**. A caller can be a real reports service without permission to read every tenant's records. Do not forward an ID token or arbitrary incoming bearer credential to unrelated audiences; use an appropriate delegation/exchange mechanism and verify its scope.

### 3b. Call chain and deadline propagation

```text
Authenticate workload → validate intended audience/delegation → authorize resource
    → allocate remaining budget → bounded dependency call → validate result
    → safe result/error + trace evidence
```

Propagate a remaining time budget or a protocol-defined deadline. Do not compare one machine's raw monotonic timestamp on another machine. The receiver applies its own cap and local clock; cancellation/timeouts do not automatically undo a committed remote effect. Assign retry ownership to avoid multiplying attempts across every layer.

Trace context correlates work; it is not authentication or permission. [W3C Trace Context](https://www.w3.org/TR/trace-context/) defines interoperable trace fields; validate/bound untrusted tracing metadata and avoid placing secrets in baggage/logs. Current authorization, backpressure, and operational metrics remain necessary even on private networks.

## 4. How to apply / implement / use it?

Save as `service_communication_demo.py`; run `python3 service_communication_demo.py`. Standard library only. The example tests an authorization/deadline boundary with **already verified workload/delegation fixtures**, not cryptographic authentication, mTLS, real RPC, or a token-exchange implementation.

Constructing `VerifiedContext` does not verify anything. In a real application, only a trusted authentication adapter may create this context from checked transport/token evidence; never construct it from raw request fields.

```python
from dataclasses import dataclass
from typing import Optional

class Unauthenticated(Exception):
    pass

class Denied(Exception):
    pass

class DeadlineExceeded(Exception):
    pass

@dataclass(frozen=True)
class VerifiedContext:
    service: str
    audience: str
    scopes: frozenset
    delegated_user: Optional[int]

class Clock:
    def __init__(self):
        self.value = 0.0

    def __call__(self):
        return self.value

workload_permissions = {"reports-api": {"task.read"}, "billing-worker": {"invoice.write"}}
memberships = {(7, 7), (9, 8)}
tasks = {42: {"tenant_id": 7, "title": "Allowed"}, 43: {"tenant_id": 8, "title": "Other tenant"}}

def fetch_task(tenant_id, task_id, timeout):
    task = tasks.get(task_id)
    if task is None or task["tenant_id"] != tenant_id:
        raise LookupError("TASK_NOT_FOUND")
    return {"id": task_id, "title": task["title"]}

def serve(context, request, remaining_ms, clock, fetch=fetch_task):
    if not isinstance(context, VerifiedContext) or context.audience != "tasks-api":
        raise Unauthenticated("WORKLOAD_AUTHENTICATION_REQUIRED")
    allowed = workload_permissions.get(context.service, set())
    if "task.read" not in allowed or "task.read" not in context.scopes or context.delegated_user is None:
        raise Denied("FORBIDDEN")
    if not isinstance(request, dict) or set(request) != {"tenant_id", "task_id"}:
        raise ValueError("INVALID_REQUEST")
    if any(type(request[field]) is not int or request[field] <= 0 for field in request):
        raise ValueError("INVALID_RESOURCE_ID")
    if (context.delegated_user, request["tenant_id"]) not in memberships:
        raise Denied("FORBIDDEN")
    if type(remaining_ms) is not int:
        raise ValueError("INVALID_BUDGET")
    if remaining_ms <= 0:
        raise DeadlineExceeded("NO_REMAINING_BUDGET")
    deadline = clock() + min(remaining_ms, 1000) / 1000
    timeout = deadline - clock()
    if timeout <= 0:
        raise DeadlineExceeded("NO_REMAINING_BUDGET")
    result = fetch(request["tenant_id"], request["task_id"], timeout)
    if clock() >= deadline:
        raise DeadlineExceeded("DEPENDENCY_EXCEEDED_BUDGET")
    return result

context = VerifiedContext("reports-api", "tasks-api", frozenset({"task.read"}), 7)
clock = Clock()
request = {"tenant_id": 7, "task_id": 42}
assert serve(context, request, 500, clock) == {"id": 42, "title": "Allowed"}
for actor, body, budget, expected in [
    (None, request, 500, Unauthenticated),
    (VerifiedContext("billing-worker", "tasks-api", frozenset({"task.read"}), 7), request, 500, Denied),
    (context, {"tenant_id": 8, "task_id": 43}, 500, Denied),
    (context, {**request, "user_id": 9}, 500, ValueError),
    (context, request, 0, DeadlineExceeded),
]:
    try:
        serve(actor, body, budget, clock)
    except expected:
        pass
    else:
        raise AssertionError("Boundary check was bypassed")

def slow_fetch(tenant_id, task_id, timeout):
    clock.value += timeout + 0.01
    return fetch_task(tenant_id, task_id, timeout)

try:
    serve(context, request, 50, clock, slow_fetch)
except DeadlineExceeded:
    pass
else:
    raise AssertionError("Late dependency result became success")
print("happy: workload plus delegated scope; unhappy: spoofed/cross-tenant/late calls rejected")
```

The local dependency is read-only. Checking elapsed time afterward prevents accepting a late result but does not preempt/cancel an uncooperative blocking call; production transport must enforce deadlines and concurrency limits itself. The slow fixture deliberately violates that transport expectation to show the caller's residual guard.

The verified-context contract assumes current, correctly verified delegation; a real system must enforce expiry, issuer/audience, binding to the calling service, scope, and account/membership freshness. Do not treat this dataclass as a replacement for those mechanisms. Add real mTLS/token/RPC integration tests, network policy, credential rotation, safe retries, and authenticated message production as applicable.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- A local module call may be simpler when independent deployment/trust/scale is not needed.
- Do not trust “inside the network” or arbitrary forwarded user/role headers as authorization.
- Do not propagate service-wide authority as if it were a user's unlimited delegated permission.
- Do not make a chain of synchronous services each reset the caller's full timeout and retry budget.
- Do not assume a mesh, queue, or RPC generator supplies domain-level idempotency and data consistency automatically.

Distributed boundaries impose partial failure, observability, deployment compatibility, and recovery costs. Choose them deliberately rather than extracting services only to reorganize folders.

## 6. How do I know I understand it?

**Blank-page check:** draw transport trust, workload identity, user delegation, resource policy, deadlines, retry ownership, tracing, and commit boundaries for one call chain.

| Constraint change | Predict the failure and response |
| --- | --- |
| Caller changes `X-User-ID` | Unverified headers cannot grant user authority |
| Service credential leaks | Limit audience/scopes, rotate/revoke, and retain resource-level checks |
| Network hop adds latency | Consume remaining budget; do not restart a full deadline at each hop |
| Async delivery replaces RPC | Define durable acceptance, ack/redelivery, identity, and schema compatibility |
| Remote write succeeds after caller timeout | Cancellation is not rollback; use safe intent identity and reconciliation |

You understand service communication when independent trust and failure boundaries remain explicit even when both services belong to the same team.
