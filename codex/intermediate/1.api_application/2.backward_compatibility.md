# Backward Compatibility

[Lesson index](../../README.md) · Previous: [Advanced API Design](1.advanced_api_design.md) · Next: [API Contract](3.api_contract.md)

## 1. What is it?

Backward compatibility lets supported older clients keep their promised behavior after a server change, like a new phone charger still working with the older connector through a correctly designed adapter.

It includes accepted inputs, observable outputs, and meaning—not only whether JSON still parses.

## 2. Why do we need it?

Mobile apps, partner scripts, queued messages, and offline clients do not update simultaneously. A server can return `200` while a renamed field, changed default, or new enum value breaks an old client.

Specific pain: replacing `title` with `name` makes old clients display blank tasks even though the new server's own tests pass.

## 3. Under the hood / mechanism / system flow

### 3a. Producer/consumer acceptance boundaries

Reason about both directions: continue accepting supported old requests, and produce responses supported consumers can interpret with the promised semantics. Widening inputs can be compatible; narrowing them often is not. Adding output fields is safe only under the supported reader/schema behavior.

Generated strict decoders, exhaustive enum switches, signatures, positional encodings, and persisted payloads can make apparently additive changes break. [Google AIP-180](https://google.aip.dev/180) discusses source, wire, and semantic compatibility. API versions are one transition mechanism, not proof that unchanged versions remain compatible.

Adapters, aliases, and dual reads/writes add CPU, storage, and maintenance. Two mutable aliases without one owner can disagree. Keeping a legacy path alive also keeps its testing/security obligations alive.

### 3b. Mixed-version rollout

```text
Identify supported consumers → record baseline behaviors → add compatible expansion
    → deploy mixed-version-safe code/schema → observe/migrate clients
    → retire obsolete contract only under an explicit policy
```

Compatibility dimensions include auth requirements, field types, default limits/order, errors/statuses, units, nullability, time formats, retry behavior, and side effects. A syntactic diff tool catches only some of them. Use consumer/provider tests plus representative workflows; do not preserve a security vulnerability merely to avoid a coordinated security fix.

## 4. How to apply / implement / use it?

Save as `backward_compatibility_demo.py`; run `python3 backward_compatibility_demo.py`. This executable old consumer deliberately tolerates extra fields but recognizes only two states.

```python
class UnsupportedContract(Exception):
    pass

def old_client(response):
    if not isinstance(response, dict) or not {"id", "title", "state"} <= set(response):
        raise UnsupportedContract("REQUIRED_FIELD_MISSING")
    if type(response["id"]) is not int or not isinstance(response["title"], str):
        raise UnsupportedContract("FIELD_TYPE_CHANGED")
    if not isinstance(response["state"], str) or response["state"] not in {"open", "done"}:
        raise UnsupportedContract("UNKNOWN_STATE")
    return response["title"], response["state"]

internal = {"id": 42, "name": "Learn compatibility", "completed": False}

def represent_v1(task):
    return {"id": task["id"], "title": task["name"], "state": "done" if task["completed"] else "open"}

def represent_v2(task):
    return {"id": task["id"], "name": task["name"], "completed": task["completed"]}

baseline = represent_v1(internal)
expected = ("Learn compatibility", "open")
assert old_client(baseline) == expected
assert old_client({**baseline, "description": "Optional addition"}) == expected
for response in [represent_v2(internal), {**baseline, "state": "paused"}, {**baseline, "id": "42"}]:
    try:
        old_client(response)
    except UnsupportedContract:
        pass
    else:
        raise AssertionError("Breaking change escaped old-consumer checks")
assert old_client(represent_v1(internal)) == expected
print("happy: additive field and v1 adapter work; unhappy: rename/enum/type break detected")
```

This consumer is not universal. A closed response schema can reject the extra description; a documented unknown-enum fallback can accept a new state. Test the real supported contract rather than assuming either behavior. Do not map `paused` to `open` merely to make a decoder pass if that changes meaning.

Add semantic tests too: an amount in cents must not silently become dollars; omitted pagination parameters must retain documented defaults. Server and database releases need compatibility independently from the public representation adapter above.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Unsupported experimental clients may have a different explicit stability policy.
- Do not maintain every historical mistake forever without a support/migration policy.
- Do not call stricter validation harmless when existing accepted requests now fail.
- Do not rely only on field-name/schema diffs to prove semantic compatibility.
- Do not delete old behavior based solely on latest-client tests or incomplete traffic telemetry.

Breaking changes can be legitimate. Provide an explicit new contract, migration window, observability, and rollback/forward-fix plan instead of silently changing the old one.

## 6. How do I know I understand it?

**Blank-page check:** classify changes to fields, enums, defaults, units, errors, and auth. Explain the consumer assumptions behind each compatibility judgment.

| Constraint change | Predict the failure and response |
| --- | --- |
| New enum value is added | Exhaustive old consumers may fail; evaluate fallback/version strategy |
| A field becomes required in requests | Old requests can stop working even if responses stay identical |
| Default sort changes | Pagination/cache/workflow meaning can break without a schema diff |
| Old and new replicas share a database | Use an expand/migrate/contract sequence compatible with both |

You understand compatibility when you can name which supported consumer behavior is preserved and prove more than “the response is valid JSON.”
