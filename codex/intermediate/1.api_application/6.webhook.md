# Webhook

[Lesson index](../../README.md) · Previous: [Rate Limiting](5.rate_limiting.md) · Next: [Third-party API Integration](7.third_party_api_integration.md)

## 1. What is it?

A webhook is an HTTP callback sent when another system wants to notify your endpoint of an event, like a courier ringing your doorbell instead of you repeatedly checking the street.

It is delivery of a claimed event, not automatic proof of authenticity, ordering, uniqueness, or business completion.

## 2. Why do we need it?

Polling every order wastes calls and still delays updates. But a naive callback endpoint can be forged, process one event twice, or lose work after replying successfully.

Specific bug: the sender retries after losing your response and your backend creates a second credit/notification. Another failure accepts a genuine payload whose timestamp/signature was never checked.

## 3. Under the hood / mechanism / system flow

### 3a. Raw bytes, signatures, and inbox storage

A common provider scheme authenticates the exact raw body plus delivery metadata using HMAC or signatures. JSON reserialization can change whitespace/key order and invalidate verification. Use the provider SDK/protocol, configured endpoint secret/key, bounded body parsing, and constant-time digest comparison where required.

A signed timestamp bounds replay age only if checked against a trusted clock; duplicates inside that window still need event identity/deduplication. Event IDs should be scoped to provider/subscription, not assumed globally unique. A durable inbox makes acceptance recoverable; indexed IDs and body hashing add storage/CPU, while holding the HTTP connection through slow work increases timeout/retry pressure.

[Stripe's webhook documentation](https://docs.stripe.com/webhooks) is one concrete example of raw-body verification, duplicate handling, retries, and ordering limitations. The runnable protocol below is a local teaching protocol, **not Stripe's header format or signing implementation**.

### 3b. Acceptance versus processing

```text
Bound raw request → verify configured sender/signature/freshness
    → parse/validate supported event → commit inbox/dedup record → acknowledge
Worker → apply allowed local state change + mark processed atomically
```

Reply success after the durability boundary promised by your contract, not merely after putting work in process memory. Acknowledgment means accepted for processing, not necessarily applied. Sender retry rules vary; never assume every provider treats all statuses identically.

Events can arrive late/out of order. Use domain versions, idempotent transitions, or an authoritative lookup as appropriate; do not let an old “pending” event overwrite a newer “complete” state. Signed payload fields still need permission/scope validation: signatures identify a sender, not unlimited authority over every tenant.

## 4. How to apply / implement / use it?

Save as `webhook_demo.py`; run `python3 webhook_demo.py`. Standard library only. This local protocol signs `ASCII(timestamp) + b'.' + raw_body` with HMAC-SHA256. One configured subscription is mapped server-side to tenant 7. No network endpoint or actual provider is contacted.

```python
import hashlib
import hmac
import json
from pathlib import Path
import re
import secrets
import sqlite3
import tempfile

secret = secrets.token_bytes(32)
SUBSCRIPTION = "partner-A"
TENANT = 7

def sign(raw, timestamp):
    return hmac.new(secret, timestamp.encode("ascii") + b"." + raw, hashlib.sha256).hexdigest()

def receive(raw, timestamp, signature, now):
    if not isinstance(raw, bytes) or len(raw) > 65536:
        return 413, {"code": "BODY_LIMIT"}
    if not isinstance(timestamp, str) or re.fullmatch(r"[0-9]{1,12}", timestamp) is None:
        return 403, {"code": "UNTRUSTED_DELIVERY"}
    if not isinstance(signature, str) or re.fullmatch(r"[0-9a-f]{64}", signature) is None:
        return 403, {"code": "UNTRUSTED_DELIVERY"}
    if abs(now - int(timestamp)) > 300 or not hmac.compare_digest(sign(raw, timestamp), signature):
        return 403, {"code": "UNTRUSTED_DELIVERY"}
    try:
        event = json.loads(raw.decode("utf-8"))
    except (UnicodeDecodeError, json.JSONDecodeError):
        return 400, {"code": "INVALID_JSON"}
    if not isinstance(event, dict) or not isinstance(event.get("id"), str) or re.fullmatch(r"[A-Za-z0-9_-]{1,128}", event["id"]) is None:
        return 422, {"code": "INVALID_EVENT"}
    data = event.get("data")
    if event.get("type") != "task.completed" or not isinstance(data, dict) or type(data.get("task_id")) is not int or not 0 < data["task_id"] <= 2**63 - 1:
        return 422, {"code": "INVALID_EVENT"}
    digest = hashlib.sha256(raw).hexdigest()
    with database:
        database.execute("BEGIN IMMEDIATE")
        previous = database.execute("SELECT digest FROM inbox WHERE subscription = ? AND event_id = ?", (SUBSCRIPTION, event["id"])).fetchone()
        if previous:
            return (200, {"code": "ALREADY_ACCEPTED"}) if previous[0] == digest else (409, {"code": "EVENT_ID_REUSED"})
        database.execute("INSERT INTO inbox VALUES (?, ?, ?, ?, 'pending')", (SUBSCRIPTION, event["id"], digest, raw.decode("utf-8")))
    return 202, {"code": "ACCEPTED"}

def process_one():
    with database:
        database.execute("BEGIN IMMEDIATE")
        row = database.execute("SELECT subscription, event_id, body FROM inbox WHERE status = 'pending' ORDER BY event_id LIMIT 1").fetchone()
        if row is None:
            return False
        event = json.loads(row[2])
        changed = database.execute("UPDATE tasks SET completed = 1 WHERE tenant_id = ? AND id = ?", (TENANT, event["data"]["task_id"]))
        if changed.rowcount != 1:
            raise LookupError("UNKNOWN_LOCAL_RESOURCE")
        database.execute("INSERT INTO effects VALUES (?, ?)", (row[0], row[1]))
        database.execute("UPDATE inbox SET status = 'processed' WHERE subscription = ? AND event_id = ?", (row[0], row[1]))
    return True

with tempfile.TemporaryDirectory() as directory:
    path = Path(directory) / "inbox.sqlite"
    database = sqlite3.connect(path)
    database.executescript("""
        CREATE TABLE tasks (tenant_id INTEGER, id INTEGER, completed INTEGER, PRIMARY KEY (tenant_id, id));
        CREATE TABLE inbox (subscription TEXT NOT NULL, event_id TEXT NOT NULL, digest TEXT, body TEXT, status TEXT, PRIMARY KEY (subscription, event_id));
        CREATE TABLE effects (subscription TEXT NOT NULL, event_id TEXT NOT NULL, PRIMARY KEY (subscription, event_id));
        INSERT INTO tasks VALUES (7, 42, 0);
    """)
    raw = json.dumps({"id": "evt-1", "type": "task.completed", "data": {"task_id": 42}}).encode()
    timestamp = "1000"
    signature = sign(raw, timestamp)
    assert receive(raw, timestamp, signature, now=1000)[0] == 202
    assert receive(raw, timestamp, signature, now=1000)[0] == 200
    assert receive(raw + b" ", timestamp, signature, now=1000)[0] == 403
    assert receive(raw, timestamp, signature, now=1401)[0] == 403
    conflicting = json.dumps({"id": "evt-1", "type": "task.completed", "data": {"task_id": 43}}).encode()
    assert receive(conflicting, timestamp, sign(conflicting, timestamp), now=1000)[0] == 409
    database.close()
    database = sqlite3.connect(path)
    assert process_one() and not process_one()
    assert database.execute("SELECT completed FROM tasks WHERE tenant_id = 7 AND id = 42").fetchone()[0] == 1
    assert database.execute("SELECT COUNT(*) FROM effects").fetchone()[0] == 1
    database.close()
print("happy: durable acceptance and one local effect; unhappy: tamper/stale/reused-ID rejected")
```

This protocol requires the same raw body for repeated event IDs; a real provider may define semantic identity differently. Timestamp tolerance is arbitrary fixture policy and server time is injected only for tests. Signature verification happens before JSON interpretation; the HTTP layer must enforce size/time limits while reading, not after unbounded buffering.

Database/inbox errors must not produce a false successful acknowledgment. The transaction covers only these local effects, not external email/payment calls. Unknown resources roll back and leave pending work; production needs bounded retries, quarantine/dead-letter handling, observability, ordering policy, key rotation, and reconciliation. TLS, actual header handling, provider verification SDKs, and multi-provider authorization are omitted.

## 5. When should I NOT use this? Trade-offs and anti-patterns

- Polling may be simpler when freshness needs are loose or callbacks cannot reach a controlled endpoint.
- Do not accept IP allowlists or a secret URL as the only substitute for the provider's authentication protocol.
- Do not reserialize JSON before checking a raw-body signature or trust arbitrary payload tenant IDs.
- Do not process duplicate event IDs as new work or assume arrival order is domain order.
- Do not acknowledge before durable acceptance if recovery is promised, or hold the request open through long effects unnecessarily.

Webhooks add an internet-facing trust boundary and delivery/recovery obligations. A reconciliation job is often still needed even when real-time delivery works well.

## 6. How do I know I understand it?

**Blank-page check:** identify exact signed bytes, trusted key selection, freshness, event identity scope, durable acknowledgment boundary, and local/external effect ownership.

| Constraint change | Predict the failure and response |
| --- | --- |
| Middleware changes whitespace | Raw-body signature verification can fail; preserve original bytes |
| Sender retries inside freshness window | Deduplicate by authenticated subscription/event identity |
| Process stops after acknowledgment | Persisted inbox must remain recoverable |
| An older event arrives last | Domain version/state policy must prevent regression |
| Worker also sends email | Inbox/local transaction alone cannot guarantee one external delivery |

You understand webhooks when authenticity, acceptance, processing, duplication, and reconciliation are separate explicit guarantees.
