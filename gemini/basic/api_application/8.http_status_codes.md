## 1. What is it?

An **HTTP Status Code** is a standardized 3-digit integer issued by a server in response to a client's request. Standardized in RFC 9110, status codes communicate the high-level semantic result of an HTTP request.

The first digit defines the **class** of the response:

| Class | Name | Core Semantic Meaning |
| :--- | :--- | :--- |
| **`1xx`** | Informational | Request received, continuing process (e.g., `100 Continue`, `101 Switching Protocols`). |
| **`2xx`** | Success | The action was successfully received, understood, and accepted. |
| **`3xx`** | Redirection | Further action must be taken by the client to complete the request. |
| **`4xx`** | Client Error | The request contains bad syntax or cannot be fulfilled due to client fault. |
| **`5xx`** | Server Error | The server failed to fulfill an apparently valid request due to server fault. |

An HTTP status code provides the **macro-level** result of a request. Application-level error codes (e.g., `INSUFFICIENT_FUNDS`) provide the **micro-level** details inside the response body.

---

## 2. Why do we need it?

1. **Protocol-Level Interoperability:**
   Network intermediaries (reverse proxies, CDNs, load balancers, browser caches, and API gateways) do not parse custom application JSON bodies. They rely entirely on standard HTTP status codes to determine:
   - Should this response be cached? (`200`, `304`)
   - Should this request be retried? (`502`, `503`, `504`)
   - Should traffic be routed to a healthy replica?
2. **Standardized Observability & SRE Metrics:**
   Monitoring frameworks (Prometheus, Datadog, Grafana) automatically calculate service health, Service Level Objectives (SLOs), and error rates based on the ratio of `2xx/3xx` vs. `5xx` status codes.
3. **Decoupled Frontend Logic:**
   Client network libraries (Axios, Fetch, Retrofit, OkHttp) intercept `401` to trigger automated token refreshes or redirect to login screens without inspecting application payload details.

## 3. How to apply / implement / use it?

### A. Essential Status Codes for Backend Engineers

#### 1. `2xx` Success
- **`200 OK`:** General success for `GET`, `PUT`, or `PATCH`. Body contains the retrieved or modified resource.
- **`201 Created`:** Resource was successfully created via `POST`. **Must** include a `Location` header pointing to the new resource (e.g., `Location: /api/v1/orders/ord_123`).
- **`202 Accepted`:** Request accepted for asynchronous/background processing, but processing is not complete. Body should return a job status tracking URL.
- **`204 No Content`:** Action succeeded, but the response body is intentionally empty (standard for `DELETE` or certain update actions).

#### 2. `3xx` Redirection & Caching
- **`301 Moved Permanently`:** Resource now permanently resides at a new URI.
- **`304 Not Modified`:** Conditional GET (`If-None-Match` or `If-Modified-Since`) confirmed that client's cached representation is still valid. Body is empty.

#### 3. `4xx` Client Errors
- **`400 Bad Request`:** Generic syntax error; malformed JSON, unparseable input.
- **`401 Unauthorized`:** Authentication is required and has failed or is missing. **Must** include `WWW-Authenticate` header (e.g., `WWW-Authenticate: Bearer realm="api"`).
- **`403 Forbidden`:** Server understood client identity, but refuses authorization. The caller lacks required permissions or roles.
- **`404 Not Found`:** Target URI or individual resource does not exist. (Can also be used to intentionally hide existence of sensitive resources from unauthorized callers).
- **`405 Method Not Allowed`:** Route exists, but does not support the HTTP verb (e.g., `POST` on a read-only endpoint). **Must** return an `Allow` header listing supported verbs.
- **`409 Conflict`:** Request conflicts with current server state (e.g., duplicate email registration, editing an archived entity, or concurrent version mismatch).
- **`415 Unsupported Media Type`:** Client sent payload in an unsupported format (e.g., sent XML when API expects `application/json`).
- **`422 Unprocessable Content`:** Request syntax is well-formed, but contains semantic/validation errors (e.g., string exceeds max length).
- **`429 Too Many Requests`:** Rate limit exceeded. Should include `Retry-After: <seconds>` header.

#### 4. `5xx` Server Errors
- **`500 Internal Server Error`:** Unhandled code exception or unexpected internal bug.
- **`502 Bad Gateway`:** Server acting as proxy received an invalid response from upstream dependency.
- **`503 Service Unavailable`:** Server is temporarily overloaded, under maintenance, or failing health checks.
- **`504 Gateway Timeout`:** Upstream server or database failed to respond within timeout window.

## 4. When should I NOT use this? (Trade-offs and Anti-patterns)

### When Status Codes Should NOT Stand Alone
- **Do not rely on the status code alone to explain business failures.**
  Returning just `409 Conflict` without a response body leaves the client guessing whether the email was duplicate, the account was suspended, or a version was stale. Always accompany error status codes with a structured error payload.

### Anti-Patterns to Avoid
1. **The "Always 200 OK" Anti-Pattern:**
   ```json
   // ❌ CRITICAL ANTI-PATTERN
   HTTP/1.1 200 OK
   {
     "success": false,
     "error": "User unauthorized"
   }
   ```
   Completely breaks HTTP caching, proxies, CDNs, and APM alerting.
2. **Confusing `401 Unauthorized` vs. `403 Forbidden`:**
   - **`401`** means **Unauthenticated**: *"I do not know who you are; please log in."*
   - **`403`** means **Unauthorized / Forbidden**: *"I know who you are, but you do not have permission to access this resource."*
3. **Misusing `404 Not Found` for Empty Collections:**
   When `GET /tasks?tag=work` finds no tasks, return `200 OK` with `[]` or `{"items": []}`. Returning `404` indicates the endpoint itself does not exist.
4. **Using `500` for Validation Errors:**
   If a user submits an invalid phone number, returning `500 Internal Server Error` is incorrect. That is a client error (`422` or `400`), not a server failure.
5. **Inventing Custom Status Codes:**
   Do not invent non-standard status codes like `499` or `701`. Adhere to RFC standards.

## 5. How do I know I understand it?

Test your decision-making across these common scenarios:

| Scenario | Correct HTTP Status | Key Reason |
| :--- | :--- | :--- |
| Task created successfully | `201 Created` | Creation must return 201 + `Location` header. |
| User deletes a task | `204 No Content` | Action succeeded; no body needed in response. |
| User searches for non-existent tag | `200 OK` with `[]` | Collection exists; it just has 0 matching elements. |
| Malformed JSON sent | `400 Bad Request` | Parser cannot decode the body. |
| Valid JSON, but `age: -5` | `422 Unprocessable Content` | Syntax is valid; business/schema validation failed. |
| Request lacks JWT token | `401 Unauthorized` | Identity missing; requires `WWW-Authenticate`. |
| Normal user hits Admin route | `403 Forbidden` | Identity known; permissions insufficient. |
| User registers existing email | `409 Conflict` | Conflicts with current database state. |
| Database connection pool exhausted | `500` or `503` | Server cannot fulfill request due to internal capacity. |
| Async video encoding queued | `202 Accepted` | Processing accepted, but not yet complete. |
