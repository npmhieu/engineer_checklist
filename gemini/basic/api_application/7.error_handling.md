# Error Handling

[Lesson Index](../../README.md) · Previous: [Business Validation](6.business_validation.md) · Next: [HTTP Status Codes](8.http_status_codes.md)

---

## 1. What is it?

**Error Handling** is the systematic strategy by which a backend application intercepts, classifies, processes, logs, and communicates failures that occur during request execution.

In a professional backend, failures are bifurcated into two distinct categories:

1. **Operational / Expected Errors:**
   Normal, expected outcomes of an application interacting with users or dependencies.
   - *Examples:* Invalid JSON, validation failures, entity not found, expired tokens, business rule conflicts (e.g., insufficient funds).
   - *Strategy:* Handled gracefully, mapped to appropriate `4xx` HTTP codes, and returned with clear, actionable client error messages.
2. **Programmer / Unexpected Errors (Defects):**
   Unanticipated bugs, infrastructure disruptions, or system failures.
   - *Examples:* Unhandled null pointer exceptions, database connection timeouts, syntax errors in dynamic queries, hardware/memory exhaustion.
   - *Strategy:* Caught by global error boundaries, logged with full stack traces and correlation IDs, and returned to clients as a sanitized `500 Internal Server Error`.

---

## 2. Why do we need it?

1. **Information Security (Preventing Data Leaks):**
   Without centralized error handling, servers default to outputting raw stack traces, SQL queries, table names, and internal file paths directly to clients. Attackers use this reconnaissance to execute targeted exploits (e.g., SQL injection, path traversal).
2. **Predictable Client Integration:**
   Frontend and mobile apps need consistent error structures with machine-readable error codes (e.g., `INSUFFICIENT_FUNDS`) to drive conditional UI flows (such as prompting the user to top up their balance).
3. **Debugging & Observability:**
   When an incident occurs in production, operators must be able to correlate a user's failure with backend log entries instantly using a unique **Correlation / Request ID**.
4. **State Consistency & Resource Management:**
   Proper error handling ensures database transactions are rolled back when failures occur and system resources (file handles, sockets, database connections) are released.

## 3. How to apply / implement / use it?

### A. Use a Standardized Error Response Envelope

Standardize your API error schema across all endpoints. You can use a custom clean format or the industry-standard **RFC 9457 (Problem Details for HTTP APIs)**.

#### RFC 9457 Problem Details Example:
```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json
X-Request-ID: req_9a8b7c6d

{
  "type": "https://api.example.com/errors/task-already-archived",
  "title": "Task State Conflict",
  "status": 409,
  "detail": "Task 'tsk_101' is archived and cannot be renamed.",
  "instance": "/api/v1/tasks/tsk_101",
  "code": "TASK_ARCHIVED",
  "requestId": "req_9a8b7c6d"
}
```

### B. Define a Domain/App Error Hierarchy

Create distinct application error classes rather than throwing generic `new Error()`:

```typescript
// Base Application Error
export abstract class AppError extends Error {
  public abstract readonly statusCode: number;
  public abstract readonly errorCode: string;

  constructor(message: string, public readonly isOperational: boolean = true) {
    super(message);
    Object.setPrototypeOf(this, new.target.prototype);
  }
}

export class NotFoundError extends AppError {
  public readonly statusCode = 404;
  public readonly errorCode = "RESOURCE_NOT_FOUND";
}

export class ConflictError extends AppError {
  public readonly statusCode = 409;
  public readonly errorCode = "STATE_CONFLICT";
}

export class ValidationFailedError extends AppError {
  public readonly statusCode = 422;
  public readonly errorCode = "VALIDATION_FAILED";
  constructor(message: string, public readonly details: any[]) {
    super(message);
  }
}
```

### C. Implement a Global Error Middleware / Boundary

Ensure all unhandled errors converge at a single, centralized error handler:

```typescript
export function globalErrorHandler(
  err: Error,
  req: Request,
  res: Response,
  next: NextFunction
) {
  const requestId = (req.headers["x-request-id"] as string) || crypto.randomUUID();

  // 1. Operational, expected error (Safe to expose message)
  if (err instanceof AppError && err.isOperational) {
    return res.status(err.statusCode).json({
      type: `https://api.example.com/errors/${err.errorCode.toLowerCase()}`,
      title: err.name,
      status: err.statusCode,
      detail: err.message,
      code: err.errorCode,
      requestId,
      ...(err instanceof ValidationFailedError ? { details: err.details } : {})
    });
  }

  // 2. Unexpected Programmer Error (Do NOT leak details to client!)
  // Log the complete error stack internally
  logger.error("Unhandled Internal Server Error", {
    requestId,
    url: req.originalUrl,
    method: req.method,
    stack: err.stack,
    error: err.message,
  });

  // Return sanitized generic response
  return res.status(500).json({
    type: "https://api.example.com/errors/internal-error",
    title: "Internal Server Error",
    status: 500,
    detail: "An unexpected error occurred on our servers. Please contact support with the requestId.",
    code: "INTERNAL_SERVER_ERROR",
    requestId,
  });
}
```

### D. Always Clean Up State and Transactions

```typescript
const tx = await db.beginTransaction();
try {
  await orderRepo.create(tx, order);
  await paymentService.charge(order.total);
  await tx.commit();
} catch (error) {
  await tx.rollback(); // Crucial: Roll back on ANY error!
  throw error; // Re-throw to be caught by global boundary
}
```

## 4. When should I NOT use this? (Trade-offs and Anti-patterns)

### When NOT to use Exceptions for Control Flow
- **Do not use exceptions for expected business branches that happen continuously.**
  *Example:* Throwing a `UserNotFoundException` when checking whether a username is available during registration.
  *Trade-off:* Generating stack traces in languages like Java, C#, or Node.js has non-trivial CPU and memory cost. For high-frequency, non-exceptional checks, prefer functional `Result<T, E>` / `Either` types or returning `null`/boolean.

### Anti-Patterns to Avoid
1. **The "Catch-All and Return 200" Pattern:**
   ```typescript
   // ❌ CATASTROPHIC ANTI-PATTERN
   try {
     doDatabaseWrite();
     return res.json({ success: true });
   } catch (e) {
     return res.json({ success: false, error: e.message }); // Returns HTTP 200!
   }
   ```
   *Why this is terrible:* Proxies, CDNs, load balancers, and monitoring tools view this as a 100% successful transaction. Metric dashboards show 0% error rates while users cannot use the system.
2. **Swallowing Errors (Silent Failures):**
   Catching an error and doing nothing (`catch (e) {}`). The failure disappears into a black hole; nobody knows data was lost until users complain.
3. **Leaking Stack Traces to the Client:**
   Directly returning `res.status(500).send(err.stack)`. This is a critical security vulnerability.
4. **Duplicate Logging (Log Noise):**
   Logging the same error at every level of the call stack (Repo logs, Service logs, Controller logs, Middleware logs). Log an error **once** at the boundary where it is handled or resolved.

## 5. How do I know I understand it?

You understand error handling when you can:

1. **Distinguish Operational vs. Programmer Errors:** Give 3 real examples of each and explain how their handling differs in logs and responses.
2. **Implement Correlation Tracking:** Demonstrate how a `requestId` generated on request arrival appears in the client response payload and connects directly to backend log aggregators (e.g., Datadog, CloudWatch).
3. **Safeguard Transactions:** Explain what happens to an uncommitted database transaction when an unhandled exception occurs inside a handler.
4. **Design Clean Error Envelopes:** Implement RFC 9457 or consistent JSON error envelopes that separate machine-readable codes (`code`) from human-readable descriptions (`detail`).
