---

## 1. What is it?

**CRUD** stands for **Create, Read, Update, and Delete**—the four foundational data manipulation operations for any persistent entity in software systems.

In backend systems:
- A **Resource** is a domain concept or entity exposed by the API (e.g., `Task`, `User`, `Invoice`, `Project`).
- A resource is **not** strictly a 1:1 mirror of a single database table. For example, a `Task` resource might aggregate fields from a `tasks` table, an `attachments` table, and an `assignees` table.
- **CRUD Operations** define how clients manage the lifecycle of that resource over standard interfaces.

| Operation | SQL Equivalent | HTTP Verb (REST) | Typical URI | Description |
| :--- | :--- | :--- | :--- | :--- |
| **Create** | `INSERT` | `POST` | `/tasks` | Creates a new resource instance |
| **Read (List)** | `SELECT` | `GET` | `/tasks` | Retrieves a collection of resources (with filtering/paging) |
| **Read (Single)**| `SELECT` | `GET` | `/tasks/{id}` | Retrieves a specific resource by identifier |
| **Update** | `UPDATE` | `PUT` / `PATCH` | `/tasks/{id}` | Replaces (`PUT`) or partially modifies (`PATCH`) the resource |
| **Delete** | `DELETE` / `UPDATE` | `DELETE` | `/tasks/{id}` | Removes or soft-deletes the resource |

---

## 2. Why do we need it?

1. **Standardized Lifecycle & Predictability:**
   Virtually all business applications revolve around maintaining records over time. CRUD establishes a uniform mental model: if an engineer or client application understands how to manage one entity, they can manage any entity in the system.
2. **Clear Authorization & Boundary Mapping:**
   CRUD maps cleanly to fine-grained security policies:
   - Who is allowed to create records? (`POST`)
   - Who has visibility over them? (`GET`)
   - Which specific attributes are editable, and by whom? (`PATCH`)
   - Who has permission to remove records? (`DELETE`)
3. **Decoupling Public Representation from Persistence:**
   Exposing a clean CRUD interface allows backend engineers to refactor schemas, migrate databases, add caching layers, or partition data without altering how clients interact with the resource.

## 3. How to apply / implement / use it?

### A. Resource Lifecycle Specification

Consider a `Task` resource. We define its public JSON shape:

```json
{
  "id": "tsk_01H1",
  "title": "Build CRUD API",
  "status": "IN_PROGRESS",
  "priority": "HIGH",
  "createdAt": "2026-10-16T10:00:00Z",
  "updatedAt": "2026-10-16T10:05:00Z"
}
```

Notice the server controls `id`, `createdAt`, and `updatedAt`. The client can only supply fields it is authorized to set.

### B. Standard Endpoint Mapping

1. **Create (`POST /tasks`):**
   - **Input:** JSON payload with initial parameters: `{"title": "Build CRUD API", "priority": "HIGH"}`.
   - **Output:** `201 Created` with a `Location: /tasks/tsk_01H1` header and the created resource body.
2. **Read Collection (`GET /tasks?status=IN_PROGRESS&limit=20`):**
   - Returns `200 OK` with an array of tasks (or a paginated envelope).
   - If no tasks exist, return `200 OK` with `[]` or `{"items": []}`, **not** a `404 Not Found`.
3. **Read Single (`GET /tasks/{id}`):**
   - Returns `200 OK` with the task object.
   - If `{id}` does not exist, return `404 Not Found`.
4. **Update (`PATCH /tasks/{id}`):**
   - Updates specified fields: `{"status": "DONE"}`.
   - Returns `200 OK` with the updated resource, or `204 No Content`.
5. **Delete (`DELETE /tasks/{id}`):**
   - Returns `204 No Content` (idempotent removal).
   - Subsequent `GET /tasks/{id}` returns `404 Not Found`.

### C. Backend Architecture Implementation Pattern

Maintain clear boundaries between your HTTP layer, Application Service, and Persistence/Repository layer:

```typescript
// 1. Controller / Route Handler: Translates HTTP to DTOs
async function updateTaskHandler(req: Request, res: Response) {
  const taskId = req.params.id;
  const updateDto = validateTaskUpdate(req.body);
  const currentUser = req.user;

  const updatedTask = await taskService.updateTask(currentUser, taskId, updateDto);
  return res.status(200).json(updatedTask);
}

// 2. Application Service: Business Rules & Transactions
class TaskService {
  async updateTask(actor: User, taskId: string, dto: UpdateTaskDto) {
    return await db.transaction(async (tx) => {
      // Fetch with row-lock or check version for concurrency control
      const task = await taskRepo.findByIdForUpdate(tx, taskId);
      if (!task) {
        throw new NotFoundError(`Task ${taskId} not found`);
      }

      // Check authorization
      if (task.ownerId !== actor.id && !actor.hasRole("ADMIN")) {
        throw new ForbiddenError("You do not have permission to modify this task");
      }

      // Enforce domain invariant
      if (task.status === "ARCHIVED") {
        throw new ConflictError("Archived tasks cannot be updated");
      }

      // Apply changes and persist
      task.applyUpdates(dto);
      await taskRepo.save(tx, task);

      return task.toDTO();
    });
  }
}
```

### D. Hard Deletion vs. Soft Deletion

When implementing `DELETE`, choose deliberately:
- **Hard Deletion (`DELETE FROM tasks WHERE id = ?`):** Physically purges the record. Required for privacy compliance (e.g., GDPR "Right to be Forgotten"). Risks breaking foreign key relationships if cascades are misconfigured.
- **Soft Deletion (`UPDATE tasks SET deleted_at = NOW() WHERE id = ?`):** Keeps data for auditing and recovery.
  *Gotchas:* Every query must filter `WHERE deleted_at IS NULL`, unique indexes must account for deleted records (e.g., partial unique index `WHERE deleted_at IS NULL`), and soft-deleted data still incurs storage and privacy obligations.

## 4. When should I NOT use this? (Trade-offs and Anti-patterns)

### When NOT to use simple CRUD
1. **Complex Workflows & State Machines:**
   Real-world domains often feature strict, irreversible state transitions (e.g., `OrderPlaced` ➔ `PaymentProcessing` ➔ `Shipped` ➔ `Delivered`).
   - *Trade-off:* Exposing an unrestricted `PATCH /orders/123 {"status": "DELIVERED"}` bypasses payment verification, stock decrement, and notification dispatches. Use explicit action endpoints or commands: `POST /orders/123/shipments` or `POST /orders/123/cancel`.
2. **High-Throughput Append-Only / Event Systems:**
   Systems dealing with IoT sensor telemetry, financial ledgers, or audit trails should never support generic update/delete operations. Use append-only event streams (Event Sourcing / Log-oriented storage).
3. **Complex Aggregations & Search Queries:**
   Searching across dozens of facets, fuzzy matching, and deep relational joins often perform poorly through standard CRUD query parameters. Prefer specialized search endpoints (e.g., Elasticsearch, GraphQL, or CQRS Read Models).

### Anti-Patterns to Avoid
- **Database Mirroring (Anemic CRUD):** Blindly generating 1:1 endpoints for every database table and passing incoming JSON directly to ORM `.save()`. This invites Mass Assignment Vulnerabilities (e.g., an attacker submits `{"isAdmin": true}` in a user update request).
- **CRUD Over-Abstraction:** Creating generic repository/service base classes (`BaseCrudController<T>`) before understanding business requirements.
- **Ignoring Concurrency (Lost Updates):** Two users open `task 42` simultaneously. User A edits title; User B edits status. The last write silently overwrites the previous one. Use optimistic locking (`version` column or `ETag`/`If-Match`) or pessimistic locks (`SELECT FOR UPDATE`).

## 5. How do I know I understand it?

You truly understand CRUD when you can answer and demonstrate:

1. **The Empty Collection Rule:** Why does `GET /tasks` with zero results return `200 OK` with an empty array `[]`, while `GET /tasks/9999` returns `404 Not Found`? *(Because the collection resource exists and is empty, but the individual resource does not exist).*
2. **Idempotency of Deletions:** Why does calling `DELETE /tasks/42` twice produce the same server-state outcome, even if the second response returns `404` or `204`?
3. **Mass Assignment Prevention:** How do you guarantee a client cannot maliciously update `ownerId`, `id`, or `created_at` when updating a resource?
4. **Concurrency Handling:** How would you prevent two simultaneous updates to the same resource from clobbering each other?
