## 1. What is it?

**Pagination** is the mechanism of dividing a large dataset into discrete, manageable chunks ("pages") returned across multiple sequential HTTP requests.

Without pagination, querying a collection with 500,000 records would attempt to serialize and transfer all records in a single payload, exhausting database memory, network bandwidth, and client rendering capacity.

There are two primary architectural paradigms for implementing pagination in backend systems:

| Dimension | Offset-Based Pagination | Cursor / Keyset Pagination |
| :--- | :--- | :--- |
| **Query Parameters** | `?page=3&limit=20` or `?offset=40&limit=20` | `?cursor=eyJpZCI6MTIzfQ&limit=20` |
| **SQL Implementation** | `LIMIT 20 OFFSET 40` | `WHERE (created_at, id) < ($cur_time, $cur_id) ORDER BY created_at DESC, id DESC LIMIT 21` |
| **Deep Page Performance** | $O(N)$ — Database must scan and discard $N$ rows before returning results. | $O(1)$ — Database seeks directly to the indexed cursor via B-Tree lookup. |
| **Data Drift (Skips / Duplicates)** | **High Risk:** New inserts/deletes shift rows between pages while user is reading. | **Resistant:** Reads resume strictly from the last seen entity pointer. |
| **Random Page Navigation** | Native: Can jump directly to "Page 15" or "Last Page". | Difficult: Can only navigate forward or backward incrementally. |
| **Total Count Requirement** | Usually requires expensive `SELECT COUNT(*)` to calculate `total_pages`. | Does not require total count; checks `has_more` using `LIMIT + 1`. |
| **Best Used For** | Traditional admin dashboards, small/static datasets (< 50k rows). | Infinite scrolls, mobile feeds, public APIs, massive datasets. |

---

## 2. Why do we need it?

1. **Predictable Memory & Latency (Bounded Execution):**
   Caps response size, memory allocation, and serialization time to a strictly bounded maximum per HTTP request.
2. **Database Protection:**
   Prevents accidental or malicious queries from executing unbounded table scans, preserving database connection pool health.
3. **Bandwidth & Network Efficiency:**
   Transfers small payloads (typically 10KB–100KB) instead of tens of megabytes, speeding up Time to First Byte (TTFB).
4. **Client Stability:**
   Browsers and mobile devices cannot instantiate hundreds of thousands of UI elements or DOM nodes without UI freezes and memory crashes.

## 3. How to apply / implement / use it?

### A. Response Envelope Patterns

API responses should include pagination metadata alongside the data items.

#### 1. Offset Pagination Response Envelope
```json
{
  "data": [
    { "id": "prod_1", "name": "Mechanical Keyboard" }
  ],
  "pagination": {
    "page": 2,
    "limit": 20,
    "total_items": 1540,
    "total_pages": 77
  }
}
```

#### 2. Cursor Pagination Response Envelope
```json
{
  "data": [
    { "id": "prod_20", "name": "Ergonomic Mouse", "created_at": "2026-03-15T10:30:00Z" }
  ],
  "pagination": {
    "limit": 20,
    "has_more": true,
    "next_cursor": "ZXlKallXTmpZV3RsZEdGMGN5STZNREF3TVNJc0luTmtJanB4ZFdsdVpYSjFjMkZ1WkdGMVpYTjBJam8xTmpRd05EQXlOell4TWpFd2ZROjoxMjM="
  }
}
```

Alternatively, standard HTTP `Link` headers can be used (RFC 8288):
```http
Link: <https://api.example.com/v1/items?cursor=abc1234>; rel="next"
```

### B. Production-Grade Cursor / Keyset Implementation

Here is a complete pattern in TypeScript using an opaque base64 cursor with the **"Limit + 1"** optimization (fetching one extra row to determine `has_more` without running a costly `COUNT(*)`):

```typescript
import { Request, Response } from "express";
import { z } from "zod";

// 1. Boundary schema validation: Cap limits strictly
const PaginationQuerySchema = z.object({
  limit: z.coerce.number().int().min(1).max(100).default(20),
  cursor: z.string().optional(),
});

interface CursorPayload {
  createdAt: string;
  id: string;
}

// Encode/Decode opaque cursors to decouple clients from internal storage details
function encodeCursor(payload: CursorPayload): string {
  return Buffer.from(JSON.stringify(payload)).toString("base64url");
}

function decodeCursor(cursorStr: string): CursorPayload | null {
  try {
    const raw = Buffer.from(cursorStr, "base64url").toString("utf8");
    return JSON.parse(raw);
  } catch {
    return null;
  }
}

export async function listAuditLogs(req: Request, res: Response) {
  const parsed = PaginationQuerySchema.safeParse(req.query);
  if (!parsed.success) {
    return res.status(422).json({
      title: "Invalid Pagination Parameters",
      errors: parsed.error.issues,
    });
  }

  const { limit, cursor } = parsed.data;
  let query = db("audit_logs")
    .select("id", "action", "created_at")
    .orderBy("created_at", "DESC")
    .orderBy("id", "DESC"); // Tie-breaker for identical timestamps

  if (cursor) {
    const decoded = decodeCursor(cursor);
    if (!decoded) {
      return res.status(400).json({ title: "Bad Request", detail: "Invalid cursor token" });
    }

    // Keyset condition: row values smaller than the cursor point
    query = query.where(function() {
      this.where("created_at", "<", decoded.createdAt)
        .orWhere(function() {
          this.where("created_at", "=", decoded.createdAt)
            .andWhere("id", "<", decoded.id);
        });
    });
  }

  // Fetch limit + 1 items to check if another page exists without running COUNT(*)
  const rows = await query.limit(limit + 1);

  const hasMore = rows.length > limit;
  const items = hasMore ? rows.slice(0, limit) : rows;

  let nextCursor: string | null = null;
  if (hasMore && items.length > 0) {
    const lastItem = items[items.length - 1];
    nextCursor = encodeCursor({
      createdAt: lastItem.created_at.toISOString(),
      id: lastItem.id,
    });
  }

  return res.status(200).json({
    data: items,
    pagination: {
      limit,
      has_more: hasMore,
      next_cursor: nextCursor,
    },
  });
}
```

### C. Database Indexing Requirement

For cursor pagination on `(created_at, id)` to execute at $O(1)$ speed, you must create a matching composite index:

```sql
CREATE INDEX idx_audit_logs_pagination ON audit_logs (created_at DESC, id DESC);
```

The database engine traverses the B-Tree directly to the index entry matching `(cursor_time, cursor_id)` and reads the next `LIMIT` entries sequentially, eliminating table scans completely.

## 4. When should I NOT use this? (Trade-offs and Anti-patterns)

### When to Use Offset vs. Cursor Pagination

- **Use Offset Pagination ONLY when:**
  - The UI explicitly requires "Jump to page N" (e.g., standard back-office admin tables).
  - The total dataset size is small and predictable (< 50,000 rows).
  - Data modifications are infrequent (low write volume).
- **Use Cursor / Keyset Pagination when:**
  - Building mobile infinite scroll or social feeds.
  - Datasets exceed 100,000 rows.
  - High-velocity inserts or deletes occur continuously.
  - Exposing high-throughput public APIs (e.g., Stripe, GitHub, Slack).

### Anti-Patterns to Avoid

1. **Unbounded Limits (No Maximum Bound):**
   ```typescript
   // ❌ CRITICAL SECURITY FLAW: Allows ?limit=99999999
   const limit = req.query.limit || 20;
   ```
   A client sending `?limit=1000000` will crash your server or tie up database connections. Always clamp limits: `Math.min(limit, 100)`.
2. **Deep Offset Performance Collapse:**
   ```sql
   -- ❌ KILLS PERFORMANCE: Reads and discards 10,000,000 rows before returning 20
   SELECT * FROM transactions ORDER BY created_at DESC LIMIT 20 OFFSET 10000000;
   ```
3. **The "Page Drift" / Missing Items Bug in Offset Pagination:**
   - User views Page 1 (`rows 1 to 20`).
   - Another user inserts 5 new records.
   - User clicks Page 2 (`OFFSET 20`).
   - The original row #20 is pushed into position #21 and appears again on Page 2 (duplicate), while row #21 was pushed to #26 and skipped entirely!
4. **Running `SELECT COUNT(*)` on Every Cursor Request:**
   Running `COUNT(*)` over multi-million row relational tables forces expensive index scans. Do not compute total counts on high-throughput or cursor-paginated endpoints.
5. **Non-Deterministic Ordering (Missing Tie-Breaker):**
   Sorting by a non-unique column (like `created_at` or `status`) without adding a unique column (like `id`) causes unpredictable ordering between pages.

## 5. How do I know I understand it?

You understand pagination when you can evaluate and design the right pagination strategy for these scenarios:

| Scenario | Anti-Pattern / Mistake | Production-Grade Solution |
| :--- | :--- | :--- |
| Twitter/X style activity feed with 500 new posts per minute | Using `?page=2&limit=20` resulting in duplicate posts appearing on scroll. | Use Keyset/Cursor pagination (`WHERE id < $last_id`). Guaranteed zero duplicates or skipped items. |
| Admin panel with 3,000 invoices needing "Page 1, 2, ... 15" buttons | Using cursor pagination which cannot jump directly to arbitrary page numbers. | Use Offset pagination (`LIMIT 20 OFFSET 40`) with a clamped max limit and cached count. |
| Client requests `GET /transactions?limit=500000` | Fetching and JSON-serializing all 500,000 transactions. | Boundary validator rejects with `422` or clamps `limit` to `100`. |
| API needs to indicate if more pages exist | Executing a second query `SELECT COUNT(*) FROM table` on a 20M row table. | Fetch `LIMIT + 1` rows in a single query; if `rows.length > limit`, set `has_more = true`. |
| Transparent cursor token exposing internal schema | Passing raw SQL strings or unencrypted internal IDs directly in query parameters. | Base64-url encode or encrypt the cursor payload into an opaque token. |
