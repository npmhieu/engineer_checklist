## 1. What is it?

An **API (Application Programming Interface)** is a formalized boundary and contract that specifies how different software components communicate. In the context of backend web systems, an API typically refers to a **Network API** exposing server capabilities to clients.

The **Request-Response cycle** is a synchronous communication pattern where:
1. The **Client** creates and transmits an explicit request message to the server, detailing the intended action and providing required parameters.
2. The **Server** processes the request (routing, authenticating, validating, executing domain logic, and persisting changes).
3. The **Server** returns a definitive response message containing the status code, relevant headers, and data or error details.
4. The cycle concludes.

```text
┌──────────────┐         1. HTTP Request (Method, URL, Headers, Body)       ┌──────────────┐
│              │ ─────────────────────────────────────────────────────────> │              │
│    Client    │                                                            │    Server    │
│ (Web/Mobile) │ <───────────────────────────────────────────────────────── │  (Backend)   │
└──────────────┘         2. HTTP Response (Status, Headers, Body)           └──────────────┘
```

### The API Contract

An API contract defines:
- **Endpoints (URL + Method):** e.g., `POST /api/v1/users`
- **Headers:** e.g., `Authorization: Bearer <token>`, `Content-Type: application/json`
- **Request Parameters / Payload:** Query params, route params, JSON request body schema.
- **Success Response Structure:** HTTP Status (e.g. `200 OK`, `201 Created`) and payload structure.
- **Error Response Structure:** Standard error format with machine-readable error codes and human-readable messages.

---

## 2. Why do we need it?

1. **Decoupling and Abstraction:**
   The client does not need to know the database structure, server programming language, caching tier, or underlying infrastructure. The API hides implementation details behind a clean, stable interface.
2. **Standardization & Independent Evolution:**
   Teams working on the frontend (React, iOS, Android) and backend can work in parallel once the API contract is established. The backend can rewrite its internal storage from SQL to NoSQL without breaking clients as long as the contract remains unchanged.
3. **Security Boundary:**
   Clients are untrusted entities. Directly exposing databases or internal services over the internet is disastrous. The API serves as a guarded gateway enforcing authentication, authorization, rate limiting, and data sanitization.
4. **Predictability:**
   A well-defined request-response cycle ensures both parties know when an operation begins, whether it succeeded or failed, and how to interpret failure scenarios.

## 3. How to apply / implement / use it?

### A. Designing the API Contract First

Before writing backend code, clearly document the request and response shapes.

#### Request Example
```http
POST /api/v1/tasks HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json

{
  "title": "Complete backend checklist",
  "priority": "HIGH"
}
```

#### Success Response (`201 Created`)
```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/v1/tasks/task_101

{
  "id": "task_101",
  "title": "Complete backend checklist",
  "priority": "HIGH",
  "isCompleted": false,
  "createdAt": "2026-10-14T10:00:00Z"
}
```

#### Error Response (`422 Unprocessable Content` / `400 Bad Request`)
Consistency in error payloads is crucial for client resilience:
```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "The payload contains invalid field values.",
    "details": [
      {
        "field": "title",
        "reason": "Title must be between 3 and 100 characters."
      }
    ]
  }
}
```

### B. The Backend Request-Response Processing Pipeline

When implementing an endpoint, code should follow a clean, layered pipeline:

```text
1. Router / Dispatcher
   └── Matches route & HTTP method

2. Middleware / Interceptors
   ├── Request logging & correlation IDs (X-Request-ID)
   ├── Rate limiting
   ├── Authentication (verifying JWT / session)
   └── Authorization (checking RBAC / permissions)

3. Controller / Handler Layer
   ├── Deserializes input (JSON to DTO / Struct)
   └── Validates schema (types, required fields, constraints)

4. Service / Business Logic Layer
   ├── Enforces domain rules
   └── Coordinates transactions

5. Data Access / Repository Layer
   └── Queries / updates Database or external services

6. Response Formatter
   └── Maps internal domain entities to external public DTOs
```

### C. Handler Pseudocode Pattern

```typescript
// Controller / Route Handler
async function handleCreateTask(req: HttpRequest): Promise<HttpResponse> {
  // 1. Content Negotiation check
  if (req.headers['content-type'] !== 'application/json') {
    return HttpResponse.status(415).json({
      error: { code: 'UNSUPPORTED_MEDIA_TYPE', message: 'Content-Type must be application/json' }
    });
  }

  // 2. Syntactic & Input Validation
  const validationResult = validateCreateTaskInput(req.body);
  if (!validationResult.isValid) {
    return HttpResponse.status(422).json({
      error: {
        code: 'VALIDATION_FAILED',
        message: 'Invalid input fields',
        details: validationResult.errors
      }
    });
  }

  try {
    // 3. Delegate to Domain/Service layer
    const currentUser = req.user;
    const newTask = await taskService.createTask(currentUser.id, validationResult.data);

    // 4. Return success response
    return HttpResponse.status(201)
      .setHeader('Location', `/api/v1/tasks/${newTask.id}`)
      .json(newTask);

  } catch (err) {
    if (err instanceof DuplicateTitleException) {
      return HttpResponse.status(409).json({
        error: { code: 'TASK_ALREADY_EXISTS', message: err.message }
      });
    }

    // 5. Unhandled server error
    logger.error('Failed to create task', err);
    return HttpResponse.status(500).json({
      error: { code: 'INTERNAL_ERROR', message: 'An unexpected error occurred' }
    });
  }
}
```

### D. Limitations of Synchronous Request-Response

- **Blocking / High Latency:** If an operation takes 30 seconds (e.g., video processing, massive PDF generation), holding a synchronous HTTP connection open causes client timeouts, thread starvation, and poor reliability.
- **Solution for Long-Running Tasks:**
  - Respond immediately with `202 Accepted` and a job status URI (`Location: /api/v1/jobs/job_123`).
  - Process the heavy task asynchronously via background workers or queues.
  - Let the client poll the job URI or notify the client via Webhooks/WebSockets.
