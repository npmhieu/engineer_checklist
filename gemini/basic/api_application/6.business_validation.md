# Business Validation

[Lesson Index](../../README.md) · Previous: [Request Validation](5.request_validation.md) · Next: [Error Handling](7.error_handling.md)

---

## 1. What is it?

**Business Validation** (also known as Domain Validation) enforces the business rules, invariants, and constraints that govern whether an operation is permissible within the domain logic of an application.

Unlike request validation (which only inspects the syntax and data types of incoming payloads in isolation), business validation depends on **business rules, domain models, and existing system state**.

### Key Concepts

- **Domain Invariant:** A business rule or condition that must remain true at all times throughout the system lifecycle.
  - *Example:* "A bank account balance cannot drop below zero."
  - *Example:* "An order cannot be refunded if it has not yet been paid."
  - *Example:* "A task cannot be completed if it has unfinished prerequisite dependencies."
- **State-Dependent Validation:** Checks where validity depends on what is currently stored in the database or cache.
  - *Example:* "Is this coupon code expired or has its redemption limit been reached?"
  - *Example:* "Is this seat still available for reservation?"

---

## 2. Why do we need it?

1. **Protecting Core Domain Integrity:**
   Syntactically perfect data can still violate company policies or corrupt business logic. A request `{"transferAmount": 5000}` is completely valid syntactically, but if the user only has \$100 in their account, processing it causes financial loss.
2. **Channel-Agnostic Rule Enforcement:**
   A production backend receives requests from multiple entry points: HTTP REST endpoints, GraphQL APIs, asynchronous queue workers (RabbitMQ/Kafka), scheduled cron jobs, and internal admin CLIs. If business rules are placed only inside an HTTP controller, all other entry points will bypass them.
3. **Preventing Race Conditions & Concurrency Violations:**
   When two users attempt to purchase the last available item simultaneously, business validation ensures that only one succeeds, while the other is rejected gracefully.

## 3. How to apply / implement / use it?

### A. Placement in Clean Architecture

Business validation belongs in the **Domain Model (Entities / Aggregates)** or **Domain Services**, **never** in HTTP controllers or database triggers alone.

```text
HTTP Controller   ──> Validates Request Schema (types, required fields)
       │
       ▼
Application Service ─> Loads Entities from Repository within a Transaction
       │
       ▼
Domain Entity     ──> Enforces Invariants & Transitions (Throws Domain Exceptions)
       │
       ▼
Repository        ──> Commits Transaction & Atomic DB Constraints
```

### B. Implementation Pattern: Rich Domain Model

```typescript
// Domain Entity enforcing invariants internally
export class Order {
  private id: string;
  private status: "PENDING" | "PAID" | "SHIPPED" | "CANCELLED";
  private items: OrderItem[];

  constructor(id: string, status: "PENDING" | "PAID" | "SHIPPED" | "CANCELLED", items: OrderItem[]) {
    this.id = id;
    this.status = status;
    this.items = items;
  }

  // Domain Method encapsulating state transition and business validation
  public cancel(reason: string): void {
    if (this.status === "SHIPPED") {
      throw new BusinessRuleViolationException(
        "ORDER_ALREADY_SHIPPED",
        "Cannot cancel an order that has already been shipped."
      );
    }

    if (this.status === "CANCELLED") {
      throw new BusinessRuleViolationException(
        "ORDER_ALREADY_CANCELLED",
        "This order has already been cancelled."
      );
    }

    this.status = "CANCELLED";
  }
}
```

### C. Concurrency-Safe Business Validation

A classic mistake is **Time-of-Check to Time-of-Use (TOCTOU)**:
```typescript
// ❌ WRONG: Vulnerable to race condition!
const seat = await seatRepo.findById(seatId);
if (seat.isBooked) {
  throw new ConflictError("Seat is already booked");
}
// Between the check above and the write below, another request can book the seat!
await seatRepo.bookSeat(seatId, userId);
```

#### Safe Strategies:

1. **Atomic Conditional Updates (Single DB Query):**
   ```sql
   UPDATE seats
   SET is_booked = TRUE, booked_by_user_id = :userId
   WHERE id = :seatId AND is_booked = FALSE;
   ```
   Check the rows affected count. If `rowsAffected === 0`, the seat was taken concurrently.

2. **Pessimistic Locking (`SELECT ... FOR UPDATE`):**
   ```typescript
   await db.transaction(async (tx) => {
     const seat = await tx.query("SELECT * FROM seats WHERE id = $1 FOR UPDATE", [seatId]);
     if (seat.is_booked) {
       throw new ConflictError("Seat already booked");
     }
     await tx.query("UPDATE seats SET is_booked = TRUE, booked_by = $2 WHERE id = $1", [seatId, userId]);
   });
   ```

3. **Optimistic Locking (`version` column):**
   ```sql
   UPDATE accounts
   SET balance = balance - 100, version = version + 1
   WHERE id = :accountId AND version = :expectedVersion;
   ```

4. **Database-Level Unique Constraints:**
   Never rely solely on `SELECT count(*) WHERE email = ?` to validate uniqueness. Always back it up with a database `UNIQUE KEY (email)` constraint to catch concurrent writes.

## 4. When should I NOT use this? (Trade-offs and Anti-patterns)

### When NOT to use heavy Business Validation
- **Simple, Stateless Data Pipelines:**
  ETL pipelines, log ingestion, or telemetry storage where data is append-only and raw data needs to be preserved as-is for downstream processing.
- **Premature Workflow Engines:**
  For simple apps with only 2–3 rules, avoid adopting massive business rule engines (e.g., Drools, Camunda) or over-engineered DDD aggregate root patterns when standard domain methods in services suffice.

### Anti-Patterns to Avoid
1. **Controller-Bound Validation:**
   Placing business logic like `if (user.role !== 'ADMIN')` or balance calculation inside Express/FastAPI route handlers. When a CLI script or worker runs, the rule is missed.
2. **"Check-Then-Act" without Transactions or Locks:**
   Querying state outside of an atomic write or transaction, leading to double-spends and overbooking under concurrent load.
3. **Leaking HTTP Status Codes into the Domain:**
   Throwing `new HttpError(409)` from a domain entity. The domain model should remain decoupled from HTTP; map domain exceptions (e.g., `OrderAlreadyShippedException`) to HTTP `409 Conflict` at the controller/middleware adapter boundary.
4. **Validating Stale Data via Slow External Microservices:**
   Making synchronous HTTP calls to 3 different remote services inside a database transaction to validate state. This holds database locks open, exhausting connection pools. Use reservation patterns (Sagas) or asynchronous event-driven checks.

## 5. How do I know I understand it?

You understand business validation when you can:

1. **Differentiate the Layers:** Confidently explain which validations happen before the database is touched (request validation) and which require transactional domain context (business validation).
2. **Prevent Race Conditions:** Write an inventory decrement or seat reservation handler that guarantees no overselling even when 1,000 concurrent requests arrive in the same millisecond.
3. **Decouple Domain from Web:** Demonstrate how domain entities enforce their invariants without importing HTTP libraries or referencing HTTP status codes.
4. **Translate Domain Failures:** Show how a custom domain error (`InsufficientFundsError`) cleanly maps to an HTTP `409 Conflict` or `422 Unprocessable Content` response envelope at the API boundary.
