# Idempotency Basics

## 1. What is it?

**Idempotency** is a mathematical and architectural property of an operation whereby performing it multiple times with the exact same input produces the exact same server-side side effect as performing it once:

$$f(f(x)) = f(x)$$

In HTTP APIs (standardized in RFC 9110), methods are categorized by their safety and natural idempotency:

| HTTP Method | Safe? (No state change) | Idempotent by Default? | Typical Behavior on Duplicate Request |
| :--- | :--- | :--- | :--- |
| **`GET`** | **Yes** | **Yes** | Returns the same resource representation; no server state altered. |
| **`HEAD`** | **Yes** | **Yes** | Returns identical headers; no server state altered. |
| **`OPTIONS`** | **Yes** | **Yes** | Returns allowed verbs/headers; no server state altered. |
| **`PUT`** | No | **Yes** | Replaces the entire resource state. Running `PUT /users/1` with `{ "age": 30 }` five times leaves the user's age as 30. |
| **`DELETE`** | No | **Yes** | Deletes the resource. First call removes it; subsequent calls leave it deleted (returns `204 No Content` or `404 Not Found`). |
| **`POST`** | No | **No** | Typically appends or creates new entities. Calling `POST /orders` five times creates five distinct orders. |
| **`PATCH`** | No | **Conditional** | Partial update. If setting a fixed value (`{ "status": "PAID" }`), it is idempotent. If appending (`{ "$push": { "tags": "new" } }` or `$inc`), it is non-idempotent. |

## 2. Why do we need it?

### The "Two Generals" Network Problem

Distributed networks are inherently unreliable. When a client sends an HTTP request to create an order or charge a credit card, three things can happen:

```
[ Client ] ──── 1. POST /payments ────> [ Server ]  (Request sent)
[ Client ] <─── 2. 200 OK (Charged) ─── [ Server ]  (Response delivered)
```

However, if the network connection drops at step 2 **after** the server successfully charged the card:
- The server successfully executed the transaction.
- The client timed out or received a network socket disconnect (`ECONNRESET`).
- The client does **not** know whether the request succeeded or failed.

```
[ Client ] ──── 1. POST /payments ────> [ Server ]  (Server charges card)
[ Client ] <─X─ (Network drops) ─────── [ Server ]  (Response lost!)
[ Client ] ──── 3. Retry POST? ───────> [ Server ]  (Without Idempotency: User is charged TWICE!)
```

Without idempotency, automated network retries, client-side button double-clicks, and message queue re-deliveries cause catastrophic duplicate mutations (e.g., duplicate charges, duplicate inventory reservations).

## 3. How to apply / implement / use it?

### A. The `Idempotency-Key` Pattern

For non-idempotent operations like `POST`, the industry standard pattern (popularized by Stripe, PayPal, and IETF draft `draft-ietf-httpapi-idempotency-key-header`) is the **Idempotency Key**.

1. The client generates a unique token (typically a UUID v4) before sending the request.
2. The client passes this token in an HTTP header:
   ```http
   POST /api/v1/charges HTTP/1.1
   Host: api.example.com
   Authorization: Bearer sk_live_xyz
   Idempotency-Key: 9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d
   Content-Type: application/json

   {
     "amount": 5000,
     "currency": "usd"
   }
   ```
3. If the request fails or times out, the client safely retries using the **exact same `Idempotency-Key`**.

### B. The Idempotency State Machine

The server enforces an atomic lifecycle for each key scoped to the authenticated user/tenant:

```
                  ┌───────────────────────────────┐
                  │ Request with Idempotency-Key  │
                  └──────────────┬────────────────┘
                                 │
                     Does key exist in store?
                     ┌───────────┴───────────┐
                    Yes                      No
                     │                       │
           Check current status       Atomic INSERT status = "PROCESSING"
          ┌──────────┴──────────┐            │
     "PROCESSING"          "COMPLETED"       │
          │                     │            ▼
   Return 409 Conflict    Check payload     Execute Domain Logic
  (Concurrent In-Flight)      hash          (Database Transaction)
                                │                    │
                     ┌──────────┴──────────┐         ▼
                  Matches?               Mismatch?  Save Response Body & Status,
                     │                      │       Update status = "COMPLETED"
                     ▼                      ▼       (with 24h TTL)
            Return Cached Response    Return 422             │
           (Status, Headers, Body)    Unprocessable          ▼
                                                         Return Response
```

### C. Under the Hood: The 5 Fundamental Building Blocks (The Mechanism)

Under the hood, an idempotency engine is not magic; it relies on five coordinating low-level primitives:

```
┌──────────────────────────────────────────────────────────────────────────────────┐
│                           Incoming HTTP Request                                  │
│                 (Method, Route, Body, Idempotency-Key Header)                    │
└────────────────────────────────────────┬─────────────────────────────────────────┘
                                         │
        ┌────────────────────────────────┼────────────────────────────────┐
        ▼                                ▼                                ▼
  [ Building Block 1 ]             [ Building Block 2 ]             [ Building Block 3 ]
   ATOMIC MUTEX / LOCK              FINGERPRINT HASH                 STATE PERSISTENCE
  Redis: SET NX EX                 SHA-256(Method +                 Status: PROCESSING
  SQL: INSERT ... ON CONFLICT      Path + CanonicalBody)            vs. COMPLETED
        │                                │                                │
        └────────────────────────────────┼────────────────────────────────┘
                                         ▼
                               [ Building Block 4 ]
                           TRANSACTIONAL ATOMICITY
                    Business Mutation + Idempotency Commit
                    (Dual-Write Protection / ACID Tx)
                                         │
                                         ▼
                               [ Building Block 5 ]
                             TTL / EVICTION CLEANUP
                    Auto-expire keys after 24-72 hours
```

#### 1. Atomic Mutex / Distributed Lock (Race Condition Guard)
* **The Problem:** Two identical requests arriving concurrently within 5ms (e.g. rapid user double-click). If both check storage, both see "key does not exist" and both execute side effects.
* **Under the Hood Primitive:** An atomic Compare-And-Swap (CAS) or reservation mechanism:
  - **Redis:** `SET idempotency:<user_id>:<key> <payload> NX EX 120` (`NX` guarantees atomic insertion only if the key does not already exist).
  - **Relational DB:** `INSERT INTO idempotency_keys (...) ON CONFLICT (user_id, key) DO NOTHING` or `SELECT ... FOR UPDATE`.
* **Behavior:** Exactly one execution thread wins the lock and transitions status to `PROCESSING`. All concurrent competitors fail to acquire the lock and immediately receive `409 Conflict`.

#### 2. Cryptographic Request Fingerprinting (Payload Integrity Verifier)
* **The Problem:** A client mistakenly or maliciously reuses the same `Idempotency-Key` with a completely different payload (e.g., first sends `amount: 10`, then sends `amount: 5000`).
* **Under the Hood Primitive:** A deterministic cryptographic hash (typically SHA-256) of normalized request parameters:
  $$\text{Hash} = \text{SHA256}(\text{Method} + \text{Canonical Path} + \text{Sorted JSON Body})$$
* **Behavior:** When a key lookup matches, the server verifies `stored_hash === incoming_hash`. If they do not match, the request is immediately aborted with `422 Unprocessable Content` before any business logic is executed.

#### 3. State Machine & Persistence Store (The Lifecycle Registry)
* **The Problem:** The server must track execution progress and store final output to replay on subsequent retries.
* **Under the Hood Primitive:** A high-speed key-value store (Redis) or dedicated SQL table holding a structured record:
  ```json
  {
    "key": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
    "user_id": "usr_abc123",
    "request_hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
    "status": "COMPLETED",
    "response_code": 201,
    "response_headers": { "Content-Type": "application/json" },
    "response_body": { "id": "ch_789", "amount": 5000, "status": "paid" },
    "locked_at": 1776323200,
    "expires_at": 1776409600
  }
  ```
* **State Transitions:**
  - `PROCESSING`: Request in-flight. Concurrently arriving duplicates get `409 Conflict`.
  - `COMPLETED`: Business action finished. Retries immediately receive cached response.
  - `FAILED / RELEASED`: Transient error occurred (e.g., DB connection dropped). Lock is released so the client can legitimately retry.

#### 4. Transactional Atomicity (The Dual-Write Boundary)
* **The Problem:** If the server completes the business write (e.g. charges card, writes order to DB), but crashes before writing `COMPLETED` to Redis, a client retry will execute the business write again.
* **Under the Hood Primitive:**
  - **SQL Same-Transaction Pattern (Highest Consistency):** The idempotency record is saved in the **exact same ACID database transaction** as the business entity:
    ```sql
    BEGIN;
    INSERT INTO orders (id, customer_id, total) VALUES ('ord_1', 'cus_1', 5000);
    INSERT INTO idempotency_records (key, user_id, status, response_body)
      VALUES ('key_1', 'cus_1', 'COMPLETED', '{"id":"ord_1", ...}');
    COMMIT;
    ```
    If the transaction rolls back, the idempotency record rolls back too. No dual-write inconsistency can occur.
  - **Distributed Two-Phase / Outbox Pattern:** For external side-effects (e.g., charging Stripe), lock acquisition happens first in Redis/DB with a short TTL lease, followed by external call execution and immediate status update to `COMPLETED`.

#### 5. Time-To-Live (TTL) & Eviction Garbage Collection
* **The Problem:** Retaining idempotency records indefinitely creates unbounded storage bloat and violates data retention policies.
* **Under the Hood Primitive:** Automatic expiration:
  - **Redis:** Built-in expiration via `EX` / `EXAT` passive & active expiration threads.
  - **SQL:** Table partitioning by date or automated background cleanup cron (`DELETE FROM idempotency_records WHERE expires_at < NOW()`).
* **Calibrating the Window:** TTL is typically set to **24 to 72 hours**—long enough to cover standard client retry backoffs and webhook redelivery cycles, but short enough to keep storage bounded.

### D. Implementation Pattern (TypeScript / Redis & SQL)

```typescript
import { Request, Response, NextFunction } from "express";
import crypto from "crypto";

interface CachedIdempotencyRecord {
  status: "PROCESSING" | "COMPLETED";
  requestHash: string;
  statusCode?: number;
  responseBody?: any;
}

// Compute deterministic SHA-256 of path + body to detect payload tampering
function computeRequestHash(req: Request): string {
  const payload = JSON.stringify({
    method: req.method,
    path: req.originalUrl,
    body: req.body,
  });
  return crypto.createHash("sha256").update(payload).digest("hex");
}

export function idempotencyMiddleware(redisClient: any) {
  return async (req: Request, res: Response, next: NextFunction) => {
    const idempotencyKey = req.header("Idempotency-Key");

    // Only apply to state-modifying requests that supply the header
    if (!idempotencyKey || req.method === "GET" || req.method === "HEAD") {
      return next();
    }

    // Always scope keys to the authenticated user/tenant to prevent collisions
    const userId = req.user?.id || "anonymous";
    const storageKey = `idempotency:${userId}:${idempotencyKey}`;
    const requestHash = computeRequestHash(req);

    // 1. Check existing record in cache/database
    const existingRaw = await redisClient.get(storageKey);

    if (existingRaw) {
      const record: CachedIdempotencyRecord = JSON.parse(existingRaw);

      // Verify request payload has not changed for the same key
      if (record.requestHash !== requestHash) {
        return res.status(422).json({
          title: "Idempotency Conflict",
          detail: "Provided Idempotency-Key has already been used with a different request payload.",
          status: 422,
        });
      }

      // If still processing, prevent concurrent race condition
      if (record.status === "PROCESSING") {
        return res.status(409).json({
          title: "Request in Progress",
          detail: "A request with this Idempotency-Key is currently being processed. Please retry shortly.",
          status: 409,
        });
      }

      // Replay original cached response
      return res.status(record.statusCode!).json(record.responseBody);
    }

    // 2. Atomically lock and claim key with status "PROCESSING" (120s lock timeout)
    const acquired = await redisClient.set(
      storageKey,
      JSON.stringify({ status: "PROCESSING", requestHash }),
      "NX", // Only set if key does not exist
      "EX", 120 // Auto-release lock if server crashes
    );

    if (!acquired) {
      return res.status(409).json({
        title: "Conflict",
        detail: "Concurrent request detected with the same Idempotency-Key.",
        status: 409,
      });
    }

    // 3. Intercept res.send / res.json to capture response before sending
    const originalJson = res.json.bind(res);
    res.json = (body: any): Response => {
      // Restore original res.json
      res.json = originalJson;

      // Only cache successful or definitive business outcomes (e.g., 2xx, 4xx)
      // Do NOT cache transient 5xx infrastructure crashes
      if (res.statusCode < 500) {
        const completedRecord: CachedIdempotencyRecord = {
          status: "COMPLETED",
          requestHash,
          statusCode: res.statusCode,
          responseBody: body,
        };

        // Cache completed response for 24 hours (86,400 seconds)
        redisClient.set(storageKey, JSON.stringify(completedRecord), "EX", 86400);
      } else {
        // Clear lock on server error so client can retry legitimately
        redisClient.del(storageKey);
      }

      return originalJson(body);
    };

    next();
  };
}
```

## 4. When should I NOT use this? (Trade-offs and Anti-patterns)

### When NOT to Use Idempotency Keys
- **Read-Only Operations:** Never demand or process `Idempotency-Key` for `GET`, `HEAD`, or `OPTIONS` requests.
- **Naturally Idempotent `PUT` Endpoints:** A well-designed `PUT /users/123/profile` that completely overwrites static values is already naturally idempotent; requiring keys adds unnecessary client overhead.
- **As a Replacement for Database Constraints:** Idempotency keys protect the API layer, but they do **not** replace database unique constraints (`UNIQUE(order_id, user_id)`). Both layers are required for defense in depth.

### Anti-Patterns to Avoid

1. **Unscoped / Global Key Collisions:**
   Storing keys as `idempotency:KEY_123` across all users. If User A happens to generate the same UUID as User B, User A will hijack User B's transaction or view their private response data. Always namespace: `idempotency:${tenant_id}:${user_id}:${key}`.
2. **Caching Transient Server Crashes (`500 / 503`):**
   If a database timeout causes a `500 Internal Server Error`, do **not** cache the `500` response against the idempotency key. Otherwise, all future client retries will receive the cached `500` error forever, even after the database recovers.
3. **Ignoring Concurrent In-Flight Requests (The Race Condition):**
   Failing to use atomic locks (like Redis `SET NX` or SQL row locks). Two identical requests arriving within 5ms will both read "key does not exist" and execute the charge twice.
4. **Ignoring Payload Mismatches:**
   Allowing a client to use the same key for `POST /charge { amount: 10 }` and later `POST /charge { amount: 1000 }`. If the key is reused with a different body, immediately reject with `422 Unprocessable Content`.
5. **No TTL (Infinite Storage):**
   Keeping idempotency payloads forever in Redis or PostgreSQL exhausts storage memory. Enforce a 24-to-72-hour TTL.

## 5. How do I know I understand it?

You understand idempotency when you can diagnose and solve these real-world backend scenarios:

| Scenario | Anti-Pattern / Mistake | Production-Grade Solution |
| :--- | :--- | :--- |
| Mobile user taps "Pay $50" twice within 200ms on a 3G network | Two `POST /payments` requests execute concurrently, charging $100. | Server uses atomic lock (`SET NX`) on `Idempotency-Key`. The second request returns `409 Conflict` or waits for the first to complete, resulting in one $50 charge. |
| Server charges payment in DB, but connection crashes before returning JSON | Client assumes failure and retries. Server charges card a second time. | Client retries with the same `Idempotency-Key`. Server finds `COMPLETED` record and returns original cached payment receipt without recharging. |
| Client sends identical `Idempotency-Key` but changes payload amount from $10 to $500 | Server replays original $10 receipt, creating billing discrepancies. | Server hashes incoming request payload. Detecting a hash mismatch on an existing key, it rejects with `422 Unprocessable Content`. |
| Database connection pool is saturated, causing initial request to throw `503` | Server caches `503 Service Unavailable` for 24 hours against the key. | Server detects `res.statusCode >= 500`, deletes the idempotency key, allowing client retry when database recovers. |
| Engineer asks whether `DELETE /orders/ord_123` needs an `Idempotency-Key` | Adding complex idempotency middleware to standard `DELETE` endpoint. | Recognize that `DELETE` is already naturally idempotent per RFC 9110 (deleting an already deleted order leaves it deleted). |
