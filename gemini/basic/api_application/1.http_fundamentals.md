## 1. What is it?

**HTTP (Hypertext Transfer Protocol)** is an application-layer network protocol used by distributed, collaborative, hypermedia information systems. In backend development, it serves as the foundational communication protocol between **clients** (web browsers, mobile apps, desktop clients, or other backend microservices) and **servers**.

HTTP operates on a **request-response model** over a reliable transport connection (typically TCP with TLS encryption for HTTPS, or UDP-based QUIC in HTTP/3).

### Anatomy of an HTTP Transaction

Every HTTP communication consists of two discrete messages: an **HTTP Request** and an **HTTP Response**.

#### 1. HTTP Request
```http
POST /api/v1/orders HTTP/1.1
Host: api.store.example.com
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json
Accept: application/json
Content-Length: 53

{
  "productId": "prod_1001",
  "quantity": 2
}
```

An HTTP Request contains:
- **Request Line:** Method (`POST`), Request Target/Path (`/api/v1/orders`), and Protocol Version (`HTTP/1.1`).
- **Headers:** Key-value pairs providing metadata (host target, authentication credentials, accepted content types, user agent, etc.).
- **Empty Line (CRLF):** Signals the end of the header block.
- **Body (Optional):** The payload being transmitted (JSON, XML, binary, multipart form data).

#### 2. HTTP Response
```http
HTTP/1.1 201 Created
Date: Wed, 14 Oct 2026 10:55:00 GMT
Content-Type: application/json; charset=utf-8
Location: /api/v1/orders/ord_98765
Cache-Control: no-store

{
  "orderId": "ord_98765",
  "status": "pending",
  "total": 59.98
}
```

An HTTP Response contains:
- **Status Line:** Protocol version (`HTTP/1.1`), Status Code (`201`), and Reason Phrase (`Created`).
- **Headers:** Metadata about the response (server time, media type, cache control policies, redirection locations).
- **Empty Line (CRLF):** Separates headers from body.
- **Body (Optional):** Data returned to the client.

### Core Protocol Characteristics

1. **Stateless:** Each HTTP request is completely isolated. The protocol itself does not retain any memory or state across multiple requests. Statefulness (e.g., shopping carts, login sessions) is handled at the application layer via cookies, session identifiers, or tokens (JWTs).
2. **Media Independent:** Any data type can be transferred as long as both client and server agree on the MIME type (specified via `Content-Type` and `Accept` headers).
3. **Evolution (HTTP/1.1 vs HTTP/2 vs HTTP/3):**
   - **HTTP/1.1:** Text-based wire protocol, persistent TCP connections (Keep-Alive), head-of-line (HoL) blocking at the request level.
   - **HTTP/2:** Binary framing, multiplexed streams over a single TCP connection, header compression (HPACK), server push.
   - **HTTP/3:** Replaces TCP with QUIC (over UDP) to eliminate TCP-level head-of-line blocking and achieve faster connection handshakes.

## 2. Why do we need it?

Without a standardized protocol like HTTP:
1. **Interoperability:** Every company, language, and operating system would invent proprietary socket communication protocols. HTTP acts as the universal lingua franca: an iOS client in Swift, a Web frontend in TypeScript, and a backend in Go, Python, or Java can effortlessly communicate.
2. **Layered Architecture & Intermediaries:** Standardized headers, status codes, and methods enable reverse proxies (e.g., NGINX, Envoy), CDNs (Cloudflare), API Gateways, and load balancers to route, cache, rate-limit, and inspect traffic transparently without understanding application-specific logic.
3. **Built-in Semantics (Safety & Caching):** HTTP standardizes caching mechanisms (`Cache-Control`, `ETag`, `Last-Modified`) and operation characteristics (safe vs. unsafe methods), allowing edge networks and browsers to optimize network efficiency automatically.
4. **Observability & Debugging:** Tooling across the industry (cURL, Postman, Wireshark, Datadog, Prometheus exporters) relies directly on HTTP status codes and semantics to track latency, error rates, and API health.

## 3. How to apply / implement / use it?

### A. HTTP Methods, Safety, and Idempotency

When designing backend endpoints, match business intentions with the correct HTTP method:

| Method | Safe? | Idempotent? | Typical Backend Purpose |
| :--- | :--- | :--- | :--- |
| `GET` | **Yes** (No state change) | **Yes** | Retrieve a resource or list of resources. |
| `HEAD` | **Yes** | **Yes** | Same as GET, but returns headers only (no body). |
| `POST` | **No** | **No** | Create a new resource or execute an arbitrary command. |
| `PUT` | **No** | **Yes** | Replace an entire resource or create at a specific URI. |
| `PATCH` | **No** | **Usually No** (RFC 5789) | Partial modification of an existing resource. |
| `DELETE` | **No** | **Yes** | Remove an existing resource. |
| `OPTIONS`| **Yes** | **Yes** | Discover supported methods / CORS pre-flight. |

- **Safe:** Calling it must not cause side effects that mutate server state.
- **Idempotent:** Making multiple identical requests produces the exact same server side-effect as a single request.

### B. Standard HTTP Status Code Categories

Return semantically accurate status codes to communicate outcomes:

- **`2xx` Success:**
  - `200 OK`: Request succeeded; body contains response.
  - `201 Created`: Resource successfully created (`Location` header indicates URI).
  - `204 No Content`: Action succeeded, but response deliberately contains no body (common for `DELETE`).
- **`3xx` Redirection:**
  - `301 Moved Permanently` / `302 Found`: URL redirection.
  - `304 Not Modified`: Cached copy on client is still valid.
- **`4xx` Client Error:**
  - `400 Bad Request`: Malformed syntax, invalid JSON, or unparseable input.
  - `401 Unauthorized`: Authentication is required and missing or invalid.
  - `403 Forbidden`: Authenticated, but lacking permission/authorization to access resource.
  - `404 Not Found`: Target resource or endpoint does not exist.
  - `409 Conflict`: Conflict with current state (e.g., unique email already taken).
  - `422 Unprocessable Content`: Syntax is valid, but semantic/business validation failed.
  - `429 Too Many Requests`: Client exceeded rate limits.
- **`5xx` Server Error:**
  - `500 Internal Server Error`: Unhandled exception or unexpected failure.
  - `502 Bad Gateway`: Upstream dependency failed.
  - `503 Service Unavailable`: Server is temporarily overloaded or down for maintenance.
  - `504 Gateway Timeout`: Upstream dependency timed out.

### C. Testing and Inspecting via cURL

Use `curl -i` (include response headers) or `curl -v` (verbose connection details):

```bash
# 1. Fetching a resource with custom Accept header
curl -i -X GET "https://api.example.com/api/v1/orders/123" \
  -H "Accept: application/json" \
  -H "Authorization: Bearer <token>"

# 2. Creating a resource sending JSON
curl -i -X POST "https://api.example.com/api/v1/orders" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{"productId":"prod_1001","quantity":2}'
```

### D. Typical Backend Implementation Pattern (Mental Model)

In modern web frameworks (Go Gin, Node.js Express/Fastify, Python FastAPI, Java Spring Boot):

```text
Incoming TCP Socket
  │
  ▼
[Web Server / Engine] ── parses raw bytes into HTTP Request Object
  │
  ▼
[Middleware Pipeline] ── Logging, CORS, Authentication, Rate Limiting
  │
  ▼
[Router] ─────────────── Matches Method + Path pattern (/orders/:id)
  │
  ▼
[Controller / Handler] ─ Extracts params/body, calls business logic, constructs Response
  │
  ▼
[Web Server / Engine] ── Serializes status, headers, body into raw HTTP bytes sent back to Client
```
