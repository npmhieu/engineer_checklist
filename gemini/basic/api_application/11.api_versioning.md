## 1. What is it?

**API Versioning** is the architectural practice of managing changes to an API's public contract over time, allowing software interfaces to evolve without breaking existing client integrations.

A public API is a formal contract between server and client. Once published, any modification that violates expectations of existing clients is a **breaking change**.

### Breaking vs. Non-Breaking Changes

| Change Type | Definition | Examples | Requires Version Bump? |
| :--- | :--- | :--- | :--- |
| **Non-Breaking (Additive)** | Changes that existing, well-behaved clients can safely ignore or adopt incrementally. | - Adding a new endpoint (`POST /api/v1/refunds`)<br>- Adding an **optional** request field<br>- Adding a new field to a response body | **No** (Safe for continuous deployment) |
| **Breaking** | Changes that alter existing contracts or cause older client parsers/logic to fail. | - Renaming/removing an existing field<br>- Changing a field type (e.g., `id: number` → `id: string`)<br>- Adding a **required** request field<br>- Changing HTTP status code semantics | **Yes** (Requires new API version) |

---

### The 4 Major Versioning Strategies

| Strategy | Syntax Example | Pros | Cons | Best Suited For |
| :--- | :--- | :--- | :--- | :--- |
| **1. URI Path Versioning** | `GET /api/v1/orders`<br>`GET /api/v2/orders` | Explicit, easy to test in browser/cURL, trivial to route at API gateway / reverse proxy. | Can lead to URI duplication; strictly couples resource identifiers to version. | Public web APIs, mobile APIs, REST standards. |
| **2. Custom Header Versioning** | `GET /api/orders`<br>`X-API-Version: 2026-03-01` | Keeps URIs clean and permanent; supports fine-grained date-based evolutions (Stripe model). | Harder to test in browser address bar; requires custom gateway routing logic. | High-volume developer platforms, fintech, enterprise SaaS. |
| **3. Content Negotiation (Accept Header)** | `GET /api/orders`<br>`Accept: application/vnd.app.v2+json` | Adheres strictly to REST HATEOAS principles; cleanly separates representation from resource URI. | Complex for external consumers to configure; awkward documentation tooling. | Strict hypermedia / academic REST systems. |
| **4. Query Parameter Versioning** | `GET /api/orders?v=2` | Simple to override in testing or ad-hoc requests. | Inconvenient to enforce globally; complicates edge/CDN caching keys. | Internal tools, ad-hoc API exploration. |

## 2. Why do we need it?

1. **Mobile Application Longevity:**
   Unlike web applications where new code is deployed immediately to all browsers, mobile apps (iOS/Android) cannot be forced to update simultaneously. Versions released two years ago will continue sending requests from users' devices.
2. **Third-Party Partner Stability:**
   Enterprise B2B consumers build mission-critical integrations around your API contract. Breaking their integration without warning damages trust and violates Service Level Agreements (SLAs).
3. **Independent Team Velocity:**
   Backend engineering teams can refactor business logic and modernize schemas without blocking on client teams or coordinating lock-step cross-platform releases.
4. **Structured Sunsetting Lifecycle:**
   Enables a controlled phase-out of legacy endpoints using standardized deprecation headers and usage telemetry.

## 3. How to apply / implement / use it?

### A. The Adapter / Transformation Pattern (Avoid Code Duplication)

**Do not copy-paste your entire codebase or database schema for a new API version.**
Instead, maintain a single, canonical domain model and use **version adapters** at the controller boundary to translate between external versioned contracts and internal domain logic:

```
[ Client v1 ] ──> [ Controller v1 ] ──> [ V1 Adapter / Mapper ] ──┐
                                                                   ├──> [ Core Domain Service ] ──> [ Database ]
[ Client v2 ] ──> [ Controller v2 ] ──> [ V2 Adapter / Mapper ] ──┘
```

#### TypeScript / Express Implementation

```typescript
import { Request, Response } from "express";

// Canonical Internal Domain Entity
interface UserProfile {
  id: string;
  firstName: string;
  lastName: string;
  email: string;
}

// ─────────────────────────────────────────────────────────────
// Version 1: Exposes legacy "full_name" string
// ─────────────────────────────────────────────────────────────
export function formatUserV1(user: UserProfile) {
  return {
    id: user.id,
    full_name: `${user.firstName} ${user.lastName}`.trim(),
    email: user.email,
  };
}

export async function getUserV1Handler(req: Request, res: Response) {
  // Inform client of impending deprecation
  res.setHeader("Deprecation", "true");
  res.setHeader("Sunset", "Fri, 01 Jan 2027 00:00:00 GMT");
  res.setHeader("Link", '<https://api.example.com/docs/v2-migration>; rel="deprecation"');

  const user = await userService.findById(req.params.id);
  if (!user) return res.status(404).json({ title: "User not found" });

  return res.status(200).json(formatUserV1(user));
}

// ─────────────────────────────────────────────────────────────
// Version 2: Exposes structured "first_name" and "last_name"
// ─────────────────────────────────────────────────────────────
export function formatUserV2(user: UserProfile) {
  return {
    id: user.id,
    first_name: user.firstName,
    last_name: user.lastName,
    email: user.email,
  };
}

export async function getUserV2Handler(req: Request, res: Response) {
  const user = await userService.findById(req.params.id);
  if (!user) return res.status(404).json({ title: "User not found" });

  return res.status(200).json(formatUserV2(user));
}
```

### B. Standard HTTP Deprecation & Sunset Headers

When sunsetting legacy versions, communicate deprecation timelines using standard HTTP headers (RFC 8594 / RFC 9110):

```http
HTTP/1.1 200 OK
Content-Type: application/json
Deprecation: true
Sunset: Wed, 11 Nov 2026 00:00:00 GMT
Link: <https://api.example.com/docs/v2-migration>; rel="deprecation"; type="text/html"
```

- **`Deprecation`**: Informs developers that the endpoint is marked for removal.
- **`Sunset`**: Defines the exact HTTP date-time when the endpoint will be permanently decommissioned and return `410 Gone` or `404 Not Found`.
- **`Link`**: Points directly to migration documentation.

### C. Database Evolution: The Expand-Contract (Parallel Run) Pattern

When modifying database columns across API versions:
1. **Expand:** Add the new column alongside the old one. Write to **both** columns in application logic.
2. **Backfill:** Migrate legacy historical rows to populate the new column.
3. **Contract:** Switch reads to the new column, deprecate the old API version, and eventually drop the old column.

## 4. When should I NOT use this? (Trade-offs and Anti-patterns)

### When NOT to Bump API Versions
- **Additive Changes:** Adding a new optional field or a new endpoint should **never** trigger a new API version. Keep the API backward-compatible.
- **Tightly Coupled Internal Microservices:** If services are deployed together or share a unified Protobuf / gRPC schema registry with automated backward compatibility checks, maintain a single evolutionary contract.

### Anti-Patterns to Avoid

1. **Version Proliferation (Bumping versions for trivial changes):**
   Creating `v3`, `v4`, `v5` every few weeks. Each major version increases testing surface, deployment complexity, and routing overhead exponentially.
2. **Breaking Changes on Unversioned or Current Routes:**
   Renaming a field or making an optional query parameter mandatory on `/v1` without a grace period or new version breaks production client applications silently.
3. **Forking the Entire Application / Copy-Paste Routing:**
   Duplicating the entire backend codebase into `/v1` and `/v2` folders. Fixes applied to `/v2` are forgotten in `/v1`, causing regressions.
4. **Infinite Lifetime for Deprecated Versions:**
   Leaving deprecated versions running forever without monitoring or a firm sunset date. Track active consumers with API Gateway metrics and proactively notify partners.
5. **Breaking Error Payloads:**
   Altering the schema or status code of error responses across versions without documenting it as a breaking change.

## 5. How do I know I understand it?

You understand API versioning if you can make the correct architectural decisions in these scenarios:

| Scenario | Anti-Pattern / Mistake | Production-Grade Solution |
| :--- | :--- | :--- |
| Adding an optional `nickname` field to user response | Creating `v2/users` and forcing all clients to migrate. | Add the field directly to `v1`. Well-behaved JSON parsers ignore unknown fields (non-breaking change). |
| Splitting `address: "123 Main St, Springfield"` into `street`, `city`, `zip` | Overwriting `address` with an object on `/v1`, breaking all legacy mobile clients. | Introduce `/v2/users` or new representation; keep `/v1` returning string via adapter. |
| Decommissioning an old API version | Shutting down `/v1` overnight with zero notice, returning `404`. | Emit `Deprecation` and `Sunset` headers for 6–12 months, monitor remaining traffic by API key, and reach out directly before decommissioning. |
| Internal database schema renaming `tbl_orders.cust_id` to `customer_uuid` | Immediately removing the database column and breaking the `v1` controller query. | Follow Expand-Contract: Keep both columns or alias in the query mapper during transition. |
| Client requests `GET /api/v1/orders` | Rewriting entire database queries from scratch in two duplicate controllers. | Route both `v1` and `v2` to the same domain service; format output through version-specific view mappers. |
