# Search / Filter / Sort

[Lesson Index](../../README.md) · Previous: [HTTP Status Codes](8.http_status_codes.md) · Next: [Pagination](10.pagination.md)

---

## 1. What is it?

**Search, Filter, and Sort** are collection querying capabilities exposed over HTTP that allow API clients to navigate, narrow down, and organize large collections of resources.

While often combined into single API endpoints, they serve distinct technical functions:

| Capability | Definition | Typical Input | DB Query Equivalent | Indexing Strategy |
| :--- | :--- | :--- | :--- | :--- |
| **Filtering** | Narrows a collection to items matching discrete criteria or operators. | `status=ACTIVE&min_price=100` | `WHERE status = 'ACTIVE' AND price >= 100` | Composite B-Tree index on filtered columns. |
| **Searching** | Finds items matching text queries across one or multiple attributes, often with ranking. | `q=wireless+headphones` | Full-text search or inverted index (`to_tsquery`, Elasticsearch) | Inverted index, GIN, GiST, or dedicated search cluster. |
| **Sorting** | Specifies the presentation order and direction of the result set. | `sort=-created_at,price` | `ORDER BY created_at DESC, price ASC` | Indexed columns matching sort order to avoid disk filesort. |

---

## 2. Why do we need it?

1. **Network & Client Bandwidth Optimization:**
   Without filtering and sorting, clients would need to download entire datasets (megabytes of JSON) and filter/sort in browser or mobile memory.
2. **Server Resource & Memory Protection:**
   Restricting queries to indexed, filtered subsets prevents the backend from loading thousands of ORM objects into RAM, avoiding garbage collection spikes and out-of-memory crashes.
3. **Structured & Secure Query Boundary:**
   Providing standard query parameter conventions prevents leaking raw database schemas and eliminates SQL/NoSQL injection risks by keeping queries strictly parameterized and allowlist-driven.
4. **Discoverability & User Experience:**
   Powers essential client features: faceted search, e-commerce filtering by price/category, and sorting by recency or relevance.

## 3. How to apply / implement / use it?

### A. API Design Conventions for Query Parameters

#### 1. Filtering
Use descriptive, standard query parameters:
- **Exact match:** `GET /api/v1/orders?status=PENDING&customer_id=cus_123`
- **Range queries:** Use explicit field prefixes/suffixes (`min_price=50&max_price=200` or `created_after=2026-01-01T00:00:00Z`).
- **Multi-value (IN condition):** Comma-separated or repeated keys:
  - `category=books,electronics` OR `category=books&category=electronics`

#### 2. Free-Text Searching
Use a dedicated parameter such as `q` or `search`:
- `GET /api/v1/products?q=mechanical+keyboard`
- Keep `q` separate from structured filters so clients can combine them:
  - `GET /api/v1/products?q=keyboard&category=electronics&min_price=50`

#### 3. Sorting
Use a unified `sort` parameter:
- Prefix with `-` for descending order, no prefix for ascending:
  - `GET /api/v1/articles?sort=-published_at,title` (Published newest first; tie-break by title ascending).
- Alternatively, use explicit paired parameters:
  - `GET /api/v1/articles?sort_by=published_at&order=desc`

### B. Implementation Pattern: Allowlist Validation & Safe Query Building

Never allow clients to pass arbitrary field names directly into database queries. Always validate incoming parameters against an **allowlist**.

```typescript
import { Request, Response } from "express";
import { z } from "zod";

// 1. Strict Query Parameter Schema Validation
const ProductQuerySchema = z.object({
  q: z.string().trim().max(100).optional(),
  category: z.enum(["electronics", "clothing", "home", "books"]).optional(),
  status: z.enum(["ACTIVE", "ARCHIVED"]).default("ACTIVE"),
  min_price: z.coerce.number().nonnegative().optional(),
  max_price: z.coerce.number().positive().optional(),
  sort: z.string().optional().default("-created_at"),
});

// 2. Allowlist of sortable columns to prevent SQL injection and index misses
const ALLOWED_SORT_FIELDS: Record<string, string> = {
  created_at: "products.created_at",
  price: "products.price",
  name: "products.name",
};

export async function listProducts(req: Request, res: Response) {
  // Validate query inputs at the boundary
  const parsed = ProductQuerySchema.safeParse(req.query);
  if (!parsed.success) {
    return res.status(422).json({
      type: "https://api.example.com/errors/validation",
      title: "Invalid Query Parameters",
      status: 422,
      invalid_params: parsed.error.issues,
    });
  }

  const { q, category, status, min_price, max_price, sort } = parsed.data;

  // Initialize query builder
  let query = db("products").select("id", "name", "category", "price", "status", "created_at");

  // Apply filters safely using parameterized SQL
  if (status) {
    query = query.where("status", "=", status);
  }
  if (category) {
    query = query.where("category", "=", category);
  }
  if (min_price !== undefined) {
    query = query.where("price", ">=", min_price);
  }
  if (max_price !== undefined) {
    query = query.where("price", "<=", max_price);
  }

  // Apply full-text search
  if (q) {
    // Postgres tsvector / full-text search
    query = query.whereRaw(
      "search_vector @@ plainto_tsquery('english', ?)",
      [q]
    );
  }

  // Parse and apply sort safely via allowlist
  const sortDirection = sort.startsWith("-") ? "DESC" : "ASC";
  const rawField = sort.startsWith("-") ? sort.slice(1) : sort;
  const dbSortColumn = ALLOWED_SORT_FIELDS[rawField];

  if (!dbSortColumn) {
    return res.status(422).json({
      title: "Invalid Sort Field",
      detail: `Sorting by '${rawField}' is not permitted. Allowed fields: ${Object.keys(ALLOWED_SORT_FIELDS).join(", ")}`,
      status: 422,
    });
  }

  // Primary sort + deterministic tie-breaker
  query = query.orderBy(dbSortColumn, sortDirection).orderBy("products.id", "ASC");

  const results = await query.limit(20);
  return res.status(200).json({ data: results });
}
```

### C. Database Indexing Strategy

A query with filters and sorting requires deliberate indexing:

1. **Equality First, Range Second, Sort Last (The ESR Rule):**
   - For query: `WHERE status = 'ACTIVE' AND price >= 100 ORDER BY created_at DESC`
   - Optimal composite index: `CREATE INDEX idx_products_esr ON products (status, created_at DESC, price);`
2. **Deterministic Tie-Breakers:**
   - Always append the primary key `id` as the final sort column. If two rows have the exact same `created_at` or `price`, without a tie-breaker the database engine may return them in non-deterministic order across multiple queries.

## 4. When should I NOT use this? (Trade-offs and Anti-patterns)

### When NOT to Use Relational DB Filtering / Searching
- **Fuzzy & Complex Full-Text Search on Large Datasets:**
  Do not use relational databases with `LIKE '%term%'` for large-scale product catalogs or document libraries. Leading wildcards (`%term`) force full table scans. Use specialized search engines (Elasticsearch, OpenSearch, Meilisearch, or Algolia) that support stemming, typo-tolerance, and tokenized inverted indexes.
- **Arbitrary Graph / Deep Relationship Filtering:**
  If clients need arbitrary, ad-hoc nested filters across 6 levels of relational joins, building endless REST query parameter permutations is brittle. Consider a GraphQL or dedicated search API instead.

### Anti-Patterns to Avoid

1. **SQL String Interpolation in `ORDER BY`:**
   ```typescript
   // ❌ CRITICAL SECURITY VULNERABILITY: SQL Injection
   query.orderByRaw(`ORDER BY ${req.query.sort}`);
   ```
   Attackers can inject malicious SQL commands (e.g., `; DROP TABLE users;` or blind boolean exfiltration via conditional subqueries) through unvalidated sort parameters.
2. **In-Memory Filtering & Sorting:**
   ```javascript
   // ❌ ANTI-PATTERN: Pulling 100,000 rows into application memory
   const allOrders = await db("orders").select("*");
   const filtered = allOrders
     .filter(o => o.status === req.query.status)
     .sort((a, b) => b.price - a.price);
   ```
   Exhausts Node.js / JVM heap memory and blocks the event loop. Always filter and sort at the database level.
3. **Leading Wildcard Queries:**
   ```sql
   -- ❌ ANTI-PATTERN: Bypasses standard B-Tree indexes completely
   SELECT * FROM users WHERE email LIKE '%@gmail.com';
   ```
4. **Unindexed Sort Columns:**
   Allowing sorting on arbitrary unindexed columns on tables with millions of records causes the database to perform expensive **filesorts** on disk, causing query latency spikes and CPU lockups.

## 5. How do I know I understand it?

You understand Search, Filter, and Sort if you can answer and resolve these operational scenarios:

| Scenario | Anti-Pattern / Mistake | Production-Grade Solution |
| :--- | :--- | :--- |
| Client requests `?sort=password_hash` | Passing sort column directly to ORM/SQL query. | Reject with `422 Unprocessable Content` using a strict sort column allowlist. |
| User searches for `"phone"` across 10 million products | Running `WHERE description ILIKE '%phone%'` causing a 12-second query. | Implement PostgreSQL `tsvector` with a GIN index, or route text search to an inverted index engine (e.g. Meilisearch/Elasticsearch). |
| Two users see different pagination order for items with the same timestamp | Query only sorts by `ORDER BY created_at DESC`. | Add a deterministic tie-breaker: `ORDER BY created_at DESC, id DESC`. |
| Query filters by `tenant_id`, `status`, and ranges on `created_at` | Separate single-column indexes on each column, leading to multiple index scans. | Create a composite B-Tree index following the ESR rule: `(tenant_id, status, created_at)`. |
| Client sends `?price_gte=abc` | Letting the invalid type reach the database driver and throwing a `500 Internal Server Error`. | Validate and coerce types at the controller boundary, returning `422` with actionable field-level errors. |
