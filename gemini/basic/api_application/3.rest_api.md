## 1. What is it?

**REST (Representational State Transfer)** is an architectural style for distributed hypermedia systems, introduced by Roy Fielding in his 2000 doctoral dissertation.

In practical backend development, a **RESTful API** is an API that organizes functionality around **resources** (entities or concepts) identified by URIs, and manipulates those resources using standard HTTP verbs and representations (typically JSON).

### Core Concepts

1. **Resource:** Any conceptual entity that can be named and addressed (e.g., `User`, `Order`, `Product`, `Invoice`).
2. **Representation:** The current or intended state of a resource transferred over the wire (e.g., a JSON document, XML, or binary stream).
3. **Identifier (URI):** A unique, predictable path identifying the resource (e.g., `/api/v1/users/42`).

### Architectural Constraints of REST

Fielding defined six guiding constraints that give REST systems their desirable properties:

1. **Client-Server Separation:** User interface concerns are separated from data storage and business logic concerns.
2. **Stateless:** Each request from client to server must contain all of the information necessary to understand and complete the request. The server holds no client session state.
3. **Cacheable:** Responses must explicitly or implicitly declare themselves cacheable or non-cacheable (`Cache-Control`, `ETag`) to eliminate client-server interactions when possible.
4. **Uniform Interface:** The cornerstone constraint:
   - *Identification of resources* (via URIs).
   - *Manipulation of resources through representations* (client holds representation + metadata to modify/delete).
   - *Self-descriptive messages* (each message has enough info to describe how to process it, e.g., `Content-Type`).
   - *HATEOAS (Hypermedia As The Engine Of Application State)*: Hyperlinks embedded in responses guide client state transitions.
5. **Layered System:** The client cannot tell whether it is connected directly to the end server, or to an intermediary (proxy, cache, API gateway).
6. **Code-on-Demand (Optional):** Servers can temporarily extend client functionality by transferring executable code (e.g., scripts).

> **Pragmatic REST vs. Pure REST:**
> Most modern production APIs follow **Resource-Oriented Architecture (Level 2 of the Richardson Maturity Model)**: they use resources, HTTP methods, and status codes properly, but often omit strict HATEOAS hyperlinks.

## 2. Why do we need it?

1. **Predictability and Developer Intuition:**
   Instead of inventing ad-hoc URLs for every action (e.g., `/getUser`, `/createNewUser`, `/updateUserStatus`, `/deleteUserAccount`), REST establishes universal conventions:
   - `GET /users/42`
   - `POST /users`
   - `PATCH /users/42`
   - `DELETE /users/42`
   Once an engineer understands one resource endpoint, they know how to interact with every other resource in the system.

2. **Leveraging HTTP Infrastructure:**
   Because REST relies on HTTP methods and headers as intended:
   - Read requests (`GET`) are automatically cacheable by CDNs and browsers.
   - Idempotent operations (`PUT`, `DELETE`) can be safely retried upon network drops.

3. **Decoupled Lifecycle:**
   Clients depend on stable resource contracts rather than internal database schemas or server-side workflows.

## 3. How to apply / implement / use it?

### A. Resource Modeling and URI Design Rules

1. **Use Nouns, Not Verbs:**
   - ❌ Bad: `/getUsers`, `/createOrder`, `/task/delete/1`
   - ✅ Good: `/users`, `/orders`, `/tasks/1`

2. **Use Plural Nouns for Collections:**
   - Collection URI: `/tasks` (List all tasks, Create task)
   - Item URI: `/tasks/{id}` (Retrieve, Update, Delete single task)

3. **Model Hierarchies and Sub-resources:**
   Represent relationships naturally in the URI:
   - `/articles/42/comments` (Comments belonging to article 42)
   - `/articles/42/comments/7` (Specific comment 7 on article 42)
   *Rule of thumb:* Avoid nesting deeper than 2 levels (e.g., avoid `/orgs/1/teams/2/projects/3/tasks/4`). Flatten deep relationships using top-level resources with query parameters: `/tasks?projectId=3`.

4. **Use Kebab-Case or Snake-Case Consistently:**
   - Prefer lowercase with hyphens for URLs: `/user-profiles`, `/order-items`.

### B. Standard CRUD Mapping to HTTP Verbs

| Action | HTTP Verb | Endpoint | Success Status | Idempotent |
| :--- | :--- | :--- | :--- | :--- |
| **List** resources | `GET` | `/tasks` | `200 OK` | Yes |
| **Get** single resource | `GET` | `/tasks/{id}` | `200 OK` | Yes |
| **Create** resource | `POST` | `/tasks` | `201 Created` (`Location` header) | No |
| **Replace** resource | `PUT` | `/tasks/{id}` | `200 OK` or `204 No Content` | Yes |
| **Partial update** | `PATCH` | `/tasks/{id}` | `200 OK` | No (by RFC) |
| **Delete** resource | `DELETE` | `/tasks/{id}` | `204 No Content` | Yes |

### C. Updating Resources: PUT vs. PATCH

- **`PUT` (Full Replacement):**
  The client sends the *complete* representation. Missing fields are either overwritten with defaults or cleared.
- **`PATCH` (Partial Modification):**
  The client sends only the fields that need changing.
  
  *Example (JSON Merge Patch - RFC 7396):*
  ```http
  PATCH /tasks/42 HTTP/1.1
  Content-Type: application/merge-patch+json

  {
    "status": "COMPLETED"
  }
  ```
  Only the `status` field is mutated; `title`, `description`, etc., remain unchanged.

### D. Practical cURL Examples

```bash
# 1. List tasks with filtering, pagination, and sorting
curl -i -X GET "https://api.example.com/api/v1/tasks?status=PENDING&page=1&limit=20&sortBy=createdAt:desc" \
  -H "Accept: application/json"

# 2. Create a new task
curl -i -X POST "https://api.example.com/api/v1/tasks" \
  -H "Content-Type: application/json" \
  -d '{"title": "Implement caching", "priority": "HIGH"}'

# 3. Partially update a task
curl -i -X PATCH "https://api.example.com/api/v1/tasks/task_101" \
  -H "Content-Type: application/json" \
  -d '{"isCompleted": true}'

# 4. Delete a task
curl -i -X DELETE "https://api.example.com/api/v1/tasks/task_101"
```

### E. Handling Non-CRUD Actions

Occasionally, real-world operations do not map cleanly to CRUD (e.g., "archive account", "checkout shopping cart", "cancel order").

Approaches:
1. **Treat the state change as a sub-resource or field update:**
   - `PATCH /orders/123` with body `{"status": "CANCELLED"}`
2. **Treat the action as a sub-resource creation:**
   - `POST /orders/123/cancellations`
   - `POST /carts/123/checkout`
3. **Use verbs only when strictly necessary:**
   - `POST /jobs/42/run`

### F. Common Anti-Patterns to Avoid
- **Using `GET` for state-mutating actions:** (e.g., `GET /tasks/delete?id=5`). Browsers and web crawlers can prefetch GET links, accidentally wiping data!
- **Tunneling all operations through `POST`:** Converting REST into an unstandardized pseudo-RPC.
- **Always returning `200 OK` with an error in the body:** (e.g., `{"status": 200, "error": "Not Found"}`). This breaks HTTP caches, proxies, and standard monitoring tools.
