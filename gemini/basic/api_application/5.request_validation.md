# Request Validation

[Lesson Index](../../README.md) · Previous: [CRUD Resource](4.crud_resource.md) · Next: [Business Validation](6.business_validation.md)

---

## 1. What is it?

**Request Validation** is the process of verifying that incoming HTTP request data adheres strictly to the API's technical interface contract **before** that data is passed to any application or domain logic.

It validates the **syntax, shape, type, and format** of the entire incoming request:
- **Route / Path Parameters:** e.g., `:id` must be a valid UUID or positive integer.
- **Query Parameters:** e.g., `?limit=20&page=1` must be positive integers within allowable bounds (`1 <= limit <= 100`).
- **Headers:** e.g., `Content-Type: application/json`, presence of `Authorization` or `Idempotency-Key`.
- **Request Body:** JSON payload shape, field types, required/optional status, string length limits, numeric ranges, and regex patterns.

### Request Validation vs. Business Validation

| Dimension | Request Validation (Boundary) | Business Validation (Domain) |
| :--- | :--- | :--- |
| **Question Asked** | *"Is this request syntactically valid and well-formed?"* | *"Is this operation permitted given the current system state?"* |
| **Context Needed** | Purely in-memory; inspects the request payload alone. | Requires querying system state (database, cache, external services). |
| **Examples** | `email` is a valid format string; `age` is an integer `>= 18`. | `email` is not already registered in the DB; account has enough balance. |
| **Execution Point** | Controller / Framework Middleware. | Service / Domain Model layer. |
| **Failure Status** | `400 Bad Request` or `422 Unprocessable Content`. | `409 Conflict`, `422`, or `403 Forbidden`. |

## 2. Why do we need it?

1. **Security & Input Sanitization (Zero Trust):**
   Never trust client input. Clients, web forms, and mobile apps are not trusted boundaries; any user can craft arbitrary HTTP requests using cURL or Postman. Proper boundary validation prevents injection attacks, buffer overflows, and prototype pollution.
2. **Fail Fast (Resource Protection):**
   Rejecting a malformed request at the API boundary takes sub-millisecond CPU time. Letting malformed data pass to database connection pools or complex domain calculations wastes computing resources and risks unexpected server crashes (`500 Internal Server Error`).
3. **Deterministic Public Contract & Actionable Feedback:**
   Clear validation returns precise error messages pointing directly to offending fields, enabling frontend forms to highlight invalid inputs immediately.
4. **Data Integrity:**
   Guarantees that once data enters your domain and storage layer, it adheres to non-null constraints, length bounds, and expected formats.

## 3. How to apply / implement / use it?

### A. Define Clear Schema Rules

Use schema validation libraries (e.g., Zod, Joi, class-validator in TypeScript/Node; Pydantic in Python; Gin/ozzo-validation in Go; Hibernate Validator/Bean Validation in Java).

```typescript
import { z } from "zod";

export const CreateTaskSchema = z.object({
  title: z
    .string({ required_error: "Title is required" })
    .trim()
    .min(1, "Title cannot be empty")
    .max(120, "Title cannot exceed 120 characters"),
  
  priority: z
    .enum(["LOW", "MEDIUM", "HIGH"], {
      errorMap: () => ({ message: "Priority must be LOW, MEDIUM, or HIGH" }),
    })
    .default("MEDIUM"),
    
  dueDate: z
    .string()
    .datetime({ message: "dueDate must be a valid ISO-8601 string" })
    .optional(),
}).strict(); // Disallow unknown/unexpected fields
```

### B. Standardized Validation Error Response

When validation fails, return structured, field-level diagnostics:

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/json

{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Input validation failed. Please correct the highlighted errors.",
    "details": [
      {
        "field": "title",
        "code": "TOO_LONG",
        "message": "Title cannot exceed 120 characters"
      },
      {
        "field": "priority",
        "code": "INVALID_ENUM",
        "message": "Priority must be LOW, MEDIUM, or HIGH"
      }
    ]
  }
}
```

### C. Validation Execution in the Request Pipeline

```typescript
// Middleware or Route Handler
function validateRequest(schema: z.ZodSchema) {
  return (req: Request, res: Response, next: NextFunction) => {
    // 1. Verify Content-Type
    if (req.method === "POST" || req.method === "PUT" || req.method === "PATCH") {
      if (!req.is("application/json")) {
        return res.status(415).json({
          error: { code: "UNSUPPORTED_MEDIA_TYPE", message: "Content-Type must be application/json" }
        });
      }
    }

    // 2. Validate Body
    const result = schema.safeParse(req.body);
    if (!result.success) {
      const errorDetails = result.error.errors.map((err) => ({
        field: err.path.join("."),
        code: err.code.toUpperCase(),
        message: err.message,
      }));

      return res.status(422).json({
        error: {
          code: "VALIDATION_FAILED",
          message: "The request body failed schema validation.",
          details: errorDetails,
        },
      });
    }

    // 3. Assign sanitized, strongly-typed DTO
    req.body = result.data;
    next();
  };
}
```

## 4. When should I NOT use this? (Trade-offs and Anti-patterns)

### When NOT to use Request Validation
- **Do NOT execute database queries or business state checks in request validators.**
  *Example:* Checking `isEmailUniqueInDatabase(value)` inside a schema validator.
  *Trade-off:* Mixing I/O and database calls into syntactic validation blurs boundaries, breaks unit tests, and creates race conditions (checking uniqueness before transaction commit is inherently prone to race conditions).
- **Do NOT validate internal trusted method calls:**
  Validation should happen at system boundaries (incoming HTTP, incoming message queues). Re-validating every private internal function adds excessive CPU overhead.

### Anti-Patterns to Avoid
1. **Silent Coercion / Mutation:**
   Automatically mutating invalid input into something valid without telling the client (e.g., silently coercing `"abc"` to `0`, or silently truncating a 200-character string to 120). *Always reject invalid input explicitly.*
2. **Permissive Unknown Fields (Mass Assignment Hazard):**
   Allowing arbitrary unknown keys to pass through validation. If an attacker submits `{"title": "Task", "isAdmin": true}`, an unstrict validator might pass `isAdmin` directly into the database. Always use `.strict()` or explicit allowlist DTOs.
3. **Vulnerable Regex (ReDoS):**
   Writing catastrophic backtracking regular expressions to validate emails or complex strings. Attackers can submit crafted inputs that cause 100% CPU lockup. Use well-tested standard parsers.
4. **Echoing Sensitive Input in Errors:**
   Returning error messages like: `Invalid password: 'MySecretPassword123' does not contain a symbol`. Never echo sensitive fields or secrets back in validation errors.

## 5. How do I know I understand it?

You have mastered request validation when you can:

1. **Draw the Clear Boundary:** Explain without hesitation why checking `email regex format` belongs in request validation, while checking `email does not already exist in DB` belongs in business validation.
2. **Distinguish Status Codes:** Explain the practical difference between returning `400 Bad Request` (malformed JSON syntax, cannot be parsed) vs. `422 Unprocessable Content` (valid JSON, but violates schema constraints like string length).
3. **Handle Edge Cases:** Properly test boundaries with empty strings `""`, whitespace `"   "`, `null`, `undefined`, boolean types passed as strings `"true"`, negative numbers, and boundary numbers (`0`, `max_int`).
4. **Prevent Mass Assignment:** Ensure your validation layer discards or rejects unexpected properties not specified in the DTO schema.
