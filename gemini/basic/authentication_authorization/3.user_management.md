## 1. What is it?

**User Management** is the system architecture, data modeling, and set of workflows responsible for managing the entire lifecycle of an identity—including onboarding, credential storage, profile evolution, status transitions, suspension, and offboarding.

> **Mental Model:** User Management is a company's **HR & Employee Records Department**. It handles hiring (registration), badge issuance (credentials), profile updates (promotions/department changes), disciplinary suspensions, and offboarding (revoking badges and archiving employment history).

---

## 2. Why do we need it?

### The Pain, Bug, and Bottleneck Without It

Without a robust user management architecture:
1. **Orphaned Access & Zombie Accounts:** When an employee leaves or a user terminates an account, credentials remain active across background systems, leading to catastrophic security breaches.
2. **Impossible Global Session Revocation:** If a user's phone is stolen or password compromised, the system has no mechanism to invalidate all existing issued tokens without breaking the entire service.
3. **Database Integrity Corruption (Broken Foreign Keys):** Naively hard-deleting a user record (`DELETE FROM users WHERE id = 123`) breaks database relational integrity, corrupting historical invoices, audit trails, and payment records.
4. **GDPR / Privacy Liability:** Inability to comply with legal mandates like GDPR's "Right to be Forgotten" or SOC2 audit trail preservation results in severe regulatory fines.

## 3. Under the Hood: The Mechanism & System Flow

### A. The User Lifecycle State Machine

A production user entity is not a simple boolean flag (`is_active: true/false`). It is governed by a strict state machine:

```
                  ┌──────────────────────────────┐
                  │      Registration (POST)     │
                  └──────────────┬───────────────┘
                                 │
                                 ▼
                     [ PENDING_VERIFICATION ]
                     (Email sent with OTP/Magic Link)
                                 │
                   Verify link / │
                   OTP confirmed │
                                 ▼
         ┌─────────────────> [ ACTIVE ] <─────────────────┐
         │                   │        ▲                   │
         │     Suspended by  │        │ Re-activated by   │
         │     Admin / Fraud │        │ Admin             │
         │                   ▼        │                   │
         │               [ SUSPENDED ]                    │
         │               (Tokens blocked,                 │
         │                logins denied)                  │
         │                                                │
         │ Soft delete / Request erasure                  │
         └───────────────────────┬────────────────────────┘
                                 │
                                 ▼
                     [ DEACTIVATED / ARCHIVED ]
                     (PII anonymized, credentials
                      purged, foreign keys preserved)
```

---

### B. Core Data Model & Separation of Concerns

Never mix volatile profile data with critical identity and credential security data. Store them in separate tables or schemas:

```
┌─────────────────────────────────┐        ┌─────────────────────────────────┐
│          users_auth             │        │          users_profile          │
├─────────────────────────────────┤        ├─────────────────────────────────┤
│ id: uuid (PK)                   │ 1 ── 1 │ user_id: uuid (FK, Unique)      │
│ email_canonical: varchar (UQ)   │        │ first_name: varchar             │
│ password_hash: varchar          │        │ last_name: varchar              │
│ status: user_status_enum        │        │ avatar_url: text                │
│ token_version: integer          │        │ timezone: varchar               │
│ failed_login_attempts: integer  │        │ locale: varchar                 │
│ locked_until: timestamptz       │        │ updated_at: timestamptz         │
│ created_at: timestamptz         │        └─────────────────────────────────┘
└─────────────────────────────────┘
```

#### The `token_version` (or `security_stamp`) Primitive
How do you immediately revoke 100 active stateless JWTs across distributed servers when a user resets their password?
- Store an integer `token_version: 1` in `users_auth`.
- Include `token_version: 1` as a claim inside every issued JWT.
- When the user clicks **"Log out of all devices"** or changes their password, increment `token_version = token_version + 1` in the database / Redis cache.
- Any older JWT presented with `version: 1` is immediately rejected.

## 4. How to apply / implement / use it?

### Smallest Working Example (User Registration & Canonical Normalization)

```typescript
import { Request, Response } from "express";
import bcrypt from "bcrypt";
import { z } from "zod";

const RegisterSchema = z.object({
  email: z.string().trim().email().max(255),
  password: z.string().min(8, "Password must be at least 8 characters"),
  firstName: z.string().trim().min(1).max(50),
  lastName: z.string().trim().min(1).max(50),
});

export async function registerUserHandler(req: Request, res: Response) {
  const parsed = RegisterSchema.safeParse(req.body);
  if (!parsed.success) {
    return res.status(422).json({ title: "Validation Error", errors: parsed.error.issues });
  }

  const { email, password, firstName, lastName } = parsed.data;

  // ── 1. Canonical Normalization: Prevent case/whitespace duplicates ───
  // 'Alice@Example.com' must map to identical record as 'alice@example.com'
  const canonicalEmail = email.toLowerCase().trim();

  // ── 2. Check duplicate identity ─────────────────────────────────────
  const existing = await db("users_auth").where({ email_canonical: canonicalEmail }).first();
  if (existing) {
    // Return generic conflict to prevent account enumeration
    return res.status(409).json({
      title: "Conflict",
      detail: "An account with this email address already exists.",
      status: 409,
    });
  }

  // ── 3. Hash password using slow, salted cryptographic hash (Argon2 / bcrypt)
  const passwordHash = await bcrypt.hash(password, 12);

  // ── 4. Atomic Transaction: Create Auth Credentials + Profile Record ─
  const newUser = await db.transaction(async (trx) => {
    const [authRecord] = await trx("users_auth")
      .insert({
        email_canonical: canonicalEmail,
        password_hash: passwordHash,
        status: "ACTIVE", // or PENDING_VERIFICATION
        token_version: 1,
      })
      .returning(["id", "email_canonical", "status", "created_at"]);

    await trx("users_profile").insert({
      user_id: authRecord.id,
      first_name: firstName,
      last_name: lastName,
    });

    return authRecord;
  });

  return res.status(201).json({
    data: {
      id: newUser.id,
      email: newUser.email_canonical,
      status: newUser.status,
    },
  });
}
```

## 5. When should I NOT use this? (Trade-offs and Anti-patterns)

### Build vs. Buy: When NOT to Build Custom User Management
If your core competitive advantage is not identity infrastructure, **do not build user management from scratch**:
- For consumer and SaaS applications, use established Identity-as-a-Service (IDaaS) platforms: **Auth0, Clerk, AWS Cognito, Supabase Auth, Firebase Auth**.
- Managed providers handle passkeys/WebAuthn, brute-force rate-limiting, breach detection, SAML/SSO enterprise connections, and MFA out of the box.

### Anti-Patterns to Avoid
1. **Hard-Deleting User Records (`DELETE FROM users`):**
   Deletes foreign key chains or sets them to `NULL`, corrupting accounting ledgers and audit records.
   *Fix:* Use **Soft Deletes** (`deleted_at` timestamp) combined with **GDPR PII Anonymization** (scramble email and name to `deleted_user_123@anonymized.internal`).
2. **Non-Normalized Email Storage:**
   Storing `User@gmail.com` without canonicalization allows an attacker to register `user@gmail.com` as a second account, confusing invoice billing and authorization lookups.
3. **Storing Fast Hashes for Passwords:**
   Using MD5, SHA-1, or plain SHA-256 for passwords. Attackers can compute billions of SHA-256 hashes per second using modern GPUs. Always use memory-hard, slow adaptive algorithms: **Argon2id** or **bcrypt** (cost $\ge 12$).
4. **Neglecting Account Suspension Enforcement:**
   Marking a user as `status: 'SUSPENDED'` in the database, but never checking user status in authentication middleware, allowing suspended users to continue making API calls.

## 6. How do I know I understand it?

### The Blank-Page Test
From a blank sheet of paper, can you explain:
1. The difference between Soft Deletion and GDPR-compliant Anonymization, and why historical financial invoices must never lose their relational integrity.
2. How the `token_version` pattern works to instantly revoke distributed access tokens upon password reset.

### Constraint Change Predictions
* **Scenario A: A user changes their password after discovering their laptop was stolen.**
  * *Prediction:* If your user management system only updates `password_hash`, the thief's existing session or JWT remains valid for hours. You must increment `token_version` or purge Redis session keys in the same transaction to terminate all active sessions instantly.
* **Scenario B: Two users register simultaneously with `john.doe@example.com` and `John.Doe@example.com`.**
  * *Prediction:* Without a unique constraint on canonicalized lowercase email (`UNIQUE INDEX ON users_auth (LOWER(email))`), both records insert successfully, causing undefined behavior during password login lookups.
