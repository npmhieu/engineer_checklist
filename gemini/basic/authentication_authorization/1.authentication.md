## 1. What is it?

**Authentication (AuthN)** is the process of verifying that a client, user, or service is genuinely who they claim to be.

> **Mental Model:** Authentication is your **national passport** at airport border control. The border guard verifies that the photo matches your face, checks the holographic watermark, and confirms your identity. It establishes **who you are**—not where you are allowed to walk in the airport.

In modern web architectures, authentication consists of **two distinct phases**:
1. **Phase 1: Primary Authentication (Login / Credential Verification):** The client proves their identity by submitting primary credentials (e.g., username/email + secret password). The server verifies the proof and **issues** an authentication artifact (a session cookie or signed token).
2. **Phase 2: Per-Request Authentication (Session / Token Assertion):** The client attaches the issued artifact to all subsequent HTTP requests so the user does not need to send their plaintext password on every single click.

---

## 2. Why do we need it?

### The Pain, Bug, and Bottleneck Without It

HTTP is an anonymous, stateless protocol. Without authentication:
1. **Total Identity Spoofing:** Anyone can send an HTTP request with `{ "user_id": "usr_999" }` or change an email in a query string and immediately impersonate any user.
2. **Zero Attribution & Auditability:** Malicious data tampering, funds transfers, or account deletions cannot be traced back to a specific legal entity or compromised credential.
3. **Boundary Collapsing:** Public resources and private user data collapse into a single unguarded space, exposing the entire database to anyone with a network connection.
4. **Why Not Send Username/Password on Every Request?** Storing plaintext passwords in browser storage and transmitting them across the network with every API call creates massive exposure to interception, credential leakage, and replay attacks. The two-phase model isolates sensitive credential verification to a single login handshake.

## 3. Under the Hood: The Mechanism & System Flow

### A. The Two-Phase Authentication Lifecycle

```
========================================================================================
PHASE 1: PRIMARY AUTHENTICATION (Login / Credential Handshake)
========================================================================================
[ Client ] ──── 1. POST /api/v1/auth/login { email, password } ────> [ Auth Controller ]
                                                                             │
                                              ┌──────────────────────────────┴──────────────┐
                                              ▼                                             ▼
                                     Canonicalize Email                           Constant-Time Hash Check
                                     (db.findUserByEmail)                         (bcrypt.compare / argon2.verify)
                                              │                                             │
                                              └──────────────────────┬──────────────────────┘
                                                                     ▼
                                                         Credentials Validated?
                                                               ┌─────┴─────┐
                                                              No           Yes
                                                               │            │
                                                      HTTP 401 │            ▼
                                                  "Invalid Credentials"   Generate Session ID / JWT
                                                                            │
[ Client ] <── 2. Return Set-Cookie: session_id OR { token } ───────────────┘

========================================================================================
PHASE 2: PER-REQUEST AUTHENTICATION (Subsequent Protected Requests)
========================================================================================
[ Client ] ──── 3. GET /api/v1/orders (Authorization: Bearer <token> OR Cookie) ──> [ Gateway / Middleware ]
                                                                                            │
                                                                   ┌────────────────────────┴─────────────┐
                                                                   ▼                                      ▼
                                                             [ Stateful ]                           [ Stateless ]
                                                           Lookup Session ID                    Verify Signature
                                                          in Redis ($O(1)$ RAM)               via Crypto Key ($O(1)$ CPU)
                                                                   │                                      │
                                                                   └──────────────────┬───────────────────┘
                                                                                      ▼
                                                                           Attach Trusted Principal
                                                                           req.user = { id, tenantId }
                                                                                      │
                                                                                      ▼
                                                                           [ Protected Business Logic ]
```

---

### B. Phase 1 Under the Hood: Primary Credential Verification

When a user submits `{ email, password }`:
1. **Canonicalization:** The email is normalized (`email.toLowerCase().trim()`) to prevent duplicate account confusion.
2. **Record Fetch:** The server retrieves the user's security record: `{ id, password_hash, status, failed_attempts, locked_until }`.
3. **Account Lockout Inspection:** If `locked_until > NOW()`, reject immediately to thwart brute-force password guessing.
4. **Slow, Constant-Time Verification:** The server invokes a memory-hard, computationally expensive hash algorithm (e.g., Argon2id or bcrypt with cost $\ge 12$):
   $$\text{bcrypt.compare}(\text{rawPassword}, \text{storedHash})$$
   - **Why Constant-Time?** Standard string comparisons (`strA === strB`) terminate early at the first mismatched character, creating a **timing attack vector** where attackers deduce passwords by measuring nanosecond CPU differences. Password hashing functions run in constant time.
5. **Artifact Issuance:** Upon success, failed attempts are reset to 0, and the server issues either:
   - An **Opaque Session ID** stored in Redis with a `Set-Cookie: HttpOnly; Secure; SameSite=Strict` header.
   - A **Stateless Cryptographic Token (JWT)** returned in the JSON response body.

---

### C. Phase 2 Under the Hood: Per-Request Verification

The incoming request passes through an authentication middleware:
1. **Extraction:** Middleware extracts the token from `Authorization: Bearer <token>` or `Cookie: session_id=<id>`.
2. **Verification Primitive:**
   - **Stateful (Sessions):** Queries Redis/DB using the session ID ($O(1)$ lookups, requiring RAM / connection pool I/O).
   - **Stateless (JWT / Asymmetric Tokens):** Verifies the digital signature mathematically using a shared secret or public key ($O(1)$ CPU computation, zero network/database I/O).
3. **Context Injection:** On success, the middleware instantiates a trusted identity object: `req.user = { id, tenantId, email }`. Downstream handlers **never** trust client payload identity fields; they only read from this verified context.
4. **Rejection Protocol:** If missing or invalid, processing halts immediately with `401 Unauthorized` and an informative `WWW-Authenticate` response header.

## 4. How to apply / implement / use it?

### Smallest Working Example: The Complete Flow (Login + Middleware)

Here is a complete, minimal implementation in TypeScript/Express demonstrating both **Primary Credential Verification** and **Per-Request Authentication**:

```typescript
import express, { Request, Response, NextFunction } from "express";
import bcrypt from "bcrypt";
import jwt from "jsonwebtoken";
import { z } from "zod";

const app = express();
app.use(express.json());

const JWT_SECRET = process.env.JWT_SECRET || "secure-secret-key-at-least-256-bits";

// Augment Request to carry trusted Principal
declare global {
  namespace Express {
    interface Request {
      user?: { id: string; email: string; tenantId: string };
    }
  }
}

// ─────────────────────────────────────────────────────────────────────────────
// PHASE 1: Primary Authentication (Login Route)
// ─────────────────────────────────────────────────────────────────────────────
const LoginSchema = z.object({
  email: z.string().trim().email(),
  password: z.string().min(1),
});

app.post("/api/v1/auth/login", async (req: Request, res: Response) => {
  const parsed = LoginSchema.safeParse(req.body);
  if (!parsed.success) {
    return res.status(400).json({ title: "Bad Request", errors: parsed.error.issues });
  }

  const { email, password } = parsed.data;
  const canonicalEmail = email.toLowerCase().trim();

  // 1. Fetch user authentication record from database
  const user = await db("users_auth").where({ email_canonical: canonicalEmail }).first();

  // ── Unhappy Path: User not found OR password mismatch ──────────────────
  // TIP: Use identical error message and timing to prevent user enumeration!
  if (!user) {
    // Run fake hash compare to prevent timing side-channel attacks
    await bcrypt.compare(password, "$2b$12$e8p2uVj6vQJ9hG9/WfKzreN6fR4X8/8c9E6G3Y8a4M2I1A5K6P8e2");
    return res.status(401).json({
      title: "Unauthorized",
      detail: "Invalid email or password.",
      status: 401,
    });
  }

  // 2. Constant-time password verification using bcrypt
  const isMatch = await bcrypt.compare(password, user.password_hash);
  if (!isMatch) {
    return res.status(401).json({
      title: "Unauthorized",
      detail: "Invalid email or password.",
      status: 401,
    });
  }

  // ── Happy Path: Primary credentials verified -> Issue token ────────────
  const token = jwt.sign(
    { sub: user.id, email: user.email_canonical, tenantId: user.tenant_id },
    JWT_SECRET,
    { expiresIn: "1h", algorithm: "HS256" }
  );

  return res.status(200).json({
    access_token: token,
    token_type: "Bearer",
    expires_in: 3600,
  });
});

// ─────────────────────────────────────────────────────────────────────────────
// PHASE 2: Per-Request Authentication (Middleware)
// ─────────────────────────────────────────────────────────────────────────────
export function authenticate(req: Request, res: Response, next: NextFunction) {
  const authHeader = req.headers["authorization"];

  // ── Unhappy Path 1: Missing or malformed header ─────────────────────────
  if (!authHeader || !authHeader.startsWith("Bearer ")) {
    res.setHeader("WWW-Authenticate", 'Bearer error="missing_token"');
    return res.status(401).json({
      title: "Unauthorized",
      detail: "Authentication credentials were missing or malformed.",
      status: 401,
    });
  }

  const token = authHeader.split(" ")[1];

  try {
    // ── Happy Path: Token signature and expiration verified ────────────────
    const decoded = jwt.verify(token, JWT_SECRET, { algorithms: ["HS256"] }) as any;

    req.user = {
      id: decoded.sub,
      email: decoded.email,
      tenantId: decoded.tenantId,
    };

    return next();
  } catch (err: any) {
    // ── Unhappy Path 2: Invalid signature or expired token ────────────────
    res.setHeader("WWW-Authenticate", 'Bearer error="invalid_token"');
    return res.status(401).json({
      title: "Unauthorized",
      detail: err.name === "TokenExpiredError" ? "Token has expired." : "Invalid authentication token.",
      status: 401,
    });
  }
}

// ─────────────────────────────────────────────────────────────────────────────
// Protected Route Example
// ─────────────────────────────────────────────────────────────────────────────
app.get("/api/v1/orders", authenticate, async (req: Request, res: Response) => {
  // Uses verified context, NEVER trusting client payload
  const orders = await db("orders").where({ tenant_id: req.user!.tenantId });
  return res.status(200).json({ data: orders });
});
```

## 5. When should I NOT use this? (Trade-offs and Anti-patterns)

### When NOT to Require Authentication
- **Public Entry Points:** Landing pages, public read-only documentation, blog posts.
- **Auth Bootstrapping Routes:** `POST /api/v1/auth/login`, `POST /api/v1/auth/register`, `POST /api/v1/auth/forgot-password`.
- **Infrastructure Health Probes:** `/healthz`, `/livez`, `/readyz` used by Kubernetes or load balancers (blocking them causes container crash loops).
- **Standards-Compliant Discovery Endpoints:** `/.well-known/openid-configuration`, `/.well-known/jwks.json`.

### Hidden Costs & Trade-offs
- **Password Hashing Cost:** `bcrypt` and `Argon2id` deliberately consume CPU and RAM (e.g., 50–100ms per verification). A flood of login attempts can exhaust CPU threads unless protected by rate limiting.
- **Session vs Token Storage:** Stateful sessions in Redis add 1–3ms network roundtrip latency per request. Stateless tokens (JWT) save Redis lookups but cannot be instantly revoked without a token-version or revocation list.

### Anti-Patterns to Avoid
1. **Transmitting Passwords on Every Request:**
   Never ask the client to send `email` and `password` on every API call. Use the two-phase pattern: verify credentials once at login, issue a temporary token/session, and verify the token on subsequent calls.
2. **User Enumeration in Login Errors:**
   ```json
   // ❌ CRITICAL SECURITY VULNERABILITY: Reveals valid accounts to attackers
   { "error": "Email does not exist" }
   { "error": "Password incorrect" }
   ```
   *Fix:* Always return a generic error: `"Invalid email or password"`.
3. **Trusting Client-Supplied Identity Fields:**
   ```typescript
   // ❌ CRITICAL SECURITY VULNERABILITY
   const userId = req.body.userId || req.query.userId;
   const profile = await db.findUser(userId);
   ```
   *Fix:* Always read identity exclusively from the verified context: `req.user.id`.
4. **Confusing AuthN (`401`) with AuthZ (`403`):**
   - Return `401 Unauthorized` **only** when identity verification fails or is missing.
   - Return `403 Forbidden` when identity is verified, but permissions are insufficient.

## 6. How do I know I understand it?

### The Blank-Page Test
From a blank sheet of paper, can you explain:
1. The difference between **Primary Authentication** (verifying email + password and issuing a token) and **Per-Request Authentication** (verifying a session cookie or bearer token on protected routes).
2. Why password hashes like bcrypt or Argon2id are deliberately slow and constant-time, while JWT verification algorithms are fast.

### Constraint Change Predictions
* **Scenario A: A malicious actor floods `POST /api/v1/auth/login` with 500 requests per second.**
  * *Prediction:* Because password hashing functions (bcrypt/Argon2id) deliberately burn 50–100ms of CPU per check to thwart brute-forcing, an unprotected login route will saturate all server CPU cores and bring the API down (Denial of Service). A production login endpoint **must** be shielded by aggressive IP- and account-level rate limiting.
* **Scenario B: A user resets their password on their laptop, but their stolen mobile phone still holds an unexpired JWT.**
  * *Prediction:* If per-request authentication is purely stateless without a database check, the stolen phone remains authenticated for the lifetime of the JWT. To prevent this, user management must implement a lightweight `token_version` check or session revocation list.
