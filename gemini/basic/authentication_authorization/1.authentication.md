## 1. What is it?

**Authentication (AuthN)** is the process of verifying that a client, user, or service is genuinely who they claim to be.

> **Mental Model:** Authentication is your **national passport** at airport border control. The border guard verifies the photo matches your face, checks the holographic watermark, and confirms your identity. It establishes **who you are**—not where you are allowed to walk in the airport.

---

## 2. Why do we need it?

### The Pain, Bug, and Bottleneck Without It

HTTP is a stateless, anonymous protocol. Without authentication:
1. **Total Identity Spoofing:** Anyone can send an HTTP request with `{ "user_id": "usr_999" }` or change an email in a query string and immediately impersonate that user.
2. **Zero Attribution & Auditability:** Malicious data tampering, funds transfers, or account deletions cannot be traced back to a specific legal entity or compromised credential.
3. **Boundary Collapsing:** Public resources and private user data collapse into a single unguarded space, exposing the entire database to anyone with a network connection.

## 3. Under the Hood: The Mechanism & System Flow

### System Placement & The Request Lifecycle

Authentication is the **outermost gatekeeper** in the request processing pipeline. It runs before request validation, business validation, authorization, and domain logic:

```
[ Incoming Request ]
         │
         ▼
[ 1. Authentication Layer ] ── Invalid / Missing ──> HTTP 401 Unauthorized
         │                                          (WWW-Authenticate Header)
         ▼ Valid Credentials
[ Attach Principal / UserContext ]
         │
         ▼
[ 2. Authorization Layer ]  ── Forbidden Action  ──> HTTP 403 Forbidden
         │
         ▼ Permitted
[ 3. Controller / Domain Service ]
```

### The Authentication Mechanism One Layer Deeper

Authentication transforms an unverified credential into a trusted **Principal** (`UserContext`):

```
Credentials (Bearer Token, Session Cookie, API Key)
                       │
                       ▼
       ┌───────────────────────────────┐
       │   Verification Mechanism      │
       └──────────────┬────────────────┘
                      │
         ┌────────────┴────────────┐
         ▼                         ▼
   [ Stateful ]              [ Stateless ]
   Lookup Session in         Cryptographic Signature
   Redis / Database          Verification (HMAC / RSA)
   (RAM / Disk I/O)          (CPU Mathematical Compute)
         │                         │
         └────────────┬────────────┘
                      ▼
            [ Verified Principal ]
        { id: "usr_123", tenantId: "t_45", roles: ["admin"] }
                      │
                      ▼
           Attached to Request Context
```

1. **Extraction:** The middleware extracts the credential from standardized locations:
   - Header: `Authorization: Bearer <token>`
   - Cookie: `Cookie: session_id=<opaque_token>`
   - Header: `X-Api-Key: <secret>`
2. **Verification Primitive:**
   - **Stateful (Sessions):** Queries Redis or SQL using an opaque token as key ($O(1)$ lookups, requiring RAM or DB connection pool I/O).
   - **Stateless (JWT / Asymmetric Tokens):** Verifies digital signature mathematically using a shared secret or public key ($O(1)$ CPU computation, zero network/database I/O).
3. **Context Injection:** On success, the middleware instantiates a trusted identity object (e.g., `req.user = { id, tenantId, roles }`). Downstream handlers **never** trust client payload identity fields; they only read from this verified context.
4. **Rejection Protocol:** If missing or invalid, processing halts immediately with `401 Unauthorized` and an informative `WWW-Authenticate` response header.

## 4. How to apply / implement / use it?

### Smallest Working Example (Happy & Unhappy Path)

Here is a minimal, production-grade authentication middleware in TypeScript/Express:

```typescript
import { Request, Response, NextFunction } from "express";
import jwt from "jsonwebtoken";

// Augment Express Request to carry trusted Principal
declare global {
  namespace Express {
    interface Request {
      user?: {
        id: string;
        tenantId: string;
        email: string;
      };
    }
  }
}

const JWT_SECRET = process.env.JWT_SECRET || "secure-secret-key-at-least-256-bits";

export function authenticate(req: Request, res: Response, next: NextFunction) {
  const authHeader = req.headers["authorization"];

  // ── Unhappy Path 1: Missing or malformed header ─────────────────────
  if (!authHeader || !authHeader.startsWith("Bearer ")) {
    res.setHeader("WWW-Authenticate", 'Bearer error="missing_token"');
    return res.status(401).json({
      title: "Unauthorized",
      detail: "Authentication credentials were missing or malformed.",
      status: 401,
    });
  }

  const token = authHeader.split(" ")[1];

  try {
    // ── Happy Path: Cryptographic signature & expiration verified ──────
    const decoded = jwt.verify(token, JWT_SECRET, {
      algorithms: ["HS256"],
    }) as { sub: string; tenantId: string; email: string };

    // Inject trusted identity into request context
    req.user = {
      id: decoded.sub,
      tenantId: decoded.tenantId,
      email: decoded.email,
    };

    return next();
  } catch (err: any) {
    // ── Unhappy Path 2: Invalid signature or expired token ────────────
    res.setHeader("WWW-Authenticate", 'Bearer error="invalid_token"');
    return res.status(401).json({
      title: "Unauthorized",
      detail: err.name === "TokenExpiredError" ? "Token has expired." : "Invalid authentication token.",
      status: 401,
    });
  }
}
```

## 5. When should I NOT use this? (Trade-offs and Anti-patterns)

### When NOT to Require Authentication
- **Public Entry Points:** Landing pages, public read-only documentation, blog posts.
- **Auth Bootstrapping Routes:** `POST /api/v1/auth/login`, `POST /api/v1/auth/register`, `POST /api/v1/auth/forgot-password`.
- **Infrastructure Health Probes:** `/healthz`, `/livez`, `/readyz` used by Kubernetes or load balancers (blocking them causes container crash loops).
- **Standards-Compliant Discovery Endpoints:** `/.well-known/openid-configuration`, `/.well-known/jwks.json`.

### Hidden Costs & Trade-offs
- **Verification Overhead:** Verifying RSA/ECDSA asymmetric signatures on high-throughput microservices consumes substantial CPU. Verifying stateful sessions in Redis adds 1–3ms network roundtrip latency per request.
- **Revocation Complexity:** Stateless tokens (JWT) cannot be instantly revoked without maintaining a distributed revocation blocklist or token-version registry.

### Anti-Patterns to Avoid
1. **Trusting Client-Supplied Identity Fields:**
   ```typescript
   // ❌ CRITICAL SECURITY VULNERABILITY
   const userId = req.body.userId || req.query.userId;
   const profile = await db.findUser(userId);
   ```
   *Fix:* Always read the user ID exclusively from the verified context: `req.user.id`.
2. **Confusing AuthN (`401`) with AuthZ (`403`):**
   - Return `401 Unauthorized` **only** when identity verification fails or is missing.
   - Return `403 Forbidden` when the identity is valid, but the user lacks permission.
3. **The "Soft 200" Auth Anti-Pattern:**
   Returning `HTTP 200 OK` with `{ "authenticated": false, "error": "Log in first" }`. This breaks standard API gateways, browser security policies, and mobile interceptors.
4. **Bespoke Cryptography:**
   Never write your own hashing, cipher, or signature algorithms. Use established, battle-tested protocols (OAuth2, OpenID Connect, WebAuthn) and libraries.

## 6. How do I know I understand it?

### The Blank-Page Test
From a blank sheet of paper, can you explain:
1. The exact difference between Authentication ("Who are you?") and Authorization ("What are you allowed to do?").
2. Why an API Gateway rejects unauthenticated requests with `401 Unauthorized` instead of `403 Forbidden`.

### Constraint Change Predictions
* **Scenario A: The server clock drifts forward by 10 minutes.**
  * *Prediction:* All incoming stateless tokens (JWTs) fail authentication immediately because the verification algorithm checks `nbf` (not before) or detects timestamp skew, triggering sudden `401 Unauthorized` spikes across all users.
* **Scenario B: A user's account is suspended, but they hold an active 1-hour JWT.**
  * *Prediction:* If authentication is purely stateless, the user remains fully authenticated until the token expires. To prevent this, authentication must incorporate a lightweight distributed version check (`token_version` check in Redis or DB).
