# Role-Based Access Control (RBAC)

[Lesson Index](../../README.md) · Previous: [User Management](3.user_management.md) · Next: [Session / Token](../../checklist.md#authentication--authorization)

---

## 1. What is it?

**Role-Based Access Control (RBAC)** is an authorization model that grants access rights to abstract **roles** rather than individual users, assigning users to those roles to govern system permissions.

> **Mental Model:** RBAC is a hospital badge labeled **"Surgeon"** or **"Nurse"**. The electronic door reader does not maintain a list of individual names ("Allow Alice, Allow Bob"). It checks whether the badge possesses the role **"Surgeon"**, and the role "Surgeon" is permitted to unlock the operating room.

---

## 2. Why do we need it?

### The Pain, Bug, and Bottleneck Without It: Permission Explosion & Drift

Without RBAC, systems must assign specific permissions directly to individual users (Direct User-to-Permission mapping):

```
Direct Assignment: 5,000 Users × 200 Permissions = Up to 1,000,000 direct links!
```

1. **Onboarding Nightmare ($O(U \times P)$ Administrative Overhead):** Onboarding an employee requires manually toggling dozens of individual permission checkboxes. Mistakes are inevitable.
2. **Privilege Creep & Drift:** When an employee transfers from Sales to Support, their previous Sales permissions are rarely manually revoked, leaving accounts over-privileged and ripe for insider threat exploitation.
3. **Impossibility of Bulk Updates:** If the definition of an "Editor" changes to include a new capability (e.g., `articles:publish`), the administrator must execute database updates across thousands of individual user rows instead of updating a single role definition.

RBAC introduces an indirection layer that reduces administrative complexity to $O(U \times R + R \times P)$:
$$\text{User} \longrightarrow \text{Assigned Role} \longrightarrow \text{Granted Permissions}$$

## 3. Under the Hood: The Mechanism & System Flow

### A. The Classic 5-Table NIST RBAC Schema

Under the hood, relational implementations of RBAC (standardized in NIST SP 800-21) rely on a classical **5-table schema**:

```
┌──────────────┐          ┌──────────────────┐          ┌──────────────┐
│    users     │          │    user_roles    │          │    roles     │
├──────────────┤          ├──────────────────┤          ├──────────────┤
│ id           │1 ──────* │ user_id (FK)     │ *────── 1│ id           │
│ email        │          │ role_id (FK)     │          │ name ("ADMIN")│
└──────────────┘          └──────────────────┘          └──────────────┘
                                                                │ 1
                                                                │
                                                                │ *
                                                        ┌──────────────────┐
                                                        │ role_permissions │
                                                        ├──────────────────┤
                                                        │ role_id (FK)     │
                                                        │ permission_id(FK)│
                                                        └──────────────────┘
                                                                │ *
                                                                │
                                                                │ 1
                                                        ┌──────────────────┐
                                                        │   permissions    │
                                                        ├──────────────────┤
                                                        │ id               │
                                                        │ code ("post:del")│
                                                        └──────────────────┘
```

---

### B. The Golden Rule of RBAC Architecture

> **Golden Rule:** Code checks **PERMISSIONS** (`posts:delete`). The database and administrators assign **ROLES** (`EDITOR`).

```
❌ ANTI-PATTERN: Hardcoding roles in application code
if (user.role === 'ADMIN' || user.role === 'SUPER_EDITOR') { ... }

✅ PRODUCTION-GRADE: Checking granular capabilities
if (user.hasPermission('posts:delete')) { ... }
```

By decoupling application logic from role names:
- Roles can be renamed, added, deleted, or customized by enterprise customers without deploying a single line of backend code.
- Permissions remain fine-grained and immutable program constants.

---

### C. Permission Resolution & Runtime Cost

Executing a 5-table relational join on every single HTTP request adds significant query latency. In production:
1. **Flattening / Caching:** When a user authenticates, the system resolves their effective permissions into a flattened array or Set:
   ```sql
   SELECT DISTINCT p.code
   FROM permissions p
   JOIN role_permissions rp ON rp.permission_id = p.id
   JOIN user_roles ur ON ur.role_id = rp.role_id
   WHERE ur.user_id = $1;
   ```
2. **In-Memory Verification:** The resolved permission set is embedded directly inside the stateless session/JWT token or cached in Redis ($O(1)$ set lookup in middleware: `req.user.permissions.has('invoices:refund')`).

## 4. How to apply / implement / use it?

### Smallest Working Example (Middleware & Permission Enforcement)

```typescript
import { Request, Response, NextFunction } from "express";

// Middleware factory: Evaluates effective permissions
export function authorizePermission(requiredPermission: string) {
  return (req: Request, res: Response, next: NextFunction) => {
    const user = req.user;

    // ── Unhappy Path 1: Unauthenticated ──────────────────────────────
    if (!user) {
      return res.status(401).json({ title: "Unauthorized", status: 401 });
    }

    // ── Unhappy Path 2: Authenticated, but lacks required permission ──
    const hasAccess = user.permissions && user.permissions.includes(requiredPermission);
    if (!hasAccess) {
      return res.status(403).json({
        title: "Forbidden",
        detail: `You lack the required permission: '${requiredPermission}'`,
        status: 403,
      });
    }

    // ── Happy Path: Permission confirmed ─────────────────────────────
    return next();
  };
}

// ── Application Route Registration ──────────────────────────────────
import express from "express";
const app = express();

// Notice: The route requires the CAPABILITY, not a specific role name
app.delete(
  "/api/v1/posts/:id",
  authenticate,
  authorizePermission("posts:delete"),
  async (req: Request, res: Response) => {
    await db("posts").where({ id: req.params.id }).delete();
    return res.status(204).send();
  }
);
```

## 5. When should I NOT use this? (Trade-offs and Anti-patterns)

### When RBAC Breaks Down
RBAC is strictly **subject-centric**. It cannot express dynamic attributes or object relationships:
- **Cannot Express Resource Ownership:** RBAC can state *"User has `posts:edit`"*, but it cannot state *"User can edit `posts` **only if** `post.author_id === user.id`"*.
- **Cannot Express Environmental Context:** RBAC cannot natively restrict access based on IP, time of day, or device compliance.
- **The "Role Explosion" Anti-Pattern:** Attempting to force dynamic rules into RBAC creates hundreds of hyper-specific roles: `EDITOR_DEPT_A`, `EDITOR_DEPT_A_WEEKEND_ONLY`, `VIEWER_MOBILE`.

> **Solution:** Combine RBAC with **ABAC** (Attribute-Based Access Control) or **ReBAC** (Relationship-Based Access Control) for fine-grained resource rules.

### Anti-Patterns to Avoid
1. **Hardcoding Role Strings in Controllers:**
   Checking `if (req.user.role === 'ADMIN')` in controllers creates rigid, brittle code that breaks the moment product managers want to introduce a "Super Editor" or custom enterprise roles.
2. **Neglecting Hierarchical Inheritance:**
   Failing to use hierarchical RBAC (where `Admin` inherits all permissions of `Editor`, which inherits `Viewer`), forcing duplicate permission entries across roles.
3. **Massive Join Queries on Every Route:**
   Re-querying 5 database tables on every request instead of caching the resolved permission set in Redis or the user token.

## 6. How do I know I understand it?

### The Blank-Page Test
From a blank sheet of paper, can you explain:
1. The 5-table relational schema used to model RBAC in a SQL database.
2. Why backend code must check permissions (`posts:create`) rather than role strings (`MANAGER`), and how this allows customers to create custom roles without code changes.

### Constraint Change Predictions
* **Scenario A: A high-tier enterprise customer requires a custom role called "External Compliance Auditor" with view-only access to billing and audit logs.**
  * *Prediction:* If your backend checked roles (`role === 'ADMIN'`), you must rewrite application code and redeploy. If you followed RBAC best practices, you simply create a new row in the `roles` table, link it to `billing:view` and `audit:view` in `role_permissions`, and zero code changes are required.
* **Scenario B: A multi-tenant SaaS platform has 10,000 tenants.**
  * *Prediction:* Roles must be tenant-scoped (`tenant_id` on the `roles` table), or global system roles (`SUPER_ADMIN`) must be strictly segregated from tenant-level roles (`MEMBER`, `BILLING_ADMIN`). Failing to scope roles allows cross-tenant permission leakage.
