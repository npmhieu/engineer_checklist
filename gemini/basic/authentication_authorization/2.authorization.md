## 1. What is it?

**Authorization (AuthZ)** is the process of determining what actions an authenticated identity is permitted to perform on specific resources.

> **Mental Model:** Authorization is your **airplane boarding pass**. Your passport verified who you are (Authentication), but your boarding pass determines where you are allowed to go (Seat 14B in Economy, but strictly prohibited from entering First Class or the Cockpit).

---

## 2. Why do we need it?

### The Pain, Bug, and Bottleneck Without It: BOLA / IDOR

Even if an application possesses rock-solid authentication, without proper authorization, any authenticated user can view, edit, or delete every other user's private records simply by changing an ID in the request:

```http
# User Alice logs in legitimately, then alters the URL parameter:
GET /api/v1/invoices/inv_999  --> Alice's invoice (Permitted)
GET /api/v1/invoices/inv_1000 --> Bob's confidential invoice! (Without AuthZ: LEAKED!)
```

This vulnerability is known as **Broken Object Level Authorization (BOLA)** or **Insecure Direct Object Reference (IDOR)**. It consistently ranks as the **#1 most critical threat in the OWASP API Security Top 10**.

Without authorization:
1. **Vertical Privilege Escalation:** Standard users invoke administrative endpoints (`POST /api/v1/users/admin-grant`).
2. **Horizontal Privilege Escalation:** Tenant A reads or mutates Tenant B's data across boundary IDs.
3. **Regulatory & Compliance Failure:** Complete non-compliance with GDPR, HIPAA, and SOC2 access control mandates.

## 3. Under the Hood: The Mechanism & System Flow

### System Placement & The Two-Tiered Enforcement Boundary

Authorization operates in two distinct evaluation tiers within the request pipeline:

```
[ Authenticated Request (req.user exists) ]
                     │
                     ▼
┌─────────────────────────────────────────────────────────────┐
│ 1. Coarse-Grained Authorization (Route / Gateway Level)    │
│    "Does the user have the general permission to perform   │
│     this action at all?"                                    │
│    e.g., User must have permission: 'invoices:read'         │
└────────────────────────────┬────────────────────────────────┘
                             │
            ┌────────────────┴────────────────┐
            ▼ No                              ▼ Yes
   HTTP 403 Forbidden                         │
                                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. Fine-Grained Authorization (Data / Domain Object Level)  │
│    "Does this user own or have access to THIS specific      │
│     invoice (inv_1000)?"                                    │
│    e.g., invoice.tenant_id === req.user.tenant_id           │
└────────────────────────────┬────────────────────────────────┘
                             │
            ┌────────────────┴────────────────┐
            ▼ No                              ▼ Yes
   HTTP 403 Forbidden /                       │
   HTTP 404 Not Found (Hide Existence)        ▼
                                   [ Execute Domain Action ]
```

### The Policy Evaluation Tuple: `(Subject, Action, Resource, Context)`

Under the hood, all modern authorization systems evaluate access via a 4-part decision tuple:

| Component | Definition | Example |
| :--- | :--- | :--- |
| **Subject** | The authenticated principal requesting access. | `{ id: "usr_42", role: "EDITOR", tenant_id: "org_9" }` |
| **Action** | The specific operation being attempted. | `"CREATE"`, `"READ"`, `"UPDATE"`, `"DELETE"`, `"APPROVE"` |
| **Resource** | The target object and its attributes. | `{ type: "Document", id: "doc_100", organization_id: "org_9" }` |
| **Context** | Environmental metadata at runtime. | `{ time: "14:30", ip: "192.168.1.1", mfa_verified: true }` |

### Core Authorization Models
1. **RBAC (Role-Based Access Control):** Permissions are attached to static roles (e.g., `ADMIN`, `MEMBER`). Easy to set up, but struggles with dynamic ownership.
2. **ABAC (Attribute-Based Access Control):** Rules evaluate dynamic attributes (e.g., `user.department === document.department AND environment.isWorkHours`).
3. **ReBAC (Relationship-Based Access Control):** Permissions are derived from graph relations (e.g., Google Zanzibar model: `user is member of team that owns folder that contains document`).

## 4. How to apply / implement / use it?

### Smallest Working Example (Coarse + Fine-Grained Checks)

Here is a minimal TypeScript/Express implementation demonstrating both route-level permission checks and object-level ownership checks:

```typescript
import { Request, Response, NextFunction } from "express";

interface UserContext {
  id: string;
  tenantId: string;
  permissions: string[];
}

// ── 1. Coarse-Grained Middleware: Check route privilege ─────────────
export function requirePermission(permission: string) {
  return (req: Request, res: Response, next: NextFunction) => {
    const user = req.user as UserContext;

    if (!user || !user.permissions.includes(permission)) {
      return res.status(403).json({
        title: "Forbidden",
        detail: `User lacks required permission: '${permission}'`,
        status: 403,
      });
    }

    next();
  };
}

// ── 2. Fine-Grained Handler: Check object-level boundary ─────────────
export async function getInvoiceHandler(req: Request, res: Response) {
  const user = req.user as UserContext;
  const invoiceId = req.params.id;

  const invoice = await db("invoices").where({ id: invoiceId }).first();

  // ── Unhappy Path 1: Resource doesn't exist ─────────────────────────
  if (!invoice) {
    return res.status(404).json({ title: "Invoice not found", status: 404 });
  }

  // ── Unhappy Path 2: Object-level authorization failure (BOLA) ──────
  if (invoice.tenant_id !== user.tenantId) {
    // TIP: Returning 404 instead of 403 prevents attackers from confirming
    // that the secret invoice ID actually exists (ID enumeration defense).
    return res.status(404).json({
      title: "Invoice not found",
      detail: "Resource does not exist or you lack permission.",
      status: 404,
    });
  }

  // ── Happy Path: Both coarse and fine-grained authorization pass ─────
  return res.status(200).json({ data: invoice });
}
```

## 5. When should I NOT use this? (Trade-offs and Anti-patterns)

### When NOT to Enforce Fine-Grained Authorization
- **Pure Public Resources:** Public product catalogs, public marketing blogs, and public system documentation where all users receive the identical view.

### Hidden Costs & Trade-offs
- **Database Query Overhead:** Every single SQL query must include multi-tenant filter clauses (`WHERE tenant_id = ?`) or join permission tables, preventing simple primary key seeks (`WHERE id = ?`).
- **Cache Fragmentation:** Responses cannot be cached globally in a shared CDN edge cache because representation depends directly on the caller's specific permission level.

### Anti-Patterns to Avoid
1. **Client-Side-Only Authorization:**
   Hiding an "Edit" or "Delete" button in the React UI while leaving the backend API endpoint unprotected. Anyone using cURL can bypass the UI instantly.
2. **Confusing `401 Unauthorized` with `403 Forbidden`:**
   - Use `401` when the client fails to prove their identity.
   - Use `403` when the client's identity is verified, but they lack permission.
3. **Hardcoding Role Checks Throughout Business Logic:**
   ```typescript
   // ❌ BRITTLE ANTI-PATTERN
   if (user.role === "ADMIN" || user.role === "SUPER_ADMIN") { ... }
   ```
   *Fix:* Check **capabilities / permissions** instead of role strings: `if (user.can("invoices:refund"))`.
4. **Neglecting List Queries (The Multi-Row Leak):**
   Checking authorization on `GET /invoices/:id`, but forgetting to apply tenant filtering on `GET /invoices`, returning every customer's invoices in the list endpoint.

## 6. How do I know I understand it?

### The Blank-Page Test
From a blank sheet of paper, can you explain:
1. What BOLA/IDOR is and how a two-line database query (`SELECT * FROM orders WHERE id = ? AND tenant_id = ?`) prevents it.
2. When an API should deliberately return `404 Not Found` instead of `403 Forbidden` upon an authorization failure.

### Constraint Change Predictions
* **Scenario A: A customer creates a custom role called "Billing Auditor" with read-only access to invoices.**
  * *Prediction:* If your code checks `if (user.role === 'ADMIN')`, the new role breaks immediately because role checks are rigid. If your code checks `if (user.hasPermission('invoices:read'))`, the system handles the new role seamlessly with zero code modifications.
* **Scenario B: A multi-tenant SaaS application implements database connection pooling without clearing user context.**
  * *Prediction:* If user authorization state leaks across pooled connections or thread-local storage, Request B will execute using Request A's permissions, causing catastrophic cross-tenant data leakage.
